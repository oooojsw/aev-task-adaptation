# 多实例协调器（Multi-Instance Coordinator）

## 它解决什么问题

我们原来的 SkillsBench 系统是 **单实例**：1 个任务跑 N 轮，沉淀出 1 份 skill。
现在引入 **多实例**：N 个同类任务并行跑，每个产出一份 skill，再合并成"通用 CORE + 特定 cases"的双层 skill。

设计来源是用户提的 路线 C（Fan-out / Fan-in）+ 路线 D（双层 skill）合并体。N=1 时退化为现有系统行为。

## 4 个阶段

```
Phase 1 (fanout)    并行跑 N 个独立 SkillsBench campaign
                    每个产出 pending-expert-package
                    ↓
Phase 2 (merge)     skill-merger agent 读 N 份 skill
                    输出 INDEX.md + CORE.md + cases/ + meta.json
                    ↓
Phase 3 (validate)  把 merged skill 当 seed 重跑每个 instance
                    检测 regression（原来过的现在不过 = 合并丢信息）
                    ↓
Phase 4 (repair)    [未实现，明天再说]
```

`auto-evolve/concurrency-config.json`：
```json
{
  "maxConcurrent": 3,        // 同时最多 3 个 OpenCode 子进程
  "maxQueueDepth": 30,       // 队列深度上限
  "acquireTimeoutMs": 3600000,  // 等待超时 1 小时
  "minSpawnIntervalMs": 0    // 启动间隔（0 = 不限速）
}
```

实测 OpenCodeGate 单元测试已全通过（信号量、队列溢出、超时、wrapper、drain 顺序）。

## CLI 用法

```bash
# 单纯并行跑 N 个 instance（保留原有行为）
bun run cli.ts run-multi-instance \
  --root <skillsbench-root> \
  --task <task-name> \
  --instances inst-1,inst-2,inst-3 \
  --rounds 5 \
  --label my-experiment \
  --skip-merge

# 完整 pipeline：fan-out → merge → validate
bun run cli.ts run-multi-instance \
  --root <skillsbench-root> \
  --task <task-name> \
  --instances inst-1,inst-2,inst-3 \
  --rounds 5 \
  --validate-rounds 2

# 控制并发：fan-out 同时只跑 2 个，gate 仍然限制全局
bun run cli.ts run-multi-instance \
  --root <skillsbench-root> \
  --task <task-name> \
  --instances inst-1,inst-2,inst-3 \
  --fanout-limit 2
```

## 产物结构

```
runtime-state/multi-instance-runs/<run-id>/
├── coordinator-state.json     # 单一事实源，原子写入
├── input-spec.json
├── phase1-fanout/
│   └── <instance-id>/
│       └── pending-expert-package/   # 该 instance 产出的 skill
├── phase2-merge/
│   ├── input-manifest.json
│   ├── prompt.txt
│   ├── response.txt
│   ├── stdout.log / stderr.log
│   └── output/                # 合并后的 skill
│       ├── INDEX.md
│       ├── CORE.md
│       ├── cases/
│       │   └── case-<id>.md
│       └── meta.json
└── phase3-validate/
    ├── summary.json
    └── <instance-id>/
        └── run.json           # 该 instance 在 merged skill 下的成败
```

## 真实运行（court-form-filling）

启动时间：2026-05-19 04:13（北京时间）

参数：
- bench：skilllearnbench
- 任务：court-form-filling（6 个实例）
- auto-split 0.33 → train 4 / test 2
- train: court-form-filling-1, 2, 3, 4
- test: court-form-filling-5, 6（held out，只 Phase 3 评估）
- rounds：2 / validate-rounds：1
- fanout-limit：4
- run id：`20260519-041313276-court-form-overnight`

**实测发现并修复的两个并发 bug：**

1. **`saveCoordinatorState` race**：4 个并行 fan-out 同时写 `coordinator-state.json.tmp-<pid>`，互相覆盖触发 ENOENT。
   修法：`repository.ts` 加 per-runRoot 串行化锁 + 临时文件名加随机后缀。
   commit：`67a887643`

2. **Campaign id 截断撞车**：原 title `multi-instance-fanout-<run-id>-<instance-id>` 经 `slugify` 截断到 48 字符后，instance-id 后缀全被砍掉，4 个并行 campaign 共用同一个目录互相覆盖（实测只生成 3 个 dir 而非 4 个）。
   修法：title 改为 `mi-<instance-id>-fanout-<run-id>`，把唯一标识前置，slug 截断也保留唯一性。
   commit：`49c7531e1`

**实测的并发能力：**
- gate maxConcurrent=4
- 4 个 train campaign 各持 1 槽，刚好不打架
- 5 个 bun.exe 进程稳定运行（1 个 coordinator + 4 个 campaign runner，每个 campaign 还会 spawn OpenCode 子进程）

定时检查：每 30 分钟自动读 coordinator-state.json + 4 个 campaign.json，phase=completed 时写结果到 test_records.md 并停 cron。

## 设计上待解决（明天讨论）

1. **合并质量** — 合并 agent 提示词靠谱否？需要看实际 CORE.md 输出
2. **回归处理** — Phase 3 检测到 regression 后怎么修？目前只是记录
3. **Train/test 分割** — 是否所有 instance 都参与训练？还是留一部分做盲测
4. **实例失败但仍想合并** — 当前默认排除 failed instance，要不要保留它们的部分知识
5. **预算控制** — N×rounds×K 的 API 调用代价，需要总预算阈值
6. **SkillLearnBench 适配** — 当前只接 SkillsBench；SkillLearnBench 的 task-N/ 嵌套结构需要新适配
