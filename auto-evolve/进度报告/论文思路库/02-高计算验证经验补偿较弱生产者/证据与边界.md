# 思路二：现有证据与边界

## 已有证据

| 项目 | MiniMax M2.7 AEV merge-as-opt | SkillOpt 官方 GPT-5.5 Skill | 含义 |
|---|---:|---:|---|
| OfficeQA，GPT-5.5 测试消费者 | 66.86% | 65.12% | 当前唯一“达到或略超过”的直接观察。 |
| OfficeQA，GPT-5.4 测试消费者 | 56.98% | 59.88% | 未追平。 |
| OfficeQA，GPT-5.4-mini 测试消费者 | 48.26% | 50.58% | 未追平。 |
| SpreadsheetBench，GPT-5.4 / mini | 不构成完整同源比较 | 官方 Skill 更高 | 不能推广为普遍优势。 |

所有 OfficeQA 数字都来自官方 172 个 valid-unseen UID、原生单轮、无工具、Oracle 文本的同一测试口径。

## 为什么现在仍不能声称“多 token 换来同等效果”

1. AEV 改变的不只是 token 数：它也改变了执行方式、验证门、失败诊断和合并方式。
2. 官方 GPT-5.5 Skill 的完整训练 token 与调用成本没有可审计总账，不能做成本比。
3. 目前只有一个直接追平格子，且训练重复不足。
4. MiniMax M2.7 测试消费者、Qwen 消费者和部分其他条件出现了无收益或负迁移。

## 当前正确结论

这是一个“高计算验证经验可能补偿生产者能力差距”的候选机制，而不是已经完成的效率论文。

## 深度缺口审计（投稿前必须逐项关闭）

以下按风险排序。前四项不补，第二篇的主张应降级为“有趣的系统观察”，不能写成严谨的能力补偿论文。

### P0：训练重复不足，测试题数不能替代训练重复

目前 172 个 OfficeQA 测试题可以证明同一份冻结 Skill 在题目上的配对差异，但不能证明“这套训练方法稳定”。因为每个方法的核心 Skill 往往只训练过一次；172 题只是同一次训练产物的 172 次部署，并不是 172 次独立的经验生产实验。

必须做法：每个主条件至少 3 个独立训练 run，固定数据切分但改变可记录 seed/请求随机性；完整报告三个结果、均值、标准差和最差值。任何“三次取最高”的工程选优只能作为部署规则，绝不能做论文主分数。

### P0：强生产者对照尚未被定义成公平对照

“SkillOpt 官方 GPT-5.5 Skill”是有价值的外部效果锚点，但其完整训练题、训练轮数、提示词、模型快照、筛选规则、上下文预算与总成本目前并不完全可审计。因此它不能单独承担“MiniMax 用计算替代 GPT-5.5 能力”的因果对照。

必须做法：重新建立一个可审计强生产者控制组，使用同一 OfficeQA train/validation UID、同一初始 Skill、同一最大输出长度、同一合并输入格式和同一最终冻结评测。官方 Skill 保留为外部参照，不能代替这个控制组。

### P0：AEV 与原生 SkillOpt 不只改变了“验证”

现有两条线可能同时改变了案例执行方式、是否只保留 verified-success、失败诊断、经验包结构、warm start、合并器、训练/验证调用次数和 Skill 长度。因此，即使 AEV 分数更高，也无法单独归因给“验证式经验计算”。

最低消融应为：在同一 MiniMax、同一训练 UID、同一初始 Skill、同一总调用或 token 上限下，比较普通 rollout、普通 rollout 加同样的合并、AEV 去验证、AEV 去失败诊断、完整 AEV。这样才能回答“哪一个环节有效”。

### P0：数据划分和经验来源需要可机械审计

必须公开并哈希：train、selection/validation、test UID 清单；每份源 Skill 对应的训练 UID；最终 Skill 的输入 manifest；以及最终 Skill 的 SHA-256。还应运行自动泄漏扫描：最终 Skill、casebook、prompt 与 test UID、test question、标准答案或其独特数值片段不能重合。

原因很直接：AEV 是“从单题经验汇总成规则”的系统。即便没有主观作弊，来源路径或回撤记录一旦误混入 valid-unseen，就会让整篇论文失效。

### P1：Skill 长度与部署上下文预算没有被控制

若 AEV Skill 比原生或官方 Skill 更长，最终消费者得到的额外文本本身就可能带来收益；这和“生产得更好”不是同一件事。反过来，某些模型的差表现也可能只是被长 Skill 挤掉了材料上下文或触发输出/上下文截断。

必须做法：报告每份 Skill 的字符数、token 数、输入上下文 token、被截断比例和每题实际 prompt token；再做一个长度匹配实验，例如把各 Skill 统一压到相同 token 上限，或为基线补等长度的无关/通用说明。只有长度匹配后仍有效，才更像经验质量收益。

### P1：部署评测自身也有随机性与版本漂移

当前评测跨日期、跨账号、跨代理和不同 provider；历史上 SpreadsheetBench 已经发生过运行时变化，导致旧 25% 基线与后来的约 70% 结果不可比较。OfficeQA 的消费者也必须固定模型快照、reasoning、temperature、最大输出、Oracle 文本生成版本与评分器版本。

必须做法：主论文只使用一个冻结 runtime cohort；每个最终 Skill 至少重复评测 2--3 次或证明 API 推理为确定性；保存完整 config hash、provider 响应元数据和原始逐题结果。模型更新后的新结果单列，不可覆盖旧表。

### P1：需要独立验证“评测正确率”本身

OfficeQA 的 oracle-page 单轮设置有意隔离了检索，但它不是完整端到端 OfficeQA；SpreadsheetBench 的 judge 曾崩溃。需要随机人工核查一小组“Skill 改善”和“Skill 退化”的样本，确认评分器、答案抽取和 Oracle 上下文没有把格式差异误判为能力差异。

建议至少审计每个主比较 20 个改善、20 个退化或全部非平局样本中的随机分层样本，并让第二位独立审阅者盲审。论文中把它写成评测有效性检查，而不是新主指标。

### P1：当前的“弱生产者”标签缺少操作化定义

MiniMax M2.7 与 GPT-5.5 的强弱，目前主要来自模型身份和官方 Skill 的最终分数，而不是一个同数据、同预算下的生产能力测量。因此标题和摘要不能把它说成已被严格排序的“weaker/stronger producer”。

改法：在补到可审计强对照前，写成“不同生产者”或“较低成本/较小可用生产者（若价格证据完整）”；完成同配方原生训练比较后，再用该比较定义“较弱”。

### P2：泛化维度仍偏窄，两个基准有共同的文档推理特征

OfficeQA 和 SpreadsheetBench 都包含材料理解、数值/结构化操作和外部工具/文本流程。它们已经说明跨任务设置，但还不能说明经验生产机制会迁移到代码、网页交互或开放式发现类任务。

最低补法不是再堆十个模型，而是补一个性质不同、硬验证清楚的第三类任务；若资源不足，就诚实将结论限定为“文档与电子表格类可验证任务”。

### P2：成本、碳足迹和实用性仍是反证风险

目前 AEV 可恢复成本下界已很高，且 merge-as-old 的 usage 缺失。第二篇若强调“用更多计算补偿能力”，审稿人必然问：需要多大的额外计算、何时值得、是否只是把成本转移到训练侧。

必须做法：不必先宣称便宜，但要报告可审计成本范围、wall-clock、有效经验包数、每次验证通过率和失败重试。把问题改写为“能力-计算交换”而不是“降本”。

## 还缺的三张关键图

1. **公平主图**：同一训练 split、同一部署消费者下，普通 rollout、长度匹配的普通 rollout、完整 AEV、可审计强生产者的均值与波动。
2. **预算曲线**：MiniMax 的低/中/高预算下，普通 rollout 与 AEV 两条曲线；横轴同时显示 raw token 与通过验证的有效经验数。
3. **稳定性与边界图**：每次训练 run 的散点，不隐藏失败和负迁移；按消费者展示收益为正、无效和负向的比例。

这三张图补齐后，第二篇才有一个清楚的闭环：不是“我们某一次分数很高”，而是“在控制条件下，验证式经验如何、何时、以什么代价补偿生产者差距”。
