# Auto-Evolve 论文方向探索树

最后更新：2026-09-01

## 用法

这是一份研究决策记录，不是论文摘要，也不是宣传材料。每个分支都必须写清四件事：我们原本想证明什么、已有证据是什么、与已有论文是否重叠、目前应继续还是停止。后续每有新的论文检索、正式实验或否定结果，都追加到对应节点，不能只保留好看的结果。

状态定义：

- `可继续`：问题仍可能成立，但必须按列出的缺口补实验。
- `降级为支撑证据`：可以帮助别的论文，不适合作为独立主张。
- `暂停`：当前证据不足，暂不投入主要资源。
- `淘汰为核心创新`：已有论文已经直接覆盖，不能再包装为新方法。

## 总根问题

长程 Agent 的执行过程能否被转成可部署 Skill，并在冻结后的新任务上带来可靠收益？

我们已经完成的系统事实是：AEV 能生产案例经验、记录运行与验证证据、合并为 Skill，并把冻结 Skill 部署到 OfficeQA 与 SpreadsheetBench 的若干消费者模型上。这个事实不自动等于算法创新；论文必须说明是哪个机制、在何种受控条件下造成了收益。

```text
长程执行经验 -> 可部署 Skill
|
|-- A. "AEV 比 SkillOpt 更强"                         [降级为支撑证据]
|-- B. "可审计的长程验证经验"                         [可继续，但创新需重定位]
|-- C. "较弱生产者 + 更多验证计算可接近强生产者"       [可继续，实验缺口很大]
|-- D. "Skill 生产 Scaling Law"                       [暂停，只有假设]
|-- E. "成功/失败/异常轨迹治理带来收益"                [淘汰为核心创新]
|-- F. "合并器本身更优"                               [降级为支撑证据]
|-- G. "把合并做成长程任务 merge-as-long-task"         [暂停，当前失败]
|-- H. "跨模型部署/经验迁移"                           [降级为支撑证据]
|-- I. "来源血统与可恢复运行是新的系统贡献"            [暂停，需找窄缺口]
```

## A. AEV 比 SkillOpt 更强

**原始想法**：用 MiniMax M2.7 生产的 AEV Skill 与同为 MiniMax M2.7 生产的原生 SkillOpt Skill 对比，若 AEV 在多消费者上得分更高，就证明 AEV 整体优于 SkillOpt。

**我们做过什么**：

- OfficeQA 官方 172 题、SkillOpt 原生单轮、无工具、Oracle 文本上下文，比较无 Skill、AEV merge-as-old、optMiniMax M2.7、AEV merge-as-opt。
- 在 GPT-5.4-mini、GPT-5.4、GPT-5.5 上，AEV 的两个主要产物多数优于 optMiniMax；MiniMax M2.7 自己作为消费者时没有稳定提升。
- SpreadsheetBench 有 AEV、optMiniMax 与官方 Skill 的局部矩阵，但历史运行时在 2026-08-12 前后变化，旧低基线和新运行时结果不能混算。

**为什么不能做主论文**：

- AEV 与 SkillOpt 同时改变了经验生产、验证、诊断、合并、调用数、Skill 长度和运行环境，不能把最终分数差直接归因给一个机制。
- `SkillOpt` 已经是非常强的直接相关工作；`Trace2Skill` 也已覆盖“多轨迹分析、失败诊断、分层合并”。
- merge-as-old 的历史 token 账不完整，不能宣传成本优势；独立训练重复不足。

**当前判定**：`降级为支撑证据`。它适合放在任何后续论文的主结果表中，说明 AEV 产物有实际部署价值；不能单独作为“我们提出比 SkillOpt 更好的优化算法”。

**保留价值**：同生产者的 `optMiniMax M2.7` 对照仍是很重要的外部基线，尤其可服务于 B、C、F、H。

## B. 可审计的长程验证经验

**原始想法**：把长程执行产生的经验变为带验证状态、来源血统、失败诊断和部署边界的经验包，再合并为可迁移 Skill。

**我们做过什么**：

- 完成可恢复运行状态、配置快照、数据 split、Skill hash、任务 ledger、验证结果与部分 token ledger 的记录体系。
- 将模型答案错误、验证器崩溃、数据集错误、provider 故障分开保留；不把已知基础设施错误直接喂回修复循环。
- 物理闭卷 Blank Eval、最终 Direct Chat 验收、case skill 与合并产物的来源关系已有工程实现。
- OfficeQA 与 SpreadsheetBench 的冻结部署结果表明，部分 GPT 消费者读取 AEV Skill 后得分提高。

**相关文献冲突**：

- `SkillsVote` 已进行任务后归因，并明确区分 skill、agent、客户端环境、外部环境和不确定环境；环境类失败不进入演化。
- `Trace2Skill` 已使用可验证的失败原因、产物访问和失败 patch 的分层合并。
- `SkillOpt` 已有验证集 gate、拒绝编辑缓存、成功/失败分开反思。

**还可能保留的窄问题**：不是泛泛的“经验要验证”，而是“真实文件产物任务中，产物验证、运行时故障隔离、可恢复来源链和冻结部署审计能否作为一个可复核实验协议，避免把平台噪声错误写成学习收益”。

**致命缺口**：目前没有证明这种协议比 SkillsVote/Trace2Skill 的归因或质量门更有效；它更像高质量系统工程和实验规范，而不是已证明的新算法。

**当前判定**：`可继续，但创新需重定位`。可投稿为系统/实践导向工作，前提是逐篇证明文件产物、运行时恢复与评测审计的联合边界确实未被覆盖；不能声称首创“验证式经验治理”。

**已有目录**：[01-可审计的长程验证经验](./01-可审计的长程验证经验/README.md)。

## C. 生产者能力—验证计算替代

**原始想法**：用较低能力或更易获得的生产者 MiniMax M2.7，投入更长程的执行、验证、诊断和合并计算，产出能够接近强生产者 Skill 的最终 Skill。

**已有观察**：OfficeQA 上，MiniMax AEV merge-as-opt 在 GPT-5.5 消费者达到 66.86%，官方 GPT-5.5 Skill 为 65.12%；但在 GPT-5.4-mini 和 GPT-5.4 上仍略低。MiniMax M2.7 作为消费者时也没有稳定收益。

**为什么它仍可能值得做**：它不必宣称“AEV 首创轨迹验证”，而是研究一个可测量的问题：在相同生产者下，把预算投入普通 rollout 与投入验证式经验闭环，最终 Skill 的部署效果是否不同；并问这种额外计算能否缩小生产者差距。

**当前不能说的话**：

- 不能说 MiniMax 已经等价或替代 GPT-5.5。
- 不能说 AEV 更便宜或更高效，现有账本不支持。
- 不能把一次超过官方 Skill 的格子写成普适结论。
- 不能把“弱模型”当成既定事实，因为缺少同配方、可审计的强生产者控制组。

**投稿前最低实验**：同 split、同初始 Skill、同长度上限、同最终评测下，至少三次独立训练比较普通 rollout、长度匹配普通 rollout、去验证 AEV、去诊断 AEV、完整 AEV；另补一个可审计强生产者控制组。报告训练波动、总 token、有效经验数和负迁移。

**当前判定**：`可继续`，但这是新项目，不是补一张表就能完成。文献审计见：[02 分支审计](./02-高计算验证经验补偿较弱生产者/文献重叠审计-2026-09-01.md)。

**已有目录**：[02-高计算验证经验补偿较弱生产者](./02-高计算验证经验补偿较弱生产者/README.md)。

## D. Skill 生产 Scaling Law

**原始想法**：研究生产模型能力、验证式经验计算预算与最终 Skill 效果之间是否存在可以拟合和预测的规律。

**我们做过什么**：已有 MiniMax、官方 GPT-5.5 Skill 与多消费者的离散结果；也有部分三次重跑观察到较大波动。

**为什么现在不能写**：没有至少三档生产者、没有 `1x/2x/4x/8x` 预算曲线、没有每点三次独立训练，也没有留出预算点验证预测。因此这不是 scaling law，连可靠曲线都还没有。

**当前判定**：`暂停`。只有在 C 的控制实验完成后才重新启用。

**已有目录**：[03-Skill生产缩放规律](./03-Skill生产缩放规律/README.md)。

## E. 成功/失败/异常轨迹治理消融

**原始想法**：同一批 AEV 长程轨迹、同一合并器、同长度同预算，只改变经验是否经过验证和故障归因，比较“全收、按 0/1 筛选、验证治理、完整 AEV”。

**为什么提出过**：我们确实在实际运行中见过 validator crash、数据答案错误、provider 401/402/429/502、路径错误和 stale recovery；直觉上，不隔离这些记录会污染经验。

**文献核验结果**：

- `Rethinking Self-Evolving Agent Skills` 在相同 parent skill、执行器、优化器、验证规则和轮数下，直接比较 `Normal（成功+失败）/ Fail-only / Success-only`。
- `SkillOpt` 已把成功和失败分开分析、分别合并，并让失败修正优先；还有 validation gate 与 rejected-edit buffer。
- `Trace2Skill` 以可验证失败原因生成失败 patch，也使用成功轨迹作为对照证据。
- `SkillsVote` 已细分 skill/agent/client environment/external environment/unknown environment，并过滤不可演化记录。

**准确结论**：我们可以做这个实验来解释自己的系统，也可以作为复现或工程验证；但不能当作新颖性主张，更不能写“现有方法默认所有 rollout 都可信”。

**当前判定**：`淘汰为核心创新`。以后只作为 C 的必要机制消融，或 B 的审计附录。

## F. 合并策略：无回撤、merge-as-old、merge-as-opt

**原始想法**：把 AEV 的优势归因于更好的 Skill 合并和回撤修复策略。

**已有结果**：OfficeQA 172 题、GPT-5.4 评测中，无回撤为 91/172，merge-as-old 为 92/172，merge-as-opt 为 98/172。merge-as-opt 点估计最高，但和另两者的配对差异未达统计显著。

**为什么不宜单独写**：

- `Trace2Skill` 已做并行 patch + 分层合并，并有程序化冲突控制。
- `SkillOpt` 已有批内/批间 patch 合并、验证 gate 和拒绝编辑记忆。
- 当前消融只是一份训练来源的一次合并，不足以证明某一合并器普遍更优。

**当前判定**：`降级为支撑证据`。它能证明“合并路径值得记录且会影响最终产物”，不能证明“merge-as-opt 是新且更优的算法”。

## G. merge-as-long-task（MSL）

**原始想法**：把合并本身做成独立长程 campaign，由新的 lead/worker/reviewer 在严格读取权限下构建合并 Skill，再以外部 Direct Chat 做最终验收和 repair。

**我们做过什么**：OfficeQA 40 个冻结 AEV case skill 做了完整层级合并；中间完成 8 -> 2 -> 1 的合并，但最终 external Direct Chat replay 只通过 17/40，3 次 repair 后耗尽，最终 Skill 未被接受。另一条每组 20 次修复的试验也在 level 1 的两个组上耗尽。

**已识别的根因**：旧长程角色的提示词、文件读取权限和工作记忆原本为“单任务专家经验生产”设计，不天然适合“多 Skill 合并、回撤、casebook 增量修复”。硬套会造成信息链断裂和无效 repair。

**当前判定**：`暂停`。它是有价值的系统研发分支，但目前是明确的负结果，不能拿来支撑 AEV 有效性。

**重新启动条件**：重新设计专用合并角色、独立权限包、source-skill manifest、失败 UID 到源 case 的可逆索引，以及每层明确的回撤/增量 casebook 规则；随后先做小规模 5 skill 端到端验收。

## H. 跨模型部署与迁移

**原始想法**：MiniMax M2.7 生产的冻结 Skill 是否能在 GPT、Qwen、Gemini、DeepSeek 等不同消费者上部署并带来收益。

**我们做过什么**：OfficeQA 已扩展到 GPT-5.4-mini、GPT-5.4、GPT-5.5、MiniMax M2.7、Qwen 3.5-4B、Qwen 3.6-35B-A3B、DeepSeek-V4-Flash、Gemini 3.7 Flash Medium；不同模型出现正收益、小收益、无收益和负收益。SpreadsheetBench 也有 GPT 和 MiniMax 的局部结果。

**价值**：这说明 Skill 不是“训练后必然跨模型通用”的文本，消费者能力、上下文窗口、指令遵循、工具 runtime 与 Skill 长度都会改变结果。负迁移是应保留的边界，不是要删掉的异常。

**为什么不是独立创新**：`SkillOpt` 和 `Trace2Skill` 都已经报告跨模型/跨 harness 转移；现有跨模型表更适合证明我们的结论有边界，而不是提出“跨模型迁移”新范式。

**当前判定**：`降级为支撑证据`。服务于 B 或 C，必须固定每个 provider 的版本、推理模式、输入长度、工具权限与评分器。

## I. 来源血统、恢复与实验可复核性

**原始想法**：将 config snapshot、split UID、Skill hash、run lineage、validator 输入输出、停止/恢复原因、token ledger 统一保存，使复杂长程实验可复现且不会因断点续传混淆结论。

**我们做过什么**：修过 task-ledger 膨胀、orchestrator-state 一致性、Windows PID 复用、JSONL 并发写、状态原子写、配置隔离、managed config 隔离、Blank Eval 物理闭卷、stale recovery 等大量基础设施问题。

**价值**：它是本项目真实且必要的能力；没有它，历史 run、stopped、recovery、provider 故障和结果统计会混在一起，实验结论不可信。

**为什么暂不能写成方法创新**：`SkillsVote` 已有技能生命周期和版本历史，`Trace2Skill` 已声明 patch 的完整审计轨迹，`EvoMal` 也讨论 provenance tracking。我们尚未证明自己的恢复/血统协议在可量化指标上解决了一个它们没有解决的问题。

**当前判定**：`暂停`。作为所有实验的强制记录规范和可复核附录；若未来能提出可测的“实验血统错误检测/恢复正确性”基准，才可能独立成系统论文。

## 当前资源优先级

1. 若目标是尽快形成一篇有诚实边界的系统论文，继续 B：先证明文件产物任务中的窄系统缺口，避免泛称经验治理首创。
2. 若目标是形成更有研究张力的方法论文，投入 C 的公平控制实验；这需要重新训练，不应从历史最好一次的分数挑结论。
3. 不再单独投入 E；它的实验只在 C 的机制消融中做。
4. 暂不投入 D、G、I 的大规模真实训练，除非先完成其重新启动条件。

## 历史猜想谱系：我们前面实际讨论过的所有方向

下面记录的是研究方向的演化过程，不代表每一条都仍然成立。它们按我们过去讨论和实验推进的顺序排列，避免后来只记住最终结论而忘记为什么放弃其他路线。

### 猜想 1：AEV 整体优于 SkillOpt

最初的直觉是：AEV 有长程任务、验证、失败修复、casebook、分层合并和回撤，因此最终 Skill 应该全面超过 SkillOpt。OfficeQA 上 AEV 的部分产物确实高于同生产者的 optMiniMax Skill，但不同模型有负迁移，且 AEV 与 SkillOpt 改变的组件太多，不能证明“AEV 算法整体更优”。

**结论**：`降级为支撑证据`。现有分数可以作为比较结果，不能作为论文唯一创新。

### 猜想 2：AEV 是以证据为中心的 Skill 学习范式

后来我们尝试把论文提升为“Data-Centric Agent Skill Learning”或“Verified Experience Governance”，强调原始轨迹包含模型失败、验证器崩溃、数据错误、网络错误和路径错误，不能直接进入 Skill。

这个问题真实存在，且我们的系统确实实现了大量审计、隔离和恢复机制。但“经验需要证据治理”已经被 `SkillsVote`、`Closing the Feedback Loop`、`SkillForge` 等研究提出；“成功/失败不是同一种信号”也已被多篇工作讨论。

**结论**：`可继续，但必须收窄`。只能写成“长程文件产物任务中的联合审计协议或系统实证”，不能宣称首次提出证据治理。

### 猜想 3：验证后的轨迹比原始轨迹更适合生成 Skill

这是最直接的因果猜想：固定同一合并器，只改变合并前的经验池，比较全部原始轨迹、只看 0/1 分数、验证后轨迹和完整 AEV 轨迹。

这个问题的广义版本已被 `SkillOpt`、`Trace2Skill`、`SkillsVote` 和 `Rethinking Self-Evolving Agent Skills` 覆盖。我们的潜在差异只剩长程文件产物、真实文件验证和非模型故障拆分。

**结论**：`作为公平比较实验保留`，`淘汰为完全原创问题`。必须与已有基线真实对齐，不能只重新命名已有流程。

### 猜想 4：一种新的任务轨迹生成方法能大幅提高 Skill 泛化

这个表述曾被提出，但不准确。AEV 没有改变 MiniMax 执行任务时如何生成原始轨迹，主要改变轨迹生成后的验证、筛选、诊断、组织和合并前准入；同时现有 OfficeQA 结果也不能推出“整体泛化”。

**结论**：`淘汰原题目`。可改写成“验证式经验轨迹构建”或“合并前轨迹准入策略比较”，但必须声明它不是全新轨迹生成模型。

### 猜想 5：长程验证计算可以补偿较弱 Skill 生产者

该方向来自一个实际观察：同为 MiniMax M2.7 生产来源时，AEV Skill 在部分 GPT 消费者上高于 optMiniMax Skill，并在 GPT-5.5 消费者上出现 66.86% 对官方 GPT-5.5 Skill 65.12% 的结果。

它不是“MiniMax 等于 GPT-5.5”，而是想检验：将生产预算投入长程执行、验证、诊断和合并，是否比普通 rollout 更有效，并能缩小不同生产者之间的 Skill 部署差距。`Trace2Skill` 已证明较小模型可以生成可迁移 Skill，因此我们的新意只能放在“生产期验证计算的替代作用”和预算控制上。

**结论**：`当前最值得继续`。但必须补同预算普通 rollout、去验证/去诊断对照、预算曲线、三次独立训练和可审计强生产者控制组。

### 猜想 6：Skill 生产存在 Scaling Law

我们曾想研究生产模型能力、经验计算量和最终 Skill 分数之间的缩放规律，并将“更多 token 换更弱模型能力”写成定律。

现有数据只有少量模型和离散结果，没有多档几何预算、能力梯度、重复训练、拟合和预测验证。即使未来看到单调提升，也不能自动称为 scaling law。

**结论**：`暂停`。只有完成猜想 5 的多预算受控实验后，才有资格重新评估。

### 猜想 7：AEV 的优势主要来自更好的合并器

我们比较过无回撤、`merge-as-old` 和 `merge-as-opt`，并设计过分层合并、回撤、repair、casebook 增量更新和最终验收。

结果显示合并路径会影响最终 Skill，但当前 `merge-as-opt` 只是在点估计上更高，配对显著性不足；`Trace2Skill` 已经有并行 patch 和分层合并，`SkillOpt` 也有批量编辑和验证 gate。

**结论**：`降级为机制分析`。可以说明“合并是重要变量”，不能说我们证明了某个合并器普遍更优。

### 猜想 8：把合并本身变成长程任务（merge-as-long-task）会更强

我们尝试把合并拆成 lead、worker、reviewer 和多轮回撤，让合并器像一个独立长程 campaign 一样运行，并用 opt Direct Chat 做最终验收。

实际运行暴露出角色权限、源 Skill 文件读取、失败 UID 回溯、repair 信息传递和验收闭环等问题；OfficeQA 40 个源 Skill 的一次真实链路最终只有 17/40 累计通过，repair 耗尽，未形成可接受的最终 Skill。

**结论**：`暂停`。这是重要的平台研发分支和负结果，不是目前可宣传的有效方法。只有专用合并角色、独立权限和端到端小规模验收重新通过后才恢复。

### 猜想 9：AEV 的成本效率高于 SkillOpt

我们一度考虑以“用更多 token 换更高分”或“每提升一个百分点需要多少成本”为论文主线。

现有事实不支持“更省”：AEV 长程保留血统的 token 账只是下界，`merge-as-old` usage 不完整，SkillOpt 与 AEV 的缓存、角色和 provider 统计也没有完全同口径。当前只能说 AEV 可能用更高过程成本换来更高部分部署分数。

**结论**：`淘汰成本优势叙事`。成本只能作为能力补偿路线的代价分析，不能写成效率优势。

### 猜想 10：AEV 具有跨模型泛化能力

我们用 GPT-5.4-mini、GPT-5.4、GPT-5.5、MiniMax、Qwen、DeepSeek 和 Gemini 等模型测试不同 Skill，观察到 GPT 消费者上较多正收益，但 MiniMax、Qwen、DeepSeek 存在无收益或负收益。

这说明 Skill 具有消费者依赖和负迁移边界，但 `SkillOpt`、`Trace2Skill` 和 `From Raw Experience to Skill Consumption` 已经研究过跨模型消费和负迁移。

**结论**：`降级为边界证据`。不能写“全面跨模型泛化”，只能报告“哪些消费者受益、哪些消费者失效”。

### 猜想 11：只要有成功轨迹就能产生好 Skill

我们曾考虑无 Skill、只成功、成功+失败、失败诊断和完整 AEV 等反馈构成。后来核验 `Rethinking` 后确认，它已经直接做了 Normal、Fail-only、Success-only 的同配置比较，并发现失败反馈通常很关键。

**结论**：`淘汰为原创主线`。可作为我们自己的复现实验或能力补偿路线中的控制条件。

### 猜想 12：Skill 是比原始轨迹更好的压缩表示

我们的系统最终把大量任务轨迹压缩成 casebook、core、合并 Skill，再让冻结消费者使用；这曾被表述成 Skill 比直接塞满轨迹更适合部署。

但我们没有完成同预算、同上下文长度的 raw-trajectory replay 对照，且已有 `Trace2Skill`、`Scaling Test-Time Compute for Agentic Coding` 等工作已经研究轨迹表示、压缩与复用。

**结论**：`暂停为主张`。除非补 raw trajectory、压缩 Skill、长度匹配和成本对照，否则不能声称 Skill 压缩优于原始轨迹。

### 猜想 13：统一的可插拔 Skill 系统本身构成创新

我们设计过可替换的 blank agent、Direct Chat、硬验证、软验证、`merge-as-old`、`merge-as-opt` 和 `merge-as-long-task`，希望把不同任务范式放进统一系统。

这对工程复用很有价值，但“可插拔角色、验证器和合并后端”本身更像系统架构能力。若没有新的形式化接口、跨任务实验和组件替换收益证明，不能直接称为论文方法创新。

**结论**：`作为系统设计支撑`。服务于猜想 2、3、5，不单独做标题。

### 猜想 14：运行血统、配置隔离和成本账本可以单独成为论文

我们遇到并修复了 stale run、错误续传、ledger 膨胀、并发 JSONL 覆盖、PID 误判、OpenCode 全局配置污染、managed config 污染和角色 token 未闭环等问题。

这些问题对实验可信度非常重要，但仅有“我们修好了工程事故”还不足以成为研究贡献。需要一个可测量的血统错误检测率、恢复正确率或实验可复现基准，才能独立成系统论文。

**结论**：`作为所有实验的基础设施与审计附录`，暂不独立投稿。

### 猜想 15：不和 SkillOpt 比，直接把 AEV 作为新的 Skill 生产结果

我们曾考虑放弃竞争叙事，改写成“AEV 在 OfficeQA 和 SpreadsheetBench 上能生成有效 Skill”。这样可以减少基线压力，但也会削弱论文问题意识；而且已有工作已经能生成有效 Skill，仅报告一个高分不够。

**结论**：`可以作为保守写法，但不是最佳主线`。必须保留直接基线和负结果，否则更像项目报告。

### 猜想 16：把 AEV 写成“弱模型用更多 token 达到强模型效果”

这是目前最有吸引力、但也最容易被质疑的叙事。已有结果提供了先导信号，却没有同配方强生产者、预算曲线和多次重复；而且 AEV 增加的不只是 token，还包括验证、诊断和合并机制。

**结论**：`作为猜想 5 的通俗解释，不作为未经补实验的结论`。论文中应写“部分补偿”而不是“达到等效”。

## 2026-09-01 方向重新收敛记录

### 本轮讨论的核心判断

我们曾经尝试把论文题目写成：

> 一种新的任务轨迹生成方法使得整体 Skill 泛化能力大幅提升。

这个题目被否定，原因不是实验没有价值，而是它把我们的实际改动说错了：AEV 没有改变任务执行模型如何生成原始轨迹，主要改变的是轨迹生成后的验证、筛选、故障归因、经验组织和合并前准入。因此“新的轨迹生成方法”不准确，“整体泛化能力大幅提升”也超出了当前正负混合的消费者结果。

### 当前可以保留的研究问题

> 在相同的 Skill 合并器、合并预算和最终评测下，不同的合并前轨迹准入策略，是否会产生质量不同的 Skill？

这是一项可以验证的比较研究，但不是一个已经证明完全原创的问题。其可能的贡献只能来自三方面的组合：

- 面向 Office/Spreadsheet 这类真实长程文件产物任务，而不是抽象文本轨迹；
- 将真实产物验证与模型失败、数据错误、验证器错误、路径/网络/运行时错误分开处理；
- 在固定合并器下，机械地比较不同轨迹池对最终 Skill 的影响，并保留负迁移和失败案例。

### 本轮专家意见的纠正记录

专家意见把“现有工作都默认成功/失败等于模型责任”说得过于绝对，这不能采用。`SkillsVote` 已经做 Skill、Agent、客户端环境和外部环境归因；`Trace2Skill` 已经做可验证失败原因、产物检查、成功/失败 patch 和分层合并；`SkillOpt` 已经做成功/失败分组、失败优先编辑、验证门和拒绝编辑缓存；`Closing the Feedback Loop` 已经讨论经验证据、可信度和治理。因此以下表述禁止写入论文：

- “现有方法都把原始 rollout 当作天然可信证据”；
- “我们首次提出成功/失败轨迹治理”；
- “我们首次提出验证后再合并 Skill”；
- “只要完成一张四条件表，审稿人就无法反驳”；
- “AEV 的轨迹治理必然显著优于所有已有方法”。

`The Blind Curator` 和 `EvoMal` 是重要相邻文献，但研究重点分别是 Judge 偏差导致 Skill 退役失效、以及代码 Skill 自中毒与传播，不应被错误写成与 AEV 完全相同的基线。

### 轨迹准入比较的正式实验设计

必须冻结原始轨迹、训练 UID、初始 Skill、后续合并器、合并输入数量、最大输出长度、最终测试集、消费者模型、评分器和运行时。唯一改变的是合并前哪些轨迹或经验单元被准入：

| 条件 | 合并前准入规则 | 要检验的内容 |
|---|---|---|
| Raw-All | 所有原始轨迹都进入 | 未治理经验池的下界 |
| Score-Only | 只按最终 0/1 分数筛选 | 传统结果筛选是否足够 |
| SkillOpt-like | 成功/失败分开分析，固定合并器 | 与已有 SkillOpt 思路的公平比较 |
| Trace2Skill-like | 轨迹 patch、失败原因和分层 patch 合并 | 与最接近方法的公平比较 |
| AEV-Artifact | 真实产物验证后准入 | 文件产物检查的独立作用 |
| AEV-Full | 产物验证 + 故障归因 + 来源血统隔离 | 完整 AEV 轨迹协议 |

这六个条件只有在后续合并器完全相同的情况下，才可以把最终差异归因到“合并前轨迹池”。如果每个条件使用不同合并器，实验回答的就不是轨迹准入问题，而是整条系统流水线的混合比较。

### 必须补充的实验

目前确实还需要补充较多实验，至少包括：

1. **公平基线实现**：不能只在文字中声称 SkillOpt-like 或 Trace2Skill-like，要用同一批冻结轨迹和同一合并器真实跑出来。
2. **同预算控制**：所有条件对齐输入轨迹数、总调用数、输入/输出 token、最大 Skill 长度和墙钟预算，避免 AEV 只是因为看了更多内容而占优。
3. **独立训练重复**：每个主要准入条件至少三次，报告均值、标准差、最差结果和逐题配对差异；不得用三次最高分作为主结果。
4. **两个任务集复现**：OfficeQA 与 SpreadsheetBench 使用各自冻结、可比的运行时和有效 cohort；不能混用旧评测器和新评测器结果。
5. **轨迹池质量指标**：除最终 Skill 分数外，记录准入数量、真实成功比例、模型失败比例、数据/基础设施剔除比例、重复经验比例、经验包长度和归因不确定比例。
6. **最终 Skill 评测**：用冻结 Skill 在未参与经验构建的题目上评测，并保存全部逐题结果、Skill hash 和输入配置。
7. **污染与泄露审计**：检查经验包、casebook、patch 和最终 Skill 是否含测试 UID、标准答案、特有数值或原始测试材料片段。
8. **故障归因准确性审计**：随机抽查 validator crash、dataset failure、provider failure、模型真实错误和真实成功，核对实际产物、验证器输入与标准答案三方证据。

### 这条路线的论文级结论门槛

只有同时满足下面条件，才可以说 AEV 的轨迹准入策略优于已有基线：

- 在至少两个任务设置中方向一致；
- 在同一合并器和相同预算下重复成立；
- 对主要比较有配对置信区间和显著性检验；
- 优势不是由 Skill 更长、测试运行时不同或有效分母不同造成；
- 失败和负迁移结果没有被删除；
- 至少能说明收益来自产物证据/故障隔离中的某个可复现组件。

如果只完成一组 OfficeQA 单次结果，论文只能写成“面向长程文件任务的系统实证观察”；不能写成普适的轨迹生成新方法。

## 前期讨论补录：同一批猜想的不同表述

这一节专门记录前面讨论中出现、但容易被误认为“新方向”的说法。它们不是新增的十几种方法，而是对上面 1--16 条路线的不同叙述角度。后续写论文或设计实验时，以“对应方向”和“当前状态”为准，避免重复开题、重复跑实验。

### 补录 1：一种新的任务轨迹生成方法提升 Skill 泛化

**当时的说法**：我们是否可以把论文写成“一种新的任务轨迹生成方法，使整体 Skill 的泛化能力大幅提升”。

**实际对应**：方向 3 和方向 4。

**为什么修正**：AEV 没有改变原始任务执行阶段如何生成轨迹；它主要在轨迹生成之后做真实产物验证、失败诊断、故障隔离、经验组织和合并前准入。因此把它叫作“新的轨迹生成方法”会把系统改动说错；“整体泛化能力大幅提升”也不能覆盖 MiniMax、Qwen、DeepSeek 等消费者上的负收益。

**当前用途**：淘汰原题目，改为“长程文件产物任务中的验证式经验构建”或“合并前轨迹准入策略比较”。它只能作为方向 2、3 或 5 的问题背景，不能单独作为创新声明。

### 补录 2：不把迁移作为重点，只研究 Skill 生产前的经验生成

**当时的想法**：不强调跨模型迁移，只研究从任务执行轨迹到 Skill 之前的经验生产质量，观察什么样的轨迹更值得进入合并器。

**实际对应**：方向 3、方向 5 和方向 11。

**可研究问题**：在固定执行模型、固定初始经验、固定合并器、固定预算和固定最终评测的条件下，只改变合并前经验池的构成，是否会产生不同质量的冻结 Skill？

**重要边界**：这个问题的广义版本已经被 SkillOpt、Trace2Skill、SkillsVote 和 Rethinking Self-Evolving Agent Skills 等工作部分覆盖。因此不应写成“首次研究高质量轨迹是什么”，而应写成“在真实 Office/Spreadsheet 文件产物任务中，对已有轨迹准入思想进行统一、可复核的受控比较”。最终 Skill 评测仍然不可省略，因为只看轨迹文本质量不能证明它真的有用。

**当前状态**：保留为实验问题，不作为完全原创的方法名。跨模型结果可降为附加证据，不必作为论文主标题。

### 补录 3：AEV 的优势来自更高质量的经验生产，而非迁移本身

**当时的想法**：AEV 与 SkillOpt 的差异，核心可能不是“Skill 能否迁移”，而是 AEV 是否生产出了更有用、更完整、更少污染的经验。

**实际对应**：方向 1、方向 2、方向 3 和方向 7。

**能支持的说法**：在部分固定消费者和固定测试协议下，AEV 产物分数高于 optMiniMax 产物；这说明经验生产流程可能影响最终 Skill 质量。

**不能支持的说法**：不能仅凭最终分数断言“AEV 经验生产效率更高”，因为当前 AEV 与 SkillOpt 同时改变了执行轮数、验证方式、诊断、合并路径、Skill 长度和调用预算；也不能说 AEV 的经验在所有消费者上都更泛化。

**当前状态**：作为主结果解释的候选因果链，但必须通过同合并器、同预算、同长度和多次独立重复实验拆分出真正原因。

### 补录 4：弱生产模型多投入计算，能否达到强生产模型的 Skill 效果

**当时的通俗说法**：能否让较弱的 MiniMax M2.7 生产者通过消耗更多 token，达到接近 GPT-5.5 生产 Skill 的效果？

**实际对应**：方向 5 和方向 16。

**正确学术问题**：当生产者模型固定时，把预算投入普通 rollout，还是投入长程执行、验证、失败诊断和受控合并，哪一种更能提升冻结 Skill 的部署质量？额外验证计算能否部分弥补生产者能力差距？

**已有先导信号**：OfficeQA 上 AEV MiniMax 产物在 GPT-5.5 消费者上出现过 66.86% 对官方 GPT-5.5 Skill 65.12% 的结果；但这只是 pilot，不能推出等价、替代或普遍成立。

**必须补的控制**：同预算普通 rollout、长度匹配、去验证、去诊断、强生产者控制组、至少三次独立训练和预算曲线。成本账必须完整，否则只能讨论“计算投入的补偿作用”，不能讨论成本效率。

**当前状态**：保留为最有研究张力的候选主线，但尚未完成论文级证据。

### 补录 5：把 AEV 说成“类似 SkillOpt 的效果”，而不是声称优于 SkillOpt

**当时的想法**：如果不把论文写成“超过 SkillOpt”，是否可以只说 AEV 能达到类似 SkillOpt 的效果，甚至用较弱生产者复现强生产者的效果？

**实际对应**：方向 1、方向 5 和方向 15。

**分析**：这是更保守、更不容易夸大的写法，但“达到类似效果”本身不是研究问题。若只展示 AEV 的几个高分，仍然会被问：相似是在哪个任务、哪个消费者、哪个预算、哪个方差范围内？因此需要把它改成可检验的“能力—计算补偿关系”或“固定预算下的生产流程比较”。

**当前状态**：保留为论文措辞策略，不作为独立研究方向。主文应报告完整矩阵、负迁移和成本，避免只挑最接近的一格。

### 补录 6：把合并前轨迹当作论文核心，而不是把最终合并器当作核心

**当时的想法**：SkillOpt 的流程可以粗略看成“任务轨迹生成 + Skill 合并”；我们的重点应放在前一部分，研究哪些任务轨迹值得被合并，而不是重新发明合并器。

**实际对应**：方向 3、方向 5 和方向 7。

**判断**：这个聚焦方式是合理的，但不能把“轨迹生成”与“轨迹准入/轨迹治理”混为一谈。AEV 目前主要改变后者。若固定合并器，确实可以把实验因果变量收窄到轨迹池；若同时使用 merge-as-old、merge-as-opt、merge-as-long-task，则回答的是整条流水线比较，不能归因于轨迹本身。

**当前状态**：推荐作为实验设计原则，尚不足以单独构成创新。

### 补录 7：只做系统实证，不声称完全原创

**当时的想法**：既然“经验治理”“成功/失败轨迹”“验证后合并”已有论文研究，是否可以把本文定位为真实长程文件任务上的系统实证或工程协议。

**实际对应**：方向 2、方向 3 和方向 15。

**优点**：可以诚实复用现有 OfficeQA、SpreadsheetBench、故障审计、合并消融和跨消费者结果，降低“首创算法”压力。

**不足**：仅仅报告 AEV 能工作仍然不够，需要明确场景难点、统一协议、可复核故障分类、固定对照和负结果分析。否则容易变成项目报告而不是研究论文。

**当前状态**：可作为保守投稿版本；如果补不齐方向 5 的公平计算控制，它是比“AEV 全面优于 SkillOpt”更稳妥、但研究张力较弱的退路。

### 补录 8：用已有论文作为比较对象，而不是只和 SkillOpt 比

**当时的想法**：既然 SkillOpt、Trace2Skill、SkillsVote、Rethinking、SkillForge 等都涉及经验生成、失败反馈、验证或 Skill 生命周期，我们是否应把它们都作为相关基线。

**正确理解**：需要区分“论文相关工作引用”和“实际可复现实验基线”。不是读过一篇论文就能在本机公平复现；只有拿到相同输入、相同预算、相同合并器和相同评测规则，才可作为定量基线。其余工作应作为机制定位、差异分析和讨论对象。

**当前状态**：文献比较必须保留；定量基线按成本和可复现性分层，不能为了表格数量而伪造等价实验。

### 补录 9：从“提高泛化”改成“提高冻结 Skill 的可部署质量”

**当时的想法**：原先常说“泛化能力大幅提升”，后来发现跨模型结果并不一致，因此考虑改成更窄的“最终 Skill 在未参与生产的任务上更可靠”。

**分析**：这是更准确的指标口径。OfficeQA/SpreadsheetBench 的 held-out 测试集可以支持任务内泛化或部署有效性；跨模型泛化则必须单独标注为消费者迁移，不应混在同一个“泛化”数字里。

**当前状态**：推荐采用“冻结 Skill 的 held-out 部署质量”作为主指标，“跨模型迁移”作为边界分析。

### 补录 10：第三篇 Scaling Law 方向

**当时的想法**：把“弱模型多花 token 换取更强 Skill 效果”继续扩展成 Skill 生产 Scaling Law。

**为什么暂缓**：目前只有零散模型结果和三次重复，不具备多档计算预算、多档生产者能力、拟合、预测点和重复稳定性。把两个模型、几个条件画成一条线会构成过度解释。

**当前状态**：单独保留为第三篇候选，当前第二篇不使用 Scaling Law 术语；方向 5 的实验完成后再决定是否恢复。

## 本次补录后的统一结论

前面讨论的各种说法并不是互相矛盾的多篇论文，而是从“AEV 是否更强”逐步收窄到“合并前哪些经验值得进入 Skill 生产”，再进一步收敛到“验证式计算能否部分补偿生产者能力差距”。当前最稳妥的论文组织方式是：以方向 5 作为待验证主问题，以方向 3 的公平轨迹池实验作为机制解释，以方向 1、7、8、10 的结果作为对照和边界；方向 2、15 作为保守系统实证退路，方向 4、6、9、11、12、14 不再单独包装成核心创新。

### 候选方向 17：生产者—消费者匹配与 Skill 效用分解

**建议题目**：`Producer–Consumer Compatibility in Long-Horizon Agent Skills: An Empirical Study of Utility, Regression, and Artifact Grounding`。

**核心问题**：同一份冻结 Skill 在不同消费者上为什么会出现增益、无效、负迁移和不同失败类型？这种差异由消费者本身能力、Skill 生产流程、Skill 长度/上下文、还是文件产物 grounding 与 verification 需求造成？

**为什么最适合复用现有工作**：我们已经有 OfficeQA 172 题和 SpreadsheetBench 280 题的多消费者矩阵，包含无 Skill、AEV merge-as-old、optMiniMax M2.7、AEV merge-as-opt、官方 Skill 等条件；还保留了 Qwen、DeepSeek、Gemini、GPT、MiniMax 的正收益和负收益。这些数据天然适合计算每个消费者的 `gain`、`regression`、`persistent failure`、`net lift` 和失败类别，而不必再把论文主张放在“AEV 全面更强”。

**与已有研究的关系**：From Raw Experience to Skill Consumption 已证明 extractor 与 consumer 不一定一致，SkillGen 和 Regression Tax 已做 paired intervention 与回归分解，ACES/AEVAL 已做可重复 Skill evaluation。因此本方向不是“首次发现匹配问题”，而是一个场景化、可审计的实证扩展。它的优势是可以诚实地把已有工作作为理论和方法基线，而不是假装没有先例。

**现有证据能支持的结论**：

- Skill 的净平均分不能代表全部效用，必须拆成修复 baseline failure 和破坏 baseline success 两部分；
- AEV 产物在不同消费者上的效果不单调，说明 Skill 效用依赖消费者和执行环境；
- MiniMax、Qwen、DeepSeek 等负结果不是噪声，应作为兼容性边界；
- 真实文件任务的 grounding、产物验证和上下文长度可能是影响匹配的任务因素。

**最小补实验包**：

1. 在一套固定、未漂移的评测运行时上，完成 OfficeQA 与 SpreadsheetBench 的四条件或至少三条件配对结果；
2. 对现有逐题结果重新计算 gain/regression/persistent failure，并按消费者模型和任务类型分组；
3. 随机抽查一小批正迁移、负迁移和无变化案例，核对 Skill 文本、输入上下文、产物/评分器输出，验证分解不是统计假象；
4. 只补一个长度或上下文敏感性控制，避免把 Skill 过长导致的截断误判成模型兼容性。

**成本与论文风险**：补实验量低于方向 5 的公平重训路线，但方法创新强度也较低。它更像高质量实证/系统研究；要达到中国计算机研究生通常所说的二区要求，必须把配对统计、失败案例、运行时固定和可复现实验协议做扎实，不能保证仅凭已有矩阵就达到二区。

**当前判定**：`新增候选，可继续；最少补实验路线`。它是目前“尽量少重训、最大限度复用现有结果”的首选，但不应包装成全新 Skill 生成算法。

**本轮详细评估**：[候选方向深度评估-2026-09-01.md](./候选方向深度评估-2026-09-01.md)。

### 候选方向 18：长程文件任务中的证据接地与 Skill 质量

**核心问题**：Skill 中哪些内容真正帮助消费者从原始文件得到正确产物，哪些内容只是通用流程文字，甚至会造成 grounding displacement 或 verification displacement？

**已有基础**：AEV 已有 `core`、`casebook`、来源 UID、硬验证结果、失败诊断和 Office/Spreadsheet 产物；现有跨模型结果也显示“Skill 有内容”不等于“Skill 对消费者有用”。

**文献边界**：SkillCoach、Regression Tax、ContractSkill 和 SkillGen 已分别覆盖过程质量、grounding/verification、契约和效用干预，因此只能把贡献收窄为“长程文件产物任务中的证据接地分析”。

**最小实验**：对现有 Skill 做内容分层或受控删除，比较 `procedure-only`、`grounding+procedure`、`verification+procedure` 和完整 Skill；但这仍需重新生成/裁剪 Skill，工作量高于候选方向 17。

**当前判定**：`可继续但次选`。若方向 17 的案例审计发现大量差异确实来自 grounding/verification，再启动本方向；现在不宜先投入。

### 候选方向 19：评测运行时漂移与 Skill 结果可复现性

**核心问题**：模型、推理强度、上下文截断、工具权限、网关和评分器变化，会不会让同一个 Skill 的分数变化大于方法本身的收益？

**已有基础**：SpreadsheetBench 历史上已经出现 2026-08-12 前后运行时变化导致的不可比结果；项目也已修复 provider 错误、validator crash、账本覆盖和配置污染。

**文献边界**：AEVAL、ACES、Rethinking evaluation of harness evolution、The Blind Curator 等已经讨论可重复评测、评分器偏差和 harness 变化。因此不能单独声称“我们首次发现运行时漂移”。

**最小实验**：同一冻结 Skill 在旧/新运行时做一个小型交叉复测，并把模型错误、provider 错误、评分器错误和上下文截断分别报告。

**当前判定**：`降级为方向 17 的方法学支撑`。它对论文可信度非常重要，但单独作为主线的算法贡献不足。

### 候选方向 20：验证计算的能力补偿

**核心问题**：较弱生产者是否可以通过更多长程执行、验证和诊断计算，部分弥补与强生产者的 Skill 质量差距？

**文献边界**：SkillTTA 已讨论 test-time compute-to-capability conversion，Rethinking 已做额外测试时计算控制，From Raw Experience to Skill Consumption 已讨论 extractor/consumer 不一致。因此它仍有空间，但必须采用严格预算控制，不能从现有最高分倒推结论。

**最小实验**：至少需要同预算 ordinary rollout、去验证、去诊断、完整 AEV、强生产者控制和三次重复；这已经不是“少补实验”。

**当前判定**：`保留为高潜力主线，但不作为当前低成本首选`。如果后续预算充足，候选方向 17 的兼容性分析可以作为它的前置证据和实验动机。

### 候选方向 21：长程任务中的小样本 Skill 生成与泛化

**原始想法**：不把论文重点放在“Skill 被不同模型使用后的迁移”，而是研究 Skill 生成本身：当可用训练任务很少时，如何将少量长程任务执行经验生成在未见任务上仍有效的冻结 Skill。

**建议研究问题**：

> 在长程、可验证的文件产物任务中，验证式经验构建能否提升小样本 Skill 生成的 held-out 泛化与稳定性？

英文工作题目可暂定为：

> `Data-Efficient Skill Generation from Long-Horizon Agent Experience`

**关键定义**：这里的“小样本”是指参与 Skill 生产的训练任务数很少，例如 `5 / 10 / 20 / 40` 个任务；“泛化”只指冻结 Skill 在未参与经验构建的同分布 held-out 任务上的效果，不混入跨模型消费者迁移。跨模型矩阵可以保留为附加边界证据，但不能成为主指标。

**为什么值得研究**：小样本场景下，普通合并容易把少数任务的偶然路径、格式细节或错误规则写进通用 Skill；AEV 的长程执行、真实产物验证、失败归因、casebook/core 分层和受控合并，理论上可能使少量经验更像“可复用规则”而不是个例记忆。

**文献边界**：

- Trace2Skill 已研究长轨迹提炼、层级合并和 held-out/OOD 泛化；不能说“从长程轨迹生成 Skill”是首次提出。
- SkillGen 已从成功/失败轨迹产生并验证 Skill；不能说“验证式 Skill 生成”是首次提出。
- Rethinking 已研究验证过滤的反馈和多轮 Skill 演化；不能说“反馈影响泛化”是空白。

因此，这一方向可保留的窄贡献不是发明新概念，而是：**在真实 Office/Spreadsheet 长程文件任务中，系统测量训练任务数量很少时，经验验证和组织方式对冻结 Skill held-out 泛化的影响。**

**可最大化复用的资产**：现有 OfficeQA 的 40/50 个冻结源任务与 SpreadsheetBench 的 69 个 verified source skills / 80 个训练任务，可提供 `5 / 10 / 20 / 40` 的分层源经验子集；OfficeQA 172 题和 SpreadsheetBench test280 可作为冻结 held-out 评测集。

**两种证据等级必须严格区分**：

| 证据等级 | 做法 | 可以说什么 | 不能说什么 |
|---|---|---|---|
| 低成本抽样合并 | 从已有冻结源经验中按规模抽取子集，再固定合并和评测 | 少量**已生成且已记录**的经验如何被合并为 Skill；经验池规模和合并策略的影响 | 不能证明完整 AEV 在少训练任务下端到端更会生成经验，因为源轨迹已来自较大任务池 |
| 端到端小样本训练 | 只给系统 `5/10/20/40` 个训练任务，从长程执行到验证、合并均独立运行 | AEV 在少训练任务条件下的真实 Skill 生成效率和泛化 | 成本较高，必须有重复和严格 split |

**最低实验路线**：

1. 先做低成本的分层抽样合并：固定 Skill 长度、合并器、随机种子、最终评测协议，对比 AEV source pool 与同规模 SkillOpt-like source pool；
2. 每个样本规模至少做多个随机子集，报告均值、波动和逐题 gain/regression，避免单次子集偶然好；
3. 如低成本曲线呈现稳定优势，再补一个小样本端到端点，例如 `10` 或 `20` 任务，确认不是只因从大池中抽到了成熟经验；
4. 最后才决定是否扩展为完整 `5/10/20/40` 端到端曲线。

**当前风险**：小样本曲线至少需要多个规模点和随机重复，不能用一个 `40` 任务结果加一个 `80` 任务结果就声称数据效率；并且必须控制 Skill 长度、合并调用预算和训练/测试 UID，防止把更多文本或泄露误认作泛化。

**当前判定**：`新增候选，可继续；Skill 生成主线候选`。它比方向 17 更符合“研究 Skill 生成”的初衷，且可先通过低成本分层抽样验证。若曲线成立，再升级为方向 20 的生产期计算—数据效率研究；若不成立，仍可回退为“经验池规模与合并稳定性”的实证结果。

## 2026-09-01 第三轮深度探索：小样本长程 Skill 方向的修正版

### 本轮新增判断

另一份分析提出“长程任务、少量训练集条件下的 Skill 生成与泛化控制”。本轮核验后，该方向保留，但研究定位必须收窄：

> **在可验证的长程文件任务中，训练任务数量和经验生产流程如何共同影响冻结 Skill 的 held-out 泛化、稳定性、回归率与成本？**

它不能写成“我们首次提出长程 Skill 生成”，因为：

- `SkillGen` 已经使用成功/失败轨迹、同题有无 Skill 干预和修复/回归分析；
- `Trace2Skill` 已经研究长轨迹、并行轨迹分析、层级合并、跨模型和 OOD 泛化；
- `Rethinking Self-Evolving Agent Skills` 已经研究多轮反馈、验证过滤、Success-only/Fail-only 和稀疏演化；
- `SKILL.state` 已经研究长程上下文增长、状态压缩和 context poisoning；
- `Long-Horizon Agent Trajectory Attribution` 已经把长程轨迹归因和组件级贡献定义为独立评测问题；
- `SkillGate` 已经研究长程 Skill 选择和信用分配。

因此，本方向可能形成的是**真实文件任务场景下的数据效率实证问题**，而不是一个完全没有先例的新概念。相关原文分别见：[SkillGen](https://arxiv.org/abs/2605.10999)、[Trace2Skill](https://arxiv.org/abs/2603.25158)、[Rethinking](https://arxiv.org/abs/2608.02636)、[SKILL.state](https://arxiv.org/abs/2608.26263)、[Trajectory Attribution](https://arxiv.org/abs/2608.06909)、[SkillGate](https://arxiv.org/abs/2608.18852)。

### 对原候选方向 21 的修正

1. “长程”是实验场景，不是单独创新点。
2. “小样本”必须指参与 Skill 生产的原始训练任务数量，不能把从 69/80 条成熟经验中抽 5 条直接称作端到端 5-shot 训练。
3. “泛化”主指标应先定义为冻结 Skill 在未参与生产的 held-out 任务上的表现；跨模型结果只能作为附加边界分析。
4. 任何 `48/52/55/57` 之类的曲线，如果没有真实实验来源，都不得进入论文。
5. 不能断言 SkillGen 只处理 3--5 步短程任务；现有原文摘要不支持这个说法。
6. 不能把“现有方法普遍会把局部特例固化成通用规则”当作文献事实，只能作为待验证假设。

### 最小可行实验层级

| 层级 | 实际做法 | 可以得出的结论 | 不能得出的结论 |
|---|---|---|---|
| 一级：经验池规模 | 从同一批已冻结经验中构造 `N=5/10/20/40` 个子集，再用同一合并器和同一评测 | 不同经验池规模如何影响 Skill 合并结果 | 不能证明端到端小样本 Skill 生产能力 |
| 二级：端到端确认 | 从 `N=10` 或 `N=20` 个原始任务重新执行、验证、生成和合并 Skill | 少量训练任务下完整生产流程的真实泛化效果 | 不能仅凭单个规模证明完整数据效率规律 |
| 三级：完整曲线 | 多个规模、多个随机子集、多个独立重复，并控制 token/长度/运行时 | 数据规模、生产流程与泛化之间的稳定关系 | 不能把结果外推到未测试模型或任务 |

### 本轮最终状态

`方向 21：可继续，但属于受控实证主线候选`。它比“AEV 全面优于 SkillOpt”更符合我们想研究 Skill 生成的初衷，但只有完成规模、重复、预算、长度和数据泄漏控制后，才可以写成论文主结论。当前已有最终分数不足以直接证明它。

## 候选方向 22：先生成基础 Skill，再合并为高层 Skill

**提出时间**：2026-09-02

### 核心研究问题

在单个长程任务的基础上，先把任务材料、执行轨迹和正确结果提炼为一份经过验证的基础 Skill，再将多份有效基础 Skill 合并为更高层的任务 Skill，是否比把多条原始轨迹直接合并成 Skill 更稳定、更容易泛化？

### 两条待比较的生成路径

```text
路径 A：多个原始任务轨迹 -> 直接合并 -> 最终 Skill

路径 B：单任务轨迹 -> 单任务基础 Skill -> 验证筛选
      -> 多份有效基础 Skill 合并 -> 最终 Skill
```

这里要明确区分两种 Skill：第一种是从单个任务中生成的**基础 Skill**，第二种是由多份基础 Skill 组织、去重、冲突处理和抽象后形成的**合并 Skill**。

### 与已有方向的区别

- 方向 01 重点研究经验验证、故障隔离和来源审计；方向 22 重点研究 Skill 生成的层次和顺序。
- 方向 21 重点研究训练任务数量对泛化的影响；方向 22 重点研究“原始轨迹直接合并”与“基础 Skill 再合并”的表示差异。
- 方向 02 重点研究生产者能力与验证计算的替代关系；方向 22 不把模型强弱或额外 Token 作为核心变量。

### 可检验的潜在优势

- 先把单个任务中的具体操作提炼成结构化经验，再做跨任务合并，可能减少轨迹重复、局部细节和任务间冲突。
- 基础 Skill 可以单独验证、冻结、回撤和定位来源，合并失败时能够回到具体任务级经验。
- 可以把“基础 Skill 生成错误”和“合并过程错误”分开分析，便于发现最终 Skill 失效的来源。

### 文献与创新边界

轨迹提炼、Skill 生成、分层合并和经验压缩已有相关研究，因此不能声称“首次从轨迹生成 Skill”或“首次进行 Skill 合并”。本方向可争取的窄贡献是：在长程文件任务中，受控验证“任务级基础 Skill 作为中间表示”是否比原始轨迹直接合并更能降低噪声，并改善最终合并 Skill 的泛化、稳定性和可回溯性。

### 最小验证实验

固定同一批训练任务、同一生产模型、同一合并模型、相近输入输出预算、相同 Skill 长度上限和同一 held-out 测试集，比较：

1. 原始轨迹直接合并；
2. 单任务基础 Skill 生成并验证后再合并。

至少报告最终硬分、软分、Skill 长度、有效经验数量、训练 Token、基础 Skill 验证通过率、逐题 gain/regression 和三次独立重复结果。基础 Skill 在进入第二层合并前必须冻结，测试题信息不能反向进入基础 Skill 或合并过程。

### 当前证据与状态

目前已有 AEV 的单任务经验、基础 Skill 和多层合并产物，但尚未完成上述同任务、同预算、同合并器的直接对照。因此当前只能把“先基础 Skill、后合并”作为研究假设，不能直接声称它已经优于轨迹直接合并。

**当前判定**：`新增候选，可优先做小规模受控实验`。若两阶段路径在相同预算下稳定优于直接轨迹合并，可作为方向 01 或方向 21 的方法化深化；若优势只来自更长文本或更多 Token，则应降级为表示形式与预算控制的观察。

4. 实验条件单独归入实验支撑区，避免把 `merge-as-old`、`merge-as-opt` 误当成论文方向；
5. 每次更新必须同时写“新增证据、改变的判断、下一步、结题条件”。

这样既不会丢掉过去的讨论，也能让后续几十个方向清楚地看出：它们是在回答不同科学问题，还是仅仅共享同一个实验资产。
