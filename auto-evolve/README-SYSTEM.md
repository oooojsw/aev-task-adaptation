# Auto-Evolve 系统定位与总体流程

更新：2026-10-19。本文说明当前任务适配分支的系统定位；设计决策、实现证据和待办见[系统架构探索树](进度报告/系统架构探索树.md)。

## 系统做什么

AEV 是由任务目标和完整验收协议驱动的长程产物演化系统。它组织规划、执行、分析、候选编写、审阅、正式检查和失败修订，积累经验，并按冻结规则选择交付版本。当前任务定义支持 Skill、报告、软件和策略四类交付物；具体任务的可运行程度由已接入的能力、协议及验证证据决定。

多 Skill 归纳合并是其中一种任务。50 题、单轮答题、5000 字和通过率选优属于这个任务的具体配置，不能反过来定义整个 AEV。

“演化”指候选产物及任务认识的持续改进，不要求更新基础模型权重。系统允许未达标、证据不足或资源耗尽后停止；不能保证任何目标都会收敛，也不保证每一轮得分递增。

## 一个共同流程，两个工作循环

```text
任务目标、材料、交付物和可用能力
  → 解释任务并选择方案（auto / manual_decision / manual_plan）
  → 冻结任务方案、完整验收协议、信息权限和预算
  → 进入同一个 Long Task Campaign
      → 轮内：规划 → 工作单元执行 → 局部检查、重试和重规划
      → 汇集执行证据 → Workers 分析 → Lead 编写或修订候选
      → 按所选协议进行候选检查、审阅和正式验收
          ├─ 按协议直接检查候选
          └─ 如需应用检验：独立执行候选 → 检查真实应用产物
      → 发布允许公开的反馈与诊断
          ├─ 正常拒绝：补查、重算、修改或换路线，进入下一次修订
          ├─ 平台故障：保存证据，按恢复规则处理
          └─ 合格：保留版本，按选择和停止规则继续或交付
  → 冻结所选产物及证据；需要时另做独立任务评估
```

轮内循环负责把工作做出来，跨轮循环负责根据证据改善候选。演化轮 round、验收次 pass、工作单元尝试 attempt 是不同计数，也都不等于 API 请求次数。具体验收顺序读取所选协议，不把某一种空白工具会话写成所有任务的必经步骤。

## 候选、应用结果与证据

| 对象 | 含义 | 例子 |
| --- | --- | --- |
| 候选产物 | 系统正在编写和改进的交付对象 | Skill、研究报告、程序、策略 |
| 应用结果 | 使用候选后得到的实际表现；按任务选择是否产生 | Skill 答卷、程序输出、策略收益测量 |
| 验收证据 | 绑定输入、版本、环境、实际输出与检查结论的记录 | 执行回执、评分结果、文件指纹 |
| 内部工作状态 | 支持后续工作的探索、记忆、路由与修复建议 | 已排除的假设、待查问题、失败路径 |

“两层产物”是候选与应用结果的常见结构，并非所有任务都强制有第二次执行。报告的结论通常属于报告正文，检查报告的来源、事实、反例和论证即可；只有需要复算或实测时才增加相应执行。内部记忆和诊断不默认成为交付物，也不默认暴露给独立执行角色。

## 检查、执行和角色

| 维度 | 可选内容 | 必须区分的关系 |
| --- | --- | --- |
| 检查对象 | 候选本身 / 应用产物 | Skill 内容检查与答卷检查不同 |
| 检查方式 | 确定性脚本 / 模型裁判 / 已接入的主动核查 | 方式由协议和宿主能力决定 |
| 检查目的 | 泛化约束、结构、事实、正确性、性能等 | 泛化器是 Skill 检查的一种功能，不是所有内容检查的名称 |
| 执行方式 | 无需执行 / 独立执行 / 受信脚本等已接入后端 | 空白 Agent 负责生成应用产物，不能替代正式评分 |
| 生命周期 | 形成候选、修订、正式验收、冻结后评估 | 学习反馈与最终评估必须说明各自用途 |

批量调度器、任务演化控制器和轮内任务调度器是程序。Planner、Executor、Workers、Lead、Reviewer 和失败诊断承担模型工作职责；Lead 统筹候选，不决定程序是否启动或验收通过。Reviewer 提供审阅意见，正式 Checker 按协议产生判定。失败诊断属于分析职责，不能自行改分。角色数量、可见材料和工具由具体方案确定。

## 随任务绑定哪些东西

完整绑定包括：目标、交付文件、来源材料、可修改范围、可用能力、角色信息窗口、检查对象与方式、可选执行后端、检查标准、可公开反馈、失败后的动作、版本选择、资源预算和停止条件。新增数据集或项目时，复用共同控制器并注册需要的能力和适配器。

选择已有能力可以自动组合；缺少可信执行器、检查器或材料时应报告缺项。声明一个能力并不证明它已经可运行。检查标准和任务身份冻结后，不能让训练侧通过修改评分标准获得通过；改变标准需要新的绑定和证据。

| 任务 | 候选 | 验收重点 |
| --- | --- | --- |
| 单例 Skill 演化 | 可复用指导及配套文件 | 所选内容约束、独立应用与真实答卷检查 |
| 深度研究 | 带来源的报告 | 问题覆盖、来源、事实、反例与论证；需要时复算 |
| 软件或策略优化 | 程序、脚本、参数或规则 | 固定环境的正确性及可信性能指标 |
| 多 Skill 合并 | 汇总后的可部署 Skill | 候选约束与规定用例上的实际表现 |

任务“深度”通过检查标准和证据要求表达，不直接等同于轮数或两类模型相互赞同。验收通过、稳定可用和新任务泛化是不同结论。

## 50 题合并在系统中的位置

该适配选择 `kind=skill` 和 Consolidation Profile，复用同一个 Campaign。输入冻结的来源 Skill，候选为 `DIRECT_CHAT.md`；先检查完整发布正文不超过 5000 个 NFC 规范化非空白 Unicode 码点，再对冻结的 50 个用例分别执行独立单轮、无工具答题，由受信检查器汇总 `pass_rate`。这不是 5000 字节或 5000 token。

允许的逐题反馈作为训练资源发布，Workers / Lead 按权限按需分页读取；私有答案、评分脚本和凭证保持在规定边界内。`best_pass` 仅从正式合格的候选中择优。这些训练用例分数用于本任务修订和选优，不自动代表盲测泛化。

原图的多实例合并、合并后源题回放与修订，以及冻结后评估，继续按任务配置启用。旧 `merge-as-old`、`merge-as-long-task`、Opt 聚合和 Opt 后续优化有各自入口与口径；新 Consolidation 任务不能被误称为上述任一路线的自动替换。Opt 验证集择优、源题回放、合并修订、版本回退分别说明。
