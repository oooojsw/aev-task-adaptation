## 2. B1 / 任务卡 A：显式 null 的探索策略不能默默被关闭

**目标生产文件**：`auto-evolve/orchestrator/task-adaptation/exploration/policy-reader.ts`  
**目标函数**：`readExplorationPolicy(value, plan)`、`explorationIdentityAny(value, plan)`  
**目标测试**：`auto-evolve/orchestrator/task-adaptation/exploration/policy-reader.test.ts`（原 8 组用例可追加）。

### A.1 当前真实行为与问题

代码现在写：

```ts
if (value === undefined || value === null) return undefined
```

但实际 Plan 的 `exploration` 是**可选字段，不是 nullable 字段**。`plan.ts::validatePlan` 仅对显式 `undefined` 有一条拒绝；传显式 `null` 时，它调用 Reader，而 Reader 把 null 当不存在返回。其后 `requireExplorationHost` 可能认为不需要探索，继续普通任务——这是**实际功能开关误判**，不是理论边界攻击。

### A.2 推荐改法（不要扩张到全系统）

- `readExplorationPolicy`：**仅 `value===undefined` 返回 undefined**（调用者字段真的没有配置时）；`value===null` 立即抛出易理解的 `Invalid exploration policy: explicit null not allowed`，其它非对象仍保留原“expected object”错误。
- `explorationIdentityAny`：同样只允许 undefined 表示缺失。对 `null` 调用 Reader 获得明确拒绝；不要在身份函数自己暗中返回 undefined。V1 身份继续直接返回旧 `explorationIdentity(policy,plan)`，V2 身份继续原样 fingerprint。
- `plan.ts` 无需新增第三层 null 校验；已经把显式字段转交 Reader，只要上述 Reader 行为修好，就能直接通过原 `validatePlan({exploration:null})` 拒绝；**不要修改 Plan 版本、无探索旧任务身份、V1 fingerprint**。
- 不改变 `mode:"off"`、没有 exploration 字段时的成功行为；off 仍由原 Intake 编译不带该字段的 Plan 表示，而不是将字段设成 null。

### A.3 直接写的 5 个回归测试

| 用例 | 输入和动作 | 预期 |
|---|---|---|
| A01 | 合法原 `fixturePlan()` 不含探索字段；`validatePlan` + Reader | 仍合法，Reader undefined |
| A02 | `validatePlan({...fixturePlan(), exploration:null})` | 抛错，而非合法的普通任务 |
| A03 | `readExplorationPolicy(null,fixturePlan())`、`explorationIdentityAny(null,fixturePlan())` | 均拒绝 |
| A04 | 正确 V1 fixture 和已批准 V2 window fixture | 都仍合法；V1/ V2 指纹与基线完全一致 |
| A05 | `exploration:undefined` 显式写在 Plan 里 | 仍由 `validatePlan` 拒绝，不变成 off |

**卡 A 不变量**：不得改变已合法 V1/V2 计划的结果、文件 SHA、身份、已落盘历史。定向测试真实退出码 0 才进入任务卡 B。
