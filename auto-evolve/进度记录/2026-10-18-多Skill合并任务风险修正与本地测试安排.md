本功能不是旧 benchmark 学习后的 Phase 2 Merge，而是一个独立的 `kind=skill` 通用 AEV Long Task Campaign：50 份源 Skill 是归纳学习材料；每轮写出唯一 `DIRECT_CHAT.md` 候选；全量发布正文 **≤5000 字**；每个案例采用独立的 **一次对话、一条模型请求**，上下文同时提供完整 Skill、该题题目、该题全部允许材料和格式合同；独立确定性判题；50 题的正式完整通过率 `pass_rate` 驱动已有 `best_pass` 选择历史最优合格版本。保留 `auto/manual_decision/manual_plan` 三轨 Intake、旧三种 Merge 默认行为、原 Campaign 和历史回执/恢复逻辑。

## 3. 修正 A：Task Plan 输入边界与 50 份 Skill 访问策略

**不采纳“Lead 只能看到少数源 Skill”作为硬限制。** 全部 50 份源 Skill 本就是要归纳的专家经验，可以按需分批读取；不可以让 Lead 直接读 50 道题的完整测试集、原始 PDF、私有答案或判题器。

建议划分三个数据域：

| 域 | 资源 | Planner/Lead | 受信 Direct Chat Executor | 受信 Checker |
|---|---|---|---|---|
| A 学习输入 | 50 个源 Skill + 无题号关联的索引 | 按需可读 | 非必要 | 非必要 |
| B 公开测试输入 | 50 个题目、每题各自公开材料、附件/公开输出合同 | **不直接可读整套** | 每题拆包、完整注入对应单轮上下文 | 检查完整性 |
| C 私有测试/运行 | 隐藏答案、oracle、validator、盲测、凭据、共享预算账本 | **禁止** | 仅受信路径访问，私有内容不注入模型 | 受信访问 |

实现顺序：
1. 私有的 `source-to-case` 映射与作者可读的 `source_index` **拆开**。公开索引只含 source ID、主题、hash 和定位；禁止 caseID、答案、评分脚本路径混入。
2. 作者侧只注册 A 域资源，Planner 先检索索引，按主题分 5–10 组、逐组读取；这只是工作策略，不降低源 Skill 的合法可访问范围。单次 Prompt 严禁简单堆叠所有源 Skill。
3. B/C 域保持 **host-owned** Dataset Bundle + 附件列表 + validator manifest，额外冻结**所有外部依赖** SHA-256、规范绝对路径和私有配置；打开前/运行前再次检查 `realpath`、symlink、路径逃逸、hash 和不可变性。
4. 单轮材料由可信 Direct Chat 按 case 拆包并预检，不能缺页、静默裁切或采用 head-tail；不把测试集 100–200 个物理文件逐个加进 `TaskPlan.resources`。

**验收门 A**：作者能有意读取全部 50 份源 Skill，但无法通过 `reads`、Prompt、反馈或源索引读取 B/C 域；每题只获得对应的完整公开材料；任一外部依赖篡改可阻断验收/旧回执复用。

## 4. 修正 B：代表性反馈而非“大段错误透传”

增加两层结果：
- **可信全量层**：所有 case 的结果、错误分类、validator 证明、Prompt 和材料/模型/Skill hash、API 调用/账单证据，永久保留在受控 evidence，供审核与恢复。
- **公开反馈层** `aev.consolidation-feedback.v1`：只含总数、通过率、错误直方图、最多 **3 个**有代表性的安全诊断例子、下一轮可执行的通用修订方向。建议初版公开消息 `≤1200` Unicode 字符且有显式 Token 上限，实际长度上限需要本地模型的预算评审确认。

代表例子按固定、可复验规则：优先覆盖不同错误类别（提取/格式/计算/材料定位/边界），同类按稳定 ID 或严重度排名，取前 3；同一冻结输入不随机选样。公开例子只包含允许披露的 case ID、抽象失败模式和改进建议；绝不输出私有预期答案、oracle、原始长日志、内部绝对路径。评分仍必须覆盖**全部 50 题**，不能只用 3 题估计通过率。

当前 `feedback.ts` 按声明的 `feedback:message` 决定是否对作者公开 Checker message，因此**优先在任务专用层构造安全摘要**，不要在通用反馈层硬编码“最多 3 个案例”；平台故障单独标记 `platform_fault`，不可反馈成“模型答错”。

**验收门 B**：即使 40/50 失败，公开反馈最多 3 例、长度有硬上限、无答案泄漏；全量正式评分未被采样；同一历史 run 能重放相同的采样摘要。

## 5. 修正 C：5000 字与 Markdown URL/注释计量

**拒绝“用正则在硬门计数前删除 Markdown URL/HTML 注释”的建议**。这会让真实送入模型的 Skill 含远超过 5000 字的未计量文本，URL/注释也可能隐藏指令、答案和安全问题；简单正则还可能误删嵌套 Markdown 结构。

- **硬指标**：继续严格限制唯一发布文本的 NFC-normalized 非空白 Unicode code points ≤5000；如变更计数规范必须提升验收版本并重新测试。所有实际注入的 Skill 字符，不论 URL、代码、注释都要计入。
- **辅助软指标**：可增加 Markdown AST 派生的 `guidance_chars`（供提示模型压缩正文）、`link_count`、`link_bytes`、预估 `prompt_tokens`；这些只能改善编辑建议，不能替代 5000 字硬门。
- **结构硬门**：拒绝断裂的 Markdown 链接、未闭合代码围栏、过长/非法控制字符、零宽格式干扰、链接中注入私有答案；表面校验不能擅自修改文本再对另一个 hash 测试。
- 业务允许的长外部地址可用简短稳定引用名称加**授权的公开题目材料**解释，但不能借外部文件/链接间接把额外 Skill 正文偷偷注入。

**验收门 C**：4999/5000/5001 字、超长 URL、注释、emoji、NFC/组合字符、零宽字符、断链都纳入边界测试；请求时 Skill hash 与正式交付版本 hash 一致，任何截断不允许。

## 6. 修正 D：Direct Chat 统一硬预算（最高优先级 / 付费阻断）

当前 `protocol-plugins/consolidation.ts` 直接调用 `runDirectChatEvaluation`，最后才统计 tokens。**仅仅限制 concurrent=2、maxAttempts=1 或结束后上报 usage，并没有全局调用次数/Token 的硬上限。**

必须复用 Task-Adaptation 现有 `budget-policy.ts / budget-transport.ts` 的持久 scope/ledger 语义，并在**实际 Direct Chat provider 网络发送之前**完成不可绕过的受信准入。

### 状态机

```text
Surface Gate + 输入/模型/材料上下文完整性检查
    ↓
对每个 case 计算可证明的输入预留上界 + max output tokens
    ↓
共享 scope ledger 原子申请 reservation（calls + tokens）
    ├─ 不够：零网络发送，记录 budget_rejected
    └─ 足够：持久化 intent/requestID → 真实 HTTP 最多一次 dispatch
             ├─ 成功且 usage 可信：settle 真实消耗，记录可审计 receipt
             └─ 超时/取消/断联/无 usage：reservation 标记 uncertain，
                不自动退款，不重复发该 case，停止后续网络发送
```

要求：
1. 预算保护必须发生在 `provider-client` 或更低的**实际发送边界**，而不只是在外层 `runDirectChatEvaluation` 启动时检查。若 provider 自带透明重试，要分别审查并禁用/逐次预扣。
2. 每次请求有持久、唯一、绑定 `plan/campaign/round/candidateHash/caseID/datasetHash/modelID/providerConfigHash` 的 requestID；恢复时不得把发送状态不明的请求当作“未运行”重新发出。
3. 与 Planner/Lead/Reviewer 共用冻结 `stop.calls / stop.tokens` 的总账；禁止另外创建 Direct Chat 私有免费配额池。并发预留必须原子，50 个并发 case 不能穿透同一个剩余额度。
4. 事前 Token 预留来自受信模型上界/真实 tokenizer 或经过验证的保守上界，**不能拿字符数/4 估算当硬保证**；输出上界和单请求上下文约束在预检时固定。
5. 不确定 usage 保留占额并故障熔断；Provider 报告迟到/网络异常时只有可信 reconcile 可恢复，不允许悄悄补发；预算耗尽只交付之前已通过硬门并正式保存的最佳版本。
6. token 预算与真实货币费用不同，若需要防金额超支还需明确定价版本、货币预算和最坏价格上界。API key 不能进入模型或日志。
7. 当前 `direct-chat/runner.ts` 与原 CLI 的默认行为不得因新 profile 改动；Budget hook 必须 opt-in、具备独立版本身份和故障阻断测试。

**验收门 D**：使用本地模拟 HTTP 对 50 个并发请求设置 `calls=3` 时真实发送次数 **≤3**；输入 token reservation 不够时 **0 次**；多进程并发/崩溃/恢复/无 usage/网络超时不穿透预算、不自动补发，不确定调用不退款。**这些证据未齐，严禁付费 API 运行**。

## 7. 独立判题器/Protocol 交叉风险

- `direct-chat/runner.ts` 旧通用判题器可能根据退出码推断 pass/fail；新任务独立 Checker 应**强制每题验证器提供明确结构化布尔 verdict**，不接受仅凭退出 0/1 为有效判题。验证器崩溃/输出不合法一律 `scoring_error` 或 `platform_fault`，不能计为普通模型错误。
- 每个候选需要绑定的身份包括：Skill 实际发布字节/hash、每题材料和 Prompt hash、模型参数、冻结题集/validator 版本、原始 requestID 与账本 receipt；正式 `pass_rate` 只能由可信验收结果计算。
- 对 `0/50`、`43/50`、`50/50` 均允许数学有效的优化指标（前提是硬门通过）；不能写“必须 50/50 才可 best_pass”。
- 独立通用 Campaign 仍需验证 `prepareTaskRun → Runtime.run → Protocol checks → selection.ts → delivery.ts` 全链、恢复与旧合并流程兼容。
