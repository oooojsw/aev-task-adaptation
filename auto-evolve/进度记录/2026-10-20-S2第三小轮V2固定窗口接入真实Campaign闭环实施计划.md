## 2. B1 / 任务卡 A：一次性理顺 V1/V2 Policy 身份与公共读取，暂不接决定器

### A.1 为什么这样改

现在 `Plan.exploration?: ExplorationPolicy` 只描述 V1。`exploration/policy.ts::explorationPolicy` 是 V1 的严格校验器；V2 在 `policy-v2.ts::validateExplorationPolicyV2` 是独立函数。不能为了让新版本能用，在 V1 里修改 `schema` 或把 V2 强制转成 V1 再落盘。**两种版本不能共享指纹语义**。

**推荐新增一个极小的版本入口**（例如 `exploration/policy-reader.ts`），统一提供：
- `type AnyExplorationPolicy = ExplorationPolicy | ExplorationPolicyV2`；
- `readExplorationPolicy(value: unknown, plan: Readonly<Plan>): Readonly<AnyExplorationPolicy> | undefined`，输入不存在时 undefined；V1 schema 调原 `explorationPolicy`，V2 schema 调原 `validateExplorationPolicyV2`；其他一律拒绝；
- `explorationIdentityAny(value,plan)`：V1 分支**原样调用**现有 `explorationIdentity`（不能重新算一个“近似值”）；V2 分支可用相同外层 `fingerprint({plan:fingerprint(plan),policy:validatedV2})` 结构但 V2 原生 policy schema，绝不能落盘 V1 投影身份；
- 如 TypeScript 需要，可提供只读公共字段访问 `policy.allowance`、`policy.bounds`、`policy.origin`、`policy.replace/preserve/dependencies`；不为这个建立通用 Policy 平台。

**目标文件 1**：`exploration/policy-reader.ts`（新增）。
当前行为：全仓只有 V1 Reader。
期望：独立、无 IO、稳定地读取并区分两种原生策略。
不能改：`policy.ts` 原函数、`policy-v2.ts` 原静态公式、V1 指纹与冻结结构。
测试：同一 V1 Plan 指纹改造前后**逐字相同**；合法 V2 window 有独立新身份；`undefined` 仍无探索；非法 schema 拒绝。

**目标文件 2**：`task-adaptation/plan.ts::Plan,validatePlan`。
当前：`exploration?: ExplorationPolicy`；`validatePlan` 尾部只调用 V1 `explorationPolicy`。
期望：`exploration?: AnyExplorationPolicy`，尾部调用公共 Reader；保留外层 `schema:"aev.task-plan.v1"`、原全部权限资源/验收/预算验证。**Schema V2 是 exploration 的内部版本，不改 TaskPlan 顶层版本**。
不能改：`planIdentity` 算法/无探索字段身份、`roleWindow` 权限。
测试：V1、无探索继续合法且 fingerprint 不变；Host 冻结的 V2 window 合法；未知/越界策略仍拒绝。

**特别提醒 TypeScript import 周期**：`policy-v2.ts` 已 `import type {Plan} from "../plan"` 且使用 V1 静态投影验证；新的 Reader 引用 Plan 时也使用 `import type`，避免增加启动时循环副作用。旧 V1 Reader 不应改为反向 import V2。

### A.2 主机读取者的最小改动清单（不能漏）

现有真正运行时直接调用 V1 Reader 的文件已逐一核对：
- `exploration/entry.ts::requireExplorationHost`：对两版本共用角色与 effect 约束；**V2 metric 此轮必须明确拒绝**并报出“Host V2 metric scoring binding not implemented”，不能在静态校验通过后误运行。
- `exploration/preflight.ts::preflightExploration`：已经使用 `plan.exploration` 的公共字段；在 `requireExplorationHost` 通过后继续复用原阶段 Token、Checker/Executor、只导出本地的预检。不能跳过。
- `exploration/ownership.ts::openTaskCampaignControl`：从同一 Reader 获得公共 `bounds`、用 Any 身份算 `scope.policy`，**必须同真实 Planner 身份匹配**。
- `exploration/origin.ts::freezeTaskOrigin`：取公共 origin/bounds、保存原候选和基线；历史候选身份不能漂移。
- `exploration/generation.ts::openTaskGeneration`：保持 generation 0/1 租约、读取 activation 状态；仅改变 Reader，不改变运行态权限。
- `exploration/stages.ts::openTaskRequestStage`：用公共 allowance/身份，保留原请求阶段准入与 Token 上限；不得令 V2 绕过 budget policy。
- `exploration/composition.ts::compose,CompositionInput`：参数类型改为 Any Policy，原有 replace 从 origin、preserve 从 current 的逻辑原样保留，使用 Any 身份，不要写第二份 composition 系统。
- `exploration/activation.ts::activate`：输入通常由 CompositionInput 携带策略，需用 Any Reader 验证其自身的 policy 和 scope，再复用 V1 的文件事务、origin/current 标识、generation=1 锁与投影。
- `exploration/evaluation.ts::archiveRound`：输入 `policy` 参数扩成 Any Policy，共享正式验收验证、候选档案保存、受信快照，用 Any 身份，**不能降低对 closed_success/closed_repairable + 正式 receipt 的强约束**。

**注意**：这组文件看似不少，但逻辑上全是“让 V2 安全使用 V1 的现有公共数据与对象身份”，不应复制大型业务函数。每个文件通常只应修改 1—3 个 Reader/type/import；如果某处需要重写数百行，应停止重新审查原因。避免新通用平台、重复分配预算。

## 3. B2 / 任务卡 B：V2 正式 Round 决定与原有激活、恢复路径打通

### B.2-1 复用已经存在的真实轮末入口——不要新增并行 Campaign

**目标文件**：`long-task-campaign/round-control.ts::completeTaskRound`（原则上**不需要修改**）。
现有真正执行路径：

```text
long-task-campaign/runner.ts
  -> completeTaskRound
      -> findTaskExplorationDecision（如同一轮已保存，直接复用）
      -> finalizeTaskRound（正式选优和快照）
      -> closeTaskExplorationRound（当前只 V1）
           -> freezeTaskOrigin / archiveRound / inspectBudget / decide(V1)
           -> host/state.json 冻结决定
      -> nextStatus / restart
  -> restart=true ? activateTaskBranch : continue
  -> 恢复入口同样 find/read/activate
```

**期望修改方法**：把 V2 版本分派放在现有 `exploration/lifecycle.ts::closeTaskExplorationRound` 内部（或同文件被它调用的私有 helper），让旧 `round-control.ts`、两处 `runner.ts` 的闭轮与恢复继续使用**同一入口**，不要在 runner 中新建第二个 V2 主循环。

**必须保留不变**：`completeTaskRound` 的正式 select/Harvest、`restart` 与状态返回、现有正常结束和恢复执行器、生成控制租约。不把模型或 Checker 调用次数当轮次。候选通过后仍由 Selection 选择，不由 V2 重新评价哪一条更好。

### B.2-2 利用 `archiveRound` 生产真正的 V2 闭轮证据

**目标文件**：`exploration/evaluation.ts::archiveRound` 和 `exploration/lifecycle.ts::closeTaskExplorationRound`。

当前 `archiveRound` 已经**真实核查**：
- 只有 `closed_success` 或 `closed_repairable` 且正式验收执行了，才接受；
- 正式 Campaign 轮号/最终 pass / feedback path / 任务训练回执绑定必须一致；
- 通过 `verifyCompletedCampaignAcceptance`、`readCompletedRejectedCampaignPass` 和 `taskFeedback` 读取真正聚合过的正式验收，而不是单个 Checker 判词；
- 被拒绝产物没有可信数值分数；合格 `best_pass` 从 `taskSelectionSource` 获取正式指标；
- `saveCandidate` 保存候选档案，`observation` 含 `round,closure,branch,verdict` 等。

**推荐最小新增字段**：`archiveRound` 返回对象除既有 `{candidate,observation}` 外，额外返回 `receipt: actual.view.receiptFingerprint`（仅内部信任返回；不要往 V1 `Observation` 里加必填字段或改变 V1 决策身份）。这里该 receipt 来自**完整正式验收回执**，绝不能取单个模型 Checker 的 response ID。

构造 V2 窗口闭轮记录：

```ts
const closed = {
  campaign: scope.campaign,
  round: observed.observation.round,
  branch: input.generation === 1 ? "alternative" : "original",
  closure: observed.observation.closure,
  receipt: observed.receipt,
  verdict: observed.observation.verdict,
  // 此轮 trigger=window，不传 metric：不需要伪造 comparison 指纹
}
```

`input.generation` 必须来自当前真正的 generation lease（现有控制器已经传递），不得根据上次状态随意猜 route。**即使一个 Round 产生三个 Checker 判词，向 decideV2 只传一个正式 closed。**

本轮限定为 `window`，因此不需要改 `selection.ts` 评分来源，不新建比较身份。未来 metric 真正接线必须验证与协议、评分器、测例、推理条件绑定，本轮 Host 应拒绝它。

### B.2-3 V2 状态独立分版，但共享路径和激活事务

**目标文件**：`exploration/lifecycle.ts`。

当前 `state()` 只认 `aev.exploration-campaign.v1`，保存 `observations: Observation[]`、`decision: Decision`；**V2 禁止把 `ClosedRoundV2[]` 生硬塞到这个 V1 observations 字段**。

建议同文件增设小的判别类型和验证读取：
- `StateV1`：现有内容、schema、指纹不变；
- `StateV2`：`schema:"aev.exploration-campaign.v2"`；`scope`、`origin`、`candidates` 仍沿用 V1 存档结构；`rounds: ClosedRoundV2[]`；`decision: DecisionV2`；
- 读取 `host/state.json` 时先校验外层 fingerprint、scope，再按原生 schema 分派。**不能默默把 V1 v1 状态当 V2 重新解码**；state 与冻结 policy.schema 版本不一致立刻拒绝。
- 同一 Round 已提交决定时，`findTaskExplorationDecision` 与 `closeTaskExplorationRound` 都只读同一旧决定，不重复归档、不重新取预算、不重跑 Checker；如下一次输入是同轮不同闭轮证据，报告身份冲突，不能覆盖。
- `StateV2.decision.identity` 应直接保存 `decideV2` 的确定性身份；**不要新造一个不兼容 V1 的“Host 自评”字段**。如需在 Host State 额外冻结 `effectiveMaxRounds` 与余额快照以稳定恢复，只添加到 V2 状态并绑定 state fingerprint，不修改 V1 状态。
- 决策生成时的 `effectiveMaxRounds = min(plan.stop.rounds, input.maxRounds ?? plan.stop.rounds)`，`remaining` 继续用现有 `inspectBudget` 的真实账本，与 V1 相同扣减口径（包括 outstanding Token）；
- `decideV2` 的 `stopped/unresolved/hardStop/firstPass/originReady` 从现有 Host 源生成，不从模型消息解析。若 V2 认为 `hold`，交还既有 `round-control` 处理；不能假装“普通拒绝”之后继续盲目换路。

当前 `decision-v2.ts` 的 `effective_window_incompatible` 校验放在原路线考虑激活时检查，这是源码现状。**本轮可先不重排纯函数所有 if 分支**：正确做法是在 Host 前置准入时校验实际有效 N，确保用户总轮次/实际 Campaign 上限不相容时**还没发第一轮请求就报错**。例如 Plan N=9、窗口 f=h=7/m=2，但实际 Campaign maxRounds=7，必须拒绝/报告，不能运行 7 轮后才发现不可能切换。

### B.2-4 重用 activation / composition / generation；不要发明另一个换路引擎

**目标文件**：`exploration/lifecycle.ts::activateTaskBranch,taskBranchStart,findTaskExplorationDecision`。已有：
- `activateTaskBranch` 从 state 读取 `decision.action==="activate"`，调用原 `activate()`，再重用原 `composition` 保留/替换指定文件、历史候选、投影和 `resetTaskBranchViews`；
- `taskBranchStart` 读取 `host/projection.json` 的 `nextRound`，用于后续 Round 正确地跳过旧路线反馈；
- `findTaskExplorationDecision` 在正常/恢复轮末和终态复用已提交决定；
- `generation.ts` 通过 `openTaskGeneration` 租约阻止在活跃一轮中途切换。

**具体要求**：
1. 对 V2 读取 V2 State 中的 `decision.action`、`last.round` 和原 V1 结构相同的 `candidates[]`；然后沿用 `activate()` 而非复制激活函数。
2. 旧 `composition/activation` 的文件记录 Schema 如结构未变就继续复用，但所有策略和 scope 的身份必须来自 `explorationIdentityAny(V2,plan)`；绝不能以 V1 伪投影策略的身份落盘。
3. `projection.json` 的 schema 若只是结构（scope/activation/nextRound）且原检查能绑定 V2 scope，可保持当前结构；如确实需要分版，仅改变 **V2** 分支，V1 原持久化不变。不要为了版本号好看而连锁重建十个组件。
4. 同轮重放已有投影时不重置 current；如果第 3 轮已经在备用路线写下成果，再恢复不能用旧 `composition` 重置成刚切换的初始文件。
5. 正常执行和 `runner.ts` 中的恢复路径必须最终仍走原来的 `activateTaskBranch`；不分别引入两个决策函数。
6. 再次校验活跃 generation 0→1 后 `origin/preserve/dependencies` 和 Checker/Selection 权限不变。**具体新工作内容由 Agent 离线 fixture 模拟，不预先硬编码固定回答。**

### B.2-5 原来的 V1 行为永远是回归基线

修改时禁止触碰 V1 旧 `decide`、旧 Policy、旧观察记录字段。**V1 之前保存的 Host State 与 projection 可从同一文件名正常读取**，V1 identity 一字不变。无探索的 TaskPlan 与 S1 `auto/observations` 默认解析不被意外升级为 V2。

### C.2 必须覆盖的完整 E2E 断言

1. 启动前经过 `validatePlan`、`requireExplorationHost`、`preflightExploration`、Host Checker/Executor/Token 阶段预检；
2. 第 1、2 轮正式正常关闭，`StateV2.rounds` 存在两条 `branch:"original"`，而不是“两次 Checker 调用”等于两轮；
3. 第 2 轮决定 `activate/window_exhausted`；原路线候选历史被归档，切换事务生成原 `activation`/`composition`/`projection`；
4. 第 3 轮是 `branch:"alternative"`，确实读取到批准的源文件内容，且其工作内容由 Mock Agent 的**新生成结果**提供；
5. 第 3 轮正式 Checker passed；原 `recordTaskVersion / chooseTaskVersion` 的合格结果交付 `verified_success`；`StateV2.decision.reason="first_pass"`；
6. `StateV2.rounds.map(branch)` 应为 `["original","original","alternative"]`；同时整个用户预算 `stop.rounds/calls/tokens` 从未增大，余额由原账本记录；
7. 保存第 3 轮完成后的模型 fixture 调用数、预算快照、交付文件哈希；重复调用同一个 `runTask` 时调用数与账本不变，交付 `reused:true`，内容哈希不变，不能重复 activation；
8. 再做一个切换点中断恢复：第 2 轮已保存决定但还没有完成 projection 时恢复，必须只激活一次、继续第 3 轮。**仅测试现有恢复机制已有的代表性故障点**，不新增大规模故障注入；
9. 同一 Round 即便有两个 required Checker 或若干 pass，闭轮数组仍只加 1 条记录；测试可在低成本额外用例用现有多 Checker fixture 验证，不能为了此加真实模型；

11. 如果实际 Campaign.maxRounds 小于冻结窗口最低需求，必须在第一轮开始前清楚拒绝，不花请求后再退回。

### 5.2 必须明确报告的两个残留源码风险（不要无故延伸成大防御）

1. **实际有效 N 的可用性**：`decision-v2.ts` 对 `effective_window_incompatible` 的检查位于触发考虑激活的阶段。本轮真正的 Host 应该**启动前**校验有效 N，以免消耗完原路线预算才发现窗口本来不可能。若实际入口无法在无大规模改动的条件下取得 Campaign.maxRounds，先报告准确阻断，再决定最小改动点；**不能靠增加 Plan.stop.rounds、缩短窗口静默修复**。
2. **比较身份未接通**：`policy-v2.ts` 有合法 metric Schema、`decision-v2.ts` 可比较明确输入；但现有真实 `archiveRound` 只产生 `metric: number`，尚未生产可信 `comparison`。所以本轮必须让 **V2 metric Host 拒绝执行**，不能伪造比较身份来假装 metric 已可运行；下一轮再专门安排正式指标绑定。

除此之外不要借题发挥做多个维度的深度安全整改。

### 5.3 停止条件

必须停止并向用户/云端报告：
- 基线 SHA 不同且已出现相关新实现，无法分辨本轮计划是否过时；
- B0 基线测试无法运行且原因涉及旧核心业务；不可掩盖；
- 需要改 V1 已落盘 State、历史最优候选或其 fingerprint；
- 需要更改预算/权限/Checker 正式协议/用户冻结条件；
- V2 切换需要复制 Campaign 主循环，或必须引入第二套 Agent 调度器；
- 无法证明触发依据是**完整验收后的正式 Round**，而非某次单独 Checker；
- 无法证明冻结 V2 与恢复 V2 使用同一 strategy identity；
- 为了使测试通过必须把 V2 metric 假装有可信 comparison；
- E2E 结果无法区分 fixture 失配与真实 V2 逻辑缺陷。

可以自行处理：纯 import/类型/fixture 修改、test helper、错误测试路径、小范围明显阻断运行的接口遗漏；每次都要重跑对应测试并记录证据。
