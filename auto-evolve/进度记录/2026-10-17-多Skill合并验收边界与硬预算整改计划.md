## 0. 保持不变的验收合同

合并是 Task-Adaptation 中的**独立 Long Task Campaign**，不是 Skill 学习完毕后的旧 Phase 2 Merge。仍然使用 `auto / manual_decision / manual_plan` 三轨 Intake、同一 Campaign 的 Planner/Lead/Reviewer/Diagnostician/Feedback、既有 `best_pass` 历史版本选择。

**输入**为 50 份已生成的只读源 Skill。**候选**为单一 `DIRECT_CHAT.md`，其实际注入每道题的完整 Skill 正文不得超过 5000 字。**评测**为 50 道题逐题独立的一次对话：每个请求包含完整候选 Skill、这一题的公开题目与全部必要材料、固定输出协议；无多轮工具 Agent、无跨题对话记忆、无隐式补发。私有标准答案与 validator 只在受信评测侧使用。完整 50 题正式验收后计算 `pass_rate=passed/50`，合格版本按分数最大化选优；训练回测不能被称为盲测泛化成绩。

真实付费 Direct Chat 必须经过同一个 Campaign 的原子**事前**调用次数与 Token 预算门禁；完成预算接入及本地 HTTP 伪服务验证前禁止进行真实收费模型批量评测。

## 2. 暗礁一：Plan 的作者可读边界和大量来源文件

### 静态审查事实

`consolidation/profile.ts` 当前 `consolidationCatalogue()` 将 50 份源 Skill 逐个注册为 `audience:"training"`，并注册 `source_index`。`task-adaptation/catalogue.ts` 的 `assemble()` 将**所有非 private**资源加入 Planner/Lead 等角色窗口的 reads。故这些 50 份源 Skill 都可读（但**不能据此断言已经被一次性塞入 Prompt**）。这不符合要求的“默认只给索引与有限样例、需要时按需读取”。

完整的 50 道题 JSONL 目前**没有**被逐份加入 `TaskPlan.resources`，而是经受信 `protocol-plugins/consolidation.ts` 的 `datasetPath`/`datasetSHA256` 配置进入 Direct Chat，这个方向是正确的。不能为了强调“private”又把几百个原题与评分文件一一注入通用 Plan。

### G1：分离作者来源域与私有评测域（P0）

**A. 作者域**：
- 启动时可读 `source_manifest`（包含受信 source_id、类别摘要、SHA-256、覆盖进度），只额外给少量经过宿主允许的样例，不暴露 50 道完整题目、隐藏答案和 validator 参数。
- 建议复用现有 Task-Adaptation 角色工具（如有真实按需读取边界），否则实现受信 `read_source_skill(source_id, section, maxChars)` 能力，只接受白名单源 ID，每次验证原始 hash、分页/分段限额、最大累计 Token、权限与读取审计。作者**最终仍应有能力学习全部 50 份源 Skill**，不能永久只看三份样例。
- 若需减少 `resources` 项数量，普通 Plan 仅有发布候选、source index 与可公开样例；实际源文件由按需读取服务管理。不能因为 Manifest 里写了私有路径就默认已经赋予安全访问控制。
- 原单题 Skill 可能含目标题的硬编码答案，来源侧需检查可疑常量与答案泄漏，并允许只提供抽象方法；不要把“源 Skill 已验证”误当成无答案证明。

**B. 私有评测域**：
- 50 道原题、各自的原始公开材料、素材资产、private oracle、validator、评分配置一律放宿主受信根；不进入作者角色的 reads、Prompt、可写目录或给模型的失败反馈。
- 若在通用 Plan 中表示元信息，仅能是不会公开明文的 `audience:"private"` 审计锚点。推荐真实评测材料仍保留在 host-owned evaluator 外部绑定里（不展开注册几百份 private 文件），其真实读取权限由插件边界判定。
- 当前仅冻结顶层 JSONL 与 models JSON SHA-256 不够：JSONL 里还有 `privateOracle.scriptPath`、图片/PDF 的内部路径、validator 参数。必须建立**传递闭包冻结**：这些实际引用的材料、判题器脚本及依赖、Prompt 模板、模型标识与参数有独立的 hash/版本，路径白名单、反 symlink/反逃逸；在请求前与恢复后重查。
- 不让未经批准的 evaluator 配置、路径或 API 凭据成为用户任务本身可以控制的输入。

**建议文件**：`task-adaptation/consolidation/{profile,source-manifest}.ts`，按需源文件读取工具，新 host-only evaluation manifest，`protocol-plugins/consolidation.ts`，`direct-chat/dataset-bundler.ts`/material adapters。若对通用 `catalogue.ts` 加权限扩展，只能是兼容性显式 opt-in。

**G1 验收**：验证 Lead/Planner 看不到完整 50 题、答案和 oracle；能按需阅读 50 个被哈希绑定的源 Skill；更换任意外部 validator、图片/PDF、模型参数或模板，在调用或恢复时均 fail closed；不把原题散文件灌进作者上下文。

## 3. 暗礁二：反馈聚合、长度与隐私

### 静态审查事实

现在的 `protocol-plugins/consolidation.ts` Product Checker 正常返回类似 `Verified 10/50; pass_rate=0.2`；`task-adaptation/feedback.ts` 只有在 Plan/Protocol 均允许 `feedback:"message"` 时才披露检查器消息。**目前没有证据表明它把 40 个失败 Trace 原封不动传给 Lead**。真实缺口是详细可诊断性不足，未来若直接转发原始 Trace 才会造成信息与隐私双重风险。

### G3-A：两级错误反馈（P1）

- **Host-only**：完整保存 50 题的 `case_id`、提示与材料 hash、原始响应、validator 判决/错误、调度与预算凭证、测试总账；禁止直接交给作者。
- **Lead-visible**：每轮给通过数/总数/率、失败类别直方图、与历史最优差值，以及**最多 3 条**确定性挑选的代表性反馈。优先分散类别（如格式/提取/公开规则失配），不得用私有正确答案伪造“逻辑错误原因”。
- 建议冻结两个上限：**最终摘要 ≤1200 个 UTF-8 字符且估算 Token ≤固定反馈预算**；较小者优先。类别 40 个也只发 3 个聚合例子；未授权则退回只报告分类计数。
- 代表性片段仅使用受信、允许反馈的公开内容或摘要；不能包含隐藏 oracle、标准答案、私有评分日志，也不能把题目内 prompt injection 提升为指令。确定性排序，按 task/round/candidateHash/datasetHash 绑定恢复身份。
- 不给作者可直接读取 Host-only log 的路径；Host-side 仍可通过审计映射追查每个错误。
- `0/50`、`10/50` 但 50 题可信完成时仍是可供 `best_pass` 评估的合格候选；**不能把分数未达100%当成 required 检查失败**。

**建议文件**：新 `consolidation/feedback.ts`（纯摘要）、`protocol-plugins/consolidation.ts`（Product Checker 输出）、必要时检查 `task-adaptation/feedback.ts` 的授权与 Token 边界；不另造 Campaign 反馈体系。

**G3-A 验收**：0/3/40/50 题失败时摘要稳定且双限额生效；恶意超长日志、伪造评分、私有答案与注入材料不泄漏；Lead 下一轮实能读到合法分类/策略建议，不只看到总分。

## 4. 暗礁三：5000 字计数与 URL/注释争议

### 设计裁定

当前实现为 `Array.from(content.normalize("NFC").replace(/\s/gu, "")).length`。**不接受“先用正则剔除 Markdown URL 和 HTML 注释再单独卡 5000”替换硬门**：如果这部分仍注入 Direct Chat，上下文实际不受限；长链接、Base64、代码及可嵌套 Markdown 还可能绕过约束。简单正则也不能可靠识别复杂 Markdown。

### G3-B：严格“发布正文 + 辅助指导字符”双指标（P1）

1. `published_chars`：**真实发送给模型的完整发布文本** NFC 后去 Unicode 空白、按 code point 计，含链接目的地址、Markdown 结构、代码和注释；硬门 `<=5000`。
2. `guidance_chars`：由 Markdown 解析器统计自然语言指导性内容，可排除经分类的冗余结构、注释作提示，不参与最终合格性。
3. `published_bytes`：独立的 UTF-8 实际字节上限，阻止过大输入；`prompt_tokens`：模型对每题完整 Prompt 的实际允许上下文硬门，不能用字符数代替 Token 预算。
4. 如果清理注释和无用链接，必须**先输出唯一正式发布文件**，然后对清理后的**实际被发送字节**重新计算所有 hash、字符、Token。不能检查删减 A 版本、发送含隐藏负担的 B 版本。
5. Direct Chat 禁工具，外部引用 URL 不等于模型可自行访问页面；可以将无关长 URL 移入**不注入模型**的 host-owned metadata，或改成明确、可核查的短标识，但不能删掉作答依赖的必要证据。

**G3-B 验收**：5000/5001 边界、中文/英文/emoji/组合字符/零宽字符/CRLF、长 URL、嵌套链接、HTML 注释、超长代码/Base64、额外文件与 head-tail 输入均有明确定义和负向检查；超标在任何真实 provider 请求之前被拒绝。规则变动必须更新协议版本并重新比较分数。

## 5. 最紧急：Direct Chat 统一事前预算门禁

### 静态审查事实

`protocol-plugins/consolidation.ts` 在 `execute` 内直接运行 `runDirectChatEvaluation()`，`direct-chat/runner.ts` 再调用 provider；预算当前只在收集 `result.results` 后形成 usage，**没有在每个 HTTP dispatch 之前共用原子 calls/tokens 门禁**。`prepare-task-run.ts` 使用 `taskRuntimeBudgets()` 只连接 `httpBudgets`、`toolBudgets`，没有把同一门禁接给 Consolidation 的 provider。

已有可复用基础：`task-adaptation/request-budget.ts` 的 `reserveRequest/settleRequest` 和原子账本；`budget-transport.ts` 的 `budgetedProviderFetch()`；`protocol-plugins/http-chat.ts` 中的收费前登记和不确定用量处理。

### G2：接入每个实际发送的原子预算（P0，阻断真实付费）

- 在宿主冻结的 `TaskBudgetPolicy` 中，明确统一 `root/scope/calls/tokens`、模型 wire ID、dialect、上下文/maxInput/maxOutput、provider、版本/角色；与其他 Task-Adaptation 模型调用共用**同一个 campaign 账本**，不能给 Consolidation 偷建第二个默认无限额余额。
- 在最后一个真实 provider HTTP POST 之前 `reserveRequest`（或适配 `budgetedProviderFetch`）；一题一次发送标识绑定 `(taskFingerprint, candidateHash, evalAttempt, caseID, requestHash)`。直接从 `Promise.all` 外层做一次总额估算**不是足够的原子拦截**。
- 请求前冻结完整 prompt/input 上界和最大输出 Token，使用明确的保守上限预留；Unicode 字符、promptBudgetTokens 等估算仅作早期诊断，不能冒充 provider 实际 Token 硬限。
- 50 题并发、其他 Campaign 调用、恢复运行时使用同一个原子锁与记账。额度不足 `blocked_before_dispatch`，绝不发送；未知响应保留预扣、不自动退额；usage 完整则 settle，超额报告 overrun 并停止后续派发。
- Direct Chat `retry.maxAttempts=1` 和 `transientRecovery.enabled=false` 只是第一层；还要验证底层 provider/SDK/HTTP 网关不会透明重传。若底层无法证明一题一次发送，则不能宣称符合当前合同。
- 阶段中任意一题因预算阻断或基础设施失败，**当前候选 50 题验收无效、不入 best_pass**；保留已发生费用和实际局部 trace。Campaign 可以停止并交付此前已正式验收的最好候选。
- 无预算配置的非 mock 模型、未覆盖的 provider 协议、与冻结模型身份不符的请求全部 fail closed；只在本地 mock/伪 HTTP 条件下继续安全验收。

**建议文件**：`task-adaptation/{budget-policy,budget-transport,request-budget}.ts` 及受信绑定；`direct-chat/provider-client.ts`、`direct-chat/providers/openai-compatible.ts`（与 siliconflow 派发复用）、`protocol-plugins/consolidation.ts`、`prepare-task-run.ts`。保持旧普通 Direct Chat CLI 默认行为不变，只有本任务显式 opt-in 强制门禁。

**G2 验收**（本地 Agent 使用无收费伪 HTTP）：50 题并发设置 calls=3 时真实外发 HTTP POST 不超过3；Token 不足时额外外发为0；完成/超额/未知用量有真实 ledger 记录；断网无重复派发；恢复后 ledger 不重新计零；修改 provider/请求模型不复用旧结果；预算硬拒绝不会被误写为模型答错。

**最高原则**：在 G2 未完整验证之前，严禁用真实付费 API 跑 50 题；测试只使用 mock provider 或 local HTTP fixture。
