## 1. 本轮要交付什么：一个真实可用的最短闭环

用户继续提交任务目标、材料、原验收协议和总预算，只需再选择“关闭 / 自动 / 正常验收观察 N 次后考虑换路”。Host 根据已批准且唯一匹配的任务模板，**自动展开现有 V1 ExplorationPolicy**；新 Plan 在首次运行前冻结，随后仍由原 \`runTask -> Campaign -> completeTaskRound -> closeTaskExplorationRound -> Checker/selection/delivery\` 执行。

**本轮不是重写路线决策器。** V1 的 \`observations=N\` 统计**正常关闭的正式轮末观察**，不承诺“Campaign 全局第 N 轮”；“严格第 N 轮”以及 \`f/h/m/b\` 自由轮次是阶段 2，绝不能在本轮混入。

**本轮功能交付标准**：一条已有受限文件报告型任务，通过 \`manual_decision + explorationRequest\` 在实际准备入口生成含 V1 exploration 的冻结 Plan，再走一次现有离线 \`runTask\`，检查仍由共同 Campaign 处理与交付；\`auto\` 也必须接线并有定向入口测试（模型侧用既有确定性假驱动，不产生真实 API 费用）。无请求的既有模式不变。

**规模控制**：本轮仅 3 个相互关联模块：A. 模板解析（2 个小新文件）；B. 输入/冻结接线（2 个已有文件，确有需要时才小改 \`catalogue.ts\`）；C. 相关测试与一小段使用说明。若任何一步需要新增 V2 策略、修改 request-budget 钱包或重构 runner，立即停止汇报，不自作主张扩容。

## 4. B1：实施三个小任务卡（按顺序，每卡先测再进入下一卡）

### 卡 A：受信模板与纯解析器 —— 不启动模型、不写文件

**目标文件**：新建 \`auto-evolve/orchestrator/task-adaptation/exploration/templates.ts\`、\`exploration/resolve.ts\`，可配套 \`resolve.test.ts\`。

**接口与现状**：\`compileTask()\` 只能给基础 Plan，V1 策略目前靠人工完整填写。本卡增加小型、静态 Host 模板声明和**纯函数** \`resolveExploration(basePlan, request, templates, support)\`。命名可以因现有导出冲突作局部调整，但提交说明必须写出最终接口。

**推荐方法**：

1. 定义受控请求判别联合：不提供、\`mode:"off"\`、\`mode:"auto"\`、\`mode:"observations",after:<正整数>\`。不能接受 \`window/metric/reserved\`，不能将它们偷偷近似转换成 V1；\`off\` 携带 after/其它覆盖参数须拒绝。仅 \`auto\` 可不指定次数，次数必须来自批准模板。
2. 定义静态可序列化的 Host 模板，具有 ID、版本、精确 Profile 集合/验收身份、executor/checker 及版本条件、声明资源槽和 Host 能力要求；完整 V1 origin/replace/preserve/dependencies、阶段额度、容量等必须由已批准的模板或受信环境算出，不能接受模型自报或文件名模糊匹配。实现**唯一匹配**：0 个→对 auto 明确“未启用”原因、对显式 observations 抛配置错误；多个→auto 给歧义原因、显式请求拒绝；模板坏/身份漂移→抛出，不能吞掉当作“不支持”。
3. \`support\` 应是入口从既有执行配置构造的只读描述，含 checker/执行器、真正的预算与任务资源布局；解析器不自行读路径、不 import driver、不调用模型。把模板 ID/version/内容摘要、适配理由、展开 V1、未启用原因返回给入口（尚不持久化）。
4. 先校验分配与共享上限，例如 \`after\` 不可为 0，至少有 V1 \`allowance.minimumRounds\` 的剩余全局轮数，明确 calls/tokens 不得大于任务总预算；再用 \`validatePlan\` + \`explorationPolicy\` 验证完整 Plan。最终执行能力由现有 \`requireExplorationHost/preflightExploration\` 核实；不能用模板里的布尔标记替代真预检。
5. **第一批只提供一个经过验证的受限 report 模板**；允许测试把静态已批准模板经依赖注入传进纯解析器；不为了“大统一”马上发布 OfficeQA、联网研究、任意 Shell 软件和 Consolidation 的生产默认模板。不能修改验收通过条件、selection、权限或原全局 stop。

**禁止改动**：\`exploration/decision.ts\`、\`lifecycle.ts\`、\`request-budget.ts\`、\`long-task-campaign/runner.ts\`，不新增“停滞判断 AI”。

**本卡测试**（\`resolve.test.ts\`）：off 和未提供无 exploration；单模板 auto 展开有效 V1；显式 observations=3 严格显示“3 个正常关闭观察”；零模板、多模板、无效模板、预算冲突、V2 请求均有正确结果；\`validatePlan\` 接受合法输出；完整基础 Plan 除可选 exploration 外 canonical 不变。第一卡仅证明解析逻辑，不声称真实 Campaign 已接通。

### 卡 B：现有三轨 Intake 接线、冻结及恢复 —— 最多动两处核心文件

**目标文件**：\`task-adaptation/prepare-task-run.ts\`、\`task-adaptation/intake.ts\`；仅编译职责确实无法在包装函数复用时才局部修改 \`catalogue.ts\`。

**目标函数**：\`prepareTaskRun\`、\`prepareTaskAuto\`、\`prepareTaskManual\` 及二者的恢复校验分支。

**当前行为**：\`prepareTaskRun\` 有 Host 执行配置但不接受 explorationRequest；\`prepareTaskAuto/Manual\` 只保存基础 \`compileTask\` / \`approvePresetPlan\` 结果。auto 遇到 compileTask 错误可让模型改 Decision；冻结依赖输入和源码身份。

**期望行为 / 接法**：

1. 在 \`TaskRunPreparation\` 顶层增加**可选** \`explorationRequest\`，类型使用卡 A 的受控联合；用 \`prepareTaskRun\` 的现成 \`input.execution\`、Catalogue 及已有预检结果构造只读 \`support\`，作为 Host 注入项传给 \`prepareTask\`。不要把 Host 权限/模板写进模型可编辑的 \`Decision\`，也不新增启动脚本。
2. auto 继续让模型只选择原来的 Decision。**Decision 基础编译成功后，在模型纠错 catch 范围之外**解析探索。模板歧义/越权/Host 不支持/预算不足都视为配置结果，不重发 Intake 模型请求。编译后的最终 Plan 才写入 \`task-plan.json\`、result 与 completed receipt。
3. manual_decision 使用同一解析函数，不产生 Intake 模型请求。manual_plan 已有批准 Plan 时不允许附加任何主动探索请求；纯 off 可与无探索 Plan 等价，但 off 与已批准的含探索 Plan 冲突必须拒绝。不要在 \`approvedPlans\` 指纹校验之后插入 exploration。
4. 只有**主动成功解析**时，在同一个 Intake 目录写 \`exploration-resolution.json\`，记录请求、匹配模板完整冻结定义及版本、support 指纹、最终 Plan 指纹和结果身份；同时将新请求、support/模板身份纳入 Intake 启动绑定。原 \`intake.completed.json\` 必须绑定新解析证据指纹。无请求/off 时**不写新 resolution、不添加 Plan 默认探索字段**，不能制造假的模型回执。
5. 恢复时不能简单重跑 \`compileTask\` 得到无探索 Plan。读取**已保存的冻结模板**与解析证据进行身份复核，复用既有 \`intake.result.json / task-plan.json\`，不再调用模型、不按后来新增的模板重选。源码变更本就受 Intake 指纹约束：不承诺跨代码版本原目录升级；已启动旧任务须使用其原冻结代码和状态。
6. 若模板解析已成功但随后真实 \`prepareExecution\` 预检失败，应保留确切错误，**不能在 Plan 已冻结后自动剥离探索再重跑**。显式 observations 若条件不符应在新的 claim/后端请求前尽早拒绝；对必须等 Profile 确定才知道的条件，在 Plan 完成前校验。
7. 运行前输出简明、程序生成的摘要：enabled/disabled、template ID、V1、\`observations\` 单位、备用最少轮数、共享预算与重建范围/未启用原因。不得把 3 次观察描述成“第 3 轮必换”。

**禁止改动**：原 auto/manual_decision/manual_plan 模型权限和验收语义、现有生成文件结构中的旧字段含义、共享请求账本、历史 claim。任何不可避免的额外源文件/接口修改，先在报告中说明理由；超出 2～4 相关模块时停止，不要连锁重构。

**本卡测试**：\`intake-three-track.test.ts\` 增补：manual_decision 生成 V1；auto 一次 Decision + 一次解析且解析错误**不再调用模型纠错**；manual_plan 完整批准策略不变、冲突拒绝；重复准备使用冻结记录零新调用；模板列表新增/更换时同一固定源码和冻结结果不改变已完成任务身份；无探索 Plan canonical 与原基线一致。已启动 run 的旧源码漂移明确拒绝，不删 claim。
