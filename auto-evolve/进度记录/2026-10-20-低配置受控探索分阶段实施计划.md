## 0. 给用户的目标说明

我们要让 AEV 在同一个任务内，不必永远沿着上一份候选小修小补：原路线尝试到规定程度后，可以从已批准起点重建候选，有限尝试一次备用路线。最终仍按原来的正式验收和选择规则交付，不拿探索中的退步版本覆盖历史合格成果。

日常仍只提供目标、材料、验收标准和总预算；想探索时加一句“允许探索”，或“原路线先做五轮”。复杂的文件范围、起点、阶段额度和能力条件由一种任务形态的受信模板负责，不要求每个案例再填一遍。

**统一的是调度与证据接口，不是把全部任务变成 50 题合并。** Skill、报告、受限程序及合并任务继续使用自己的完整验收协议。轮数不是质量分数，换路线不代表已证明陷入局部最优，更不保证真实收益。

### 改动在整体流程中的位置

```text
目标、材料、完整验收、总预算 + 可选简化探索请求
  -> 原任务解释及基础 Plan 编译
  -> [新增：匹配受信模板、预检、展开并冻结探索策略]
  -> 原准备与同一个 Campaign
       -> 原规划、执行、分析、Lead 修订、审阅及正式验收
       -> [升级：共同轮末读取真实证据，决定继续/另试/停止]
            -> 继续：原路线下一轮
            -> 另试：原有受控激活与视图重建 -> 同一 Campaign 下一轮
       -> 原请求预算准入 [第三阶段才增加未来备用额度保护]
  -> 原正式合格版本选择、harvest、冻结交付
```

不是把训练侧改成单次答题，也不是替换正式 Checker，更不是让 Planner 自行修改探索权限。

## 4. 用户输入契约：简单入口与完整策略分开

以下为**拟实施契约，当前代码不能直接接受**。普通用户只需理解关闭、自动、指定轮次三种用法；其余属于高级设置或过渡接口。

### 4.1 简化请求

在现有 `TaskRunPreparation` 顶层增加可选 `explorationRequest`；不塞进模型 Decision，也不把字符串填到 `Plan.exploration`。

| 请求 | 字段及含义 | 何时可用 |
| --- | --- | --- |
| 不提供，或 `mode: off` | 不向基础 Plan 新增探索字段 | 第一阶段 |
| `mode: auto` | 采用唯一匹配、已批准模板的默认策略 | 第一阶段先展开 V1；第二阶段由已发布模板显式选择 V2，不回写旧 run |
| `mode: observations, after: n` | 原路线正常闭合 n 次质量观察后考虑备用 | 第一阶段，明确是过渡/高级接口，不叫“全局第 n 轮” |
| `mode: window, afterRound: k` | 原路线第 k 轮正常结束，未完成时尝试备用；展开 `f=h=k` | 第二阶段 |
| `mode: metric` | 可选覆盖 `minimumRounds`、`maximumRounds`、`patience`，其余从已批准评分模板取得 | 第二阶段，仅可信指标支持的任务 |

主动请求允许可选 `template`，只选择 Host 已发布的模板 ID；不接受任意脚本路径。第二阶段主动请求还可选择 `budgetMode: best_effort`；`reserved` 直到第三阶段完成才开放。普通用户不必填写预算模式，模板明确采用 best_effort。

第一阶段遇到 window/metric/reserved 请求直接报“不支持该请求版本”，不能转换成近似 V1 后继续。请求与完整 Plan 同时提供时按第 6 节处理。off 不允许夹带 afterRound、预算预留等字段。

用户不能通过简化请求覆盖：验收标准、模型/材料、重建资源范围、合法起点、权限、总预算、正式选择规则、存档容量或指标单位。额度与轮数超出模板授权范围则拒绝，不偷偷截小。

### 4.2 运行前摘要

冻结前/准备结果中输出一份程序生成的简明摘要：是否启用及原因、选中模板、策略版本、触发单位、原路线窗口、备用最少/最多轮数、预算模式、总额、合法起点及可重建范围。

例如“正常观察 5 次”与“原路线第 5 轮结束”必须使用不同文字。没有合适模板时明确写“探索未启用，原任务流程保留”，不能只输出 ready 让用户以为已开启。

## 5. 受信模板：少量静态定义，不做管理平台

### 5.1 位置与职责

拟新增 `task-adaptation/exploration/templates.ts`，保存少量 Host 维护的静态、可序列化模板定义；新增 `resolve.ts` 负责严格校验、唯一匹配和展开。模板不是 Agent 写的，也不由运行时联网获取；测试可通过显式依赖注入替换受信列表。

模板最少包含：

| 字段组 | 内容 |
| --- | --- |
| 身份 | 模板 schema、ID、version；发布内容 canonical hash 由程序计算 |
| 匹配条件 | 精确 Profile 集合及内容身份、执行器/Checker 类型与版本、资源角色布局、允许动作、模型预算绑定形态 |
| 重建配置 | initial 或已明确指定的合法历史起点、replace/preserve/dependencies 的资源 ID 映射 |
| 轮次配置 | 允许生成的策略版本、默认分配及可覆盖范围；不是“全任务默认两轮” |
| 阶段与容量 | author/acceptance/delivery 的 calls/tokens 上限、候选/依赖/档案容量 |
| 评分支持 | 如有：可信来源、metric 名称/方向/单位/精度、minimumDelta 和可比较条件 |
| Host 条件 | 已接通重建、受限视图、选定交付及预算约束；不能用模板自报替代真实预检 |

匹配依据是任务形态，不是每道题的材料 hash；否则模板无法复用。具体源文件、案例、模型参数及协议指纹在展开/绑定时加入本次身份。模板可以通过 Host 已声明的资源槽映射 ID，禁止按文件名相似度或 LLM 猜测映射。

### 5.2 匹配结果必须确定

| 情况 | auto | 显式指定 template/window/metric/observations |
| --- | --- | --- |
| 恰好一个合适模板且能力支持 | 展开并记录依据 | 展开并记录依据 |
| 零个模板或已确认的探索能力不支持 | 记录未启用原因，保留原来可运行任务 | 启动前拒绝 |
| 多模板同时匹配 | 记录歧义，不自行按顺序挑一个 | 要求明确已有模板 ID，否则拒绝 |
| 模板本身无效、指纹漂移、文件/权限/账本故障 | 阻断，不能当普通“不支持”降级 | 阻断 |
| 正式验收缺能力 | 依原任务机制阻断 | 阻断 |

不添加优先级引擎、LLM 模板裁决、插件市场、动态模板合并或用户逐题审批表。第一批先接已有受限文件报告形态，再复用受信 JS 软件及 Consolidation 夹具核验共用性；哪些真实 Profile 发布模板，按已核验支持清单登记。历史 OfficeQA/NBA/联网研究不自动列为支持。

本计划不替项目批准一个新的生产默认轮数或阶段额度。已有明确获批的完整配置可抽成模板；没有获批分配时，auto 记为未启用，不能把测试夹具的两轮、巨大预算或本文的 5+2 算术例子发布为生产默认值。新任务形态首次发布只需一次确认，后续案例复用；这与逐题增加材料不同。

### 5.3 解析纯函数和 Host 检查分层

纯解析器拟定义为 `resolveExploration(basePlan, request, templates, support)`：不读取全局配置、不写文件、不调用模型；输出启用策略或明确未启用原因。

`support` 由实际准备入口显式提供，含执行配置、预算及资源映射的受信描述；不能要求现有 `compileTask(catalogue, decision)` 凭空寻找这些信息。涉及真实文件、后端和预算的检查使用现有预检能力。

实现可用小型共同编译包装函数连接“基础 Plan -> 纯解析 -> 只读能力预检 -> 最终 Plan”。已知条件在 Intake 前检查；选定 Profile 后才能确定的条件，在 Intake 结果保存前检查。auto 的不启用回退只允许发生在此冻结之前；准备完成后发现漂移必须阻断，不能删掉冻结策略。

对预检结果使用有类型的 supported/unsupported；磁盘错误、内容漂移等继续抛出。禁止 catch 全部异常或解析错误字符串后假装不支持。

## 6. 三种 Intake、冻结和恢复契约

### 6.1 接线位置

| 入口 | 新行为 |
| --- | --- |
| auto | 原模型只产生原有 Decision；基础编译成功后，在模型纠错 catch 范围之外解析探索，完成后才写 result/plan/completed |
| manual_decision | 基础编译后调用同一解析/预检流程；不新增 Intake 模型调用 |
| manual_plan | 原完整 Plan 原样走 approvedPlans 校验；不在批准后追加探索。主动简化设置拒绝，先生成新的完整 Plan 再按原机制批准 |
| 直接完整 Plan/旧调用入口 | 保留高级用法及现有能力门禁；不强迫使用简化请求 |

manual_plan 未提供新请求时，可继续使用原已批准探索策略。off 与已批准的探索 Plan 冲突时拒绝，不能静默删除其策略。无探索 Plan 加 off 与未设置等价。

**错误分流红线：** 无效模型 Decision 才能进入已有有限纠错；模板歧义、预算不足、unsupported Host、新请求参数错属于平台配置结果，不反馈给模型要求重新解释任务，不增加付费请求。

### 6.2 冻结证据

主动解析时在原 Intake 目录新增 `exploration-resolution.json`，schema 拟为 `aev.exploration-resolution.v1`，绑定以下内容：简化请求、选中模板完整数据/ID/version/hash、支持环境描述指纹、解析器实现身份、展开策略、采用/未采用原因、计数语义与预算模式、最终 Plan 指纹。原完成回执绑定该证据指纹。

不设置新请求或纯 off 时不补探索字段、不生成虚假的解析记录。新证据不包含 API Key、私有答案正文或无关运行文件。新解析模块加入实际实现身份依赖。

同一新版代码、相同冻结输入恢复时：核对原请求及解析证据，使用冻结模板而非当前注册列表，再按同一解析器核验结果；不重发已完成 Intake。新模板发布不改变已冻结 run。完成记录缺失或调用未结算时沿原人工核查/显式恢复规则处理，不用“重新解析”掩盖半完成请求。

### 6.3 三种不同兼容性

| 兼容类型 | 承诺 |
| --- | --- |
| 新代码上未配置探索的新任务 | 基础 Plan canonical/指纹等价，验收、角色和正式选择流程不变；除必要主机证据外不引入探索工作 |
| 新代码读取 V1 策略 | 保留 V1 字段、原指纹算法和决策语义；不补 V2 默认值 |
| 升级前已启动的旧 run | **不承诺跨源码版本直接恢复**；Intake/准备/宿主等绑定源码，保留匹配版本在原目录续跑 |

旧 run 不删除 claim、不换 out、不清消费、不跳过源码漂移校验。新功能用于经批准的新运行；复用旧合格产物时按来源清单/指纹输入新任务，不能伪称原 run 的无缝续传。

开发前保存基线 commit 和已有活动任务的代码/依赖/配置定位；不要在活动任务正在使用的工作树原地更新。没有活动任务也保留 Git 基线可检出，回退源码不回退或覆盖运行账本。

## 7. V2 完整策略契约

保留外层 `aev.task-plan.v1` 的可选 exploration，内部按 schema 区分 V1/V2。拟定义 `ExplorationPolicy = V1 | V2`；V1 校验和决定维持原值。公共配置通过只读访问器取得，不将 V1 转成 V2 后重新计算身份。

V2 采用下列**固定字段组**，不是允许实现 Agent 临时补接口的示意：

| 字段 | 契约 |
| --- | --- |
| `schema` | `aev.exploration-policy.v2` |
| `origin/replace/preserve/dependencies` | 沿用 V1 的起点和资源约束 |
| `window` | `minimumRounds=f, maximumRounds=h`，原路线最少/最多已关闭轮数 |
| `trigger` | `{kind: window}`；或 `{kind: metric, name, direction, minimumDelta, minimumObservations, patience}` |
| `allowance` | 沿用 V1 字段：rounds=b、minimumRounds=m 表示备用最大/最少准入窗口；其余为每轮阶段 calls/tokens 与唯一最终交付上限 |
| `budget` | `{mode: best_effort}`；第三阶段后才接受 `{mode: reserved}` |
| `bounds/safety` | 沿用 V1 容量及 declared_entries/sandbox_only 约束 |

任何未知字段拒绝。窗口模式不允许夹带 metric 字段。阶段上限不能被自然语言请求扩大。当前 Host 仍只允许本地导出，deliveryCalls/deliveryTokens 保持 0；公式保留 D 只是为了不与已有抽象冲突，不借此新增远程交付后端。

### 7.1 轮数与边界

有效全局上限 `N=min(Plan.stop.rounds, 实际Campaign.maxRounds)`。

`1 <= f <= h`、`1 <= m <= b`、`h+m <= N`、`b <= N-f`，均为有限安全整数。实际备用最多 `min(b, N-切换时全局已用轮数)`。超出直接拒绝，不截断参数来假装满足。

固定第 k 轮后另试：`f=h=k`。原路线起点为第 1 轮，因此这里也对应其第 k 轮；备用局部轮数从激活投影的 nextRound 起算。中断恢复同一轮不再计数。pass、attempt、API 调用与 round 分开。

故障可能占用全局资源，却不产生正常质量证据；不能仅因时钟或轮号到达窗口就把故障变成换路许可。故障修复后应关闭原有这一轮，而非跳过未结算证据开启新一轮。

保留原路线 7 轮再给备用 2 轮，N 至少 9；总额 7 时 5+2 或 4+3 都是明确预算取舍，不是经验上已证明最优的默认值。模板没有获批的分配时，不自行猜一半或默认两轮。

### 7.2 评分停滞

只在原 best_pass 实际执行产物已提供可信指标时启用；正式选择资格和排序不变。比较身份包括协议、评分器、用例/材料、模型推理条件；候选自身是变量，不能放进“必须完全相同”的比较身份。

每条有效新测量按以下确定性规则处理：

1. 第一条建立进展锚点，不计停滞。
2. 相对锚点按 direction 计算 gain；`gain>0 且 gain>=minimumDelta` 更新锚点并清零耐心，其余有效评分耐心加 1。
3. 需要达到 minimumObservations 的连续合法评分数量及 patience，并且原路线至少 f 轮，才能评分触发。
4. 正常拒绝且协议合法无分：清除本路线评分锚点、连续评分数和耐心，下一合法评分重新建立。历史正式最好版本不清。
5. 同一实际验收回执复用不增加测量、耐心或观察；保留必要闭轮记录，不凭正文 hash 重复判质量停滞。
6. 宣称必有评分却缺失、比较身份漂移、非有限数或判分故障：暂停，不填 0、不换路。
7. 只要走到 h 且本轮正常闭合，按窗口边界另试；原因写 window_exhausted，不伪称评分停滞。

正文不同不等于进步，正文相同也不独立证明停滞。允许已有协议规定的新测量，但不为探索额外调用评分器或额外重复考试。minimumDelta 的单位/精度/噪声依据由模板声明；未核验的指标不自动启用此模式。无分任务用窗口，不增加用户材料。

备用路线按自己的有限窗口运行，不因低于原路线历史最好而提前砍掉；不加入第二次备用或新的备用评分耐心机制。

## 8. 共同决策、保存与恢复

### 8.1 决策顺序

```text
用户停止、安全/数据/平台故障、未结算或超额请求
  -> 按相应停止/暂停路径，保留合格档案；不激活
first_pass 且本轮正式合格
  -> 正常交付，即使还没达到路线最少轮数
best_pass 且本轮正式合格
  -> 更新合格档案，不在此执行旧 stagnant；继续本轮调度判定
全局硬上限已到
  -> 结束，只交付已有合格版本
备用已达到自身最大窗口
  -> 结束，不再开分支
原路线未到 f 或本轮无正常闭合证据
  -> 正常继续或故障阻断
到 h / 可信评分触发 / 第三阶段冻结的预算边界触发
  -> 核验起点、容量、轮次、真实余额与屏障
  -> 满足则一次 activate，否则明确 finish/hold
否则
  -> 可准入下一正常周期则 continue，否则按预算不足结束
```

决定依据与实际 admit 检查采用一致的阶段上界，不以平均 token 推断能跑。备用资源不够时不偷扩预算、不换父候选、不让模型追加授权，也不默默把窗口改大。first_pass 成功、全局停止、无结构化信号等原保护优先。

探索开启时由共同决定覆盖旧质量软停止；正式选择器仍保留原合格判断和排序。探索关闭时旧 stagnant 行为保留。fresh/resume、正常/预算/异常收尾、harvest 和终态导出须核对同一决定，不能在某个出口又按 V1 重算 V2 停止。

### 8.2 V2 持久化

策略不同语义使用 `aev.exploration-campaign.v2` 的 Host 记录，不把新轮数混进 V1 observations。保存正常闭合 round 身份、branch/generation、路线起始轮、实际回执和可比身份、候选档案 ID、决定及余额证据。计数从这些冻结记录确定性导出，不维护三套可独立漂移的计数器。

同一 round/closure 重复关闭幂等；同轮不同证据拒绝。保存决定前检查真实起点、容量和余额。决定身份绑定策略版本、有效 N、已关闭轮、回执集合、余额快照及相关 gate/账本状态指纹。

已经提交的 continue/activate/finish 不因后续余额或模板变化而改写。激活前只核验原条件仍成立；异常变化阻断并保留决定。恢复未提交的同一关闭意图可以按原证据完成，不伪造新观察；缺证据先核查，不补发请求。

档案/合成/激活等结构没有变化时继续用现有版本，不为数字好看把所有记录升级。需要加预算转换引用的 Host 投影单独分版，V1 解析不容忍未知字段。

## 9. 两种预算模式与第三阶段的严格预留

### 9.1 best_effort：前两阶段交付边界

沿用 V1 的阶段上限与本轮验收/交付保护，触发时检查备用完整最低周期是否可准入。它不保护未来余额，不保证走到窗口时还留有备用资源。

因此摘要必须写“备用按届时余额准入”。用户明确要求 reserved 时，在第三阶段之前拒绝，不能自动降级。第一阶段 V1 同样只提供这项能力；不用 UI 承诺尚未实现的资源保护。

### 9.2 reserved：保护什么

对 calls 和 tokens 分别计算。设每轮作者上限 A、验收上限 C、唯一最终交付剩余保护 D、备用最少 m 轮，未来备用保护 `F=m*(A+C)`。F 不含 D，避免重复保护交付。

| 当前阶段 | 要阻止被花掉的额度 |
| --- | --- |
| 原路线作者 | 本轮尚未消耗的验收额度 + F + D |
| 原路线验收 | F + D；同轮多 pass 按已消费部分扣减，不重新发一份额度 |
| 备用作者 | 本轮尚未消耗的验收额度 + D；F 的边界已转换为备用正常花费资格 |
| 备用验收 | D |
| 终态 | 未用 F 可解除，保留完成交付所需 D |

保护是同一钱包可花余额的边界，不增加总额、不新增假请求、不算第二次消费或退款。最低轮数是准入资源条件，不保证外部 API 成功、模型必然产出合格候选或故障后仍跑满。

预检包含已结算 Intake 与明确固定开销、逐请求输入/输出预留、实际角色和同轮多 pass。验收上界必须覆盖冻结执行器案例数、Reviewer、收费 Checker 等规定请求，不能只按一轮一个请求估算。最终至少覆盖原路线 f 轮和备用 m 轮的声明周期额度及 D；阶段额度本身也须符合现有有限运行条件。

### 9.3 最小钱包升级，不平行造账本

仅 reserved 新运行启用受保护钱包状态版本，例如 `aev.request-budget.v2`；普通/V1/best_effort 保留现有钱包格式及行为。原代码必须因不识别 V2 而拒绝，不能让旧写入器忽略保护字段后继续消费。

新版状态继续保存原 attempts/gates/Intake 前缀，新增一条绑定冻结 Plan/协议/策略/Campaign 的保护记录，包含向量 F、状态 held/activated/closed 及稳定转换 ID。所有 reserve、stage-open、settle、inspect 共用原锁内事务并验证它。

auto 的 Intake 可能已经产生 V1 消费：只允许**事先声明 reserved 的新运行**在首次作者 gate 安装时，在同一钱包锁内保留已结算 Intake 前缀并升级状态/建立 held。不是给旧生产 run 自动迁移。存在其他角色、未知消费、额外 gate、绑定冲突则拒绝。

固定的钱包 V2 附加契约如下；不允许后续 Agent 分散设计不同的释放字段：

| 位置 | 固定内容 |
| --- | --- |
| 钱包外层 | schema 改为 `aev.request-budget.v2`，保留 binding、attempts、gates、intakePrefix、lastDenial 原语义 |
| `explorationHold` | schema=`aev.exploration-budget-hold.v1`、原 ArchiveScope、`amount:{calls,tokens}`、status、initialization、可选 transition |
| `initialization` | 稳定 init ID、初始化意图 hash、原已结算 Intake 前缀身份、首 author gate ID |
| `transition` | 稳定转换 ID、kind=activate/close、原 held 身份、前驱 gate ID、决定 hash、投影 hash（activate 必须）、目标完整 gate 与转换意图 hash |

初始化 ID 由 schema、scope、F、Intake 前缀身份和首 gate 完整策略确定性生成。只用既有钱包锁，保存一个 `budget.json.protection.intent.json`，内容固定原 V1 钱包指纹、init ID、前缀及目标初始化数据；它不是消费账本。

初始化依次为“保存意图 -> 写既有 `budget.json.stages.claim` 的 V2 绑定标记 -> 原子写 V2 钱包及首 gate”。V2 标记是 schema、原 binding、scope、init ID 与前缀的稳定指纹，不随请求消费变化。先写标记的原因是让中断后的 V1 钱包也无法被旧写入器按无保护模式消费；旧阶段标记期望不同，必须拒绝。

标记已写但钱包仍 V1 时，只能显式完成同一初始化，先核验意图及原钱包完全未变，不允许普通请求。钱包已是完整 V2 时按初始化身份和后续合法账本核验，不再要求钱包等于初始化时的零作者消费快照。标记、保护记录或意图缺失/冲突时阻断，不能回退为 V1 或重新从零初始化。无请求的初始化故障也保留证据；旧未保护钱包的标记算法不变。

### 9.4 激活及崩溃恢复顺序

磁盘激活与钱包不是一个原子文件，不能声称二者同时提交。复用现有关闭/激活意图、整轮租约及原子写机制，固定以下顺序：

1. 原路线整轮正常关闭、全部角色收束；核验 wallet 无在途/unknown/overrun，冻结预算快照和稳定转换 ID。
2. 保存共同决定、既有关闭/激活意图及稳定转换 ID；此时尚不保存要求投影 hash 的完整钱包转换意图。恢复复用同一 ID，不重新申请另一份保护。
3. 在现有激活事务下准备并物化选定起点/视图，构造确定性的 V2 投影数据及 hash；先保存含该 hash 的完整钱包转换意图，再提交引用共同决定和转换 ID 的磁盘投影。此时仍不允许新代次请求。
4. 在原钱包锁内核对原 held、决定/投影及预算状态，**同事务**将保护改为 activated，并安装 generation=1 的首个 author gate；消费总数不动，旧 gate 立即失效。
5. 只有磁盘投影和钱包 gate 两者均一致时，才启动备用角色请求。

转换 ID 固定由 schema、scope、kind、原正常关闭身份、前驱 gate ID 和目标 generation 生成，**不依赖还没生成的投影 hash**；决定与投影都引用此 ID，避免相互计算 hash 的循环。钱包转换意图另存为 `budget.json.transition.<ID>.intent.json`，在转换前绑定：原 held hash、转换前钱包指纹、决定 hash、已准备投影 hash、目标 gate 完整 Admission 及其 ID。它是同一转换的恢复证据，不新增消费。

未转换时核对原钱包及前驱 gate 后执行；已转换时按钱包中的 transition 回执、意图及目标 gate 核验，不能继续要求整个钱包等于转换前快照。后续备用请求已合法消费时，只复核转换凭证及 gate 血统，不撤销它们。相同转换重入返回同一结果，冲突 ID/目标 gate/决定拒绝。正常 close 同理，安装原代次的 delivery gate 并关闭未用保护；本地导出仍为零请求，旧作者 gate 不得继续发送。

崩溃在 2/3/4 之间时按已保存意图补齐缺失部分；已转换就只复核，不二次释放，不把已有备用正文还原成起点。若必要余额、起点或身份不一致，hold；不能删除意图后重开。

first_pass 提前成功或其他正常结束，在同一预算/阶段事务中关闭未用保护，仍保留 D。安全/未知计费故障先封存，不能以“释放额度”恢复发送。状态 V2 的记录读写、claim 与阶段身份更新须全部接入，不能只在 reserve 函数里加一个减法。

### 9.5 预算边界触发

只对已冻结 reserved 模式开放：共同轮末若已经满足原路线 f，下一完整原路线周期将无法与 F+D 并存，但当前 F+D 仍足够，则在本轮产生 `budget_boundary` 决定。

这是资源调度原因，不叫质量停滞；不等到下一轮打开 gate 失败后再覆盖上一轮 continue。余额/账本状态参与决定身份，恢复不拿新余额静默改写旧决定。

## 10. 分阶段实施任务与停止点

### 阶段 0：批准前固定契约和保护旧任务

本阶段就是当前计划工作，不修改业务代码。记录 baseline、文档、支持范围和未批准项。实施指令到来后才创建开发分支，保留当前集成候选；先核对活动任务是否使用该工作树，有则另建代码工作树，不能为了开发中止/改写旧任务。

阶段 0 完成条件：用户可明确选择只做第一阶段，或批准按阶段推进；没有默许真实实验、推 main 或部署。

### 阶段 1：低配置入口，生成完整 V1

| 工作 | 具体产物 |
| --- | --- |
| S1-1 | 静态模板定义、严格请求校验、纯匹配/展开解析器 |
| S1-2 | prepareTaskRun 显式传入 Host 支持描述；auto/manual_decision 保存前共用解析；manual_plan 冲突检查 |
| S1-3 | resolution 冻结/恢复、友好摘要和平台错误分流 |
| S1-4 | 无新请求旧 Plan 等价、三入口、模板唯一性、V1 决策及实际离线入口回归 |

此时只开放 off/auto/observations，展开现有 V1；不做 V2、不碰未来预算保护，不谎称支持 afterRound。第一阶段有独立可用价值，但**不能因此登记“自由轮次和预算保护已完成”**。

验收后形成单独 commit 和范围说明；第二阶段未经批准不能顺带开发。可以评估易用性，不必先启动大规模真实效果实验。

### 阶段 2：V2 窗口与可选评分，best_effort

| 工作 | 具体产物 |
| --- | --- |
| S2-1 | V1/V2 判别联合、资源/阶段公共访问器、严格 V2 schema 和 N/f/h/m/b 预检 |
| S2-2 | 新的 V2 纯决定函数；轮/观察/评分计数及缺分规则；仍保留原 V1 decide 路径 |
| S2-3 | V2 关闭记录和决定身份、lifecycle 版本分派；fresh/resume/harvest/终态共用 |
| S2-4 | 模板明确发布 V2 配置；开放 window/metric，reserved 仍拒绝 |
| S2-5 | 三种既有任务形态离线闭环及旧路径回归；不新增外部模型请求 |

逐项检查政策读取者：plan、ownership、origin、composition、activation、generation、entry、preflight、stages、evaluation、lifecycle；不能只改 policy/decision 两个文件就结束。共享资源层尽量不分叉，每个版本仅保留自己的算法/证据解释。

完成条件：用户能自由设置被授权的轮次，按真实正常闭轮切换；第六轮才成功的合成序列，在未提前分配备用窗口时仍能正常成功；指定更早窗口则按明确取舍另试，而非错误宣称停滞。first_pass 和 best_pass 的最终交付不变，预算不足明确终止，严格预留尚未开放。

### 阶段 3：独立增加 reserved

| 工作 | 具体产物 |

## 12. Git、回退和交付纪律

1. 先保留当前集成基线及匹配旧任务的代码定位；检查工作区无冲突。按批准阶段从实际基线建立开发分支，不覆盖原集成候选。
2. 每个阶段至少有 schema/解析、实际接线、测试与文档等清晰检查点，提交说明写明真实 API 未执行及尚未开放项。不能将计划写入误称功能完成。
3. 修改前/后看 diff，运行必要回归，独立只读复核最终改动。不得顺带处理全仓历史类型问题或改底层模型接口。
4. 回退使用原 Git 版本或独立工作树，旧 run 保留原代码在原路径继续；V2 run 用匹配版本恢复，不把其账本交给旧实现消费。
5. 更新系统架构树和任务适配 README，分别标记已接线、离线验证、真实验证、部署状态。实验/论文分数仅在实际产生后按各自树规则登记。
6. 仅提交核心源码、配置、提示、轻量 fixture 和文档；不提交 runtime、模型回复、私有材料、密钥或测试生成目录。
7. 本计划不授权 push/main 合并、跨仓自动同步或生产替换。届时核对任务适配仓与正式主链各自规则及用户批准，不能用历史主链默认值绕过当前集成候选的审批。
