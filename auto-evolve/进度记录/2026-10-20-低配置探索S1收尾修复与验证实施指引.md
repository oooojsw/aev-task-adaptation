## 4. B1：三个小任务卡（每张卡通过对应测试再做下一张）

### 任务卡 A：受信模板来源 + 确定性精确匹配

**目标文件**：`auto-evolve/orchestrator/task-adaptation/exploration/templates.ts`、`resolve.ts`、`task-adaptation/prepare-task-run.ts`；相应 `resolve.test.ts`。

**目标接口**：`TaskRunPreparation.explorationRequest`，`resolveExploration(basePlan,request,templates,support)`。

**当前行为**：启动 JSON 可通过顶层 `explorationTemplates` 注入所谓批准模板；内置 report 模板默认两次观察和测试额度；模板 `profiles` 实际被作为 `deliverable.kind` 使用，比较规则与名字和计划语义不一致；多个匹配 auto 直接 throw。

**期望行为**：
1. 顶层任务 JSON **不得提供** `explorationTemplates` / 任意模板定义。模板仅由 Host 静态已批准表或内部显式依赖提供；`prepareTaskRun` 的普通用户输入若携带模板列表应报明确错误，不允许被静默采用。为离线 E2E 保留**仅通过函数 dependencies 参数**注入 fixture 模板的方式，不新增新公开脚本。
2. 撤掉未批准的内置“report 两次观察 + 巨额调用/Token”默认值；如果仓库当前确实有带身份和审批依据的正式报告模板，可复用那个**实际获批**值并给证据；否则内置发布列表先为空，`auto` 如实返回“无批准模板”，不要造通用默认策略。测试通过 Host 注入 fixture 模板证明代码能力。
3. 解析器的匹配需由受信基础编译输出的**所选 Profile ID 集合**、对应验收检查列表和 Host checker/executor 版本、计划资源槽与可用动作共同约束。不要仅靠 `kind=report` 或 `checkers[0]` 判断支持；缺必需 Host 支持信息视不支持，而不是默认通过。多个模板：auto 给清楚的 disabled/ambiguous 原因；显式请求拒绝，且零模型纠错调用。只有模板结构本身错误或实际配置/账本漂移才抛错误。
4. 对合法策略继续调用原 `explorationPolicy`/ `validatePlan`，并由 `prepareExecution` 执行真实 preflight。预算至少核对全局轮数和当前 V1 备用最低周期上界；不能自行扩大冻结 `stop`。
5. 保持无探索输入生成的基础 Plan canonical 不变。

**不能改动**：模型是否合格的含义、Checker、分支激活次数、请求账本、执行角色权限。

**定向测试**：攻击者通过启动 JSON 冒充模板时拒绝；测试依赖注入模板正常启用；某个报告匹配 Profile A 但 Checker B 不符时 auto disabled；多个匹配 auto disabled、显式拒绝；无批准模板不启用且记录原因；`observations:3` 真正展开成 V1 的 attempts=3；无请求/off 原 Plan 无差异。

### 任务卡 B：冻结证据、模板升级后的恢复和可见状态

**目标文件**：`task-adaptation/intake.ts`、`prepare-task-run.ts`；相应 `intake-three-track.test.ts`。

**目标函数**：`prepareTaskAuto` 与 `prepareTaskManual` 的 fresh / resume 分支。

**当前行为**：manual_decision 的 `finalValue` 在恢复前用当前模板重新解析，即使随后读取旧 `exploration-resolution.json`，仍拿新策略与旧记录比较；auto 和 manual 的 disabled 原因没有形成对用户可读的固定摘要；保存的 resolution 包含 request/template/policy/support 指纹，但恢复检查集中在文件 hash，没有充分确认字段与最终 Plan 一致。

**期望行为**：
1. 新任务开始时，模板解析只在基础编译成功后发生，发生平台配置错误时不进入 auto 模型 Decision 纠错。**完成的旧 Intake** 在相同代码、相同原输入下恢复时，以已保存的冻结模板和 policy 为准，不按当前 Host 模板注册表重新挑选；只核对原请求/冻结 support 的身份、resolution 文件 hash、展开 policy 与保存 Plan 的精确对应，以及原完成回执。恢复不得新发模型请求。
2. 主动 `mode:auto` 但无模板/多模板/确定不支持时，返回并持久化 `enabled:false` 与具体 reason 的解析记录或相等强度的启动摘要；**Plan 不加 exploration 字段**；无探索请求/off 不产生该新记录。已知不支持且不依赖模型选 Profile 的检查尽量发生在付费模型 Intake 之前；模型选完才能知道的匹配条件在冻结前处理。
3. auto/manual_decision 使用同一解析方式；manual_plan 保留批准的完整 Plan，主动探索请求拒绝，off 与含探索的完整 Plan 冲突拒绝；无请求/off 的结果和预算语义不变。
4. 若解释后才发现不能通过原真实 Host 的 preflight，不得在已经写入 Plan/完成回执后静默删除 exploration。对已知能力不足的 auto 应在冻结前给 disabled 原因，真实故障或身份漂移不应伪装 disabled。

**不能改动**：原三轨 Intake 的模型请求回执与人工批准契约、不覆盖历史 `intake.started.claim`、不额外增加模型调用。

**定向测试**：manual_decision 和 auto 第一次使用受信 fixture 模板生成有效 V1；在同一冻结源码和相同输入下改变 Host 注册模板列表，再恢复旧 run，仍复用冻结策略且模型调用数不变；刻意破坏 resolution/policy/Plan 对应关系时拒绝；auto 未启用原因能在产物中找到且 Plan 未添加 exploration；manual_plan 三种冲突情况不改变；无请求旧 Plan canonical 相同。
