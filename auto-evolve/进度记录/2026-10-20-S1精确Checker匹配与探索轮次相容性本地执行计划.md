### A.1 目标文件与函数（最多三个生产文件）

2. `auto-evolve/orchestrator/task-adaptation/exploration/resolve.ts`：`ExplorationSupport`、`resolveExploration` 中模板匹配逻辑。
3. `auto-evolve/orchestrator/task-adaptation/prepare-task-run.ts`：`prepareTaskRun` 内构造 `support` 的地方。

**只动这些业务文件即可完成 A；** `intake.ts` 已能把 `compiled.profiles` 传给 resolver，原则上不需改动。允许配套修改 fixture 和测试，但不能为了支持匹配重写 Intake 三种模式。

### A.2 明确区分三种 ID（最容易犯的错误）

现有代码同时有以下三个不同概念：

- **Profile ID**：由 `compileTask(...)` 的 `value.profiles` 提供，例如 `["report"]` 或 `["reviewed-report"]`，说明采用哪套验收协议；
- **Plan 的 Checker 名称**：`value.plan.acceptance.checks[].id`，例如 `quality`、`review`，说明哪个验收检查；
- **Host 插件绑定 ID**：`execution.checkers[].binding.id`，例如 `script-json-checker`、`http-model-judge`，说明怎样执行某个检查；连接关系在 **`execution.checkers[].name`**。

这三个 ID **不能相互代替**。特别是 `c.mechanism === "script"` 只是 Plan 检查机制类别，**不是**具体宿主 Checker 的身份。今后不允许再使用这种表达式：

```ts
c.id === template.checker.id ||
c.mechanism === template.checker.id ||
c.mechanism === "script"
```

### A.3 推荐的最小数据改法（具体改哪里）

**步骤 1：调整 Host 模板所声明的 Checker 结构。**

当前 `templates.ts`：

```ts
checker: { id: string; version?: string }
```

改为“指定 Plan 检查项名称 + 绑定插件 ID”的明确声明：

```ts
checker: { name: string; id: string; version?: string }
```

其中 `name` 必须精确对应 `Plan.acceptance.checks[].id` 与 `execution.checkers[].name`；`id` 必须精确对应 `execution.checkers[].binding.id`。如果现有模板声明没有 name，不要根据产物种类自动猜一个：**Host 测试 fixture 直接补充 name**。例如已有报告 E2E 使用 `name:"quality"` 与 `binding.id:"script-json-checker"`，对应模板应为：

```ts
checker: { name: "quality", id: "script-json-checker" }
```

`intake-three-track.test.ts` 使用检查项 `review` 的 fixture，可以写 `checker: { name:"review", id:"review" }`（其 support 需对应）。**不要在没有正式批准的情况下增加生产默认模板**：`BUILTIN_EXPLORATION_TEMPLATES` 继续保持空数组。

**步骤 2：把单 Checker support 换成带名称的完整集合。**

当前 `resolve.ts::ExplorationSupport`：

```ts
checker?: { id: string; version?: string }
```

改为：

```ts
checkers?: ReadonlyArray<{
  name: string
  id: string
  version?: string
}>
```

`prepare-task-run.ts::prepareTaskRun` 不再取 `input.execution.checkers[0]?.binding`，而是按现成配置映射：

```ts
checkers: input.execution.checkers.map((item) => ({
  name: item.name,
  id: item.binding.id,
  version: item.binding.version,
}))
```

可根据 TypeScript 对可选字段的约束，在 version 缺失时省略该字段；重要的是三个字段来源必须正确。现有 `executor`、`capabilities`、`budget` 字段原样保留。**不得为了新数组修改真实 Checker 的执行顺序或增加请求。**

**步骤 3：在 `resolveExploration` 中采用确定性、可复核的匹配。**

将 `const selectedProfiles = profiles && profiles.length > 0 ? profiles : [basePlan.deliverable.kind]` 替换为以下语义：
- 对 `undefined/off` 请求仍直接返回 disabled，不要求 Profile。
- 对主动 `auto` 或 `observations`，`profiles` 为空/缺失时视为**缺少可信所选 Profile**：auto 返回 disabled 和原因，显式 observations 拒绝；不再把 `kind=report` 猜成 Profile ID。
- `template.profiles` 与已选 Profile **集合相同**时才匹配：忽略顺序，不允许模板 `["report"]` 偶然匹配实际 `["report","recompute"]`。若未来需要多 Profile 组合，由 Host 显式声明那个组合；本轮不做复杂模板继承。
- `template.checker.name` 必须恰好出现在 `basePlan.acceptance.checks[].id` 中；`support.checkers` 必须存在唯一一个 `name` 相等的 Host 绑定；其 `id` 必须等于 `template.checker.id`。
- `template.checker.version` 如果指定，则对应 Host 绑定的 `version` 必须存在**且完全相同**，不能“Host 缺 version 也算通过”；`executor.version` 同理。
- 对 **Plan 所有 required=true 的检查项**，都必须在 `support.checkers` 有唯一同名的 Host 绑定；不能“第一个 Checker 匹配就忽略其他必需 Checker”。**不要求**一个模板给每个额外的必要检查重复声明插件类型；其余检查由既有 `preflightBindings / preflightExploration` 进一步验证实际可执行性。
- 保留原来的 `replace/preserve/dependencies`、Host 执行器、原全局预算和 V1 Policy 预检。不要新增模型匹配或额外请求。

如有不同 checker `name` 或插件 `id`，auto 给 `enabled:false` 与明确 reason；显式 observations 则拒绝；不要静默删除 checker 或更改 `Plan.acceptance`。

**为何不用重构多 Checker 平台？** 现有 `execution.checkers` 本就携带全部名称和绑定，只是解析器没有完整使用。最小修改就是把真实列表传进去，再准确匹配，并沿用原 preflight。

## 3. B1 / 任务卡 B：探索触发观察次数必须给备用路线留下轮数

### B.1 目标文件与函数（一个生产函数即可）

**仅修改** `auto-evolve/orchestrator/task-adaptation/exploration/resolve.ts::resolveExploration` 的“已唯一匹配模板、即将展开 V1”的配置相容性阶段；**不改** `decision.ts::decide`、`policy.ts` 或轮末处理函数。

**当前行为**：代码在模板过滤阶段检查 `allowance.rounds <= plan.stop.rounds` 和 `minimumRounds <= plan.stop.rounds`，之后构造 `trigger.observations`，但**不检查触发原路线时是否剩下最低备用轮数**。当 total=7、after=7、minimumRounds=2，Plan 可能被生成，但运行到触发时已经没有可分配的全局轮数。

**期望行为**：在**尚未写入冻结 Plan/启动请求之前**，对已选模板取：
- `N = request.after`（显式模式）或 `template.policy.defaultObservations`（auto）；
- `M = template.policy.allowance.minimumRounds`；
- `T = basePlan.stop.rounds`。

执行**必要**的静态相容条件：

```ts
Number.isSafeInteger(N) && N >= 1
Number.isSafeInteger(M) && M >= 1
Number.isSafeInteger(T) && T >= 1
Number.isSafeInteger(N + M)
N + M <= T
```

数学含义为“假设原路线每轮都产生正常观察，刚达到 N 时至少还留 M 个全局轮次”。**这是必要但非充分条件**：若平台故障消耗了轮次、请求消费超预期、任务提前通过或 Host 不满足运行约束，V1 实际仍可能不激活。代码及用户状态文字不得把它叫“保证备用激活”。

**非常重要：用 `minimumRounds`，不能用 `allowance.rounds` 当作必需条件。** 例如总轮数 7、触发 5、备用至少 2、备用最多 4，虽然备用**最多**跑不到 4，但最低 2 仍有机会启动，这个配置可以静态通过；要运行完整 4 轮属于用户预算分配/后续 V2 决策，不在本轮更改。

### B.2 推荐实现顺序（不要在模板遍历中混乱判错）

1. 先保留卡 A 得到的**模板与 Host 能力匹配**逻辑。不要为了轮次配置问题伪造“Checker 不匹配”。
2. 只有匹配唯一模板后，确定有效的 `N`，再取 `M/T` 进行约束校验；代码可用一个 10～20 行的**纯 helper**，放同文件，例如 `validateObservationWindow(...)`，不必新建包和全新 Policy Schema。
3. 如果 `N + M > T` 或不是安全整数，定义清晰的结果：
   - `mode:"auto"`：`{enabled:false,reason:"Exploration observation window leaves fewer than minimum alternative rounds ..."}`，不为 Plan 添加 exploration；由现有 Intake `exploration-resolution.json` 记载 disabled。
   - `mode:"observations"`：抛可读配置错误，包含 N、M、T 和原因；**不要**改 `after`、缩短 `M` 或增加 T 来自动修复。
4. 保留原 `explorationPolicy(candidatePolicy,basePlan)` 完整验证调用，不能由于已有早期检查而删除 Policy 校验。
5. 遇到 calls/tokens 等不足时，仍由现有 `explorationPolicy` 和后续 `preflightExploration / decide` 负责；不要在这里新增 reserved 钱包或自定义“预估模型用量”。
6. `resolveExploration` 必须在 Intake 写 `task-plan.json` 与 `intake.completed.json` 之前报出问题；platform 配置错误不能进入 auto 模型 Decision 的 repair loop。若有完全独立于模型决策的无效 `after`，可尽早在 Intake 前置校验，但**不要为提早检查而重复完整解析流程**。

### B.3 必须使用的测试矩阵（明确各数值）

修改 `exploration/resolve.test.ts`，尽量以 `fixturePlan()` 改 `plan.stop.rounds` 与 clone 模板的 `minimumRounds` 构造用例。不要改变生产 V1 trigger 语义。用例：
