## 当前真正的主线

```text
run-task.ts --input <绝对配置路径>
  -> prepareTaskRun / 冻结任务方案和协议
  -> 原runLongTaskCampaign（恢复用原resumeLongTaskCampaign）
  -> 原规划、执行、Workers和Lead修订
  -> campaignAcceptance / selectedRuntime
  -> Consolidation DirectChat评测全部50题
  -> 独立判卷进程 / Checker核验真实答案与分数
  -> 正式回执及逐题反馈发布
  -> taskFeedback / authorizeInvocation
  -> 下一轮Workers和Lead按授权读取逐题反馈、修订候选
  -> best_pass选择合格版本 / 冻结交付
```

这是原Campaign的显式可选协议，不是另写一条合并训练主链。旧任务未选择该协议时，保留原验收、工具、批量与回放规则。50题是本模式的训练反馈题集，不自动等同于50份来源Skill，也不是172题盲测。

## 实际测试发现的生产问题

1. 后端注册和协议范围校验不一致：已补显式Consolidation选择与严格范围匹配。
2. 冻结资源已经足够，但原spec加载强制额外materials非空：仅对明确的自适应协议放开，旧任务保持原规则。
3. 普通角色读取反馈摘要时，被误要求拥有逐题Reader权限：摘要与完整反馈分开授权；显式越权仍拒绝。
4. Lead验收pass身份未传递，Worker新建/恢复入口漏传上一轮反馈：在原调用链补齐，不能靠资源自报身份。
5. 请求账本只用题号与模型，第二轮不同候选撞号：编号改为具体评测目录指纹；同目录未知请求仍禁止盲重发。
6. 故障时已有合格交付，恢复后更优版本无法写固定交付目录：新版本独立保存，旧交付不覆盖，旧布局先核验再兼容复用。

测试夹具自身还出现过“Write之前未Read”和“inspectBudget传错配置字段”两种失败，均保留原日志并修改夹具；没有删除生产安全门禁来凑通过。
