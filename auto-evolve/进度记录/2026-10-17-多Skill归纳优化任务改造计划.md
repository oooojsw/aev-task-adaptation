# 2026-10-17 多 Skill 归纳优化任务改造计划

> 状态：**待实施 / 设计基线**。这是对 `aev-task-adaptation` 仓库现有 Task-Adaptation 的增量实施计划，不表示代码、真实模型实验或端到端验收已经完成。
>
> 基线：`oooojsw/aev-task-adaptation`，`main@7c5539ee0ac260d6a689c1754390c4f16efee6d9`。日期：2026-10-17。
>
> 需求原话的硬边界：**把合并本身作为一次独立学习/演化任务**。以已有的 50 份 Skill 为输入，迭代得到**实际发布内容不超过 5000 字**的一份合并 Skill；对于原始 50 道题，**每题独立、单次对话，把这道题的 Skill、题目与材料一次填入上下文，不启动多轮 Blank Agent，也不调用工具**；根据外部确定性评分提高总体通过率，始终保留历史最高分的合格版本。

## 1. 决策摘要（与旧 Merge 的区别）

1. 新增可复用的 **Multi-Skill Consolidation Task**（任务 Profile / 受信适配器），`deliverable.kind = "skill"`；不新增第四种 Intake 模式、不创建第二套 Campaign、不修改旧 `mergeConfig.mode` 的默认行为。
2. `auto / manual_decision / manual_plan` 三轨 Intake 均可选择这个任务；真正的归纳、压缩、缺陷诊断、候选修改与验收，发生在 **同一次 Task-Adaptation Long Task Campaign 的多轮循环内部**。
3. **不把原来的 `merge-as-old / merge-as-long-task / merge-as-opt` Phase 2 后处理器作为该任务的总控**。可引用其来源清单、归纳技巧、表面检查等**模块化方法**，但新任务的轮次、回退、恢复、经验积累、最佳版本都交给现有通用 Campaign。
4. 验收选择 **Direct Chat（每题单次模型请求）**，而不是传统的自主 Blank Eval：固定候选发布文本，对 50 道题分别构造独立上下文 `[Skill + question + that case's materials + output contract]`，得到 50 份单轮答案，再由每题原有的确定性 validator 判分。
5. 采用已有 `best_pass`：强制每轮候选先满足长度、安全、完整性和测试证据硬条件；合格后用**真实执行产物** `pass_rate`（0～1）进行选优，最终交付历史最高分版本，而不是最后一轮版本。
6. **5000 字是整个实际注入推理上下文的 Skill 正文上限**，不是 `CORE.md` 上限。`casebook/`、侧载文件或仅对后续工具可见的内容不得作为绕过字数上限的手段。
7. 只在本计划确认的专用边界做扩展，保留现有 Legacy Merge、原有 Skill 学习、Task-Adaptation 的报告/软件/策略流程及默认配置。

### 1.1 通用闭环的位置

```text
[Task-Adaptation Intake: auto | manual_decision | manual_plan]
      └─ 选定 kind=skill、Multi-Skill Consolidation Profile
          └─ Long Task Campaign（唯一学习/演化控制器）
              ├─ Planner：梳理 50 份源 Skill、分组与冲突
              ├─ Executor / Lead：写出并迭代单份候选 Skill
              ├─ Checker（先执行）：全量发布字数、来源/安全/结构硬门
              ├─ Independent（单次 Direct Chat 验收）：
              │    候选 Skill + 每题材料 + 题目 → 单轮回答 → 原题 validator
              │    50 题并发但相互隔离，严格每题最多一次模型发送
              ├─ 正式执行结果：passed/total/pass_rate + 50 题证据
              ├─ Diagnostician / Reviewer：失败分类、修订建议、不改评分真源
              └─ best_pass：冻结合格最优版本；按轮次、停滞、调用/Token 预算停机
                   └─ 最终交付：≤5000 字 Skill + 分数与溯源报告
```

## 3. 精确定义输入、候选、评分及信任边界

### 3.1 输入：源 Skill 是学习材料，不是 50 个模型轮次

- 宿主提供 `sources.manifest.json`，每一项含稳定 `source_id`、文件路径、SHA-256、可公开给创作者的标志，以及对应的 `case_id`；固定数量第一轮为 50，但适配器设计不得硬编码 50，数量由冻结数据集决定。
- 建议将各份源 Skill **只读、按文件隔离**地列为 Task Plan resources；可生成按主题分类的索引，Planner/Lead **按需分批阅读**，不能一次性把几十万字塞到同一个请求。
- 宿主同时冻结用于 Direct Chat 的 `dataset.bundle.jsonl` 或等价合法 Bundle：50 条唯一 `case_id`、完整题干/输出合同、题目所需公开材料与验证器引用。每个输入的文件哈希和必要配置都进入同一运行血统。
- **公开给创作者**：源 Skill 内容、可公开题干/资料、已规范化失败类型、必要的反馈摘要；**不得提供**：验证器私有答案、oracle、隐含评分判据或未来盲测题集。Direct Chat 评分脚本在独立的受信边界内读取私有依据。
- 不从源 Skill 中照搬特定题的最终答案、答案常量或私有 oracle；保留可复用的操作方法、边界判断、解题流程与经验证例的抽象。设置泄漏检查与必要的人工复核。
- 必须保证 Task-Adaptation 当前资源约束能够表达该结构。`Plan.resources` 目前是**单文件相对路径**，不直接接受把 50 个任意外部目录当成裸目录资源；第一阶段显式提供冻结后的安全只读扁平文件或受信索引，不扩大通用读权限。

### 3.2 候选与 5000 字计数

第一版**只允许一个正式推理发布正文**：

```text
candidate/
  DIRECT_CHAT.md        # 唯一进入 Direct Chat 的 Skill 内容，≤5000 字
```

- 宿主负责字数真源；模型不能自行声明“已达标”。推荐可复算规则：`NFC` 归一化、按 Unicode code point 计数、**去除 Unicode 空白符后**计算实际可见字符数，包含标题、Markdown 标记、代码片段、标点、英文、数字和任何引用的可见正文。`Array.from(content.normalize("NFC").replace(/\s/gu, "")).length <= 5000`。这是一项**建议采用并冻结的规范**；落实之前须由测试明确该规则。
- 这不是 UTF-8 字节数，也不是 `CORE.md` 字节数。禁止通过 `casebook/`、隐藏文件、另一个自动加载的发布文件或链接规避。若未来允许多文件，则**对实际注入模型的最终发布 Bundle 全量计数**，且二者哈希必须完全对应。
- **在测试模型请求前**先校验：唯一发布文件、路径及大小限制、真实发布 Bundle hash、5000 字、无符号链接/路径逃逸、没有未授权额外注入内容、没有禁止的私有答案。未通过则失败并提供有限错误诊断；**不花费 50 题模型成本**。
- 发布时禁止 `head-tail`/`core-files` 截断或多档自动切换，避免“训练时测试的不是最终交付的 Skill”。可保留系统必需的固定 Prompt 框架，但候选正文的字数门与请求真实 Skill hash 必须一致。
- `DIRECT_CHAT.md` 即为此任务的可交付 Skill。若未来面向多轮工具 Agent 的 Skill Package 需要 `INDEX.md/CORE.md/casebook`，应另设明确产品合同及验收，不以这个 5000 字单轮任务的成功冒充多工具场景的成功。

### 3.3 每题一轮 Direct Chat，不是多轮 Blank Agent

对每个 `case_id`，在独立、无历史的对话中构造：

```text
System: 只使用下面的 Skill 与本题公开材料解题；不调用工具；约束输出格式
Skill:  同一候选 DIRECT_CHAT.md 的全部文本（固定 hash）
User:   本题题目 + 此题完整允许材料 + 此题输出合同
Model:  **一次**完成答题，返回约定 <answer>...</answer>
Validator: 独立确定性脚本判定这道题是否通过
```

- **一次对话/一次请求**是指一个 case + 一个候选 + 一个评估配置最多一次实际模型发送；50 个 case = 至多 50 个模型调用（基础设施预检不过时少于 50），**每轮可重新对同 50 题测试一个新候选**。如产品内部存在 SDK/HTTP 自动重试，还必须在传输层验证禁用；“设置 maxAttempts=1”本身不是对底层透明重传的数学保证。
- Direct Chat Profile 明确：`modelIDs` **恰好一个**、`includeNoSkillBaseline=false`、`noSkillOnly=false`、`skillInputMode="full"`、`allowOmittedMaterials=false`、`retry.maxAttempts=1`、`transientRecovery.enabled=false`；每题保留请求、模型、Skill/数据集/材料 hash、响应、提取、评分与使用量证明。
- 50 题**可以按受控并发**发出，但无相互共享的对话历史、上一题答案、人工工具调用或搜索。固定模型 ID、温度、输出 token 上限、材料处理、Prompt 模板版本、validator 版本；比较不同候选时，不能暗中变更测试合同。
- 所有输入材料必须可由当前选定模型在单轮上下文中**完整表示**；图片/PDF 若走现有能力需做模型能力证明与材料预检。**禁止因为塞不下就静默裁剪、跳页、降低 Skill 档位**；预检不满足时判运行无效并提出材料准备方案。
- 不能承诺“一定只花几毛钱或十秒”。实际成本与延迟取决于模型、提供商限流、材料体积、最长题、并发和响应时长；试运行需实测并冻结预算。

### 3.4 评分：可最大化的通过率 + 不能协商的硬门

- 可信适配器必须核实 50 个**唯一** case、每个恰好一条合法最终判定、输入/模型/Skill hash 一致、无未识别来源、评分器全部执行成功、无材料缺失和输出截断；然后才计算：`pass_rate = passed / total`，`total = 50`（或冻结配置的大小）。
- 每道题判定 `pass=true/false` 由独立 validator 决定；提取失败单独标注为 `answer_extraction`，而 API auth、quota、超时、上下文不足、材料准备失败、判题器故障等为**基础设施/配置错误**，不能直接吞掉并计作模型能力不通过。
- 如某次测试发生基础设施/判题故障，**该候选本轮结果作废、不入 best_pass**，保留诊断和已实际计费证据；不得在同一“每题一次”的记录上悄悄补发。宿主可在修复环境后启动**明确的新验收 attempt**，保留旧 attempt，不伪称旧 attempt 只有一次请求。
- **硬门**（正式候选合格要求）：发布字数≤5000、格式/路径/来源合法、无已知答案泄漏、固定评测合同可完整执行、评分结果可信且所有 50 题完成；**软优化指标**：`pass_rate` 尽量高。不得把“50/50 全部通过”设置成每轮 `required` 检查，否则 43/50 等中间最优候选无法被保存。
- 返回由受信执行器**自行计算**的 JSON（示意，数值不是实测）：

```json
{
  "schema": "aev.consolidation-eval.v1",
  "candidate_sha256": "<candidate-hash>",
  "dataset_sha256": "<frozen-dataset-hash>",
  "model_id": "<frozen-model-id>",
  "total": 50,
  "passed": 43,
  "failed": 7,
  "pass_rate": 0.86,
  "skill_chars": 4872,
  "integrity": "passed",
  "evidence_manifest": "<host-owned-manifest-reference>"
}
```

- `selection.rule = "best_pass"`、`selection.metric = "pass_rate"`、`selection.direction = "max"`；每轮的正式 **candidate/product checks 全部通过后**再允许 `selection.ts` 冻结此版本。比较率相同时，沿用现有“保留较早版本”的行为，不偷换选择器语义。
- 不把反复优化的原 50 题通过率称为“泛化测试成绩”：应留出**不向 Lead 反馈、仅最终最佳版本执行一次**的独立盲测集，另行报告其结果。盲测不参与 `best_pass`，不把盲测正确答案纳入后续 Skill。
- 对确有随机性的模型，一次判题结果只是本实验设置下的一次观测；首版严格遵循用户“每题一次”，可在另一份单独的稳定性评测协议中研究重复采样。

## 4. 新 Task Profile 与插件接口提案

### 4.1 推荐配置形态（**说明性草案，不是可直接传给 intake.ts 的完整 JSON**）

```json
{
  "taskProfile": "multi_skill_consolidation_v1",
  "intakeMode": "manual_decision",
  "deliverableKind": "skill",
  "candidateEntries": ["DIRECT_CHAT.md"],
  "acceptance": {
    "surfaceGate": {
      "maxSkillChars": 5000,
      "measure": "nfc_non_whitespace_unicode_code_points",
      "publication": "DIRECT_CHAT.md"
    },
    "application": {
      "backend": "direct_chat",
      "casesFromFrozenDataset": true,
      "oneRequestPerCase": true,
      "skillInputMode": "full",
      "requireCompleteMaterials": true,
      "failClosedOnInfrastructure": true
    },
    "metric": "pass_rate"
  },
  "selection": {
    "rule": "best_pass",
    "metric": "pass_rate",
    "direction": "max"
  },
  "stop": {
    "rounds": "<host finite budget>",
    "calls": "<host finite budget>",
    "tokens": "<host finite budget>",
    "stagnant": "<host finite budget>"
  }
}
```

实际接入使用既有 `TaskCatalogue + Decision` 或宿主批准的 `Plan`。`catalogue.profiles[].acceptance` 定义 candidate 校验、`execution="script"`、product 校验；`selection` 采用上述三元组。`taskProfile` 等辅助字段不能不经 Schema 变更直接塞到现有 `TaskCatalogue/Plan`（它们严格拒绝未知字段）。新的评测参数放到**宿主所有的 adapter 配置/可信脚本 settings**，经哈希绑定，再映射到现有 Plan 的已知能力与资源字段。

### 4.2 推荐先沿现有脚本协议落地

1. **Surface Checker（candidate / before_execution）**：受信脚本检查发布文件和长度、内容边界。用已有 `script-json-checker`；须确认 its `skill` target、资料和 candidate 映射与 Plan 的 checker window 一致。
2. **Direct Chat Executor（independent / execution）**：优先使用已有 `script-json-executor` 的 `trusted_host_runner`，调用受信的薄入口到 `runDirectChatEvaluation`，在隔离目录内生成逐题 trace 和可信评分 JSON。必要时**只扩展薄 adapter / 注册项**，不能让 Lead 获得执行器私有 oracle、模型凭据或写验证器的权限。
3. **Product Checker（product / after_execution）**：校验总数、唯一 case、hash、请求次数、材料完整、基础设施错误、评分公式及产品回执（不能只看单个 `pass_rate` 浮点数）。采用同一个现有脚本 checker 机制，受信输入读取审计证据。
4. **Best-pass**：不变更 `task-adaptation/selection.ts` 算法；以 `script-json-executor` 的已检查 JSON product 为分数真源，必要时调整 Task-Adaptation 侧的绑定设置/表层 Schema，而**不是在 Campaign 中为合并另写一套 best-of-N**。
5. **反馈**：给 Lead 的只有该轮失败 case_id、合理公开的 validator 错误分类、与修复建议，不暴露私有答案。经验树/Reviewer 使用现有跨轮证据权限边界，不允许从评分目录直接读取隐藏 oracle。

注意：`script-json-executor` 当前 `skillFormats=["text","files"]`、`productKinds=["json"]`、`materialKinds=["text","json"]`。包装时需验证最终输入适合这些类型，且 `maxInputBytes/maxOutputBytes/timeoutMs` 能覆盖**整个真实测试**；绝不能通过把 50 题数据偷偷复制给模型侧来规避这些限额。若当前形态无法在隔离 runner 内正确承载分批模型请求，应新增专用**受信 execution plugin**，其输出契约仍沿用现有 Protocol，而非冒充现有 script executor 能自动完成一切。

## 5. 落地拆分、交付件、验收门

### P0 — 任务合同、字数定义和只读输入（必须先完成）

**拟新增（命名供实现时确认）**
- `orchestrator/task-adaptation/profiles/multi-skill-consolidation.ts`：宿主构造 Catalogue/Profile/Decision 的模块化配置；不在核心 Plan 增加无需求的第五种 kind。
- `orchestrator/task-adaptation/consolidation/source-manifest.ts`：冻结 50 份 Skill 与对应题集，唯一 ID、哈希、权限、路径和错误反馈白名单。
- `orchestrator/task-adaptation/consolidation/publication.ts`：唯一 `DIRECT_CHAT.md` 计数、完整发布构建与哈希核验。
- 专项 fixtures：10～50 份无答案的微型 Skill / 题目 / mock validator；真题、私有答案和 runtime 不入库。

**完成判据**：3 种 Intake 可选择同一 Profile；合法材料的输出稳定；源文件更改、manifest 漏/重 case、symlink、路径逃逸、发布字数 5001 都在付费前拒绝；5000 正好允许；多文件偷渡失败；代码没有修改 Legacy Merge 默认值。

### P1 — 单次 Direct Chat 执行桥接与可信结果

**拟新增**
- `orchestrator/task-adaptation/consolidation/direct-chat-executor.ts`（或 host-owned `scripts/run-consolidation-direct-chat.ts`）：构造唯一 Direct Chat 运行，冻结一次请求语义、模型与材料合同、Skill/hash；调用现有 `direct-chat/runner.ts`，读取完整 `summary.json` 与逐题 evidence。
- `orchestrator/task-adaptation/consolidation/score-checker.ts`：结果完整性、公式、失败类型、model/skill/dataset/validator 版本校验；输出协议允许 `selection.ts` 读取的数值 `pass_rate`。
- 固定协议版本 `aev.consolidation-eval.v1`、证据 manifest、每题请求使用量/尝试次数和审计 trace；执行侧凭据绝不进入文件化候选资源。

**完成判据**：50 个不同 case 触发 50 个独立请求（配置允许的前提下），每题上下文均含**相同完整候选**和**该题全部公开材料**；同一候选不因截断变成另一套技能；模拟网络超时、缺材料、validator 故障时不能产生合格分数；重复/伪造 `pass_rate` 被拒绝；0/50、43/50、50/50 均可作为合法评分结果（但仅硬门通过时可进入最佳版本）。

### P2 — 同一 Campaign 闭环、反馈与最佳版本

**拟复用**
- `task-adaptation/prepare-task-run.ts`、`run-task.ts` 与原 `long-task-campaign/runner.ts`：准备、启动、恢复、跨轮记忆。
- `task-adaptation/feedback.ts`、`selection.ts`、`delivery.ts`：只提供可授权反馈、冻结最优、按历史最优交付。

**完成判据**：一个实例从第一轮候选 38/50、第二轮 43/50、第三轮 41/50 走完全程，最终交付**第二轮**的已验证 5000 字内版本；真实候选改动会改变请求哈希；来源/评分器/材料变更触发 identity drift；失败、模型中断、预算停止后不可绕过历史证明而自动重新计费。注意 `best_pass` 是在**满足正式验收**的候选中比较，故评分高低不是 `required` 通过条件。

### P3 — 防泄漏、盲测、成本/预算和兼容回归

- 加盲测只读配置与**仅终局执行一次**的结果报告；避免把 50 题训练回测成绩错误表述为泛化。
- 验证冻结 provider/temperature、上下文、最大输出和预算；`retry=1`、关闭 transient recovery，测试断网后没有隐式补发；计费不确定时 fail closed。
- 验证子进程超时、并发、停止恢复、checkpoint、幂等输出、导出报告和模型调用总额记录；实际费用用 SDK/provider 回执统计，不能用粗略估算替代硬限额。
- 老路径的 `legacy_script / long_task / skillopt` 不退化；普通 `report / software / strategy / skill` 的 task-adaptation 测试不受影响。无需求不修改默认 `mergeConfig.mode=legacy_script`。
- 先 mock/local service 做**不计费**集成验证；随后在人为批准的明确数据集和模型上做受限小样本真跑，再做 50 题演示。没有真实跑过，不写“已达到准确率”。

## 7. 最终交付与报告

交付应包含：
- **一份** `DIRECT_CHAT.md`：经过绑定与字数复核、实际参与回测和选优的**最佳历史版本**。
- `delivery.json`：由现有通用选择器/导出器签发的候选文件列表、hash、轮次、正式验收回执与选优指标。
- 专用 `consolidation-report.json`：源 Skill 数、冻结来源清单 hash、训练题数量、版本轨迹、最佳轮次、最佳 `passed/total`、`pass_rate`、Skill 字数、每题结果引用、基础设施错误分类、token/成本回执；盲测部分另列，不混报。
- 出错或提前停机时：明确 `taskStopReason`、是否存在已通过硬门的可交付最佳版本、未解决问题；不虚构“全部通过”“稳定泛化”。

## 8. 明确非目标 / 风险

- 不给新 Intake 增加 `merge` 第四条轨道；不把合并任务插回旧 benchmark 的 Phase 2；不重写 `best_pass`；不让候选文本控制判题逻辑。
- 不承诺模型权重更新；本任务改进的是**外部 Skill 产物与跨轮经验**。
- 不承诺 5000 字能保留所有 50 份 Skill 的全部长尾特例；长度和分数存在 Pareto 权衡，最优定义只相对于冻结模型、测试集和有限搜索预算。
- 不声称重复使用原 50 题优化得到的是外部泛化成绩；保持盲测独立性。最终精确度与费用只能经过实测判断。
- “每题一次”与“平台级自动补发”存在冲突：首版以**不透明失败不重发、保留不确定调用证据**为原则；允许后续定义显式的新 attempt，但不得悄悄复用旧的尝试 ID。
- 修改受信脚本/评测规格/模型配置后不能沿用旧最佳版本同一评分口径而不重新验证，防止跨协议的虚假“进步”。

## 9. 工程实施顺序与合并准入

1. **先完成 P0**，冻结计数字符规则、数据边界、Profile 与产物布局；跑负向预检与旧三轨回归。
2. **再完成 P1**，用不产生外部付费请求的本地服务验证完整 Direct Chat/Checker/Executor 的 50 题事实链；对接真实 `script-json-executor` 与私有评分边界。
3. **再完成 P2**，用确定性 38→43→41 情景跑真实 Campaign 进入、修复、选优、续传与导出；禁止只测独立 helper 就声称完成集成。
4. **最后 P3**，在隔离环境执行全面回归、真实模型试跑和留出盲测，收集分数/成本/耗时；有可复核证据后才将 Profile 标记为可用。
5. 每阶段单独代码 PR；保持此计划文档作为评审真源，在实际设计变化时追加版本说明，不静默改写历史验收口径。
