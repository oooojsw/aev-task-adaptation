# 通俗报告：为什么我们要改成“元操作 + 代码编排方法”

日期：2026-04-10

## 一句话结论

我们现在决定把系统做成：

**一组稳定的元操作 + 每种反向传播方法各自的一套代码编排。**

这意味着：

- 系统底层动作是共用的
- 不同方法只是“怎么调用这些动作”不同
- 以后你要加很多种反向传播方法，不需要把主系统越改越乱

---

## 1. 先说问题出在哪里

我们前面做了一步“方法 flow”设计，也就是用一个 `FLOW.md` 文件写：

- 先 solve
- 再 refine
- 再验证
- 再回归

表面上看，这样很清楚。

但你指出了一个关键问题：

**真实系统不是一条简单的直线流程。**

它里面其实有很多复杂情况：

- 如果一开始就答对了，直接结束
- 如果是测试模式，不能学习
- 如果 refine 没改到知识库，要直接停
- 如果修改了不该改的文件，要回滚
- 如果当前题修好了，但旧题变差了，也要回滚
- 如果以后要做双分支比较，就更复杂

这些情况一多，`FLOW.md` 就会越来越像一门小程序语言。

换句话说：

**如果我们继续让 Markdown 负责真正的流程控制，后面会越来越难维护。**

---

## 2. 为什么“代码编排方法”更合适

因为复杂控制流，本来就是代码更擅长的事情。

代码天生适合处理：

- 条件判断
- 循环
- 提前结束
- 回滚
- 多分支比较
- 不同失败路径

而 Markdown 更适合做：

- 方法说明
- Prompt 模板
- 人类阅读的流程文档

所以我们现在决定分清楚：

### 代码负责什么

- 真正的执行逻辑
- 每种方法怎么走
- 哪些条件下继续
- 哪些条件下回滚

### Markdown 负责什么

- 解释这个方法是什么
- 解释这个方法大概怎么工作
- 提供具体 prompt 文本

这样职责更清楚，也更稳。

---

## 3. 什么是“元操作”

元操作可以理解成系统里最小的标准动作。

例如：

- `solve_case`
  - 用当前知识库解题
- `prepare_feedback`
  - 整理失败信息
- `refine_knowledge`
  - 修改知识库
- `verify_current_case`
  - 检查当前题修没修好
- `run_regression`
  - 跑回归测试
- `accept_or_reject_change`
  - 决定保留还是回滚

你可以把它们理解成一套“标准工具箱”。

以后任何方法都不需要重新发明这些基础动作，只需要决定：

**这套方法要以什么顺序、在什么条件下调用这些元操作。**

---

## 4. 什么是“代码编排方法”

这一步是最关键的。

以后每种方法，不再主要靠 `FLOW.md` 真正控制执行，而是写成一个独立的方法模块。

比如：

- `SequentialRefineMethod`
- `SequentialLiteMethod`
- `AdversarialTestMethod`

这些方法模块本质上就是一段代码，负责定义：

- 先做什么
- 再做什么
- 什么情况下停止
- 什么情况下进入下一次尝试
- 反馈包怎么构造
- 接受标准是什么

也就是说：

**方法 = 一套调度元操作的代码。**

---

## 5. 这样做最大的好处是什么

### 好处 1：系统不会被越来越多的方法拖垮

以后你加新方法，不需要一直改主流程。

新方法只要：

- 复用已有元操作
- 自己写自己的编排代码

这样主系统不会越来越乱。

### 好处 2：回传终于能真正变成“方法的一部分”

你前面已经说得很准确：

> 回传其实就等于反向传播的方法

现在这条路终于合理了。

以后不同方法可以有不同的“回传包”：

- 方法 A 看 `actual + expected + evaluation`
- 方法 B 再加 `action_trace`
- 方法 C 甚至会先做对抗测试，再构造反馈

这些都不会再被主系统硬绑死。

### 好处 3：更适合未来的双分支实验

以后如果你要做：

- 方法 A 跑一条分支
- 方法 B 跑另一条分支
- 最后比较结果

那“代码编排方法”会比“Markdown 执行流程”稳定得多。

### 好处 4：更方便调试

如果某个方法跑错了，你可以直接看：

- 它调用了哪些元操作
- 哪一步返回了什么
- 为什么提前结束

而不是去排查一套越来越复杂的 Markdown 流程语言。

---

## 6. 这不代表 Markdown 没用了

Markdown 仍然很重要，只是职责变了。

以后 Markdown 继续保留这 3 类：

### 1. `METHOD.md`

给人看：

- 这个方法的目的是什么
- 适合什么场景

### 2. `FLOW.md`

给人看：

- 这个方法大概会经历哪些步骤

注意：

以后它更像“方法说明图”，而不是“真正执行引擎”。

### 3. `prompts/*.md`

给模型看：

- solve prompt
- refine prompt
- adversarial probe prompt

所以未来会变成：

- **代码**负责真正执行
- **Markdown**负责解释和提示词

---

## 7. 系统以后会长成什么样

你可以把未来的系统理解成四层：

### 第一层：稳定内核

负责基础能力：

- 调 OpenCode
- 读写知识库
- 评分
- 监控
- 存运行日志

### 第二层：元操作

负责标准动作：

- 解题
- 构造反馈
- 修改知识库
- 验证
- 回归
- 接受 / 拒绝

### 第三层：方法代码

负责真正的反向传播路径。

例如：

- 顺序法
- 轻量顺序法
- 对抗测试法

### 第四层：文档层

负责说明和 prompt：

- `METHOD.md`
- `FLOW.md`
- `prompts/*.md`

---

## 8. 这和我们现在刚做的那一步是什么关系

我们刚刚做的那一步并没有浪费。

因为之前做的这些东西仍然有价值：

- 元操作命名
- 方法运行轨迹
- `method_runtime.json`
- 方法目录结构

只是现在方向更清晰了：

- 不再让 `FLOW.md` 承担复杂控制流
- 以后真正复杂的方法控制，交给代码模块

也就是说：

**我们不是推翻前面的工作，而是把它纠正到更合理的方向上。**

---

## 9. 现在最合理的下一步是什么

我建议后面这样做：

### 第一步

不再继续强化 `FLOW.md` 的执行能力。

它保留，但降级为“说明文档”。

### 第二步

开始设计真正的方法代码模块。

比如：

- `sequential-refine.ts`
- `sequential-lite.ts`
- `adversarial-test.ts`

### 第三步

让每个方法模块调用同一组元操作。

这样不同方法之间才真正可比。

### 第四步

等方法系统稳定后，再接 Git-tree 和双实验分支。

---

## 10. 最后一句最重要的话

如果只用一句话总结这次方向调整：

**以后系统的核心，不是“用 Markdown 写流程”，而是“用代码编排元操作，用 Markdown 解释方法和提供提示词”。**

这会更适合你后面做很多复杂的反向传播方法实验。
