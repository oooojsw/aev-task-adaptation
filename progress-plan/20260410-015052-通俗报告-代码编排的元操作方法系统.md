# 通俗报告：我们接下来真正要做成什么系统

日期：2026-04-10

## 一句话结论

我们现在要把系统做成这样：

**底层是一组稳定的元操作，上层是不同的反向传播方法代码，而知识体系本身由一个专门的“经修 agent”负责维护。**

也就是说：

- 解题的 agent 负责解题
- 反向传播方法负责决定“怎么反馈、怎么验证、怎么接受”
- 经修 agent 负责真正修改和重组专家经验体系

这样以后不管你有多少种反向传播方法，主系统都不会越来越乱。

---

## 1. 为什么之前的想法还不够

我们前面已经意识到一个问题：

**“回传”本身，其实就是反向传播方法的一部分。**

所以：

- 回传不应该写死
- 验证不应该永远固定
- 接受和拒绝规则也不应该永远固定

但你这次又补了一个更重要的点：

**知识体系本身也不能写死。**

因为现在的知识库虽然已经比一开始合理很多，但它仍然还是一种“当前版本的结构”。

现实里以后可能出现这些情况：

- 经验越来越多，不可能都塞在几个固定文件里
- 某种方法可能只保留一个最优版本
- 另一种方法可能要保留多个版本
- 还有的方法可能会给不同经验加“权重”或“优先级”
- 有的经验可能适合按主题拆
- 有的经验可能适合按失败类型拆

所以结论就是：

**知识体系的结构也必须是可变的。**

这意味着以后不能再靠纯代码去硬写“知识一定长什么样”，而应该让专门的 agent 去维护它。

---

## 2. 现在最核心的新设计

新的核心设计可以概括成 4 个角色。

### 角色 1：解题 agent

这个 agent 的任务很单纯：

- 读取当前经验体系
- 读取当前材料
- 输出答案

它不负责设计经验体系，也不负责决定系统策略。

它只是“当前这一轮拿着已有知识去做题的人”。

---

### 角色 2：经修 agent

这个是以后最关键的角色。

它的职责不是解题，而是：

- 维护专家经验体系
- 重新组织经验文件
- 新增、删除、拆分、合并经验文档
- 调整经验体系的布局
- 让经验体系更适合未来 agent 读取和执行

注意：

它不是“胡乱改知识库”，而是：

- 在明确约束下改
- 在反向传播方法给出的要求下改
- 在系统允许的边界里改

你可以把它理解成：

**一个负责维护“专家经验操作系统”的专门 agent。**

#### 当前阶段的现实约束方式

这里有一个非常重要的现实条件：

**当前阶段，我们暂时不对经修 agent 做很重的硬权限切分。**

也就是说，现阶段它的约束主要来自：

- 提示词契约
- 反向传播方法给它的修改要求
- 系统后续的验证与回滚

这么做不是因为以后不要权限，而是因为：

- 我们当前最优先的目标是先把整条系统链路跑通
- 先观察经修 agent 在真实运行里会如何维护经验体系
- 避免过早的权限墙把系统问题和权限问题混在一起

所以当前阶段可以概括成一句话：

**先用提示词约束经修 agent，先跑通系统，再逐步收紧权限。**

---

### 角色 3：反向传播方法

这个部分不再负责“亲自修改知识库”，而是负责：

- 决定什么时候触发反馈
- 构造什么反馈包
- 告诉经修 agent 应该朝什么方向修改
- 决定这次修改之后怎么验证
- 决定最后接受还是拒绝

也就是说：

**反向传播方法是“策略层”，经修 agent 是“知识维护层”。**

这两个一定要分开。

---

### 角色 4：系统内核

系统内核负责：

- 跑 OpenCode
- 跑评估器
- 存日志
- 调监控
- 调用元操作
- 组织实验

这一层尽量稳定，不要被具体方法污染。

---

## 3. 以后整个系统会怎么运作

最通俗的理解方式是下面这条链：

1. 解题 agent 先做题
2. 系统评估答案
3. 如果失败，当前反向传播方法决定：
   - 要收集什么失败材料
   - 要不要回归
   - 要不要做对抗探测
4. 系统把这些材料交给经修 agent
5. 经修 agent 根据当前方法的要求去修改经验体系
6. 系统再验证这次修改值不值得保留
7. 保留或回滚

这里最关键的变化是：

**以后真正修改经验体系的，不是固定代码，而是经修 agent。**

---

## 4. 为什么经修 agent 必须单独存在

因为“经验体系维护”其实是一件和“做题”完全不同的事。

### 解题 agent 擅长的是：

- 看材料
- 找规则
- 产出答案

### 经修 agent 擅长的是：

- 分析失败
- 抽象经验
- 决定经验写在哪
- 决定是否拆文件
- 决定是否新增专题文档
- 决定经验体系是否要重组

如果让一堆纯代码去决定这些东西，就会很快出现问题：

- 结构被写死
- 难扩展
- 一旦知识体系变大，代码规则会越来越多

所以未来更合理的方式是：

**代码负责规则边界，agent 负责知识布局。**

---

## 5. 经验体系以后应该怎么理解

以后不要再把它只理解成一个固定的 `knowledge-pack`。

更准确的名字应该是：

**经验工作区**

也就是：

- 这里存的是专家经验
- 但具体长成什么样，不是完全固定的
- 当前版本只是一个起点，不是永远的最终结构

这个工作区未来可能长成这样：

- 有总索引
- 有主题规则
- 有失败教训
- 有专项策略
- 有版本集合
- 有候选方案
- 有方法专属经验
- 有共享经验

所以未来要允许：

- 增加文件
- 删除文件
- 拆分文件
- 合并文件
- 改变目录结构

前提是：

- 经修 agent 要遵守系统约束
- 不能乱动系统外部内容
- 要保持经验体系可读、可追踪、可验证

---

## 5.1 还要再加一个“初始模板库”

这个点非常重要。

以后系统里应该同时存在两个不同的东西：

### A. 初始模板库

它的作用是：

- 给经修 agent 提供可参考的结构模板
- 提供常见经验体系布局
- 提供常见索引写法
- 提供常见工具说明文档模板

但是它**不是最终专家经验的一部分**。

也就是说：

- 经修 agent 可以看模板库
- 经修 agent 可以借用模板思路
- 但最终经验工作区里不应该把模板库原样塞进去

你可以把它理解成：

**模板库是“施工参考图纸”，不是“最终建筑物”。**

### B. 最终经验工作区

这个里面只放：

- 当前真的有效的专家经验
- 当前 agent 真正需要读取的内容
- 当前方法和经修 agent 共同维护后的结果

所以：

- 模板库是外部参考
- 经验工作区是最终产物

这两个一定要分开。

---

## 5.2 不管经验体系怎么长，必须有一个单入口文件

这一点我认为应该定成硬约束。

无论以后经验工作区变得多大、多复杂，都应该始终保留：

- 一个入口文件

这个入口文件的作用是：

- 告诉新 agent 这套经验体系怎么读
- 告诉它有哪些分区
- 告诉它先读什么、后读什么
- 告诉它遇到什么任务时应该去哪一块

也就是说：

**以后经验体系再复杂，也不能让一个空白 agent 一上来就迷路。**

所以单入口文件相当于：

- 总导航
- 总索引
- 总阅读协议

---

## 5.3 大型体系下不能全量读取，只能选择性读取

这也是一个关键设计点。

以后如果经验体系越来越大，
一个“一无所知”的新 agent 不应该每次都把全部内容读完。

更合理的方式是：

1. 先读入口文件
2. 先判断当前任务是什么类型
3. 再根据入口文件指引，只读相关分区

也就是说：

经验工作区以后应该支持：

- 分区存储
- 分主题存储
- 分任务类型存储
- 分工具类型存储

这样 solve agent 才能做到：

- 不全量加载
- 只读取当前任务相关内容

这会让大型系统更可用。

---

## 5.4 经验体系里以后应该包含“工具使用说明文档”

你这个判断也非常对。

很多经验并不只是“规则是什么”，而是：

- 某种任务该优先用哪个工具
- 某种工具什么时候该用
- 某种工具该怎么组合
- 哪些工具调用方式容易失败

所以未来经验体系里应该允许存在一种文档：

- 任务专用工具使用说明

例如：

- 读文件任务怎么读
- 结构化抽取优先用什么流程
- 大型体系中先读入口，再读局部索引，再读目标文档

这类文档的意义是：

**让新 solve agent 不只是“知道规则”，还知道“该怎么行动”。**

---

## 5.5 所以未来经验体系最合理的样子

综合起来，未来经验体系应该包含这些共同特征：

- 有单入口文件
- 有选择性读取协议
- 有按任务或主题拆分的分区
- 有任务专用工具说明文档
- 有真实专家经验
- 但不直接包含模板库本身

你可以把它理解成：

**模板库在外面，经验工作区在里面；入口文件负责导航；经修 agent 负责维护整个布局。**

---

## 6. 那系统约束到底是什么

经修 agent 虽然可以改经验体系，但不是无限制自由发挥。

这里要特别分成两个阶段来看：

### 当前阶段：软约束优先

当前阶段我们采用的是：

- 主要靠提示词约束
- 主要靠方法给出的修改意图约束
- 主要靠验证和回滚约束

也就是说：

- 现在不急着做重型硬权限切分
- 现在先证明“经修 agent + 经验工作区”这条主线能跑通

### 未来阶段：硬权限逐步补上

等系统跑通、稳定、看清真实问题后，再逐步补：

- 工作区边界
- 文件边界
- 方法授权边界
- 结构性规则边界

所以当前不是“不要权限”，而是：

**权限后置，验证前置。**

以后它应该被约束在这些规则里：

### 约束 1：只能改经验工作区

它不能去乱改：

- 数据集
- 运行脚本
- 核心代码

除非未来某种方法明确允许它动某些脚本层能力。

---

### 约束 2：必须维护经验体系的可读性

也就是说：

- 经验文件要清楚
- 索引要清楚
- 文件职责要清楚

以后新来的解题 agent 才能读懂。

---

### 约束 3：必须留下变更痕迹

经修 agent 每次改动，都应该留下：

- 改了什么
- 为什么改
- 基于哪次失败改
- 这次改动服务于哪种方法

这样以后不同方法之间才能比较。

---

### 约束 4：必须服从当前方法要求

这一点很重要。

经修 agent 不是自己决定一切，而是要服从当前方法的要求。

例如：

- 顺序法可能要求它只做最小修改
- 对抗法可能要求它把脆弱点单独拆成一个专题
- 某种多版本法可能要求它保留多个知识版本
- 某种权重法可能要求它把经验拆成高优先级和低优先级

也就是说：

**经修 agent 是知识维护者，但不是策略制定者。**

### 约束 5：当前先靠契约，未来再靠硬边界

这一条单独写出来非常重要：

当前阶段：

- 经修 agent 先靠提示词契约约束
- 先不做过重的硬权限分割

未来阶段：

- 再把这些约束逐步变成真正的系统权限

例如未来可以补的权限控制包括：

- 只能修改经验工作区
- 不允许改数据集
- 不允许改主代码
- 不允许破坏单入口文件
- 不允许生成失去导航能力的经验结构
- 不同方法拥有不同的结构修改权限

策略还是由反向传播方法来定。

---

## 7. 所以以后最好的系统分层是什么

现在我认为最合理的是五层。

### 第一层：系统内核

负责：

- OpenCode 调用
- 评估
- 监控
- 日志
- 运行上下文

---

### 第二层：元操作

负责最小标准动作。

例如：

- 解题
- 评估
- 构造反馈包
- 调经修 agent
- 跑验证
- 跑回归
- 接受或拒绝修改

这些动作以后可以继续增加。

---

### 第三层：反向传播方法代码

这层负责：

- 怎么组织元操作
- 何时触发经修 agent
- 给经修 agent 什么修改要求
- 这次修改之后如何验证

也就是说：

**每种方法就是一套调度元操作和经修 agent 的代码。**

---

### 第四层：经修 agent

这层负责：

- 接受当前方法给它的修改任务
- 阅读当前经验工作区
- 按要求维护经验体系

它应该是“经验维护者”，不是“固定格式写文件机”。

---

### 第五层：经验工作区

这是最后真正被维护的东西。

它不是固定结构的死目录，而是：

- 当前方法和经修 agent 共同维护的经验体系

你可以理解成：

**这是整个系统的“长期记忆空间”。**

这里再加一个非常重要的补充：

- 它应该只有一个统一入口文件
- 它不应该默认要求 solve agent 全量读取
- 它应该支持按区域、按主题、按工具说明、按任务类型进行选择性读取
- 它不直接包含模板库，而是只包含最终有效经验
- 当前阶段经修 agent 对它的维护先依赖提示词约束
- 未来阶段再把维护权限精细化成真正的系统边界

---

## 8. 这样做最大的好处是什么

### 好处 1：方法可以无限增加

因为方法只是在调度元操作和经修 agent，
不会一直污染主系统。

---

### 好处 2：元操作可以无限增加

以后你要加：

- 对抗探测
- 候选分支比较
- 版本选择
- 权重更新

都可以作为新元操作加入。

---

### 好处 3：经验体系也可以不断变化

这个非常重要。

以后知识体系不需要一直维持现在这种固定布局，
而是可以随着方法和数据规模变得越来越合理。

---

### 好处 4：系统会更像真正的实验平台

因为以后比较的不是：

- 某个大 prompt

而是：

- 某种方法
- 某种经验维护策略
- 某种经验结构

这会更像真正可研究的系统。

---

## 9. 现在最重要的方向变化

我现在给出的新方向，和之前相比，最关键的变化只有一句话：

**经验体系的结构，不再由我们预先彻底写死，而是交给经修 agent 在约束内维护。**

这一步非常关键，因为它决定了以后系统能不能变大、变复杂、变成熟。

---

## 10. 现在就要先定死的“稳定初始设计”

与其只写一个推进顺序，更重要的是把后面最不想反复推翻的核心抽象先定下来。

我建议现在就把下面 5 件事当成系统的稳定初始设计。

### 第一件：经修 agent 的职责现在就定死

经修 agent 以后永远只做一类事：

- 维护经验工作区

它不负责：

- 直接决定实验策略
- 直接决定哪种反向传播方法更好
- 直接替代 solve agent 去做题

它负责：

- 重写经验
- 拆分经验
- 合并经验
- 调整经验结构
- 新增索引
- 新增工具说明文档
- 维护入口文件

也就是说：

**经修 agent 永远是“知识维护者”，不是“总调度器”。**

这个角色边界一旦定清楚，后面系统就不会乱。

---

### 第二件：经验工作区的共同规则现在就定死

虽然经验工作区未来可以长成很多样子，但有些共同规则应该现在就固定下来。

我建议固定这几条：

1. 永远只有一个统一入口文件
2. solve agent 默认不全量读取，只按入口导航选择性读取
3. 所有经验内容都必须能从入口一路导航过去
4. 经验工作区里可以有：
   - 规则
   - 教训
   - 专题
   - 工具说明
   - 版本区
   - 分区索引
5. 经验工作区不直接包含模板库本体

也就是说：

**结构可以变，但“单入口、可导航、可局部读取”这三个原则不要变。**

---

### 第三件：模板库和最终经验必须永久分开

这个也应该现在就定死。

模板库的作用是：

- 给经修 agent 提供参考结构
- 提供常见组织方式
- 提供常见工具说明模板

但模板库本身不是最终专家经验。

所以以后要明确：

- 模板库是只读参考层
- 经验工作区是最终生效层

solve agent 默认读取的是：

- 经验工作区

而不是：

- 模板库

这能避免以后系统越来越大时，把一堆“参考模板”误当成真实经验。

---

### 第四件：反向传播方法的接口现在就定死

以后每种反向传播方法虽然会很不一样，但它们和系统交互的方式最好统一。

我建议每种方法都固定成下面这个接口思路：

输入：

- 当前 case
- solve 输出
- 评估结果
- 行动轨迹
- 当前经验工作区
- 模板库引用

输出：

- 给经修 agent 的修改意图
- 本轮允许的结构动作
- 本轮验证方式
- 本轮接受标准

这样以后不同方法的差别主要在：

- 反馈包怎么构造
- 对经修 agent 提什么要求
- 验证时看什么

而不是系统接口每次都变。

这会极大提高泛化性和稳定性。

---

### 第五件：未来权限路线现在就定清楚

虽然我们当前阶段不打算立刻上硬权限，但权限路线现在就应该写死。

我建议明确成三阶段：

#### 当前阶段

- 主要靠提示词约束经修 agent
- 主要靠验证 / 回滚控制风险
- 先让系统完整跑通

#### 中期阶段

- 把经修 agent 的活动范围收敛到经验工作区
- 不允许碰数据集和主代码
- 不允许破坏单入口和索引

#### 后期阶段

- 不同方法有不同的结构修改权限
- 可以精细控制：
  - 能不能新增分区
  - 能不能保留多个版本
  - 能不能加权
  - 能不能删旧经验

这样我们现在既不会被权限卡死，
也不会把未来权限体系留成模糊地带。

---

## 10.1 所以真正的下一步是什么

如果按这个稳定设计来做，下一步最合理的顺序就很清楚了：

1. 先定义经修 agent 的正式输入输出契约
2. 先定义 Experience Workspace 的最低不变规则
3. 再让当前顺序法改成“调用经修 agent”
4. 然后再做第二种方法

这样后面不管你再增加多少方法、多少经验结构变化，底层抽象都不用经常改。

---

## 11. 最后一句最重要的话

如果只用一句话总结这次新的系统方向：

**未来系统的核心，不是“固定知识库 + 固定回传”，而是“元操作 + 方法代码 + 经修 agent + 可演化的经验工作区”。**

这才更适合你后面要做的大规模、长周期、多方法实验。
