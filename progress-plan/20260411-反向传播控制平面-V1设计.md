# 反向传播控制平面 V1 设计

## 核心结论

可以做一个统一平台来管理反向传播算法，但这个平台不应该假设所有算法都是同一种模块。

最合适的形态是：

- `Reverse Propagation Control Plane（反向传播控制平面）`

它负责：

- 注册 `Registration`
- 分类 `Classification`
- 装配 `Composition`
- 状态传递 `State Channels`

它不负责直接替代：

- `Judge Layer（判断层）`
- `Maintainer（经修代理）`
- `Governance Layer（版本治理层）`
- `Optimization Layer（全局优化层）`

## 为什么不能做成单一模块平台

原因不是“做不到统一”，而是不同算法的职责天然不同。

例如：

- `add-only` 和 `direct-rewrite` 是 `Maintenance Module（维护模块）`
- `Momentum（动量）` 是 `Constraint Policy（约束策略）`
- `Dual-Axis BP（双轴归因）` 是 `Routing Policy（归因/路由策略）`
- `branch-preserving` 是 `Governance Strategy（治理策略）`
- `adversarial-suite-builder` 是 `Optimization Strategy（优化策略）`

它们的输入、输出、状态依赖和作用层级都不同。

所以平台应该统一管理它们，而不是强迫它们共享同一个执行接口。

## 控制平面要管理的五类对象

### 1. `Maintenance Module（维护模块）`

处理局部经验怎么被改写。

当前已落地：

- `direct-rewrite`
- `add-only-memory`

### 2. `Constraint Policy（约束策略）`

处理修改时的限制条件和跨轮记忆。

当前状态：

- `no-extra-constraint` 已落地
- `text-learning-rate`
- `maintenance-momentum`

后两者先作为规划中的注册对象保留。

### 3. `Routing Policy（归因/路由策略）`

处理错误如何被转成维护请求。

当前已落地或预留：

- `default-judge-routing`
- `batch-aggregate-routing`
- `error-to-edit`
- `dual-axis-bp`

### 4. `Governance Strategy（治理策略）`

处理第三层版本对象怎么被管理。

当前已落地或预留：

- `single-branch-governance`
- `branch-preserving`
- `merge-compare-promotion`

### 5. `Optimization Strategy（优化策略）`

处理第四层如何提出或生成更泛化的候选经验版本。

当前先注册为规划对象：

- `experience-compression`
- `adversarial-suite-builder`
- `sensory-augmentation-suite`

## 状态通道 `State Channels`

统一平台真正有价值的地方，不只是“记住有哪些方法”，而是管理跨层状态。

V1 先定义这些标准状态通道：

- `maintenance_round_history`
- `judge_routing_signal`
- `regression_evidence`
- `campaign_lineage`
- `optimizer_memory`

这些通道的意义是：

- 某些算法并不是一个叶子插件
- 它们需要读历史、读 judge、读回归、读 branch lineage
- 控制平面应该知道谁生产这些状态，谁消费这些状态

## Recipe（配方）装配

V1 里控制平面先管理三条已存在 recipe：

- `sequential-refine`
- `add-only`
- `parallel-batch-5-add-only`

每条 recipe 至少绑定：

- `Execution Strategy（执行策略）`
- `Packetization Policy（打包策略）`
- `Maintenance Module（维护模块）`
- `Constraint Policy（约束策略）`
- `Routing Policy（路由策略）`
- `Acceptance Policy（验收策略）`

这样后面系统就能逐步从“方法名驱动”过渡到“配方驱动”。

## V1 已做什么

- 建立了控制平面的注册表壳子
- 建立了组件分类
- 建立了状态通道定义
- 建立了 recipe 注册
- 让现有 `Local Learning Recipe（局部学习配方）` 从控制平面读取定义
- 让维护模块注册从控制平面读取内建模块定义

## V1 还没做什么

- 没有把所有旧方法系统完全替换成控制平面
- 没有实现真正的 `Momentum`
- 没有实现真正的 `TLR`
- 没有让第三层和第四层完全通过控制平面调度
- 没有做 UI 或可视化管理台

## 最关键的一句话

V1 的目标不是“一次性统一所有反向传播算法的执行方式”，而是先统一：

- 分类语言
- 注册入口
- recipe 组装方式
- 跨层状态通道

这样后面无论新增哪种算法，都能知道它该挂在哪，而不是重新把一二三四层搅乱。
