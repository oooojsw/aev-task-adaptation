# 20260412 长短程统一学习维护 V1 执行计划

## 1. 背景

当前系统已经同时存在两条主链：

- `short task / 短程任务`
  - 典型链路：`solve -> judge -> maintainer -> acceptance`
  - 目标是围绕单 case 的失败与改进，直接维护正式专家经验区。

- `long task / 长程任务`
  - 典型链路：`plan -> work-unit loop -> retry/replan -> completion validate`
  - 目标也是学习并最终服务专家经验区，但当前主要停留在 run 内执行、summary、shadow memory，尚未稳定进入统一 maintainer 后端。

我们前面的讨论已经暴露出几个核心问题：

1. 长程任务虽然有 `learning_units / 学习单元`、`shadow memory / 影子记忆`、`retry bundle / 重试包`，但没有形成真正的“失败后下一次同节点重试会使用”的闭环。
2. 当前长程任务把“是否通过”过度依赖 `validators / 验证器`，导致 `claim / 断言` 为 `false` 时，仍可能被错误放行。
3. 长程任务结束后只写 `archive + shadow summary`，没有稳定产出“可共享给 maintainer 的候选经验包”。
4. 长短程最终都服务正式专家经验区，但目前没有共享的后续经验沉淀出口。

## 2. 设计总纲

本次 V1 采用以下总纲：

- `Unified Entry Later / 统一入口后置`
  - 先不实现自动入口切换。
  - 先保留 `short` 与 `long` 两个显式入口。
  - 后续统一入口只做人类显式指定 `mode: short | long`。

- `Different Execution Kernels / 不同执行内核`
  - 短程与长程执行控制保持分离。
  - 不强行统一 solve loop、judge loop、work-graph loop。

- `Shared Post-Learning Plane / 共享学习后平面`
  - 两类任务最终都要产生可供后续 maintainer 使用的候选经验材料。
  - 长程本次先补出 `candidate package / 候选经验包`。

- `Tracked Experience vs Runtime Memory / 正式经验与运行记忆分层`
  - `Canonical Expert Experience / 正式专家经验`：最终稳定经验区。
  - `Long-task Local Retry Memory / 长程局部重试记忆`：只服务同一 work unit 的下一次 retry。
  - `Long-task Shadow Memory / 长程影子记忆`：run 级沉淀，不直接修改正式专家经验。
  - `Maintainer Candidate Package / 维护候选包`：维护者的统一输入候选层。

## 3. V1 明确要做什么

### 3.1 长程局部重试学习闭环

新增一层 `Local Retry Lesson / 局部重试经验`，目标是：

- 当某个 `work unit / 工作单元` 失败时，不只写 `failure packet / 失败包`。
- 还要再生成一条局部可执行经验。
- 这条经验在同一节点的下一次 `attempt / 尝试轮次` 中必须进入 `retry bundle / 重试包`。

V1 的局部重试经验内容聚焦于：

- 上一次到底失败在哪里
- 不应该重复什么
- 下一次优先改什么
- 下一次提交 claim 前应该跑哪些自检

### 3.2 长程成功判定收紧

当前问题：

- `validator pass / 验证器通过` 过强
- `claim false / 断言失败` 过弱

V1 规则改为：

- 只有 `claim.claimedSuccess === true`
- 且当前 unit 所有 validators 均通过
- 才允许把该 unit 标记为 `verified`

否则一律进入失败路径：

- 写 `failure packet`
- 写 `retry journal`
- 写 `local retry lesson`
- 进入同节点下一轮 retry 或 replan

### 3.3 长程 retry bundle 分层

当前 bundle 只有：

- `recentClaims`
- `recentFailurePackets`
- `relevantScratchUnits`
- `relevantLearningUnits`
- `relevantShadowMemory`

V1 改为显式补出：

- `sameUnitLastFailure / 同节点最近失败`
- `sameUnitRetryLessons / 同节点局部重试经验`
- `sameUnitRecentClaims / 同节点最近断言`
- `dependencyEvidence / 依赖节点证据`

这样 agent 不需要自己从混合上下文里猜“上次我为什么死”。

### 3.4 长程执行输出补充 retry 协议字段

执行 prompt 增加 retry 协议：

- 如果当前是 retry attempt，则 agent 必须说明：
  - `retry_ack / 我理解上次失败点`
  - `strategy_change / 这次改变了什么策略`
  - `self_checks_run / 这次做了哪些自检`

V1 目的不是做复杂审计，而是先把“有没有真的吸取上次失败”做成结构化记录。

### 3.5 长程候选经验包

长程 run 完成后，不管成功失败，都保留：

- `archive record / 归档记录`
- `shadow memory record / 影子记忆记录`

另外补充：

- `candidate package / 候选经验包`

候选经验包的目标不是立刻改正式专家经验，而是给统一 maintainer 后端准备输入。

V1 候选经验包至少包含：

- run 基本信息
- task family / domain tags
- final summary
- failure packet refs
- learning unit refs
- retry lesson refs
- summary / progress / task spec refs
- promotion hint

## 4. V1 明确不做什么

本次不做以下内容：

1. 不实现自动 `short / long` 判定。
2. 不把长程直接接入短程现有 `knowledge maintainer / 知识维护者` 实际执行。
3. 不直接修改正式专家经验区。
4. 不做第四层经验优化层。
5. 不做长短程统一 solve kernel。

## 5. 本次代码落地方向

### 5.1 长程合同与仓储层

新增或补强：

- `LongTaskRetryLesson`
- `LongTaskCandidatePackage`
- run 级 `retry_lessons.jsonl`
- `buildRetryInputBundle()` 的分层注入
- `writeLongTaskCandidatePackage()` 或同类写入函数

### 5.2 长程 runner

补强：

- 失败时同步写 `retry lesson`
- `claim false` 也进入失败路径
- finalize 时生成 candidate package

### 5.3 长程 prompts

补强：

- retry 协议
- 要求 agent 在 retry attempt 时显式说明策略变化

## 6. 测试原则

测试必须从“最小初始包”出发，不使用历史成功路线。

具体原则：

1. 使用当前最小化后的真实长程任务包：
   - `auto-evolve/real-long-tasks/try4-machine-equipment-e2w`
2. 运行前清空该任务包的运行期产物：
   - `outputs/`
   - `workspace/`
3. 保留原始材料、任务目标、skills、最小 validators。
4. 不回填历史成功脚本，不人工补路由。
5. 测试目标优先验证：
   - 同节点失败是否触发 retry memory
   - retry bundle 是否真的带入上次失败经验
   - candidate package 是否生成

## 7. V1 成功标准

本次实现完成后，至少要满足：

1. 长程 work unit 如果 `claim false`，不会再被 validator 假通过掩盖。
2. 某个 work unit 一旦失败，下一次 attempt 的 bundle 能看到它自己的失败原因与局部重试经验。
3. run 结束后能生成独立的 long-task candidate package。
4. 整个测试过程从最小初始包起跑，不依赖中间污染产物。

## 8. 后续衔接
