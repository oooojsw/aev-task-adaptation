# 工作区管理逻辑说明

这份说明只解释当前系统如何管理 Experience Workspace，也就是专家经验工作区。

当前系统应把工作区理解成两个平面：

- 经验平面
- 运行时侧车平面

## 1. 工作区是什么

Experience Workspace 是系统当前真正保存“最终专家经验”的地方。

它不是模板库，也不是运行日志目录。

它现在允许两类内容：

- 专家经验 Markdown 文档
- 受控的本地 helper assets
  - 只能放在 `tools/` 或 `skills/`
  - 目前只允许文本型资产，例如 `SKILL.md`、Python 脚本、JSON/TOML/YAML/TXT 等

## 2. 工作区的基本合法性

当前系统会把一个工作区视为“合法”，至少需要满足这些条件：

- 有且只有一个入口文档
- 入口文档必须属于专家经验 Markdown 体系
- 必须保留 `change_log.md`
- 专家经验 Markdown 文档应带有可识别的 `auto-evolve-role`
- helper assets 只能位于 `tools/` 或 `skills/`
- 不允许出现系统不认可的杂项文件

但要注意：

- `.opencode/` 这种运行时侧车目录不再属于经验平面
- 它允许存在，但不属于专家经验内容

换句话说，工作区不是“能写点东西就行”，而是必须满足一组结构约束。

## 3. 为什么系统会自动回滚

系统自动回滚，通常不是因为模型没输出内容，而是因为：

- 输出后的工作区结构不合法
- 经修后当前 case 仍没修好
- 经修后回归样本退化
- 后置判断策略拒绝接受这次修改

其中“工作区结构不合法”这一类，最常见的表现是：

- 新建了不该出现的隐藏目录或临时目录
- 新增 Markdown 文档却没有清晰角色
- 把 helper 资产放到了 `tools/` / `skills/` 之外
- 丢失入口文件或 change log

现在 `.opencode/` 不再属于这类非法内容；它被视为运行时侧车，而不是经验污染。

## 4. bootstrap 时的管理逻辑

bootstrap 不是直接在原工作区上盲改。

当前流程是：

1. 先读取原始工作区快照
2. 写入最小种子工作区
3. 让 bootstrap session 在这个种子上生成初始经验
4. 读取 bootstrap 后的工作区结果
5. 对结果做布局合法性校验

如果校验通过：
- 保留 bootstrap 结果

如果校验不通过：
- 自动恢复到 bootstrap 前的种子工作区
- 在运行目录中记录 `rolledBackInvalidWorkspace: true`

所以 bootstrap 的自动回滚，本质上是一层“结构守门”。

## 5. learn / maintain 时的管理逻辑

在普通学习链路里，Experience Workspace 也不是直接改完就算成功。

当前流程更像：

1. solve 失败后，准备反馈包
2. pre-judge 判断是否值得进入维护
3. 如果允许维护，先保存维护前快照
4. 经修 Agent 修改工作区
5. 读取维护后的工作区结果
6. 先做工作区布局校验
7. 再做 verify / regression / post-judge
8. 最后决定接受还是回滚

所以维护后的工作区至少要通过两层门：

- 结构门
- 效果门

## 6. 工作区快照与回滚

系统现在会在关键阶段保存工作区快照，用来做：

- diff
- 变更记录
- 验证失败后的恢复
- 运行目录留档

也就是说，工作区回滚不是“随缘还原”，而是基于明确快照恢复。

这里有一个重要边界：

- 快照只记录经验平面
- `.opencode/` 这类运行时侧车不进入快照
- rollback 只恢复经验平面，不触碰运行时侧车

## 7. 文档和 helper assets 的区别

当前系统会把工作区内容分成两类：

- `documents`
  - 专家经验正文
  - 面向 solve / maintainer 的长期知识
- `assets`
  - 本地 helper 工具或技能资产
  - 只在 `tools/` / `skills/` 下合法

这两类内容都会进入：

- 工作区快照
- diff
- 回滚
- 运行元数据

但它们语义不同：

- 专家经验文档是“知识本体”
- helper assets 是“知识辅助执行工具”

另外现在还有第三类：

- `runtime sidecar`
  - 例如 `.opencode/`
  - 属于 OpenCode 运行时生态
  - 可以承载全局规则要求的日志文件，例如 `test_records.md`
  - 但不属于最终专家经验
  - 不进入经验 diff、经验回滚、经验快照和版本树

## 8. 为什么要保留这层工作区管理

如果没有这层工作区管理，系统会很容易出现这些问题：

- 模型把临时草稿误写进最终经验区
- 工作区越改越乱，最后 solve agent 无法导航
- 方法之间互相污染，难以比较
- 出错后没法稳定回滚

所以工作区管理层的作用，不是限制创造力，而是保证：

- 经验可以长期维护
- 结构可以持续演化
- 失败后可以安全恢复

## 9. 当前状态的重点

当前系统已经支持：

- 专家 Markdown 文档
- 受控 helper assets
- 布局合法性校验
- 关键阶段快照
- 自动回滚

当前还没有做得很细的部分包括：

- 更细粒度的加载策略
- 更细粒度的维护权限等级
- 更大型经验体系下的分区读取规则

这些后面会继续演化，但不影响当前工作区管理主链。
