# Auto Evolve Session Monitor 监控系统显示说明

> 编写日期：2026年4月11日
> 面向读者：非技术人员，需要理解监控系统展示内容的含义

---

## 一、监控系统是什么

Auto Evolve 在运行过程中，会启动一个**实时监控服务**（默认地址：http://127.0.0.1:4219）。

它的作用是让你在浏览器里**实时看到当前有哪些任务在跑、跑到哪一步、刚刚做了什么**。

每间隔几秒（默认2秒）会自动刷新一次，也可以手动点击"立即刷新"。

## 三、每个数字卡片的含义

| 卡片名称 | 含义 |
|---------|------|
| **总数** | 当前监控范围内所有 session 的总数量 |
| **运行中** | 正在执行的 session（绿色圆点） |
| **重试中** | 任务失败了，正在自动重试（黄色圆点） |
| **已完成** | 正常结束（蓝色圆点） |
| **错误** | 出错了（红色圆点） |
| **已归档** | 历史 session，已结束并归档（紫色圆点） |

## 四、表格每列的含义

### 4.1 Session（会话ID）

每个任务在系统中有一个唯一的 ID，格式类似 `ses_28489d806ffea04lLFcnygj4gN`。

这是内部标识符，一般不需要关心具体内容。

### 4.2 状态

| 状态 | 含义 |
|------|------|
| **running** | 正在执行中 |
| **idle** | 空闲等待中 |
| **retry** | 执行失败，正在重试 |
| **done** | 正常结束 |
| **error** | 出错了 |
| **archived** | 已归档的历史记录 |

### 4.3 步骤（Step）

描述当前 session 正在做什么操作，显示的是系统内部的操作名称。

常见值：

| 步骤 | 含义 |
|------|------|
| `step` | 正在执行一个操作步骤 |
| `tool:read` | 正在用工具读取文件 |
| `tool:write` | 正在用工具写入文件（注意：目前此值不会出现在监控中，详见后文"已知限制"） |
| `text` | 正在输出文字回复 |
| `reasoning` | 正在思考/推理 |
| `awaiting-assistant` | 等待模型响应 |
| `done:stop` | 正常结束并停止 |
| `retry #N` | 正在进行第N次重试 |
| `idle` | 空闲状态 |

### 4.4 最近动作（Recent Actions）

**最重要的一列。** 显示最近6条实际操作，按时间顺序从旧到新排列。

每条动作包含两部分：
- **动作标签**（action-label）：动作的类型
- **动作细节**（action-detail）：动作的具体内容

常见动作标签：

| 动作标签 | 含义 |
|---------|------|
| `read:completed` | 读取文件完成（此时 detail 会显示读取的内容片段） |
| `reasoning` | 模型的思考内容（此时 detail 会显示思考片段） |
| `assistant_text` | 模型输出的文字回复 |
| `step_start` | 开始一个操作步骤 |
| `step_finish:tool-calls tokens:21762` | 结束一个步骤，共调用了 21762 个 token |
| `assistant_error` | 模型执行出错 |

**注意事项：**
- `reasoning` 动作的 detail 显示的是模型**思考的前 160 个字符**，不是完整的思考内容
- `read:completed` 动作的 detail 显示的是**读取内容的前 160 个字符**
- `write` 工具（写文件）的完成状态**目前不会出现在 recent actions 中**，这是一个已知的监控限制（详见后文"已知限制"）

### 4.5 最近更新

该 session 最后一次有动静的时间。格式：`2026/4/11 15:34:04`。

### 4.6 目录

该 session 相关文件存放的目录路径。

### 4.7 标题 / 细节

显示任务的名字，以及额外的一些上下文信息：

- **标题（title）**：任务的名称，格式类似 `auto-evolve solve case-006 attempt 1`，意思是"正在解决 case-006，这是第1次尝试"
- **最近用户输入（user）**：用户给模型的最新指令片段
- **父Session ID（parent）**：如果这是一个子任务，显示它从属的父任务 ID

## 五、一次完整的 Auto Evolve 任务生命周期

假设你启动了一个 `run-round` 命令，让系统自动学习多个 case，监控中会看到以下典型流程：

### 阶段一：Bootstrap（初始化知识包）

| Session | 状态 | 步骤 | 最近动作 |
|---------|------|------|---------|
| ses_xxx | 运行中 | tool:read | reasoning: 先读取经验模板库... |

系统第一次运行时，会调用 AI 模型从训练 case 中生成初始的"经验知识包"（一组 Markdown 文件）。此时你看到的 `reasoning` 动作会包含模型正在阅读和分析案例内容。

### 阶段二：Solve（解题）

| Session | 状态 | 步骤 | 最近动作 |
|---------|------|------|---------|
| ses_xxx | 运行中 | tool:read | read:completed 正在读取 case-001 的材料... |

系统开始解决一个具体的 case：
- `reasoning` 动作显示模型在思考任务
- `read:completed` 显示模型在读取相关文件
- `tool:read` 步骤表示模型在调用"读取文件"工具

### 阶段三：Judge（评判）

| Session | 状态 | 步骤 | 最近动作 |
|---------|------|------|---------|
| ses_xxx | 运行中 | text | reasoning 评估当前输出是否符合预期... |

解题完成后，系统会调用"软法官"（soft judge）来判断答案是否正确。此时 `reasoning` 动作显示的是法官模型的评判思路。

### 阶段四：Knowledge Maintain（知识维护）

如果解题失败，系统会启动知识维护流程：

| Session | 状态 | 步骤 | 最近动作 |
|---------|------|------|---------|
| ses_xxx | 运行中 | reasoning | reasoning 正在分析失败原因，更新经验... |

此时模型在分析为什么失败，然后把新的经验写入知识包文件。**但由于监控限制，你看不到"正在写文件"这个动作本身，只能看到分析过程（reasoning）。**

### 阶段五：回归测试（Regression）

| Session | 状态 | 步骤 | 最近动作 |
|---------|------|------|---------|
| ses_xxx | 运行中 | step | step_finish:tool-calls tokens:xxxx |

系统会用之前已解决的 case 来验证新学到的知识是否破坏了已有能力。此时会反复出现 `read:completed` 和 `reasoning`，显示模型在用其他 case 做验证。

### 阶段六：结束

| Session | 状态 | 步骤 | 最近动作 |
|---------|------|------|---------|
| ses_xxx | 已完成 | done:stop | 暂无动作 |

## 七、已知限制

### 7.1 看不到"写入文件"的动作

**现象：** recent actions 里只有 `read:completed` 和 `reasoning`，从未出现过 `write:completed`。

**原因：** 这是当前监控系统的一个设计限制。当模型执行"写文件"工具时，系统确实记录了这个操作，但监控界面在提取最近动作时，没有把写入动作纳入 recent actions 显示。

**实际情况：** 知识维护流程中模型确实在写文件，只是监控界面看不到这个动作。你可以通过查看 `runs/` 目录下对应 session 的输出文件，来确认文件写入的内容。

**影响：** 不影响系统正常运行，只影响实时观察体验。你仍然可以通过以下方式确认写入了：
- 查看 `knowledge-pack/` 目录下的 Markdown 文件修改时间
- 查看 session 输出目录里的执行报告

### 7.2 reasoning 内容只显示前 160 字符

模型的思考过程（reasoning）通常很长，但监控界面只显示前 160 个字符。

这是故意的设计——目的是让你快速扫一眼模型在想什么，而不是看完整的长篇思考。

### 7.3 刷新间隔 2 秒

如果操作执行得非常快（比如只用了 1 秒），可能刚好错过某个动作，被下一轮刷新覆盖。这是轮询设计的固有限制，不是 bug。

## 八、常见问题

**Q：某个 session 一直显示"运行中"，但我等了很久没动静？**
A：可能是模型正在执行一个很长的 reasoning（思考），或者在等待 API 响应。可以观察 recent actions 里的 `reasoning` 动作是否在更新。如果 token 消耗数（`tokens:21762`）在增加，说明还在工作。

**Q：显示"错误"状态怎么办？**
A：查看该行"标题/细节"列，会显示具体的错误信息。常见原因包括：API 请求超时、文件权限问题、JSON 格式错误等。

**Q：我想看一个已经归档的 session 还有可能吗？**
A：可以。"已归档"只是状态为 archived，不影响查看。调整"显示数量"可以包含更多 session，找到对应 ID 即可。

**Q：刷新的内容是实时的还是滞后的？**
A：每隔 2 秒（默认）轮询一次，有最多 2 秒的延迟。同时手动点击"立即刷新"可以立即获取最新状态。

## 九、总结速查表

| 你想知道的 | 去哪看 |
|-----------|-------|
| 现在有多少任务在跑 | 看顶部数字卡片 |
| 具体哪个任务在做什么 | 看表格的"步骤"列 |
| 模型在想什么/读到了什么 | 看"最近动作"中的 `reasoning` 和 `read:completed` |
| 模型有没有在写文件 | 目前监控看不到，用别的方式确认（见7.1） |
| 任务有没有正常结束 | 看"状态"列是否为"已完成" |
| 失败的原因是什么 | 看"标题/细节"列 |
| 任务消耗了多少算力 | 看 `step_finish:tool-calls tokens:数字`，数字越大消耗越多 |
