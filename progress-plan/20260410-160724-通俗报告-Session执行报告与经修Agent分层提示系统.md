# 通俗报告：Session 执行报告与经修 Agent 分层提示系统

## 1. 这次要解决的核心问题

我们现在已经知道一件很重要的事：

- 经修 agent 不能只看“最后答错了什么”
- 它还要看“失败 agent 当时到底是怎么一步一步做的”

否则会出现这些问题：

- 它不知道为什么会调错工具
- 它不知道哪些探索是空跑
- 它不知道哪里开始走偏
- 它只能看到结果，无法总结行为教训

所以接下来系统必须多出一个正式能力：

**给每一个 session 生成一份完整但可读的执行报告。**

这份报告不是散落在很多文件里，而是：

**一个 session 对应一个单独文件，按顺序记录这个 session 做了什么。**

---

## 2. 什么叫“Session 执行报告”

你可以把它理解成：

**这个 session 的完整行动录像文字版。**

它不是一句摘要，也不是只保存工具失败，而是按顺序写清楚：

- 这个 session 什么时候开始
- 做了几个 step
- 每一步调了什么工具
- 每个工具的输入大概是什么
- 每个工具的输出大概是什么
- 有没有失败
- assistant 输出了什么
- 最后是怎么结束的

但为了避免文件太大：

- 长文本要截断
- 大 JSON 要截断
- 大输出只保留前面关键部分

也就是说，它是：

**完整顺序 + 关键截断版**

---

## 3. 为什么一定要“一 session 一个单文件”

因为经修 agent 后面需要的是“读一份完整案件材料”，而不是在十几个文件之间跳来跳去。

如果还是像现在这样拆成：

- `events.json`
- `action_trace.md`
- `tool_failures.json`
- `response.txt`

那对人类调试还行，但对经修 agent 不够自然。

所以后面每个 session 应该都有一个统一入口，比如：

- `session_execution_report.md`

这样经修 agent 只需要拿到这个文件路径，就能自己去读。

这份文件应该放在**具体实验目录 / 具体 case 目录 / 具体 attempt 目录**下面，和这次运行强绑定，不要散到别处。

---

## 4. 经修 agent 后面应该看到哪些 session 报告

不是所有方法都看同样的 session。

这件事必须交给“反向传播方法”自己决定。

也就是说：

**不同方法，自己定义应该把哪些 session 报告交给经修 agent。**

### 举例

### 顺序修正法

它最需要看：

- 当前失败的 `solve` session 报告
- 当前失败的 `verify` 结果
- 必要时再看回归 session 报告

### 对抗测试法

它可能更需要看：

- 原始 `solve` session 报告
- `adversarial probe` session 报告
- 某个失败分支的对抗结果

### 多候选权重法

它可能需要看：

- 多个候选 solve / maintain session 报告
- 每个候选分支的验证结果

所以系统不应该写死：

- “经修 agent 永远只看 action trace”

而应该改成：

- “每个方法自己决定给经修 agent 哪些 session 报告”

---

## 5. 经修 agent 的提示词以后不该是一整坨

现在最容易出问题的地方，就是把所有要求都堆到一个 prompt 里。

后面应该拆成两层。

### 第一层：经修 agent 自己的通用内核提示词

这是不管什么方法都要有的基础人格和基础操作定义。

这层主要定义：

- 你是谁
- 你的职责是什么
- 你维护的是 Experience Workspace
- 你只能修改经验体系，不改数据集和主代码
- 你要保持单入口
- 你可以做哪些“经验元操作”

例如这些元操作：

- 新建规则模块
- 合并两个规则文件
- 拆分一个过大的规则文件
- 新建工具说明文档
- 增加失败教训模块
- 更新入口导航
- 标记某个模块已过时

注意：

这里说的元操作，不是代码函数，而是**经修 agent 在经验体系层可以做的标准动作定义**。

### 第二层：每种反向传播方法的专属补充提示词

这层不讲“你是谁”，而讲：

- 这次你要重点看什么
- 这次更偏向保守修复还是结构重组
- 这次应该优先保留单版本还是允许形成多版本经验
- 这次更重视当前 case 修复，还是更重视全局稳定
- 这次需要参考哪些 session 报告

所以后面经修 agent 的完整提示词应该是：

**通用内核提示词 + 方法专属补充提示词 + 当前运行时上下文**

而不是一份大 prompt 管全部。

---

## 6. Experience Workspace 后面应该怎么理解

Experience Workspace 以后不应该再被看成固定目录。

它应该被看成：

**经修 agent 维护的最终专家经验工作区。**

它有几个长期不变的共性：

- 必须有且只有一个入口文件
- 最终只保存真正有用的专家经验
- 模板库不直接算进最终经验
- 空白 solve agent 不应该全量读完，而应该从入口出发按需选择性读取
- 可以有规则文件、例外文件、工具说明、任务路由、分区索引等

但它的具体结构不应该被系统写死。

也就是说：

- 现在的 `rule-chain.md`、`output-contract.md`
- 未来可能变成更复杂的分区结构

这都应该允许。

---

## 7. 模板库和最终经验必须继续分开

模板库的作用是：

- 给经修 agent 提供结构灵感
- 告诉它大型体系常见怎么组织

但模板库本体不应直接进入最终经验区。

因为最终经验区应该只保留：

- 真正被案例证明有效的东西

而不是模板说明。

---

## 8. 未来系统应该怎么跑

后面完整逻辑应该是这样：

1. solve agent 跑某个 case
2. 系统为这个 solve session 生成一份单文件执行报告
3. 评估器判断是否失败
4. 反向传播方法决定：
   - 需要哪些 session 报告
   - 需要哪些额外失败材料
5. 系统把这些路径交给经修 agent
6. 经修 agent 读取：
   - Experience Workspace
   - 模板库
   - 方法补充要求
   - session 执行报告
   - 其他失败材料
7. 经修 agent 修改经验工作区
8. 系统再做验证、接受或回滚

---

## 9. 这套设计最大的好处

### 好处 1

经修 agent 不再只看“错了什么”，而是能看“怎么错的”。

### 好处 2

不同反向传播方法可以有不同的反馈包设计，不会互相污染。

### 好处 3

经修 agent 的基础职责稳定下来，后面方法越多，系统越不容易乱。

### 好处 4

大型经验体系未来更容易扩展，因为经验结构不再被写死。

### 好处 5

后续做 Git-tree、双分支实验、对抗测试时，都会更自然。

---

## 10. 这次设计定下来的关键原则

### 原则 1

每个 session 都应该有一个完整顺序版执行报告。

### 原则 2

执行报告应该是单文件，不是碎片化文件集合。

### 原则 3

经修 agent 拿哪些 session 报告，由反向传播方法自己决定。

### 原则 4

经修 agent prompt 必须拆成：

- 通用内核
- 方法专属补充
- 运行时上下文

### 原则 5

Experience Workspace 是最终经验，不是模板仓库。

### 原则 6

Experience Workspace 必须保留单入口，但具体结构允许演化。

---

## 11. 接下来真正要做什么

按合理顺序，后面应该这样推进：

### 第一步

先定义 Session 执行报告格式。

### 第二步

让每个 solve / maintain / verify / regression session 自动生成自己的单文件报告。

### 第三步

把经修 agent prompt 拆成：

- 核心提示词
- 方法补充提示词

### 第四步

让每种方法自己定义：

- 给经修 agent 提供哪些 session 报告
- 给哪些额外失败材料

### 第五步

再继续扩展新的反向传播方法。

---

## 12. 一句话总结

这次设计的本质是：

**让经修 agent 从“只看结果修文件”，升级成“能看完整行为路径、再按方法要求维护经验体系”的真正知识维护者。**
