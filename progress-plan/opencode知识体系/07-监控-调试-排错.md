# 监控、调试与排错

## 1. 为什么要专门讲监控

因为如果没有监控，OpenCode 在你眼里就只剩下：

- 最终答案
- 或者最终报错

但真正决定系统能不能长期进化的，是：

- 它中间做了什么
- 卡在哪
- 是工具错了还是模型错了
- 是权限问题还是路径问题
- 是 session 崩了还是只是方法没学会

## 2. 当前可用的监控方式

现在至少有两类：

### 2.1 OpenCode 自带 session monitor

终端里可以看：

- 有哪些 session
- 当前状态
- 当前 step
- 最近 detail

### 2.2 OpenCode 自带 session dashboard

浏览器里可以看：

- session 列表
- 状态
- step
- 标题
- 更新时间

### 2.3 我们项目自己的外部 dashboard

`auto-evolve` 还额外接了一层外部 dashboard。

它的目标不是替代 OpenCode，而是：

- 在实验运行时自动拉起
- 帮你盯实验相关 session
- 持续自动刷新

## 3. 一次 session 最值得先看的文件

在当前项目里，如果你想知道某个 session 到底干了什么，优先看：

### 3.1 `session_execution_report.md`

这是最适合人看的。

它会按顺序讲：

- step
- tool
- 输入输出摘要
- 错误
- 行为总结

### 3.2 `events.json`

这是原始事件流。

适合：

- 深查问题
- 做二次分析

### 3.3 `run.json`

适合看：

- 标题
- 模型
- agent
- paths
- exitCode

### 3.4 `tool_failures.json`

适合快速看：

- 哪些工具挂了

### 3.5 `response.txt`

适合看：

- 最终 assistant 文本到底是什么

## 4. 怎么判断问题出在哪一层

### 如果 `events.json` 几乎没有内容

更像是：

- OpenCode 启动层出问题
- 运行时崩溃
- 模型/provider 接口层失败

### 如果有很多 `tool_use`，但结果错

更像是：

- 行为路径不对
- 经验不足
- Judge / 经修逻辑没修住

### 如果当前 case 修好了，但 regression 掉了

更像是：

- 经修策略太激进
- 经验改坏了旧能力

### 如果最终 response 是空

更像是：

- session 出错
- provider 报错
- 工具链异常中断

## 5. 当前监控系统能直接告诉你什么

比较稳定能看到：

- 正在运行哪个 session
- 现在处于 `running / retry / done / error / archived / idle` 哪种状态
- 现在大概在：
  - `tool:read`
  - `tool:edit`
  - `reasoning`
  - `text`
  - `done:stop`
- 最近几次动作摘要
- 最后一次 user 输入摘要

## 6. 但监控不能替代执行报告

这个边界一定要清楚。

监控更像：

- 实时盯现场

而执行报告更像：

- 事后审计材料

所以：

- 运行时先看监控
- 要深查时再看执行报告和事件流

## 7. 当前排错时最有效的阅读顺序

建议顺序：

1. 先看 `run.json`
2. 再看 `session_execution_report.md`
3. 再看 `tool_failures.json`
4. 如果还不够，再看 `events.json`

## 8. 一句话总结

监控解决的是“现在发生了什么”，  
执行报告解决的是“刚才到底发生了什么”。

这两者都需要。
