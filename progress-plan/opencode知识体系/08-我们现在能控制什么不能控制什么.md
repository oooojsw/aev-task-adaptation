# 我们现在能控制什么，不能控制什么

## 1. 这是最重要的一篇现实文档

因为学习 OpenCode 最容易出现两种错觉：

### 错觉一

“我都能发 prompt 了，应该什么都能控制。”

### 错觉二

“模型都自己思考了，我们其实什么也控制不了。”

这两种都不对。

正确理解是：

**我们已经能稳定控制很多运行面，但仍然有清晰边界。**

## 2. 我们现在稳定能控制的东西

### 2.1 能控制模型

包括：

- 用哪个 provider / model
- variant
- 当前项目默认模型
- 本地 RPM 限流

### 2.2 能控制 session 启动方式

包括：

- 新建
- continue
- session 指定继续
- fork
- title
- 运行目录

### 2.3 能控制输入组织方式

包括：

- 纯路径模式
- 是否使用附件
- 给它哪些参考路径
- 给它哪些权限路径

### 2.4 能控制权限模式

包括：

- 开放模式
- 限制模式
- 某些工具 allow / deny
- 某些路径读写 allow / deny

### 2.5 能控制监控与记录

包括：

- 是否开 dashboard
- session monitor
- session execution report
- run artifacts
- Judge 记录

### 2.6 能控制实验层角色

包括：

- solve
- judge
- maintain
- verify
- regression

也就是说，我们可以决定：

- 什么时候开哪个 session
- 让它扮演什么角色

## 3. 我们现在已经能比较稳定看到的东西

### 能看到

- 工具调用
- 工具输入摘要
- 工具输出摘要
- 工具错误
- assistant 文本输出
- step 开始与结束
- token / cost / finish reason
- session 当前状态
- 父子 session 关系的一部分

### 能整理成正式产物

- `events.json`
- `run.json`
- `tool_failures.json`
- `response.txt`
- `session_execution_report.md`

## 4. 我们现在看不到或看不全的东西

### 4.1 完整私有思维链

这是最关键的边界。

我们现在拿不到：

- 模型脑内完整 chain-of-thought

即使 provider 愿意暴露 reasoning block：

- 那也只是暴露的一部分
- 不等于全部私有思考

### 4.2 provider 内部实现细节

例如：

- provider 内部重试细节
- provider 内部路由
- provider 隐藏上下文处理

### 4.3 OpenCode 没有输出成事件的内部中间态

例如：

- 某些内部 prompt 处理细节
- 未外显的缓存与裁剪过程

## 5. 一个非常重要的现实点

我们现在虽然能控制 OpenCode 很多东西，  
但“最终底层模型到底具体看到的全部上下文”这件事，仍然不能简单等同于：

- 我们写的 `prompt.txt`

因为中间还有：

- OpenCode 自己的 agent/system 组织
- provider 相关处理
- 工具调用产生的新上下文

所以最准确的说法是：

- 我们能控制很多输入和运行条件
- 但不能把 OpenCode 简化成“prompt 原封不动发给模型”

## 6. 当前最值得记住的系统边界

### 我们能控制运行方式

但不能完整控制模型脑内推理过程。

### 我们能看到外显行为

但不能看到全部隐藏状态。

### 我们能通过实验层编排 Session

但 OpenCode 内部仍然有它自己的运行机制。

## 7. 这对你后面学习意味着什么

后面你研究 OpenCode 时，要尽量用下面这个判断框架：

### 问题一

这件事是“模型能力问题”，还是“OpenCode 运行问题”，还是“我们实验层编排问题”？

### 问题二

这件事是“我们能直接控制的”，还是“只能间接影响的”？

### 问题三

这件事是“已经能稳定观测”，还是“只能推测”？

## 8. 一句话总结

我们现在对 OpenCode 已经有了：

- 比较强的运行控制力
- 比较强的行为可观测性

但还没有：

- 对底层模型私有思考的完全可见性
- 对所有内部中间态的完全控制权

这就是当前最真实的边界。
