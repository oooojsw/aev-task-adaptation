# 权限、模型、限流与配置

## 1. 为什么这部分很重要

OpenCode 不是一个裸模型调用。

你每次运行它，实际上都在同时控制这些维度：

- 模型
- agent
- 运行目录
- 权限
- 限流
- 监控方式
- Judge 模式

所以真正的“系统控制力”有很大一部分就在配置层。

## 2. 当前模型配置是怎么管理的

当前项目已经把模型控制抽成单独文件。

也就是说：

- 模型不需要散落在很多脚本里改
- 可以集中指定默认模型和阶段差异

当前已知默认模型是：

- `minimax-cn-coding-plan/MiniMax-M2.7`

当前限流配置里还设置了：

- `requestsPerMinute = 14`

所以当前项目不是完全放开打模型，而是有本地 RPM 控制。

## 3. 当前权限配置是怎么理解的

项目里现在有一套独立的权限模式配置。

当前主要有两种思路：

### 3.1 open

表示：

- 基本不限制 OpenCode 的项目内操作

### 3.2 restricted

表示：

- 通过路径和工具规则限制它能做什么

不过你们后来已经明确过一个阶段性原则：

**当前优先先跑通系统，所以权限先偏开放。**

这也是为什么现在很多实验阶段会让权限处在更开放的状态。

## 4. 权限是在哪一层生效的

要分清楚：

- 不是模型自己知道权限
- 也不是 prompt 里一句话就能真正限制一切

真正会影响 OpenCode 行为的是：

- 运行时 override config
- permission 配置
- 工具是否 allow / deny
- 路径是否 allow / deny

所以权限有两层：

### 4.1 软约束

通过 prompt 告诉 agent：

- 不该做什么
- 应该做什么

### 4.2 硬约束

通过运行时 permission 真的限制：

- 哪些工具能调用
- 哪些路径能读
- 哪些路径能写

## 5. 当前 Judge 也有独立配置

Judge 层现在也不是写死的。

它目前已经有自己的模式配置，例如：

- `soft_plus_hard`

并且还可以指定自动运行哪些本地 Judge Skill。

这说明项目里已经开始形成：

- 模型配置
- 权限配置
- Judge 配置
- 监控配置

这些相互独立的控制体系。

## 6. 监控配置

监控目前也有自己的配置，例如：

- 是否启用
- 是否自动启动
- 监听地址
- 端口
- 刷新间隔
- 是否自动打开浏览器

当前默认监控服务端口是：

- `4219`

## 7. 当前系统对 OpenCode 的一个关键做法

每次任务现在不是共享一个全局运行配置，而是：

- 尽量生成独立的 runtime config 目录

这样做的意义是：

- 避免不同任务相互污染
- 避免运行时崩溃和冲突
- 提高实验稳定性

## 8. 为什么模型和权限一定要分开看

因为它们作用完全不同：

### 模型控制的是

- 智能能力
- 推理风格
- 成本
- 稳定性

### 权限控制的是

- 它能不能动文件
- 它能不能调 bash
- 它能不能访问某些路径
- 它能不能做危险动作

后面如果你要系统性研究 OpenCode，这两者一定不能混。

## 9. 一句话总结

真正能把 OpenCode 控住的，不只是 prompt，  
还包括：

- 模型配置
- 权限配置
- Judge 配置
- 限流配置
- 监控配置

这些合起来，才是运行控制面。
