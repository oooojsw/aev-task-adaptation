# 系统总设计文档（全景版）

## 1. 这套系统到底是什么

这套系统的目标，不是简单地“自动改一个规则文件”，而是：

**从案例中学习，逐步形成一套可演化的专家经验体系，再用这套经验去指导新的 agent 完成任务。**

它最终想做成的是一个长期演化系统，而不是一次性的 prompt 工具。

这意味着系统必须同时处理两类问题：

1. 单次任务怎么完成
- 当前材料怎么解
- 当前 session 做了什么
- 当前失败该怎么总结

2. 长期经验怎么积累
- 哪些教训应该进入专家经验
- 经验体系如何组织
- 经验如何版本化、分支化、回滚和比较

所以这套系统本质上是：

**一个把“单次任务表现”不断翻译成“长期专家经验”的演化系统。**

---

## 2. 系统的两大层面

这套系统始终要分成两个层面来理解。

### 第一层：单次任务层

这一层关心的是：

- 当前来了一个什么任务
- 开哪些 session
- 由哪些 agent 参与
- 产出哪些记录
- 最后是否需要修经验

这一层更像是：

**这一次怎么跑。**

### 第二层：长期经验层

这一层关心的是：

- 最终专家经验体系长什么样
- 如何组织入口、模块、分区、工具说明
- 如何保存版本
- 如何分支、比较和回滚
- 不同方法如何使用不同的经验加载方式

这一层更像是：

**经验系统长期如何存在和演化。**

---

## 3. 单次任务层的总体闭环

单次任务层的最小闭环可以理解成：

**任务输入 -> Worker Sessions -> Session 标准记录 -> Judge Layer -> 经修 Agent -> 后置验证 -> 接受 / 回滚**

这条链的重点是：

- 先执行
- 再判断
- 再决定是否维护经验
- 维护之后还要验证
- 不通过就不能直接留下

---

## 4. 任务（Task）是统一运行单位

以后系统里的每一次运行，都应该统一理解成一种任务。

例如：

- 初始化任务
- bootstrap 任务
- learn 任务
- eval 任务
- verify 任务
- regression 任务
- probe 任务
- maintenance 任务

也就是说：

**bootstrap 不再是系统外的特殊阶段，而只是某种任务。**

这样做的好处是：

- 不同方法可以有不同启动方式
- 不同方法可以决定是否需要 bootstrap
- 后面复杂方法可以自然加入，而不是不断打补丁

---

## 5. Worker Sessions 是干活层

任务真正执行时，会启动一个或多个 Worker Session。

例如：

- solve
- bootstrap
- probe
- verify
- regression

它们的职责非常简单：

**执行任务，并留下标准记录。**

它们不是 Judge，不是经修 Agent，也不是版本管理器。

---

## 6. Session 标准记录层

每个关键 session 后续都应该留下标准化记录。

这些记录不是零散日志，而是正式产物。

至少包括三类：

### 6.1 session_execution_report

作用：

- 记录这个 session 按顺序做了什么
- 包括工具调用、关键输出、错误、结果
- 大段内容允许截断，但顺序必须保留

它更像是：

**行为录像文字版。**

### 6.2 session_learning_log

作用：

- 记录这个 session 在运行过程中即时学到了什么
- 不是最后一次性总结
- 而是边运行边追加

它更像是：

**现场学习笔记。**

### 6.3 session_task_manifest

作用：

- 记录这个 session 原本被要求做什么
- 让后面的 Judge 和经修 Agent 不只知道“做了什么”，还知道“本来应该做什么”

它更像是：

**任务说明书。**

---

## 7. Judge Layer

Judge Layer 是整个单次任务层里非常关键的一层。

它的位置在：

- Worker Sessions 之后
- 经修 Agent 之前

它的职责不是执行任务，而是：

**读取 session 记录，分析问题，决定是否值得启动经验维护。**

也就是说：

- Worker 负责做事
- Judge 负责看这件事做得怎么样
- 然后决定要不要把这次局部失败上升为经验维护

---

## 8. Judge Layer 的核心职责

Judge Layer 至少要回答这些问题：

- 这次失败到底是什么类型
- 这次失败是不是偶然噪音，还是值得沉淀为经验
- 这次更像是规则问题、输出问题、工具问题、行为问题，还是结构问题
- 是否应该启动经修 Agent
- 如果启动，应该给经修 Agent 哪些材料
- 经修以后，后置验证应该重点看什么

所以 Judge Layer 不只是“判对错”，而是：

**把原始 session 记录整理成可用于经验维护的判断结果和维护建议。**

---

## 9. Judge Layer 的三部分结构

Judge Layer 最合理的结构，不是只有一个 Judge Agent，而是三部分：

### 9.1 Runtime Guards

这是永远不能关的系统护栏。

它们负责：

- session 是否正常结束
- 必要产物是否真的生成
- 工作区结构是否损坏
- rollback 是否还能执行
- 基础运行条件是否满足

它们不是“智能判断”，而是：

**系统护栏。**

### 9.2 Hard Judge

Hard Judge 是客观判断能力。

它后续最合理的形态是：

**项目本地的 Judge Skill 工具包。**

例如它们可以做：

- 精确输出比较
- JSON 结构比较
- 工具失败汇总
- 回归前后差异比较
- session 行为统计
- 重复调用统计
- 空探索统计

这些能力的特点是：

- 客观
- 可重复
- 可拔插
- 可按项目替换

### 9.3 Soft Judge Agent

Soft Judge Agent 负责综合分析。

它负责：

- 阅读 session 记录
- 阅读 learning log
- 阅读 task manifest
- 在需要时调用本地 Judge Skills
- 输出统一判断结果

它不是凭空瞎评，而是：

**会调用判断工具的分析员。**

---

## 10. Judge Layer 的两种模式

Judge Layer 后续至少要支持两种模式：

### 10.1 soft_only

含义：

- 不自动运行 Hard Judge
- 由 Soft Judge 自己决定要不要调用本地 Judge Skills

适合：

- 项目差异很大
- 不希望过早把硬规则固定死
- 希望 Soft Judge 更自由地决定怎么判断

### 10.2 soft_plus_hard

含义：

- 系统先自动运行一组指定 Hard Judge
- 再把这些结果交给 Soft Judge
- 最后由 Soft Judge 输出统一判断记录

适合：

- 需要更稳定
- 需要更可比较
- 需要更强约束的项目

---

## 11. 统一 Judge Record

无论系统运行在 `soft_only` 还是 `soft_plus_hard` 模式，

**最后都应该只向下游暴露一份统一 Judge Record。**

这份 Judge Record 的作用是：

- 给经修 Agent 读取
- 给人类查看
- 给后置验证使用
- 给实验比较使用

也就是说：

- `soft_only` 时，它主要来自 Soft Judge
- `soft_plus_hard` 时，它是 Hard + Soft 合并后的统一结果

这样下游不需要自己再去拼“软判断”和“硬判断”。

---

## 12. 经修 Agent 的系统位置

经修 Agent 是整个系统里最关键的桥梁。

它不是简单的“改文件 agent”，而是：

**把局部任务失败翻译成长期经验演化的中枢。**

它正好位于两个层面之间：

- 下接：单次任务层
- 上接：长期经验层

所以它必须同时理解：

- 本次失败是怎么来的
- Judge 是怎么判断的
- 当前方法想怎么修
- 当前经验体系是什么状态
- 最终经验应该如何演化

---

## 13. 经修 Agent 不是什么

经修 Agent 不是：

- solve agent
- judge agent
- 版本管理器
- 纯文件编辑器

它也不应该自己决定整个方法怎么跑。

它只是：

**经验演化事务的执行者。**

---

## 14. 经修 Agent 的内部结构

从系统设计上，经修 Agent 应由下面几个部分构成：

### 14.1 Maintainer Core

这是稳定内核。

负责定义：

- 你是谁
- 你维护什么
- 经验体系的长期不变量
- 你的基础经验维护动作

这部分尽量稳定，不随着方法频繁变化。

### 14.2 反向传播模块

这是经修 Agent 最重要的可插拔部分。

它定义：

- 这次可以怎么改经验
- 允许的改动方式是什么
- 偏保守还是偏激进
- 是直接重写、只增不删、保留变体，还是其他方式

当前第一种方法可以理解为：

- `direct-rewrite`

后面第二种很合适的是：

- `add-only`

以后还可以有：

- subtract-only
- weight-based
- adversarial-memory
- branch-preserving

所以后面不是“方法 = 一个 prompt”，而是：

**方法会调用某种反向传播模块，让经修 Agent 在该模块约束下工作。**

### 14.3 经验加载策略

经修 Agent 后面不能默认每次全量读取经验区。

尤其是经验体系变大以后，这样一定会出问题。

所以经修 Agent 后续应支持：

- 从入口开始加载
- 按任务相关性加载
- 按分区加载
- 按 Judge 推荐加载

不过当前阶段，这部分先保留接口，默认允许全读。

### 14.4 经验维护动作

经修 Agent 对经验区的操作，应始终理解成一组标准维护动作。

例如：

- 新建模块
- 重写模块
- 拆分模块
- 合并模块
- 标记过期
- 调整入口
- 增加工具说明
- 增加失败教训
- 创建分区

这些动作本身应该可增加、可减少、可拔插。

### 14.5 维护级别

经修 Agent 每次维护，不应该永远拥有完全相同的自由度。

后面更合理的是分层：

- 小修补
- 结构重组
- 版本分化

不同反向传播模块决定：

- 这次允许经修 Agent 改到哪一层

不过当前阶段，这部分先保留接口，默认全开。

---

## 15. 经修 Agent 的输入

经修 Agent 的输入应该统一理解成：

**维护请求。**

它至少应包括：

- 当前任务上下文
- 当前方法信息
- 当前反向传播模块
- 当前经验工作区
- 模板库
- baseline
- scripts
- session 记录
- Judge 结果

也就是说，经修 Agent 不应该直接面对一堆散乱输入，而应该总是收到一份标准维护请求。

---

## 16. 经修 Agent 的输出

经修 Agent 每次运行，不应该只留下“改后的经验区”。

它还应留下正式维护产物，例如：

- 维护摘要
- 维护报告
- 变更摘要
- 维护决策日志

这样以后系统才能知道：

- 它为什么这么改
- 它到底改了什么
- 这次属于哪类维护
- 后面重点该验证什么

---

## 17. 后置验证与重试机制

经验维护之后，不能直接默认接受。

后面必须还有：

- verify 当前 case
- regression 检查旧能力
- acceptance 决定接受还是回滚

这里有一个非常重要的原则：

**即便是 `add-only`，也不是无脑追加。**

如果维护后：

- 当前 case 没修好
- 或者旧能力退化
- 或者风险过高

那么这次维护不能直接接受。

但这里也不能“一次失败就彻底打死”。

更合理的设计是：

### 17.1 经修应允许有限重试

也就是说：

- 经修 Agent 改完一次
- 后置验证发现问题
- 系统把“哪里不对”反馈回去
- 再让经修 Agent 尝试下一轮维护
- 最多尝试有限次数，例如 3 次

### 17.2 重试不是简单重复

每次重试都应该带上新的失败信息，例如：

- 当前 case 为什么仍没修好
- 哪个 regression 被改坏了
- 上一轮维护哪里风险太大
- Judge 对上一轮维护的总结是什么

这样经修 Agent 才是在“递进修正”，而不是盲目重来。

### 17.3 最终仍需接受 / 回滚

即使允许经修重试，最后仍然必须有明确结论：

- 接受
- 回滚

所以系统最终不会留下“不知道该不该保留”的中间态。

---

## 18. 长期经验层

长期经验层是整个系统的“记忆世界”。

它不是一次任务里的 prompt，而是系统长期积累下来的经验基础设施。

---

## 19. 模板库

模板库是参考库。

它的作用是：

- 提供结构模板
- 提供入口模板
- 提供分区模板
- 提供工具说明模板
- 给经修 Agent 提供组织灵感

但模板库本身不应直接成为最终专家经验。

---

## 20. Experience Workspace

Experience Workspace 是最终专家经验区。

这是 solve agent、Judge、经修 Agent 最终都围绕的核心知识区。

它的长期特点应该是：

- 只有一个入口
- Markdown 为真源
- 可分区
- 可导航
- 可维护
- 可持续重组

它的具体结构可以变化，但这些基本性质不能丢。

---

## 21. 加载体系

经验体系不是只有存储，还必须有装载逻辑。

因为以后系统变大以后，不可能所有 agent 每次都全量读取。

所以后面应支持：

- 入口优先
- 相关模块优先
- 按任务分区加载
- 按方法分区加载
- 按 Judge 推荐加载

这意味着：

**经验体系除了“怎么存”，还要定义“怎么读”。**

---

## 22. 版本树 / Git-tree

长期经验层最终必须支持版本化。

也就是说：

- 当前经验有一个版本
- 经修后形成新版本
- 不同方法可以走不同分支
- 分支之间可以比较
- 失败时可以回滚
- 长期可以合并和择优

这就是后面 Git-tree 的位置。

它不属于单次任务层，而属于长期经验层。

---

## 23. 整个系统的完整流向

这套系统完整来说，应该这样理解：

1. 来了一个任务输入
2. 方法层决定用什么任务类型和什么运行路线
3. Worker Sessions 去执行
4. 每个 session 留下标准记录
5. Judge Layer 分析这些记录
6. Judge 决定是否需要启动经修 Agent
7. 如果需要，经修 Agent 在约束下维护经验工作区
8. 后置验证决定接受还是回滚
9. 如果不通过，可在限定次数内再次经修尝试
10. 最终经验进入版本树或主经验区

这才是完整闭环。

---

## 24. 这套系统最关键的设计原则

### 原则 1
单次任务层和长期经验层必须分开理解。

### 原则 2
经修 Agent 是桥梁，不是全能大脑。

### 原则 3
反向传播方法不直接改经验，而是通过经修 Agent 的反向传播模块来影响经验。

### 原则 4
经验体系不仅要能存，还要能有选择地读。

### 原则 5
Judge Layer 不只判对错，还决定是否值得维护经验。

### 原则 6
Runtime Guards 应始终存在，不能与可选 Judge 逻辑混为一谈。

### 原则 7
Judge 的硬能力后续应尽量组织成项目本地 Judge Skill 工具包，而不是散落在主流程里。

### 原则 8
任何经验修改最终都必须经过后置验证和接受 / 回滚。

### 原则 9
经修失败后应允许有限重试，但不能无限循环。

---

## 25. 一句话总结

这套系统最准确的定义是：

**一个以任务为运行单位、以 session 标准记录为反馈材料、以 Judge Layer 决定维护时机、以经修 Agent 执行经验演化、以 Experience Workspace 和版本树承载长期专家经验的演化系统。**
