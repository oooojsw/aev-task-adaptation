# 系统总设计文档（全景版）

## 1. 系统是什么

这套系统不是单纯的“自动改规则文件”，而是：

**从案例中学习，逐步形成一套可演化的专家经验体系，再用这套经验去指导新的 agent 完成任务。**

它最终想做成的是长期演化系统，而不是一次性的 prompt 工具。

所以它始终要处理两类问题：

1. 单次任务怎么完成
- 当前任务怎么跑
- 当前 session 做了什么
- 当前失败该怎么总结

2. 长期经验怎么积累
- 哪些教训应该进入专家经验
- 经验体系如何组织
- 经验如何版本化、分支化、比较和回滚

一句话：

**它是一套把“单次任务表现”持续翻译成“长期专家经验”的演化系统。**

---

## 2. 系统的三层结构

### 第一层：单任务执行层

这一层关心：

- 这次是什么任务
- 要开哪些 session
- 各个 session 做什么
- 记录哪些材料
- 是否需要进入经验维护

这一层更像：

**这一次怎么跑。**

### 第二层：经验维护层

这一层关心：

- 当前失败应不应该沉淀成经验
- 应该怎样改经验
- 应该由哪种维护风格来改
- 维护完后是否接受还是回滚

这一层更像：

**局部失败如何变成经验更新。**

### 第三层：经验传播实验层

这一层关心：

- 已有经验如何做更高层传播实验
- 哪个版本更好
- 哪种方法更不容易过拟合
- 哪些分支该保留、合并或晋升

这一层更像：

**经验系统如何长期进化。**

---

## 3. 第一层：单任务执行层

第一层的统一运行单位是 Task。

当前可以统一理解为这些任务类型：

- bootstrap
- solve
- judge
- maintain
- verify
- regression
- post_judge

也就是说：

**bootstrap 不再是系统外的特殊步骤，而是某种任务。**

这样做的好处是：

- 不同方法可以有不同启动方式
- 所有关键 session 都能拥有统一产物
- 后面扩展新方法时，不需要再发明新的平行流程

---

## 4. Worker Sessions

Worker Session 是真正执行任务的 session。

例如：

- solve
- bootstrap
- verify
- regression

它们只负责：

**执行任务，并产出标准记录。**

它们不是 Judge，不是经修 Agent，也不是版本管理器。

---

## 5. Session 标准记录层

每个关键 session 后续都应该留下标准记录。

当前核心记录包括三份：

### 5.1 session_execution_report

作用：

- 按顺序记录这个 session 做了什么
- 包括工具调用、关键输出、错误和结果
- 大段内容允许截断，但顺序必须保留

### 5.2 session_learning_log

作用：

- 记录这个 session 从本次运行中学到了什么
- 总结行为、工具使用、失败线索和可提炼教训

### 5.3 session_task_manifest

作用：

- 记录这个 session 原本被要求做什么
- 让 Judge 和经修 Agent 不只看到“做了什么”，还看到“本来要做什么”

此外，每个 attempt 现在还可以有：

### 5.4 task_index

作用：

- 汇总这一轮 attempt 中有哪些任务
- 每个任务对应的 execution report、learning log、task manifest 在哪里

一句话：

**第一层现在已经不是只有运行结果，而是开始拥有统一任务记录体系。**

---

## 6. Judge Layer

Judge Layer 位于：

- Worker Sessions 之后
- 经修 Agent 之前

它的职责不是执行任务，而是：

**读取任务记录，判断失败类型，决定是否值得启动经验维护。**

Judge Layer 至少要回答这些问题：

- 这次失败是什么类型
- 这次失败是否值得沉淀成经验
- 更像是规则问题、工具问题、输出纪律问题、行为问题还是结构问题
- 是否应该启动经修 Agent
- 如果启动，应给经修 Agent 哪些材料

---

## 7. Judge Layer 的三部分

Judge Layer 由三部分构成。

### 7.1 Runtime Guards

这是永远不能关的系统护栏。

它们负责：

- session 是否正常结束
- 必要产物是否真的生成
- 工作区结构是否损坏
- rollback 是否还能执行

它们不是智能判断，而是：

**系统安全护栏。**

### 7.2 Hard Judge

Hard Judge 是客观判断能力。

当前最合理的形态是：

**项目本地 Judge Skill 工具包。**

例如：

- 精确输出比较
- 工具失败汇总
- session 行为统计

这些能力的特点是：

- 客观
- 可重复
- 可拔插
- 可按项目替换

### 7.3 Soft Judge

Soft Judge 负责综合分析。

它会：

- 读取 execution report
- 读取 learning log
- 读取 task manifest
- 读取 hard judge 结果
- 输出统一的 Judge 结论

它不是凭空主观判断，而是：

**会结合本地判断工具的分析员。**

---

## 8. Judge 的前后两段

Judge 现在不再只存在于维护之前。

### 8.1 Pre-Judge

位于经修之前。

它负责：

- 判断是否值得启动经修
- 给经修 Agent 提供维护方向和重点材料

### 8.2 Post-Judge

位于经修之后。

它负责：

- 读取 verify 和 regression 结果
- 用策略判断这次维护是否应该接受
- 输出接受或重试结论

这意味着：

**系统现在已经从“只有前置 Judge”升级成“前置 Judge + 后置 Judge”的闭环。**

---

## 9. Post-Judge 的位置

Post-Judge 不直接代替 Runtime Guard，也不直接等于旧 acceptance。

它的作用是：

- 对维护后的结果做结构化判断
- 把后置接受逻辑从旧式散落判断中抽出来
- 让不同方法挂不同的后置策略

当前更合理的原则是：

- 前置 Judge 决定是否开始维护
- Post-Judge 决定这次维护是否值得保留
- 最终仍然要能接受或回滚

---

## 10. 第二层：经验维护层

第二层的核心是：

**经修 Agent。**

经修 Agent 不是 solve agent，不是 judge，也不是版本管理器。

它是：

**把局部失败翻译成长期经验更新的中枢维护者。**

它位于：

- 下接第一层任务结果
- 上接长期经验体系

---

## 11. 经修 Agent 的内部结构

从系统设计上，经修 Agent 由以下部分组成：

### 11.1 Maintainer Core

这是稳定内核。

它只定义跨方法共享的不变量，例如：

- 维护的是最终经验工作区
- 保持单入口
- 模板库只是参考
- 最终经验区只保存最终专家经验
- 未来 solve agent 应该从入口开始选择性读取

Maintainer Core 不应该侵入模式层。

也就是说：

- 不应该在核心里写死“可以随便 split / merge / 重构”
- 这些属于方法模块和维护动作层

### 11.2 反向传播模块

这是第二层最关键的可插拔部分。

它定义：

- 这次经验可以怎么改
- 偏保守还是偏激进
- 是重写、追加、局部改，还是其他方式

当前已经有：

- `direct-rewrite`
- `add-only`

以后还可以有：

- subtract-only
- section-local
- weight-based
- adversarial-memory

### 11.3 经验加载策略

它定义：

- 这次经修 Agent 读取经验区的方式

这部分当前先保留接口，默认允许全读。

### 11.4 经验维护动作

它定义经修 Agent 可以进行哪些维护动作。

这些动作应是可增加、可减少、可拔插的。

### 11.5 维护级别

它定义一次维护的自由度有多大。

这部分当前也先保留接口，默认全开。

---

## 12. 经修 Agent 的输入

经修 Agent 的输入应被统一理解成：

**维护请求。**

它至少包含：

- 当前任务上下文
- 当前方法
- 当前反向传播模块
- 当前经验工作区
- 模板库
- baseline
- session 记录
- Judge 结果

也就是说，经修 Agent 面对的不应该是散乱材料，而应该是一份标准维护请求。

---

## 13. 经修 Agent 的输出

经修 Agent 的输出不应只有“改后的文件”。

它还应留下维护产物，例如：

- 维护摘要
- 维护报告
- 变更摘要
- 维护决策日志

这样系统后面才能知道：

- 改了什么
- 为什么改
- 改动风格是什么
- 后置判断该重点看什么

---

## 14. 维护后的后置验证与重试

经验维护之后，不能直接默认接受。

后面必须还有：

- verify 当前 case
- regression 检查旧能力
- post-judge
- 接受 / 回滚

这里有一个非常重要的原则：

**即便是 add-only，也不是无脑追加。**

如果维护后：

- 当前 case 没修好
- 或旧能力退化
- 或后置判断认为风险过高

那么这次维护不能直接保留。

但系统也不能“一次失败就彻底打死”。

更合理的方式是：

- 在单次 attempt 内允许有限维护重试
- 每轮维护后都把失败原因反馈给下一轮
- 达到上限后再真正进入下一次 attempt 或结束

也就是说：

**第二层现在已经开始具备“维护回路”，而不是单次经修。**

---

## 15. 长期经验层

长期经验层围绕以下对象展开：

### 15.1 Experience Workspace

这是最终专家经验区。

它的长期原则是：

- 有单入口
- Markdown 为真源
- 可导航
- 可维护
- 可逐步扩展

### 15.2 Template Library

模板库是参考库。

它提供：

- 结构模板
- 工具说明模板
- 分区模板

但它本身不属于最终经验区。

### 15.3 加载体系

长期来看，经验体系不仅要能存，还要能选择性读取。

当前这一层已经在设计中，但还没有完全展开。

---

## 16. 第三层在当前系统中的位置

第三层是：

**建立在第二层之上的传播实验层。**

它未来负责：

- snapshot
- branch
- campaign
- merge
- promotion

但当前主工作仍然是：

- 先把第一层和第二层真正做稳
- 先让真实专家经验可靠地产出

所以第三层当前先保留底座，不作为当前主要施工对象。

---

## 17. 当前系统最关键的设计原则

### 原则 1

第一层、第二层、第三层必须分层理解。

### 原则 2

Session 不能只留下零散日志，必须有标准记录。

### 原则 3

Judge 不只存在于维护之前，维护之后也需要独立判断层。

### 原则 4

Maintainer Core 只保留共享不变量，不侵入方法模式层。

### 原则 5

反向传播方法应通过模块和扩展影响经修 Agent，而不是把模式逻辑写死在核心里。

### 原则 6

任何经验更新都必须经过后置验证与接受 / 回滚。

### 原则 7

第二层的方法未来会进入第三层，但第三层不会被第二层完全取代。

---

## 18. 一句话总结

这套系统最准确的定义是：

**一个以任务为运行单位、以 session 标准记录为反馈材料、以前后 Judge 决定维护时机和维护结论、以经修 Agent 执行经验演化、以 Experience Workspace 承载长期专家经验、并为未来传播实验层预留版本与分支接口的演化系统。**
