# 系统总设计文档-全景版

## 1. 系统是什么

这套系统不是一个“自动改规则文件的小工具”，而是一套把**单次任务表现**不断转化为**长期专家经验**的演化系统。

它的核心目标是：

- 从带标注的案例中学习
- 形成可持续演化的专家经验体系
- 用专家经验指导新的 solve agent
- 在失败后通过判断、维护、验证、回滚来更新经验
- 在更高层对经验版本做传播实验、比较和治理

一句话：

**这是一个以任务为运行单位、以经验为长期资产、以版本治理为高层实验容器的专家经验演化系统。**

---

## 2. 四层结构

当前总设计按四层理解最清楚。

### `Layer 1: Task Execution Layer（任务执行层）`

回答的问题是：

- 这次任务怎么跑
- 开哪些 session
- 是串行还是并行
- 每个 session 产出哪些标准记录

这一层只负责执行，不负责真正修改专家经验。

### `Layer 2: Local Experience Maintenance Layer（局部经验维护层）`

回答的问题是：

- 一次或一批局部失败，如何转化为一次局部经验维护事务
- 维护风格是什么
- 如何验收、回滚、重试

这一层是当前系统的核心施工层。

### `Layer 3: Version Governance Layer（版本治理层）`

回答的问题是：

- 多个经验版本如何快照、分支、比较、保留
- 哪个候选版本应该成为新的高层实验结果

当前已经有底座，但仍然是最小实现。

### `Layer 4: Generalization & Overfit Control Layer（泛化与过拟合控制层）`

回答的问题是：

- 如何让已有专家经验更泛化、更稳定、更不容易过拟合
- 如何做提纯、压缩、拆分、合并、对抗性优化

这一层当前只完成了设计边界，尚未进入正式实现。

---

## 3. 各层之间的关系

### 第一层到第二层

第一层运行任务，生成标准记录；第二层读取这些记录，把失败转成经验维护。

### 第二层到第三层

第二层负责产生局部维护后的经验结果；第三层负责把这些结果纳入版本治理体系。

### 第四层到第三层

第四层未来不只是提建议，而是会直接生成**优化候选版本**；第三层负责治理这些候选版本的命运，例如评测、比较、保留、淘汰。

### 第四层不会直接改 canonical

第四层未来可以直接修改经验，但只能修改**候选版本 / 优化分支**，不能直接改当前 canonical。

---

## 4. 第一层当前设计

第一层现在已经不再只是零散脚本，而是以 `Task` 为统一理解单位。

当前主要任务类型包括：

- `bootstrap`
- `solve`
- `judge`
- `maintain`
- `verify`
- `regression`
- `post_judge`

其中最重要的变化是：

- `bootstrap` 不再被理解成系统外的特殊阶段，而是某种任务
- 关键 session 现在都有标准记录产物
- 第一层已经开始支持不同执行策略

---

## 5. Session 标准记录体系

关键 session 当前都会保留标准化记录。

### `session_execution_report`

记录这个 session 按顺序做了什么。

包含：

- 工具调用
- 关键输出
- 错误
- 结果摘要

### `session_learning_log`

记录这个 session 在本次运行中学到了什么。

它不是专家经验本体，而是本次任务学习痕迹。

### `session_task_manifest`

记录这个 session 原本被要求做什么。

它的作用是让 Judge 和 Maintainer 不只是看到“做了什么”，还能看到“本来应该做什么”。

### `task_index`

按 attempt 汇总本轮有哪些任务，以及三份主记录分别在哪里。

---

## 6. Judge Layer

Judge Layer 位于：

- Worker 之后
- Maintainer 之前

它的作用不是执行任务，而是：

**判断当前失败值不值得转化为经验维护。**

### 当前 Judge 由三部分组成

#### `Runtime Guards（运行护栏）`

始终开启。

负责：

- session 是否正常完成
- 必要文件是否存在
- 工作区是否损坏
- 基础回滚能力是否仍然可用

#### `Hard Judge（硬判断）`

当前以本地 `Judge Skills` 形式存在。

它们提供客观判断能力，例如：

- exact output compare
- tool failure summary
- session behavior summary

#### `Soft Judge（软判断）`

负责综合：

- execution report
- learning log
- task manifest
- evaluation
- hard judge 结果

并最终输出统一 Judge 结论。

### Judge 分前后两段

#### `Pre-Judge`

在经修之前：

- 判断是否值得维护
- 判断维护大致方向

#### `Post-Judge`

在经修之后：

- 读取 verify / regression 结果
- 给出接受还是重试的结构化结论

也就是说，Judge 现在已经是：

**前置判断 + 后置判断** 的闭环，而不是只有前置路由。

---

## 7. 第二层当前设计

第二层是当前系统的主施工对象。

它围绕 `Knowledge Maintainer Agent（经修 Agent）` 展开。

经修 Agent 当前不是单一 prompt，而是由几部分组成：

### `Maintainer Core`

只保留跨方法共享的不变量，例如：

- 维护的是最终经验工作区
- 保持单入口
- 模板库只是参考
- 最终经验应留在工作区内，不应散落在别处

### `Maintenance Module（维护模块）`

决定这次怎么改经验。

当前已实现：

- `direct-rewrite`
- `add-only`

### `Loading Strategy（加载策略）`

当前主要还是全读，但接口已经预留。

### `Maintenance Ops（维护动作）`

已经做成可插拔体系。

### `Scope Level（维护级别）`

接口已预留，当前默认全开。

---

## 8. 当前 Experience Workspace 设计

当前工作区不是“只有 Markdown 文件”那么简单，而是双平面模型。

### `Tracked Experience Plane（受跟踪经验平面）`

这是真正参与经验治理的内容。

包括：

- 专家 Markdown
- 受控 helper assets
- 入口文件
- change log
- 规则模块、工具说明、失败教训等

这些内容参与：

- diff
- validation
- rollback
- snapshot
- propagation commit

### `Runtime Sidecar Plane（运行时侧车平面）`

这类内容当前以 `.opencode/**` 为代表。

它们允许存在，但：

- 不参与经验 diff
- 不参与 rollback
- 不参与快照
- 不进入第三层 commit

所以 `.opencode` 现在被系统兼容，但不被视为专家经验的一部分。

---

## 9. 第一层新增的 V1 批量内核

当前系统已经进入了第一版 `V1 batch local learning kernel（批量局部学习内核）`。

### 核心思路

不是“5 个 case 同时改同一份经验”，而是：

**5 个 case 并行学习收集，1 个 batch maintainer 串行统一维护。**

### 当前 V1 的组成

#### `Execution Strategy（执行策略）`

已支持：

- `sequential`
- `parallel-batch-5-light-shard`

#### `Packetization Policy（打包策略）`

已支持：

- `single-case-packet`
- `batch-5-aggregate`

#### `Maintenance Module（维护模块）`

当前 batch 已验证：

- `add-only`

### 当前 V1 采用 `light shard`

也就是每个 shard 只做：

- solve
- pre-judge
- learning packet 抽取

不会在 shard 内本地开 maintainer。

### V1 的 batch 流程

1. 冻结一个 batch 基线工作区
2. 5 个 case 并行跑 shard
3. 产出 case 级学习结果
4. 聚合成 `Batch Learning Packet`
5. 开 1 个 batch maintainer
6. 对整批做一次维护写入
7. 跑 verify / regression / post-judge
8. 接受或回滚

一句话：

**并行学习收集，串行统一维护。**

---

## 10. 第三层当前设计

第三层当前已经不是纯设想，但仍然是最小实现。

它当前已经有：

- 快照 / commit 概念
- branch 概念
- campaign 概念
- candidate commit
- 最小可用的 branch 运行容器

当前更重要的一点是：

**第三层已经可以直接复用第一层 + 第二层的 recipe。**

也就是说，第三层不是重新定义一套独立学习器，而是可以直接在 branch workspace 上运行下层 recipe。

但当前第三层还没有做：

- merge
- promotion
- multi-branch compare
- 复杂治理策略

---

## 11. 第四层当前设计边界

第四层当前只完成了概念和接口方向，尚未进入实现。

### 未来第四层的职责

- 读取当前专家经验版本
- 读取历史实验结果
- 读取 optimizer 自己的 memory
- 直接产出一个优化后的候选经验版本

### 未来第四层不会做的事

- 不直接改 canonical
- 不代替第三层做版本治理

### 未来与第三层的交互

- 第四层产出 `Optimization Candidate Package`
- 第三层接收候选版本并治理其命运
- 第三层再把结果反馈回第四层的 optimizer memory

---

## 12. 当前系统最准确的状态判断

如果只看现在的真实实现状态，可以这样概括：

### 已经真正做成的

- 第一层任务化主链
- session 三记录 + task index
- pre-judge + post-judge
- 双平面工作区
- `sequential-refine`
- `add-only`
- `parallel-batch-5-add-only`
- 第三层最小治理底座
- 第三层直接复用下层方法

### 还没有真正做成的

- 第四层优化器
- augmentation / adversarial suites
- 第三层复杂 merge / promotion
- 多分支治理
- 更完整的方法矩阵

---

## 13. 一句话总结

当前系统最准确的定义是：

**一套拥有四层清晰分工、以任务执行为起点、以局部经验维护为核心、以版本治理为高层实验容器、并为未来全局泛化优化预留正式接口的专家经验演化系统。**
