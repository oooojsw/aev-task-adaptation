# 系统能力总览

状态：当前真实实现版

这份文档只回答三件事：

- 系统现在已经能做什么
- 每个模块拿什么作为输入
- 每个模块产出什么并流向哪里

不展开代码实现细节。

---

## 1. 总体能力

当前系统已经具备以下主能力：

- 从数据集读取 case，执行 solve / judge / maintain / verify / regression
- 以顺序学习方式维护专家经验
- 以 add-only 方式维护专家经验
- 以 batch V1 方式并行收集小批量失败经验
- 在维护后做接受 / 回滚
- 把经验快照纳入第三层版本治理
- 用控制平面注册和组织现有反向传播 recipe

## 4. Session 标准记录层

### `session_execution_report`

输入：

- session 运行事件

输出：

- 执行摘要

- Judge

### `session_learning_log`

输入：

- 本次运行中的局部学习内容

输出：

- 本轮即时学习痕迹

流向：

- Judge
- Maintainer

### `session_task_manifest`

- task 参数

- Judge

- session 清单与路径索引

- 人工查看
- 后续追踪

## 5. Judge Layer（判断层）

### 它现在能做什么

- 判断是否值得启动经验维护
- 判断维护后该接受还是回滚
- 输出结构化 judge 记录

### 组成部分

#### `Runtime Guards（运行护栏）`

输入：

- 运行状态
- 必要文件
- 工作区布局

输出：

- 系统级保护结论

流向：

- 中止 / 回滚判断

#### `Hard Judge（硬判断）`

当前已实现的本地 judge skills：

- `exact-output`
- `tool-failures`
- `session-behavior`

输入：

- evaluation
- tool failures
- session records

输出：

- hard check artifacts

流向：

- Soft Judge

#### `Soft Judge（软判断）`

输入：

- execution report
- learning log
- task manifest
- hard check 结果
- evaluation

输出：

- `judge_summary.json`
- `judge_report.md`

流向：

- Maintainer
- 后续 acceptance

### 前后两段

#### `Pre-Judge`

作用：

- 判断是否启动 maintainer
- 识别 failure class
- 提供 suggested targets / session refs

#### `Post-Judge`

作用：

- 读取 verify / regression 结果
- 决定 `accept` 还是 `retry`
- 如果不是 accept，则系统会回滚并把原因喂回下一轮维护

## 6. 第二层：Local Experience Maintenance Layer（局部经验维护层）

### 它现在能做什么

- 接收 judge 结论和 session 记录
- 更新经验工作区
- 支持单 case 维护和 batch 维护
- 维护后做验证、接受、回滚

### 组成部分

#### `Maintainer Core`

输入：

- 工作区
- baseline
- 模板库
- 维护约束

输出：

- 统一的维护基础规则

#### `Maintenance Module（维护模块）`

当前已实现：

- `direct-rewrite`
- `add-only-memory`

输入：

- 维护请求
- 当前工作区
- method extension

输出：

- 实际经验修改

流向：

- verify / regression / post-judge

#### `Loading Strategy（加载策略）`

当前状态：

- 已有接口
- 默认全读

作用：

- 决定 maintainer 可以读哪些工作区内容

#### `Maintenance Ops（维护动作）`

当前状态：

- 已可插拔

作用：

- 定义 maintainer 允许执行的具体操作

#### `Scope Level（范围级别）`

当前状态：

- 已有接口
- 默认全开

作用：

- 限定 maintainer 改动范围

## 10. 当前可运行的方法

### `sequential-refine`

输入：

- 单 case
- 当前工作区
- baseline

输出：

- solve 结果
- judge 结果
- maintain 结果
- acceptance 结果

特点：

- 顺序执行
- `direct-rewrite`

### `add-only`

输入：

- 单 case
- 当前工作区
- judge 结论

输出：

- additive maintenance 结果
- verify / regression / acceptance

特点：

- 顺序执行
- `add-only-memory`
- 支持多轮维护重试

### `parallel-batch-5-add-only`

输入：

- 一批 case
- 当前工作区
- shard solve / judge 结果

输出：

- `Batch Learning Packet`
- batch maintainer 更新
- batch verify / regression / acceptance

特点：

- 5 case 并行轻 shard
- 1 个 batch maintainer 串行写入

## 16. 当前系统最准确的状态结论

如果只看当前真实实现：

### 已经成熟的主干

- 第一层任务主链
- Judge 前后闭环
- 第二层经修主链
- 双平面工作区
- 顺序学习与 add-only 学习
- V1 batch local learning kernel
- 第三层最小治理
- 控制平面 V1

### 还处于接口或预备阶段的

- 第三层复杂治理
- 第四层优化器
- augmentation / adversarial / purification
- 更强的跨层 constraint policy

### 一句话总结

**当前系统已经是一套可以跑通“任务执行 -> 判断 -> 局部经验维护 -> 接受/回滚 -> 最小版本治理”的专家经验演化系统，并且已经开始用控制平面统一管理现有反向传播 recipe。**
