# 当前系统能力总览

状态：当前实现版

这份文档只描述系统现在是什么样、有哪些能力、各模块拿什么输入、产出什么结果、结果流向哪里。

不展开任何代码实现细节。

---

## 1. 系统的核心目标

这套系统的目标是：

- 从带答案的案例中学习
- 逐步形成一套可演化的专家经验体系
- 用这套经验指导新的 session 完成任务
- 在失败后，通过判断系统和经修系统决定是否更新专家经验

可以把它理解成：

**一个把“单次任务表现”不断翻译成“长期专家经验”的实验系统。**

---

## 2. 系统现在分成哪两个层面

### 2.1 单次任务层

这一层负责：

- 这次任务怎么跑
- 开哪些 session
- 记录什么运行信息
- 如何判断这次失败值不值得进入经验维护

### 2.2 长期经验层

这一层负责：

- 最终专家经验放在哪里
- 经验怎么组织
- 模板库怎么供参考
- 后面如何支持更多方法、更多加载方式、更多版本

当前这两个层面已经分开思考，但长期经验层还在持续建设中。

---

## 3. 现在系统支持哪些任务模式

当前已经明确支持两种主要模式：

### 3.1 `eval`

作用：

- 只测试当前经验能不能解题
- 不学习
- 不修改经验

输入来源：

- 当前 case 的材料
- 当前经验工作区
- baseline

输出去向：

- solve 结果
- 评估结果
- session 记录

### 3.2 `learn`

作用：

- 先解题
- 如果失败，再进入 Judge 和经修流程
- 尝试把这次失败转化成专家经验更新

输入来源：

- 当前 case 的材料与答案
- 当前经验工作区
- baseline
- Judge 输入所需的 session 记录

输出去向：

- solve 结果
- Judge 记录
- 经修记录
- verify / regression 结果
- 接受或回滚结果

---

## 4. 当前支持哪些方法

### 4.1 `sequential-refine`

状态：

- 已完整实现
- 是当前默认基线方法

特点：

- 失败后走保守维护路线
- 允许经修 agent 直接改现有经验体系
- 通过 verify 和 regression 决定是否接受

### 4.2 `add-only`

状态：

- 已实现并已完成基础烟测

特点：

- 失败后优先追加经验，而不是大改旧经验
- 倾向新增补充说明、失败教训、工具说明、小模块
- 维护后仍然要经过 verify 和 regression
- 当前已支持单次 attempt 内多轮经修尝试

### 4.3 `adversarial-test`

状态：

- 目前还是方法脚手架
- 还没有正式接成可运行方法

---

## 5. 当前系统支持哪些运行入口

### 5.1 `bootstrap`

作用：

- 从训练案例生成第一版经验工作区

输入来源：

- train split 中的案例
- 模板库
- baseline
- 最小种子经验区

输出去向：

- 第一版经验工作区
- bootstrap session 记录

### 5.2 `run-case`

作用：

- 跑单个 case
- 可选择 `eval` 或 `learn`
- 可选择方法

输入来源：

- 单个 case
- 当前经验工作区
- baseline
- 当前方法配置

输出去向：

- 单个 case 的完整运行目录

### 5.3 `run-round`

作用：

- 按 split 批量跑多个 case

输入来源：

- 指定 split
- 当前经验工作区
- 当前方法

输出去向：

- round 汇总结果
- 每个 case 的独立运行目录

### 5.4 `run-baseline`

作用：

- 统一完成：
  - bootstrap
  - train
  - test
  - scorecard

输入来源：

- 当前方法
- 训练 / 测试切分
- 当前模型配置

输出去向：

- baseline 目录
- scorecard
- 经验区快照

## 6. 当前的数据层

### 6.1 案例集

来源：

- `dataset/cases`

内容：

- 材料
- 标准答案
- case 元信息

### 6.2 训练 / 测试切分

来源：

- `dataset/SPLIT.md`

作用：

- 明确哪些案例用于学习
- 哪些案例只用于测试

当前默认：

- train：`case-001` 到 `case-005`
- test：`case-006` 到 `case-010`

---

## 7. 当前的经验体系

### 7.1 Experience Workspace

这是当前真正的最终专家经验区。

作用：

- 给 solve agent 读取
- 给 Judge 参考
- 给经修 agent 修改

当前特点：

- 以 Markdown 为主
- 有单入口文件
- 可以逐步演化出更多模块
- 当前已经不再强绑定旧的固定文件清单

输入来源：

- bootstrap 生成
- 经修 agent 维护

输出去向：

- solve
- judge
- maintainer
- baseline 快照

### 7.2 Template Library

这是模板参考库，不是最终经验本体。

作用：

- 给 bootstrap 参考结构
- 给经修 agent 参考组织方式

输入来源：

- 项目自带模板

输出去向：

- bootstrap
- maintainer

### 7.3 Baseline 文件

作用：

- 保存用户自己的起始想法
- 提供给 solve / bootstrap / maintainer 作为参考上下文

特点：

- 不是系统控制文件
- 不决定流程
- 当前默认中文

---

## 8. Worker 层现在有哪些能力

Worker 是真正干活的 session。

当前已经有这些主要 worker 类型：

### 8.1 Solve Session

作用：

- 读取当前经验
- 解当前题

输入来源：

- case 材料
- 经验工作区
- baseline

输出去向：

- response
- evaluation
- execution report
- learning log（后续会继续增强）

### 8.2 Bootstrap Session

作用：

- 从训练案例建立初始经验

输入来源：

- 训练案例
- 模板库
- baseline
- 最小种子经验区

输出去向：

- 新的经验工作区
- bootstrap 运行记录

### 8.3 Verify Session

作用：

- 经修后重新验证当前 case 是否修好

输入来源：

- 更新后的经验工作区
- 当前 case

输出去向：

- verify 结果
- verify session 记录

### 8.4 Regression Session

作用：

- 经修前后检查旧能力是否退化

输入来源：

- regression 采样 case
- 当前经验工作区

输出去向：

- regression 摘要
- regression session 记录

---

## 9. Session 记录层现在有哪些能力

每个关键 session 现在都能产出标准记录，当前最重要的是：

### 9.1 `session_execution_report`

作用：

- 记录单个 session 按顺序做了什么
- 包括工具调用、关键信息、错误、输出
- 大段内容会截断，但顺序保留

输入来源：

- session 原始事件流

输出去向：

- Judge
- 经修 agent
- 人类排查

### 9.2 其他运行产物

还包括：

- `events.json`
- `action_trace.md`
- `tool_failures.json`
- `run.json`
- `prompt.txt`

这些共同组成 session 的原始材料层。

---

## 10. 当前 Judge Layer 的能力

Judge Layer 位于：

- Worker 之后
- 经修 Agent 之前

它的作用是：

- 读取 solve 及相关 session 记录
- 判断这次失败值不值得进入经验维护
- 给经修 Agent 产出统一判断结果

### 10.1 Runtime Guards

作用：

- 保障运行链不崩
- 检查基础产物是否存在
- 保证系统有基本护栏

### 10.2 Hard Judge

当前形态：

- 项目本地 Judge Skill 工具包

当前已落地的技能有：

- `exact-output`
- `tool-failures`
- `session-behavior`

它们的输入来源：

- solve 评估结果
- tool failures
- session events

输出去向：

- Hard Judge 结果文件
- Soft Judge

### 10.3 Soft Judge

作用：

- 结合 session 记录和 hard judge 结果做综合判断

当前支持两种模式：

- `soft_only`
- `soft_plus_hard`

当前默认：

- `soft_plus_hard`

Soft Judge 的输入来源：

- execution report
- action trace
- evaluation
- routing
- Judge Skill 结果

Soft Judge 的输出去向：

- `judge_summary.json`
- `judge_report.md`
- 经修 Agent 是否启动的结论

## 11. 当前经修系统的能力

经修 Agent 现在已经不是单个 prompt，而是一个独立维护系统的雏形。

它的职责是：

- 读取失败上下文
- 读取 Judge 结果
- 读取经验工作区
- 在某种反向传播模块约束下维护经验

### 11.1 Maintainer Core

作用：

- 定义经修 Agent 的基础身份和通用规则

### 11.2 Reverse Propagation Module

当前已支持：

- `direct-rewrite`
- `add-only-memory`

作用：

- 决定经修 Agent 这次能怎么改经验

### 11.3 Maintenance Ops

这是经修 Agent 可用的经验维护动作集合。

当前已经做成可拔插体系。

目前已落地的操作能力包括：

- inspect workspace
- inspect templates
- inspect failure context
- inspect session records
- rewrite module
- create module
- append to existing module
- split / merge / deprecate
- create partition
- rewrite entry navigation
- add tool guide
- add failure lesson
- record change

### 11.4 Loading Strategy

当前状态：

- 接口已预留
- 当前默认允许从入口出发、但全工作区可读

### 11.5 Scope Level

当前状态：

- 接口已预留
- 当前默认相当于全权限描述模式
- 还没有细化成硬权限边界

### 11.6 经修输入来源

经修当前主要读取：

- 经验工作区
- 模板库
- baseline
- 当前失败上下文
- Judge 结果
- 选中的 session execution reports

### 11.7 经修输出去向

经修当前会产出：

- 更新后的经验工作区
- maintain summary
- maintain session 记录
- 变更文件清单

## 12. 当前的后置验证与接受层

这是经验维护后的最后一道关。

作用：

- 验证当前题是否真的修好
- 检查旧能力是否被改坏
- 决定接受还是回滚

### 12.1 Verify

输入来源：

- 更新后的经验工作区
- 当前 case

输出去向：

- verify 结论
- verify session 记录

### 12.2 Regression

输入来源：

- regression 采样 case
- 更新后的经验工作区

输出去向：

- regression 前后比较

### 12.3 Acceptance / Rollback

输入来源：

- verify 结果
- regression 结果
- 维护前快照
- 维护后快照

输出去向：

- 接受当前经验修改
或
- 回滚到维护前经验

---

## 13. 当前 add-only 方法额外带来了什么

这是这次新增加的重要能力。

### 13.1 Add-only 方法本身

作用：

- 作为第二种正式反向传播方法
- 通过追加经验而不是大改经验来修复失败

### 13.2 单次 attempt 内多轮经修

当前能力：

- 经修失败后不会立刻一票否决
- 在限定轮数内，可以继续下一轮经修尝试
- 后一轮会读取前一轮失败信息

当前默认上限：

- 每次 attempt 最多 `3` 轮维护

### 13.3 维护轮次独立记录

每一轮维护现在都有独立目录和独立产物。

这意味着：

- 可以清楚看到每轮做了什么
- 可以清楚看到哪一轮被拒绝
- 后面更适合继续扩展更多方法

## 14. 当前的配置能力

### 14.1 模型配置

作用：

- 统一管理默认模型和各阶段模型

当前默认模型：

- `MiniMax-M2.7`

当前还支持：

- 请求频率限制

### 14.2 Judge 配置

作用：

- 管理 Judge 模式
- 管理自动运行哪些 Judge Skill

当前默认：

- `soft_plus_hard`

### 14.3 权限配置

作用：

- 预留运行权限模式切换

当前状态：

- 已有开关
- 当前按你的要求保持开放优先

### 14.4 监控配置

作用：

- 管理外部 session 监控页

当前能力：

- 可以打开外部监控窗口
- 可以持续查看当前 session 状态、步骤和最近动作

- 哪些已经结束

这层的输入来源：

- OpenCode session 事件

## 16. 当前系统已经真正具备的能力总结

当前已经真正能做的事包括：

- 维护训练集 / 测试集切分
- 运行 bootstrap
- 跑单个 case
- 跑 round
- 跑 baseline
- 支持 `eval` 与 `learn`
- 支持 `sequential-refine`
- 支持 `add-only`
- 支持 Judge Layer
- 支持本地 Judge Skills
- 支持经修 Agent
- 支持 session execution report
- 支持 verify / regression / acceptance / rollback
- 支持 add-only 多轮经修尝试
- 支持模型统一配置
- 支持外部监控页

---

## 17. 当前仍然属于“已预留但未完全展开”的部分

这些方向已经定了，但还没完全做成终态：

- 更复杂的 loading strategy
- 更细的 maintenance scope level
- 更强的长期版本树 / Git-tree
- 第三种及更多反向传播方法
- 大型经验体系的分区装载体系
- 更完整的 session learning log 体系
- 后置 Judge 的系统化接入

---

## 18. 一句话总结

现在这套系统已经不是一个“自动改规则的小脚本”，而是一个已经具备：

- 任务运行层
- session 记录层
- Judge Layer
- 经修系统
- 经验工作区
- 多方法扩展能力

的专家经验演化平台雏形。

如果只看当前实现状态，最准确的描述是：

**它已经能稳定地跑“解题 -> 判断 -> 维护经验 -> 验证 -> 接受/回滚”这条闭环，并且已经支持至少两种正式反向传播方法。**
