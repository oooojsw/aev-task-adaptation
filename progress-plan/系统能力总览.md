# 系统能力总览

更新时间：2026-04-12

这份文档只回答三件事：

1. 系统现在已经能做什么。
2. 每个模块吃什么输入、吐什么输出。
3. 下一阶段准备补什么。

---

## 1. 总体能力

当前系统已经具备以下主能力：

- 跑短程任务，并在失败后进入 Judge 和 Maintainer 闭环
- 跑长程任务，并在失败后进入本节点重试学习闭环
- 对短程维护结果执行 verify / regression / accept / rollback
- 对长程 run 输出 summary / shadow memory / candidate package
- 区分正式专家经验与运行时副产物
- 用控制平面统一管理已接入的反向传播 recipe
- 支持顺序学习、add-only 学习、以及 V1 批量局部学习

一句话概括：

**系统已经能从“执行任务”走到“验证结果”再走到“沉淀经验”，并开始进入版本化治理阶段。**

---

## 2. 输入对象

当前系统主要接收四类输入：

### 2.1 Case / Dataset（case 与数据集）

适用于短程任务。

主要包含：

- 输入材料
- 目标输出
- 基线说明
- 训练 / 测试切分

### 2.2 Long Task Package（长程任务包）

适用于长程任务。

主要包含：

- materials
- goal
- validators
- capabilities
- editable paths
- initial expert context

### 2.3 Expert Experience Workspace（专家经验工作区）

这是系统长期维护的经验载体。

主要包含：

- 专家经验文档
- 输出契约
- 检查清单
- 经验规则
- 失败教训

### 2.4 Template / Helper Assets（模板与辅助资产）

主要用于：

- bootstrap
- maintainer
- 格式参考
- 任务模板

---

## 3. 短程任务能力

### 3.1 已实现能力

短程任务当前已经能做：

- `solve`
- `pre-judge`
- `maintain`
- `verify`
- `regression`
- `post-judge`
- `accept / rollback`

### 3.2 当前可运行方法

当前已接入并可运行：

- `sequential-refine`
- `add-only`
- `parallel-batch-5-add-only`

### 3.3 短程任务输出

短程任务会输出：

- solve 结果
- Judge 结果
- 维护结果
- verify / regression 结果
- acceptance / rollback 结果
- session 标准记录

### 3.4 当前短程任务意义

短程主线现在已经是系统最成熟的经验反向传播主链。

它适合：

- 小步学习
- 快速修补
- 局部验证
- 小批量经验累积

---

## 4. 长程任务能力

### 4.1 已实现能力

长程任务当前已经能做：

- 自动生成初始 work graph
- 按 work unit 执行
- 每个 unit 跑 validators
- 失败后同节点 retry
- 必要时 replan
- 最终 completion validate
- 生成 summary
- 生成 shadow memory record
- 生成 maintainer candidate package

### 4.2 本轮新完成的关键能力

这轮之后，长程任务新增了真正可用的“失败后学习再重试”：

- unit 失败时会写 `failure packet`
- 同时写 `retry lesson`
- 下一次同 unit attempt 会自动带入 `retry bundle`
- `claim false` 不再被 validator 的局部通过掩盖

这意味着长程任务不再只是“失败了再跑一遍”，而是“失败了以后带着失败经验再跑一遍”。

### 4.3 长程任务输出

长程任务当前会输出：

- work graph
- progress state
- claims
- validator results
- scratch units
- learning units
- failure packets
- retry lessons
- retry journal
- summary
- shadow memory record
- candidate package

### 4.4 当前长程任务意义

长程主线现在已经具备真实实验价值。

它适合：

- 材料多
- 路径不固定
- 需要边做边检查
- 中途可能多次失败
- 需要逐步长出任务做法的任务

---

## 5. Judge / Validator 能力

### 5.1 Short Task Judge

短程 Judge 当前已经具备：

- 是否启动维护的判断
- 失败类型归因
- 维护后接受 / 回滚判断

结构上已经分成：

- `Pre-Judge`
- `Post-Judge`

### 5.2 Long Task Validators

长程当前依赖 validator 驱动。

当前支持：

- script validator
- prompt_json validator
- completion-only validator
- unit validator

### 5.3 当前意义

Judge / Validator 层的作用，是把“agent 的自述”变成“外部可验证结果”。

没有这层，系统只能执行，不能稳定学习。

---

## 6. Maintainer 能力

### 6.1 已实现能力

当前 maintainer 已具备：

- 读取 Judge 结论
- 在经验工作区内进行修改
- 支持直接改写
- 支持 add-only 写入
- 支持维护后验证
- 支持失败后回滚

### 6.2 当前已实现模块

- `direct-rewrite`
- `add-only-memory`

### 6.3 当前边界

maintainer 当前主要负责：

- 局部经验维护
- 当前失败驱动的经验更新

它当前还不负责：

- 全局经验优化
- 多版本高级治理
- 反过拟合结构优化

---

## 7. Experience Workspace（经验工作区）能力

### 7.1 Dual Plane（双平面）

当前工作区已经正式采用双平面模型：

- `Tracked Experience Plane`
- `Runtime Sidecar Plane`

### 7.2 当前系统已知规则

`Tracked Experience Plane`：

- 参与 diff
- 参与 rollback
- 参与 snapshot
- 参与 commit / candidate / governance

`Runtime Sidecar Plane`：

- 当前主要是 `.opencode/**`
- 允许存在
- 不参与经验 diff
- 不参与 rollback
- 不进入正式治理

### 7.3 当前意义

这解决了一个非常关键的问题：

系统不再把运行时副产物误当成正式经验。

---

## 8. 记录与可追踪能力

### 8.1 Session 标准记录

当前短程 / 通用记录包括：

- `session_execution_report`
- `session_learning_log`
- `session_task_manifest`
- `task_index`

### 8.2 Long Task 专项记录

当前长程记录包括：

- `claims`
- `validator_results`
- `failure_packets`
- `learning_units`
- `retry_lessons`
- `retry_journal`
- `summary`
- `candidate package`

### 8.3 当前意义

系统已经不是黑箱。

现在我们可以追踪：

- 它做了什么
- 为什么失败
- 下次怎么改
- 哪些经验被保留

---

## 9. 控制平面能力

### 9.1 当前已实现

控制平面当前已能做：

- 注册组件
- 分类组件
- 装配 recipe
- 校验现有方法配置
- 为后续跨层状态传递预留通道

### 9.2 当前已接入 recipe

- `sequential-refine`
- `add-only`
- `parallel-batch-5-add-only`

### 9.3 当前意义

控制平面让系统开始从“方法名驱动”走向“recipe 驱动”。

这一步的意义是：

- 后续新方法不必再全部硬编码在单个大 runner 里
- 方法可以逐渐变成可注册、可组合、可治理的对象

---

## 10. Layer 3 当前能力

当前 Layer 3 已具备最小治理能力：

- commit
- branch
- candidate
- campaign
- source ref
- campaign state

当前它已经能做：

- 保存经验版本快照
- 组织实验运行
- 保留 lineage
- 承接后续治理基础

当前还不能完整做：

- merge
- promotion
- 多分支 compare
- 完整候选晋升机制

---

## 11. Layer 4 当前状态

Layer 4 现在还没有真正上线执行器，但已经明确了方向。

未来它负责的不是局部修补，而是：

- 经验压缩
- 经验提纯
- 结构拆分 / 合并
- 泛化增强
- 反过拟合优化

当前已拥有的是接口方向，不是执行能力本身。

---

## 12. 当前系统最有价值的意义

如果用业务语言来讲，当前系统已经具备三层意义：

### 12.1 从“一次执行”升级为“可复盘执行”

不是做完就结束，而是做完还能解释过程、解释失败。

### 12.2 从“个体经验”升级为“可保存经验”

不是某个 agent 临时会做，而是可以把经验留下来给后续新 agent 使用。

### 12.3 从“经验堆积”升级为“经验治理”

不是把所有内容都塞进专家经验区，而是开始区分：

- 临时经验
- 影子经验
- 候选经验
- 正式经验

---

## 13. 当前明确未完成的部分

下面这些还没有做完，文档里必须明确：

- 统一学习任务入口
- 长短程共享 maintainer 候选摄入
- Layer 3 完整治理
- Layer 4 优化器
- augmentation / adversarial / purification 套件
- 更长程友好的 session ledger 体系
- 更强的跨层 constraint policy 执行

---

## 14. 下一阶段计划

下一阶段最明确的计划是：

### 14.1 统一入口

建立统一任务入口，但先由人类指定：

- `short`
- `long`

先不做自动判断。

### 14.2 长短程共享后续插件平面

让短程和长程共享后续的：

- validator
- evidence extraction
- candidate packetization
- maintainer ingestion
- governance hooks

### 14.3 长程接入统一 maintainer 出口

把长程当前已经产出的 candidate package，真正接入统一后续维护与治理主线。

### 14.4 做实 Layer 3

优先补：

- merge
- promotion
- compare
- campaign 治理闭环

### 14.5 启动 Layer 4 V1

第一版先做：

- optimizer candidate package
- optimizer outcome
- optimizer memory

而不是一口气把所有全局优化方法都做完。

---

## 15. 一句话总结

当前系统已经不是一个单纯的任务执行器，而是一套：

**能执行、能验证、能复盘、能局部学习、能保留候选经验，并正在走向正式经验治理平台的专家经验系统。**
