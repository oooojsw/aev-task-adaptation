# 系统能力总览

状态：当前实现版

这份文档只描述系统现在已经具备的能力、每个模块拿什么输入、产出什么结果、结果流向哪里。

不展开任何代码实现细节。

---

## 1. 系统当前的总目标

当前系统的目标是：

- 从带答案的案例中学习
- 逐步形成一套可演化的专家经验体系
- 用这套经验指导新的 session 完成任务
- 在失败后，通过判断系统和经修系统决定是否更新专家经验

一句话：

**这是一套把局部任务表现转化为长期专家经验的实验系统。**

---

## 2. 当前系统分哪几层

### 2.1 第一层：单任务执行层

负责：

- 这次任务怎么跑
- 开哪些 session
- 产生哪些记录
- 是否进入经验维护

### 2.2 第二层：经验维护层

负责：

- 根据失败和 Judge 结果维护经验工作区
- 使用不同反向传播模块完成经验更新
- 决定维护结果是否保留

### 2.3 第三层：传播实验层

当前只做了初步底座，不是当前主工作。

负责：

- 基于已有经验做更高层传播实验
- 管理快照、分支、候选版本

---

## 3. 当前支持哪些任务模式

### 3.1 `eval`

作用：

- 用当前经验去解题
- 只测试，不学习

输入来源：

- 当前 case 的材料
- 当前经验工作区
- baseline

输出去向：

- solve 结果
- 评估结果
- session 标准记录

### 3.2 `learn`

作用：

- 先 solve
- 如果失败，再经过 Judge 和经修流程尝试更新经验

输入来源：

- 当前 case 的材料与答案
- 当前经验工作区
- baseline
- Judge 所需 session 记录

输出去向：

- solve 结果
- Judge 结果
- 经修结果
- verify / regression / post-judge 结果
- 接受或回滚结果

---

## 4. 当前支持哪些方法

### 4.1 `sequential-refine`

状态：

- 已完整实现
- 是当前基线方法

特点：

- solve 失败后进入保守维护链
- 允许经修 Agent 直接修改现有经验体系
- 通过 verify、regression、post-judge 决定是否接受

### 4.2 `add-only`

状态：

- 已实现并完成基础烟测

特点：

- solve 失败后优先追加经验，而不是大改旧经验
- 倾向新增局部补充、失败教训、工具说明、小模块
- 支持单次 attempt 内多轮维护尝试
- 仍然必须经过 verify、regression、post-judge

### 4.3 其他方法

例如：

- `adversarial-test`

当前还没有变成正式可运行方法，仍属于未来扩展方向。

---

## 5. 当前支持哪些运行入口

### 5.1 `bootstrap`

作用：

- 从训练案例生成第一版经验工作区

输入来源：

- train split 中的案例
- 模板库
- baseline
- 最小种子经验区

输出去向：

- 新的经验工作区
- bootstrap 的标准 session 记录
- bootstrap 的 task index

### 5.2 `run-case`

作用：

- 跑单个 case
- 可选 `eval` 或 `learn`
- 可选方法

输入来源：

- 单个 case
- 当前经验工作区
- 当前方法

输出去向：

- 单个 case 的完整运行目录

### 5.3 `run-round`

作用：

- 按 split 批量跑多个 case

输入来源：

- 指定 split
- 当前经验工作区
- 当前方法

输出去向：

- round 汇总结果
- 每个 case 的独立运行目录

### 5.4 `run-baseline`

作用：

- 统一完成：
  - bootstrap
  - train
  - test
  - scorecard

输入来源：

- 当前方法
- 数据集切分
- 当前模型配置

输出去向：

- baseline 总目录
- scorecard
- 经验区快照

## 6. 当前的数据层能力

### 6.1 案例集

来源：

- `dataset/cases`

包含：

- 材料
- 标准答案
- case 元信息

### 6.2 训练 / 测试切分

来源：

- `dataset/SPLIT.md`

作用：

- 定义哪些案例用于学习
- 哪些案例用于测试

当前默认：

- train：`case-001` 到 `case-005`
- test：`case-006` 到 `case-010`

---

## 7. 当前的经验体系能力

### 7.1 Experience Workspace

这是当前真正的最终专家经验区。

作用：

- 给 solve 读取
- 给 Judge 参考
- 给经修 Agent 修改

当前特点：

- Markdown 为主
- 有单入口文件
- 能逐步长出更多模块
- 不再完全写死为旧的固定文件清单

输入来源：

- bootstrap
- 经修 Agent

输出去向：

- solve
- judge
- maintainer
- baseline 快照

### 7.2 Template Library

这是模板参考库，不是最终经验本体。

作用：

- 给 bootstrap 参考结构
- 给经修 Agent 参考组织方式

输入来源：

- 项目自带模板

输出去向：

- bootstrap
- maintainer

### 7.3 Baseline 文件

作用：

- 保存用户自己的起始想法
- 提供给 solve / bootstrap / maintainer 作为可选上下文

特点：

- 不是系统控制文件
- 不是硬规则
- 只是参考

---

## 8. 第一层当前有哪些 Worker 能力

### 8.1 Solve Session

作用：

- 读取当前经验
- 解当前题

输入来源：

- case 材料
- 经验工作区
- baseline

输出去向：

- solve response
- evaluation
- 标准 session 记录

### 8.2 Bootstrap Session

作用：

- 从训练案例建立初始经验

输入来源：

- 训练案例
- 模板库
- baseline
- 最小种子经验区

输出去向：

- 新经验工作区
- bootstrap 标准记录

### 8.3 Verify Session

作用：

- 经修后重新验证当前 case 是否修好

输入来源：

- 更新后的经验工作区
- 当前 case

输出去向：

- verify 结果
- verify 标准记录

### 8.4 Regression Session

作用：

- 检查经修前后旧能力是否退化

输入来源：

- regression 采样 case
- 当前经验工作区

输出去向：

- regression 摘要
- regression 标准记录

---

## 9. Session 记录层当前有哪些能力

当前关键 session 已经统一产生标准记录。

### 9.1 `session_execution_report`

作用：

- 顺序记录这个 session 做了什么
- 包括工具调用、关键输出、错误、结果
- 大段内容会截断，但顺序保留

输入来源：

- session 原始事件流

输出去向：

- Judge
- 经修 Agent
- 人类排查

### 9.2 `session_learning_log`

作用：

- 概括这个 session 从本次运行中学到的内容
- 记录行为模式、工具使用和失败线索

输入来源：

- session 事件
- evaluation

输出去向：

- Judge
- 经修 Agent

### 9.3 `session_task_manifest`

作用：

- 明确这个 session 被要求执行什么任务

输入来源：

- task descriptor
- session 的运行参数

输出去向：

- Judge
- 经修 Agent

### 9.4 `task_index`

作用：

- 汇总一个 attempt 中有哪些任务
- 每个任务的三份主记录在哪里

输入来源：

- attempt 内各任务记录

输出去向：

- 人类查看
- 后续流程排查

---

## 10. 当前 Judge Layer 的能力

Judge Layer 位于：

- Worker 之后
- 经修 Agent 之前

作用：

- 判断这次失败是否值得启动经验维护
- 给经修 Agent 产出统一判断结果

### 10.1 Runtime Guards

作用：

- 保证运行链不崩
- 检查基本产物存在
- 保证系统至少有基本护栏

### 10.2 Hard Judge

当前形态：

- 项目本地 Judge Skill 工具包

当前已落地技能：

- `exact-output`
- `tool-failures`
- `session-behavior`

输入来源：

- solve 评估结果
- tool failures
- session events

输出去向：

- hard check 结果文件
- Soft Judge

### 10.3 Soft Judge

作用：

- 综合 session 记录和 hard judge 结果做统一判断

当前支持两种模式：

- `soft_only`
- `soft_plus_hard`

当前默认：

- `soft_plus_hard`

输入来源：

- execution report
- learning log
- task manifest
- evaluation
- action trace
- routing
- hard judge 结果

输出去向：

- `judge_summary.json`
- `judge_report.md`
- 经修 Agent

### 10.4 Post-Judge

作用：

- 在维护完成之后，对 verify 与 regression 结果做独立后置判断

当前特点：

- 是硬编码但可拔插的策略层
- 已经从旧 acceptance 逻辑中独立出来

当前已实现策略：

- `strict-regression-guard`
- `add-only-conservative-guard`

输入来源：

- verify 结果
- regression 前后结果
- workspace 变更信息

输出去向：

- `post_judge_summary.json`
- `post_judge_report.md`
- acceptance 决策

---

## 11. 当前经修 Agent 的能力

经修 Agent 是第二层的核心。

作用：

- 根据失败上下文和 Judge 结果维护专家经验

它当前已经不是单一 prompt，而是由几层组成：

### 11.1 Maintainer Core

作用：

- 规定所有方法共享的不变量

当前特点：

- 只保留跨方法基础规则
- 不再直接侵入模式层

### 11.2 反向传播模块

作用：

- 决定这次经验以什么风格维护

当前已实现：

- `direct-rewrite`
- `add-only`

### 11.3 加载策略

作用：

- 决定经修 Agent 如何读取经验区

当前状态：

- 已预留接口
- 默认全读

### 11.4 维护动作系统

作用：

- 决定有哪些经验维护动作可用

当前状态：

- 已做成可拔插系统

### 11.5 维护级别

作用：

- 决定经修 Agent 的维护自由度

当前状态：

- 已预留接口
- 默认全权限

---

## 12. 经修 Agent 的输入和输出流向

### 输入来源

- 当前任务上下文
- 当前方法与反向传播模块
- 当前经验工作区
- 模板库
- baseline
- Judge 结果
- 选中的 session 记录

### 输出去向

- 更新后的经验工作区
- maintain summary
- 维护过程产物
- 后置 verify / regression / post-judge

---

## 13. 当前 acceptance / rollback 能力

维护之后，系统当前已经支持：

- verify 当前 case
- regression 检查旧能力
- post-judge 判断
- 接受或回滚

也就是说：

当前不再是“改完就留下”，而是：

**改完以后必须经过后置验证链。**

同时，现在单次 attempt 内也支持有限维护重试。

---

## 14. 当前监控和运行管理能力

系统当前已经有外部监控页，能持续看到：

- 哪些 session 在运行
- 当前做到哪一步
- 最近做了什么

此外，系统还已经具备：

- 模型配置文件
- Judge 配置文件
- 权限配置文件
- baseline scorecard

---

## 15. 当前第三层的状态

第三层当前已有初步底座，但不是当前主施工对象。

已具备：

- propagation 仓库目录
- 初步的 commit / branch / candidate 概念
- 第三层直接使用第二层方法作为传播方法的能力

未完成：

- merge
- promotion
- 多分支治理
- 完整 campaign 系统

所以当前对第三层的准确判断是：

**有基础，但仍是初步实现。**

---

## 16. 当前系统最重要的能力结论

如果只看当前真实可用能力，可以概括成：

1. 系统已经能以任务方式运行关键 session，而不只是零散脚本。
2. 关键 session 已经能统一留下 execution report、learning log、task manifest。
3. Judge 已经不再只有前半层，维护后也有独立的 post-judge。
4. 经修 Agent Core 与具体维护模式已经开始分层。
5. `sequential-refine` 和 `add-only` 已经都是正式可跑方法。
6. 第三层已经有底座，但目前主工作仍然是把第一层和第二层做稳。

---

## 17. 一句话总结

当前系统已经从“会自动改规则的小工具”升级成：

**一个拥有任务层、Judge 层、经修层、经验工作区、标准 session 记录和初步传播实验底座的专家经验演化系统。**
