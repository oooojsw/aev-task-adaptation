# 三层记忆与路由控制实施计划

## 目标

把当前 campaign 流程中的三件事彻底拆开：

1. 存档
2. 给模型看的工作记忆
3. 直接驱动下一轮建图的路由控制

这样做的目的不是增加更多总结文件，而是让经验真正变成下一轮行为的最小控制信号。

## 当前问题

- 经验同时散落在 `campaign-operational-memory`、`run trace`、`exploration tree`、`pending package`、reviewer/worker suggestion 里，重复严重。
- `pending package` 被写成了“历史档案 + 当轮指挥板”，不再是稳定可执行的专家经验面。
- `exploration tree` 不是一棵真正的树，而是轮次叙事摘要。
- planner 没有独立读取“必须怎么转向”的控制信号，导致学到了也不改变下一轮图。

## 新的三层

### 1. 存档层

保留完整原始证据，供人排查和离线分析：

- `run-trace-full.json`
- 原始 `campaign-operational-memory.json`
- 原始 worker / reviewer suggestion
- 每轮 `pending package` 快照
- 每轮 `exploration-tree.json` 快照

规则：

- 只存档，不直接喂模型
- 允许保留 `id/runID/timestamp/refs/sourceRunIDs/tags`

### 2. 工作记忆层

只保留高价值、低噪音、可跨轮复用的压缩信号：

- 稳定事实
- 已验证方法
- 真实 blocker
- 高置信禁行路径
- package gap

规则：

- 同一句只保留一条
- 重复出现只增加 `evidenceCount`
- 每条最多保留 1 到 2 个证据引用
- 不保留大串路径、时间戳、sourceRunIDs

### 3. 路由控制层

这是 planner 必读的小型硬控制文件，只放能直接改变下一轮建图的内容：

- `currentPhase`
- `requiredNextRegions`
- `forbiddenUnits`
- `forbiddenRegions`
- `prerequisites`
- `blockedBy`
- `readyForFinalAcceptance`

规则：

- planner 必须读取
- 如果 planner 生成的图违反了这里的限制，则该图无效

## 树的真源

只维护一份：

- `exploration-tree.json`

规则：

- JSON 是唯一真源
- 不再维护树的 Markdown 版本
- 树中只保留区域、状态、前沿、禁止重复区域、先决条件等结构化信息
- 不再把按轮叙事写进树里

## run trace 改造

保留两层：

- `run-trace-full.json`：完整账本，进存档层
- `run-trace-digest.json`：压缩摘要，给 worker / lead / reviewer 读

`run-trace-full.json` 需要挂完整索引：

- 每个 attempt 的 `retry_input_bundle_path`
- `claim_path`
- `failure_packet_path`
- `tool_failures_path`
- `response_path`
- `events_path`
- `session_execution_report_path`
- `commandRecords`
- `attemptFindings`

`run-trace-digest.json` 只保留：

- explored regions
- key success paths
- key failure paths
- blockers
- package impact
- validated methods
- forbidden paths
- package gaps

## planner 输入面

新一轮 run 的 planner 只直接读取：

- 当前 `pending package`
- 当前 `exploration-tree.json`
- 当前 `routing-control.json`
- 原始材料
- 能力包
- 任务目标和输出定义

planner 不直接读取：

- 原始 op memory
- 原始 reviewer 建议历史
- 大体量 archive
- campaign seed context markdown

## campaign lead 输入面

campaign lead 只读取：

- `run-trace-digest.json`
- 当前 `pending package`
- 当前 `exploration-tree.json`
- 当前 `working-memory.json`
- 当前 `routing-control.json`
- 当前轮 worker suggestions
- 最新 reviewer suggestion（如果存在）

campaign lead 不直接读取：

- 原始 op memory archive
- campaign failure lessons markdown
- campaign seed context markdown

## 第一轮与后续轮次

### 第零轮

只做初始化：

- 建空的 `exploration-tree.json`
- 建空的 `working-memory.json`
- 建空的 `routing-control.json`
- 从 seed 建 `pending package current`

### 第一轮

允许：

- run 执行
- 生成 full trace / digest
- campaign lead 更新 package / tree / routing / working memory

不做：

- worker 全套总结
- reviewer

### 第二轮及以后

在已有 `pending package + tree + routing control` 基础上继续：

- planner 建图
- run 执行
- reducer 压缩
- worker
- lead
- reviewer
- 如果 reviewer 判断 ready，再跑最终硬验收

## 最小改动策略

尽可能复用现有模块：

- 保留 `campaign-operational-memory.json`，但改成存档层
- 新增 `campaign-working-memory.json`
- 新增 `routing-control.json`
- 保留 `run-trace.json` 现有位置，但改名为 full，并新增 digest
- 保留 `pending package` 版本快照机制
- 保留单一 `exploration-tree.json`
- 复用现有 worker / lead / reviewer 会话执行框架

## 本轮实施顺序

1. 扩展 contract 与 repository
2. 新增 compact working memory / routing control 文件与 reducer
3. 把 generated round spec 改成显式携带 `routing-control.json`
4. 从第二轮开始不再复用 `baseSpec.initialGraph`，而是让 planner 基于 package/tree/routing control 重建图
5. 改 prompts，停止直接喂全量历史
6. 补 smoke 与回归测试
