# 专业计划书：Session 执行报告与经修 Agent 分层提示系统

## 1. 目标

在现有“元操作 + 代码方法策略 + 经修 agent + Experience Workspace”架构上，新增两项基础能力：

1. **Session Execution Report**
   - 每个关键 session 生成一个单文件、顺序化、截断版执行报告
   - 作为方法层和经修 agent 的正式输入材料

2. **Knowledge Maintainer Prompt Layering**
   - 经修 agent 提示系统拆成：
     - 通用内核提示词
     - 方法专属补充提示词
     - 运行时上下文块

这两项能力的目标是为后续：

- 多种反向传播方法
- 更大规模经验体系
- Git-tree 分支实验
- 对抗测试
- 多候选维护策略

提供稳定底座。

---

## 2. 当前问题

### 2.1 当前运行信息过于碎片化

当前每次 session 的外显执行信息分散在：

- `events.json`
- `action_trace.md`
- `tool_failures.json`
- `response.txt`
- `stderr.log`
- `run.json`

这对程序调试够用，但对经修 agent 不友好。

### 2.2 当前经修 agent 仍然只拿到“简化行为摘要”

目前主要输入是：

- `actual_output.txt`
- `evaluation.json`
- `action_trace.md`

这不足以支持更强的行为归因，例如：

- 工具误用
- 无意义重复探索
- 空目录/空文件探索
- 工具调用失败模式
- 错误 patch 行为
- 子 session 行为结构

### 2.3 当前经修 agent prompt 仍然是单体式

虽然已经有“方法契约块”，但整体上仍然偏向：

- 一份模板承载大部分约束

长期看不利于：

- 多方法扩展
- 方法间差异清晰化
- 维护稳定的经修 agent 核心身份

---

## 3. 总体设计

### 3.1 核心新抽象

新增两个正式抽象：

#### A. `SessionExecutionReport`

定义：

- 某个 session 的统一单文件行为报告

用途：

- 人类阅读
- 经修 agent 输入
- 方法层反馈包输入
- 实验留档

#### B. `KnowledgeMaintainerPromptStack`

定义：

- 经修 agent 完整提示词由三层拼接而成

层次：

1. `maintainer_core`
2. `method_maintenance_extension`
3. `runtime_context_blocks`

---

## 4. Session Execution Report 设计

## 4.1 保存原则

每个 session 必须生成 **一个完整顺序版单文件报告**。

报告必须：

- 单文件保存
- 存放在该 session 所属实验目录中
- 与该 session 的其它产物同目录或同级目录
- 不再要求经修 agent 自己去组合多个碎片文件

建议命名：

- `session_execution_report.md`

若一个 attempt 下有多个 session，则每个 session 自己目录内各有一份：

- `solve/session_execution_report.md`
- `maintain/session_execution_report.md`
- `acceptance/current-case-verify/session_execution_report.md`
- `acceptance/regression-before-maintain/case-002/session_execution_report.md`

注意：

- **这里的“不能分开存放”指的是：每个 session 的完整行为路径必须集中在一个文件中。**
- 原始 `events.json` 可以保留作低层调试输入，但不再作为经修 agent 主输入。

## 4.2 报告内容结构

建议结构：

```md
# Session Execution Report

## Session Meta
- session id
- phase
- case id
- attempt
- method
- model
- agent
- start / end
- exit code
- finish reason

## Final Outcome
- final response summary
- evaluation summary (if any)
- tool failure count
- session error summary

## Ordered Timeline
### 1. step_start
...
### 2. tool_use: read
...
### 3. tool_use: edit
...
### 4. assistant_text
...
### 5. step_finish
...

## Tool Failure Summary
- failed tools
- repeated failing tools

## Behavior Summary
- repeated reads
- empty explorations
- long/noisy outputs
- likely wasted actions
```

## 4.3 信息来源

底层数据来源仍然来自 OpenCode 已暴露事件：

- `step_start`
- `step_finish`
- `tool_use`
- `text`
- `error`
- 未来可选 `reasoning`（如果开启）

核心原则：

- 顺序完整
- 长内容截断
- 保留输入/输出摘要
- 保留失败信息

## 4.4 截断策略

统一截断策略应系统化，而不是零散写死：

- 最大行数
- 最大字符数
- JSON 展开层数
- 二进制/超长块跳过

后续应抽成公共 formatter。

## 4.5 会话范围

并不是所有 session 都必须交给经修 agent，但所有关键 session 都应有报告：

- solve
- maintain
- verify
- regression
- adversarial_probe
- branch_compare

---

## 5. 经修 Agent Prompt 分层设计

## 5.1 目标

让经修 agent 的提示系统从“单模板”升级为“稳定内核 + 方法扩展 + 运行时上下文”。

## 5.2 三层结构

### A. `maintainer_core`

这是经修 agent 的稳定身份层，不随方法变化。

负责定义：

- agent 身份
- 长期职责
- Experience Workspace 基本不变量
- 模板库与最终经验分离
- 必须保持单入口
- 经验体系默认中文
- 只维护经验，不改数据集和主代码
- 通用经验元操作

建议经修 agent 的经验元操作（文义层，不是代码 API）：

- 创建规则模块
- 拆分规则模块
- 合并规则模块
- 创建例外模块
- 更新输出契约
- 更新执行清单
- 创建任务路由
- 创建分区索引
- 创建工具说明
- 记录失败教训
- 标记某模块弃用
- 更新入口导航

### B. `method_maintenance_extension`

每个反向传播方法单独拥有自己的维护扩展层。

它定义：

- 这次应更保守还是更激进
- 这次更偏向修当前题还是维持全局稳定
- 这次允许怎样的结构变化
- 这次需要查看哪些 session 报告
- 这次应该怎样组合失败材料
- 这次维护后优先看哪些验收信号

示例：

#### `sequential-refine`
- 最小修改优先
- 单一规范版本优先
- 先修当前题，再看回归

#### `adversarial-test`
- 明确关注被对抗样本击穿的薄弱点
- 允许新增专门的防错模块
- 更强调工具误用与错误探索的行为教训

### C. `runtime_context_blocks`

这层由运行时动态生成，包含：

- Experience Workspace 概况
- 模板库概况
- baseline 概况
- 当前 case 上下文
- 当前失败反馈包
- session 报告路径列表
- 方法路由提示

---

## 6. 经修 Agent 的输入设计

## 6.1 固定输入

所有方法都应稳定传入：

- Experience Workspace 根目录
- 单入口文件路径
- 当前工作区文件索引
- 模板库根目录与模板索引
- baseline 路径
- scripts 目录路径

## 6.2 当前失败上下文

至少包括：

- case id
- instruction
- material 路径
- expected 路径
- actual output 路径
- evaluation 路径

## 6.3 Session 报告路径

这部分由方法自己决定。

建议统一成运行时字段：

- `sessionReportPaths: string[]`

例如：

```json
{
  "sessionReportPaths": [
    "attempt-01/solve/session_execution_report.md",
    "attempt-01/acceptance/current-case-verify/session_execution_report.md"
  ]
}
```

注意：

- 提供给经修 agent 的应是**路径**
- 不是把这些报告正文预塞进 prompt
- 经修 agent 自己按需读取

---

## 7. 方法层如何决定“给哪些 session 报告”

这部分不能写死在经修 agent。

必须由方法代码负责。

## 7.1 方法接口新增建议

每个方法策略应能定义：

- `selectSessionReports(context): string[]`

即：

- 当前失败发生后
- 从已有 session 报告中挑出应该给经修 agent 的那几份

## 7.2 示例

### `sequential-refine`

建议给：

- 当前失败 solve report
- 如果有 verify 失败，再加 verify report
- 必要时加前一轮被拒绝的 maintain report

### `adversarial-test`

建议给：

- solve report
- adversarial probe report
- 对抗失败验证 report

---

## 8. Experience Workspace 不变量

为了未来大规模演化稳定，建议现在固定这些不变量：

1. 最终经验工作区只保存最终有效经验，不包含模板库副本
2. 必须存在且仅存在一个入口文件
3. 空白 solve agent 应从入口开始，选择性读取
4. 工作区允许分区、路由、工具说明、规则模块、教训模块
5. 结构允许演化，但不能失去可导航性
6. Markdown 仍然是经验真源

---

## 9. 与当前实现的衔接方式

当前系统已有：

- `ExperienceWorkspace`
- `knowledge maintainer`
- `method strategies`
- `action_trace`

下一步应演化成：

### 9.1 替换 `action_trace.md` 的主地位

保留 `action_trace.md` 作为简化摘要，但新增并提升：

- `session_execution_report.md`

### 9.2 扩展 `knowledge maintainer` 输入契约

在 `KnowledgeMaintainerRequest` 中加入：

- `sessionReportPaths: string[]`

### 9.3 拆出经修 agent 核心 prompt

建议新增：

- `auto-evolve/prompts/knowledge-maintainer-core.md`

### 9.4 方法目录中新增维护扩展 prompt

例如：

- `methods/sequential-refine/prompts/maintain_extension.md`
- `methods/adversarial-test/prompts/maintain_extension.md`

### 9.5 Prompt 组装顺序

建议：

1. core prompt
2. method maintenance extension
3. runtime context blocks

---

## 10. 未来权限路线

当前阶段仍保持我们已定策略：

- 经修 agent 主要通过提示词约束
- 先跑通系统
- 先收集真实维护行为

未来权限演化方向：

### 阶段 1
- prompt 软约束
- 验收/回滚兜底

### 阶段 2
- 经验工作区硬边界
- 不允许越界修改数据集/主代码

### 阶段 3
- 方法级权限
- 不同方法拥有不同结构修改权限

### 阶段 4
- 大型体系下的分区权限/角色权限

---

## 11. 开发顺序建议

### Phase 1

实现 `session_execution_report.md`

### Phase 2

让所有关键 session 自动生成报告：

- solve
- maintain
- verify
- regression

### Phase 3

把经修 agent prompt 拆成：

- core
- method extension
- runtime context

### Phase 4

让方法代码正式决定 `sessionReportPaths`

### Phase 5

再扩展新方法，例如：

- `sequential-lite`
- `adversarial-test`

---

## 12. 设计结论

这次设计的本质是：

**把经修 agent 从“读取少量失败摘要并修改经验”，升级成“读取完整行为路径、结合方法特定修复策略、维护可演化经验工作区”的正式知识维护层。**

它将成为后续所有反向传播方法的公共底座。
