# V1 批量局部学习内核落地说明

## 本次做成了什么

这次落地的是四层设计里的第一版 `V1`，重点是把第一层和第二层之间的“批量局部学习内核”真正做出来，而且不破坏现有顺序链路。

当前已经落地的核心能力：

- `Layer 1 / Task Execution Layer（任务执行层）`
  - 新增 `parallel-batch-5-light-shard`
  - 支持把一批 case 按 5 个为一组切成微批次
  - 每个 shard 并行执行
  - shard 当前采用 `light shard（轻分片）`

- `Layer 2 / Local Experience Maintenance Layer（局部经验维护层）`
  - 新增 `batch-5-aggregate`
  - 支持把 5 个 shard 的学习结果聚合成一个批次学习包
  - 支持一个 batch maintainer 一次性读取批次学习包并写入经验区
  - 支持 batch 级别的 post-judge / acceptance / rollback

- `Layer 3 / Version Governance Layer（版本治理层）`
  - 现有最小治理层已能直接复用新的 batch recipe
  - 当前第三层已验证可以直接把 `parallel-batch-5-add-only` 当传播方法运行

## 当前第一版 recipe

### `Execution Strategy（执行策略）`

- `sequential`
- `parallel-batch-5-light-shard`

### `Packetization Policy（打包策略）`

- `single-case-packet`
- `batch-5-aggregate`

### `Maintenance Module（维护模块）`

当前 batch 第一版复用已有维护模块：

- `add-only`
- `direct-rewrite`

但这次真正验证过的是：

- `parallel-batch-5-light-shard + batch-5-aggregate + add-only`

### `Acceptance Policy（验收策略）`

当前 batch 第一版支持：

- `strict-batch-improvement-guard`
- `add-only-batch-conservative-guard`

## 轻分片是什么意思

这次第一版明确采用了：

- `light shard（轻分片）`

每个 shard 只做：

- `solve`
- `pre-judge`
- `learning packet extraction（学习包抽取）`

每个 shard **不会**：

- 本地开 maintainer
- 本地改经验区
- 本地做小型 branch

也就是说：

- shard 只负责“并行学习收集”
- 真正写经验只发生在 batch maintainer

这保证了：

- 不会 5 个并发 shard 同时改同一份经验
- 经验写入仍然是单事务、可回滚、可验收的

## 当前 batch 流程

第一版实际流程是：

1. 冻结一个批次基线经验区
2. 5 个 case 并行跑 shard
3. 每个 shard 产出：
   - solve 结果
   - judge 结果
   - learning packet 片段
4. `batch-5-aggregate` 聚合成一个 `Batch Learning Packet（批次学习包）`
5. 开一个 batch maintainer
6. batch maintainer 统一写一次经验区
7. 跑 batch verify / regression / post-judge
8. 接受或回滚

一句话：

- `并行学习收集，串行统一维护`

## 这次新增的方法

新增了第一版批量方法：

- `parallel-batch-5-add-only`

这个方法的职责不是定义新的维护风格，而是定义：

- 第一层怎么并行跑
- 第二层怎么聚合写回

它当前复用的维护风格仍然是：

- `add-only`

所以它更准确地说是：

- `batch execution recipe + add-only maintenance module`

## 这次没有做什么

为了保证层次干净，这些东西明确没有放进 `V1`：

### 没做的 `Layer 4 / Generalization & Overfit Control Layer（泛化与过拟合控制层）`

当前只保留设计，不做实现：

- `Augmentation Suite（增广套件）`
- `Adversarial Suite（对抗套件）`
- `Compression / Purification（压缩 / 提纯）`
- `Optimizer Agent（优化器代理）`
- `Optimizer Memory（优化器记忆）`

### 没做的复杂第三层治理

当前第三层仍然只保留最小可用能力，没有进入复杂治理：

- `merge`
- `promotion`
- `multi-branch compare`
- `branch-preserving campaigns`

## 为什么这样切层

这次最重要的不是“又加了一个方法”，而是把边界切清楚了。

### 第一层现在只负责

- 任务怎么跑
- 是否并行
- shard 怎么切

### 第二层现在只负责

- 怎么把一批局部失败变成一次局部经验维护事务

### 第三层现在只负责

- 如何治理版本、分支和 candidate

### 第四层现在只保留设计接口

- 未来如何做全局反过拟合、提纯和泛化优化

## 这次实际验证过什么

### 已验证

- `validate`
- `run-round --method parallel-batch-5-add-only --split train --limit 5`
- `run-baseline --method parallel-batch-5-add-only --train-limit 5 --test-limit 5 --force-bootstrap`
- `run-propagation --method parallel-batch-5-add-only --train-limit 1 --test-limit 1`
- `run-case --method sequential-refine --mode eval`

### 验证结论

- 新的 batch kernel 已经真实跑通
- 现有顺序链路没有被带坏
- 第三层已经可以直接复用新的 batch recipe

## 当前版本的真实边界

虽然 V1 已经能跑，但它仍然是第一版，当前有这些边界：

- batch shard 还只是 `light shard`
- batch maintainer 当前仍然只有一个
- 还没有 batch 级增强器、对抗器、压缩器
- 第四层优化器尚未实现
- 第三层还没有复杂治理

所以当前 V1 的真实定位应该是：

- 一个已经跑通的、层次边界清楚的 `Local Learning Kernel（局部学习内核）`

而不是：

- 完整的四层全量系统

## 下一步最自然的方向

在保持当前边界稳定的前提下，后面最自然的扩展顺序应该是：

1. 把 `parallel-batch-5` 从单一方法继续抽象成更正式的第一层执行策略
2. 增加更多第二层维护模块的 batch 组合
3. 再把第四层的 `Optimization Candidate Package（优化候选包）` 接到第三层
4. 最后再做第四层真实优化器与 suite 构建器
