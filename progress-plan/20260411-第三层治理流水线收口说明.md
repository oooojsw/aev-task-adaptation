# 第三层治理流水线收口说明

这份文档只服务当前实现，不追求把第三层一次做完。

当前第三层已经有：

- Git-like 的对象仓库底座
- `canonical / branch / commit / optimization candidate` 来源解析
- 第三层直接委托第一层和第二层 recipe 运行
- candidate commit 生成与 branch head 更新

当前第三层最主要的问题，不是能力缺失，而是职责混在一个主入口里：

- `run.ts` 同时负责来源解析、workspace materialize、执行、收尾、结果回写
- campaign 只有输入文件和最终结果文件，中间没有正式状态
- execution adapter 的结果主要靠同步返回值承载，不够透明
- 持久治理对象和临时运行对象在概念上还没正式分开

这次收口的目标是：

1. 不改变现有命令入口
2. 不改变现有成功路径
3. 不碰第三层之外的主逻辑
4. 让第三层的长链执行变得可观察、可恢复、可继续扩展

本次收口后，第三层内部按下面四块理解：

## 1. Source Adapter

负责把：

- `canonical`
- `branch:<name>`
- `commit:<id>`
- `optimization:<id>`

解析成一个明确的起始 commit。

## 2. Campaign Runtime

每个 campaign 除了原本的：

- `campaign.input.json`
- `campaign.json`

再新增：

- `campaign.state.json`

用于记录阶段状态，而不是只在最后一次性写总结果。

建议阶段：

- `created`
- `source_resolved`
- `workspace_materialized`
- `execution_started`
- `execution_finished`
- `candidate_commit_created`
- `branch_updated`
- `finalized`
- `failed`
- `aborted`

## 3. Execution Adapter

第三层不自己理解下层 recipe 的细节，而是通过执行适配器去调用：

- `single-branch-baseline`
- delegated layer1/layer2 recipe

执行适配器除了同步返回值，还应该把自己的结果正式落盘。

## 4. Finalization & Outcome

执行完成后，第三层负责：

- 生成 candidate commit
- 更新 branch ref
- 写 `campaign.json`
- 写 `campaign-summary.md`
- 在需要时回写 `Optimization Outcome`

## 双平面原则

第三层以后明确分成两个平面：

### Governance Repository Plane

持久治理状态：

- `objects/`
- `commits/`
- `refs/`
- `optimization/` 下持久对象

### Campaign Runtime Plane

临时实验运行状态：

- `campaigns/<campaign-id>/`
- `workspaces/<runtime-id>/`
- branch 内部的 `runs/`

这次代码先把“状态文件”和“执行结果文件”补齐，先不大改目录结构。

## 本次实现边界

这次只做：

- `campaign.state.json`
- execution result 落盘
- `run.ts` 改成阶段式写状态

这次不做：

- multi-branch compare
- merge
- promotion
- 第三层 GC
- branch 身份与 runtime workspace 身份彻底拆分

也就是说，这次是第三层的“治理流水线收口”，不是第三层功能扩张。
