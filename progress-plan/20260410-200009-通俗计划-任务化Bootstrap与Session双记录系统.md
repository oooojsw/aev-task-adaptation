# 通俗计划：任务化 Bootstrap 与 Session 双记录系统

## 1. 这次要解决的核心问题

我们现在已经走到一个关键节点：

- `bootstrap` 不能再被看成系统外面的一段特殊流程
- 它也应该和后面的训练、测试、验证一样，被看成一种“任务”
- 每个 session 不能只留下最终答案，还要留下：
  - 它到底做了什么
  - 它在过程中学到了什么

后面如果系统要支持很多种反向传播方法，这两件事必须先定下来：

1. **所有运行步骤统一叫 Task**
2. **每个关键 Session 都留下两份记录**

一句话说：

**以后系统不是“先 bootstrap，再训练”，而是“不断执行不同类型的任务”。**

---

## 2. 什么叫“任务化”

任务化的意思不是把东西改个名字，而是把系统统一成一种运行方式：

- 每次给 OpenCode 一个明确任务
- 系统告诉它这次任务的目标是什么
- 系统给它必要的路径
- 它执行这个任务
- 运行后留下标准化产物

这样做的好处是：

- bootstrap 不再特殊
- 训练不再特殊
- 测试不再特殊
- 对抗测试以后也不特殊

它们都只是不同类型的任务。

---

## 3. 以后系统里的任务大致分成什么

我建议现在就先把任务分成下面几类。

### A. 初始化类任务

这类任务的作用是让系统从零开始有一个可工作的经验区。

例如：

- `seed_workspace`
  - 创建一个最小经验工作区
  - 只有入口和基础记录文件
- `bootstrap_from_examples`
  - 根据少量或多量案例，生成第一版经验体系

注意：

**bootstrap 是否存在、用多少案例、跑几次，应该由具体方法决定。**

不是所有方法都必须“用 1-5 一起 bootstrap 一次”。

---

### B. 学习类任务

这类任务的作用是让系统根据已有经验继续学习。

例如：

- `learn_case`
  - 用当前经验解一个案例
  - 如果失败，构造反馈
  - 触发经修 agent
- `maintain_experience`
  - 经修 agent 维护经验工作区

---

### C. 评估类任务

这类任务不负责学习，只负责判断当前经验有多好。

例如：

- `eval_case`
  - 只解题，不改经验
- `verify_case`
  - 专门检查某次经验修改是否修好了当前题
- `run_regression`
  - 检查经验修改有没有把旧能力改坏
- `run_test_suite`
  - 在测试集上统一评分

---

### D. 探测类任务

这是给以后更复杂方法准备的。

例如：

- `adversarial_probe`
  - 故意去找薄弱点
- `branch_compare`
  - 比较多个经验版本谁更好

---

## 4. 每个关键 Session 以后必须留下哪两份核心文件

我建议以后每个关键 session 都留下两份主记录。

### 文件 1：`session_execution_report.md`

这是“它做了什么”的完整顺序记录。

它应该记录：

- session 基本信息
- 当前任务类型
- 这次目标是什么
- 每一步工具调用
- 工具输入摘要
- 工具输出摘要
- 错误信息
- assistant 文本输出
- 最终结果

注意：

- 必须按时间顺序
- 必须是单文件
- 大段内容要截断
- 不再让后续 agent 去拼一堆碎文件

你可以把它理解成：

**这个 session 的“行为录像文字版”。**

---

### 文件 2：`session_learning_log.md`

这是“它在运行过程中自己学到了什么”的持续追加记录。

这是这次最重要的新设计点。

它不是最后才一次性总结，而是：

**这个 session 在运行过程中，每学到一点，就应该立刻追加进去。**

它可以记录：

- 刚发现的规则线索
- 刚确认的模式
- 刚发现的例外
- 某条路径走不通
- 某个工具在这个任务里不适合
- 某个目录是空的，不要再反复探索
- 某种输出方式会导致失败
- 某次尝试为什么放弃

你可以把它理解成：

**这个 session 自己写下来的“现场学习笔记”。**

---

## 5. 为什么一定要有 `session_learning_log.md`

因为只看执行路径还不够。

执行路径只能告诉我们：

- 它做了什么

但很多真正有价值的信息是：

- 它为什么改了方向
- 它发现了什么规律
- 它意识到哪里是死路
- 它暂时相信什么
- 它后来又推翻了什么

这些东西如果不在运行中持续写下来，最后就会丢失。

所以以后经修 agent 读取的，不能只有行为报告，还应该包括：

- `session_execution_report.md`
- `session_learning_log.md`

两者一起看，才知道：

- 这个失败 agent 做了什么
- 它过程中到底学到了什么
- 哪些教训值得真正进入专家经验体系

---

## 6. 经修 agent 以后到底怎么工作

经修 agent 不是一个“直接改文件的脚本替身”，而是：

**专门维护最终专家经验体系的维护者。**

它以后读取的东西应该分成三类。

### 第一类：稳定背景

- Experience Workspace
- 模板库
- baseline
- scripts

### 第二类：当前任务上下文

- 当前 case 材料
- 标准答案
- 实际错误输出
- 评估结果

### 第三类：之前 session 留下的记录

- `session_execution_report.md`
- `session_learning_log.md`

其中最关键的是：

**每种反向传播方法自己决定，要把哪些 session 的记录交给经修 agent。**

不是系统统一写死。

---

## 7. 经修 agent 的提示词应该怎么拆

后面不能再靠一个大 prompt 管全部。

我建议固定拆成三层。

### 第一层：经修 agent 的通用内核

这一层定义：

- 你是谁
- 你维护什么
- 你不能乱改什么
- 经验体系有哪些最基础的维护动作

例如它的基础经验维护动作可以包括：

- 新建规则模块
- 拆分规则模块
- 合并规则模块
- 新建工具说明模块
- 更新入口导航
- 记录失败教训
- 标记过期模块

这层不跟方法变化。

---

### 第二层：具体反向传播方法的维护扩展

这一层由方法决定。

它定义：

- 这次更保守还是更激进
- 这次优先修当前题还是优先保守全局
- 这次允许不允许结构变化
- 这次更该看哪些 session 记录

也就是说：

**方法不是直接改经验，而是告诉经修 agent 这次该怎么维护经验。**

---

### 第三层：运行时上下文

这一层每次都不同。

它包括：

- 本次任务说明
- Experience Workspace 路径
- 模板库路径
- 当前 case 路径
- 错误输出路径
- 评估结果路径
- 被选中的 session 报告路径
- 被选中的 session 学习日志路径

注意：

**这里继续保持只给路径，不预塞全文。**

---

## 8. Experience Workspace 后面应该怎么看

以后不要再把它理解成一套写死的固定目录。

它应该被理解成：

**最终专家经验区。**

这个区域可以演化，但应该保留几个长期不变的规则：

- 只有一个入口文件
- 模板库不算进最终经验
- solve agent 应该从入口出发选择性读取
- 允许分区
- 允许工具说明
- 允许任务导航
- 允许规则拆分和合并

换句话说：

它的具体结构可以变，但它必须始终可导航、可维护、可扩展。

---

## 9. 这套设计最大的变化是什么

最大的变化有三条。

### 变化 1

bootstrap 不再是系统特殊阶段，而是某种方法可以选择调用的一种任务。

### 变化 2

每个 session 不再只留下结果，而是留下：

- 行为记录
- 学习记录

### 变化 3

经修 agent 不再只根据“最后答错了什么”改经验，而是根据：

- 做了什么
- 学到了什么
- 哪些路径是错的
- 哪些经验值得沉淀

来维护最终经验体系。

---

## 10. 这次建议现在就定死的核心规则

### 规则 1

以后所有运行步骤都统一抽象成 Task。

### 规则 2

bootstrap 是 Task，不再是系统外特殊阶段。

### 规则 3

每个关键 session 必须有：

- `session_execution_report.md`
- `session_learning_log.md`

### 规则 4

经修 agent 后续读取哪些 session 记录，由方法决定。

### 规则 5

经修 agent prompt 固定拆成：

- 通用内核
- 方法扩展
- 运行时上下文

### 规则 6

Experience Workspace 是最终经验区，模板库只是参考。

---

## 11. 下一步最合理怎么做

如果按这次设计继续推进，我建议顺序是：

### 第一步

先定义统一 Task 模型。

### 第二步

把 `bootstrap` 也正式变成 primitive op / task type。

### 第三步

让每个关键 session 自动生成：

- `session_execution_report.md`
- `session_learning_log.md`

### 第四步

扩展经修 agent 输入契约：

- 增加 session 报告路径
- 增加 session 学习日志路径

### 第五步

让方法层决定：

- 要提供哪些历史 session 记录
- 什么时候维护
- 是否 bootstrap
- bootstrap 用几个案例

---

## 12. 一句话总结

这次设计的核心不是再改一层 prompt，而是把系统升级成：

**一个以 Task 为统一运行单位、以 Session 双记录为反馈基础、以经修 agent 为最终经验维护者的专家经验学习系统。**
