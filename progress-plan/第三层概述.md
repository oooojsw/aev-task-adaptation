# 第三层概述

## 1. 第三层是做什么的

第三层不是用来处理“单个 case 失败后怎么修”的。

第三层处理的是：

- 在已经有一套专家经验之后，如何围绕这套经验做真正的传播实验
- 如何比较不同传播方法谁更稳、谁更泛化、谁更不容易过拟合
- 如何管理经验版本、分支、候选版本、合并和晋升

一句话：

**第二层是维护经验，第三层是拿已有经验做长期传播实验。**

---

## 2. 为什么第三层必须单独存在

如果不把第三层单独提出来，后面会出现两个问题：

- 第二层的经修 Agent 会被迫同时负责局部修复、分支治理、合并建议、版本晋升，职责过重
- Judge 和经修 Agent 会被迫承载本来属于长期实验治理的问题，系统会越来越混乱

所以必须明确区分：

- 第一层：单任务执行层
- 第二层：经验维护层
- 第三层：经验传播实验层

第三层关心的是：

- 一整套经验的长期表现
- 多个经验版本之间的比较
- 多种传播方法之间的实验

而不是某一次 solve 对不对。

---

## 3. 第三层和第二层是什么关系

第三层不是推翻第二层，而是建立在第二层之上。

第二层负责：

- 把某次失败整理成维护请求
- 让经修 Agent 在某种反向传播模块下维护经验工作区
- 产出新的经验状态

第三层负责：

- 把这些经验状态变成可比较、可追踪的版本节点
- 在多个节点、多个分支、多个方法之间做实验
- 决定哪个版本值得保留、合并、晋升

也就是说：

- 第二层是局部学习器
- 第三层是全局传播实验层

---

## 4. 第三层包含第二层，但不等于第二层

第三层会直接使用第二层的方法。

例如：

- `direct-rewrite`
- `add-only`

这些第二层方法，后面都可以直接作为第三层的一种传播方法来使用。

但第三层不会只停留在这些方法上，因为第三层还会有第二层没有的能力，例如：

- 多分支实验
- 合并策略比较
- 晋升策略比较
- 对抗传播
- 分支间语义比较

所以更准确地说：

- 第二层方法会成为第三层的方法子集
- 第三层还会拥有第二层没有的传播实验方法

---

## 5. 第三层的核心对象

第三层后续至少围绕下面这些对象工作：

### 5.1 Experience Commit

一次经验提交。

它表示某个时刻的经验状态，并记录：

- 父提交是谁
- 由什么方法产生
- 这次提交的评估结果摘要

### 5.2 Experience Branch

一条经验演化分支。

它表示：

- 当前这条实验线走到哪个 commit
- 这条线用的是什么方法
- 这条线是否仍在继续实验

### 5.3 Campaign

一轮完整传播实验。

它包含：

- 起始经验版本
- 要比较的方法集合
- 要创建的分支集合
- 使用的数据切分
- 最终的实验结论

### 5.4 Candidate

某次实验中的候选经验版本。

它可能来自：

- 单个分支
- 多分支合并结果
- 某种传播方法处理后的结果

### 5.5 Evaluation Pack

统一评估包。

它负责把不同候选版本放到同一标准下比较，至少包括：

- train / test 表现
- 回归损失
- 泛化表现
- 稳定性
- 复杂度或长度惩罚

### 5.6 Merge Policy

定义如何把多个经验分支合并成新候选。

### 5.7 Promotion Policy

定义什么样的候选版本可以晋升为新的 canonical 经验。

---

## 6. 第三层的快照不该是整目录复制

第三层后续不应该靠“每次复制整个经验目录”来做版本化。

更合理的方式是接近 Git 的增量思路：

### 6.1 Live Workspace

当前正在使用的经验工作区。

### 6.2 Snapshot Manifest

每次快照只记录：

- 当前文件树结构
- 每个文件的内容哈希
- 父快照
- 本次快照的来源、备注、评估摘要

### 6.3 Blob Store

真正的文件内容按哈希存一份。

如果内容没变，就不重复存。

所以第三层的理想快照不是：

- 复制整目录

而是：

- 记录一个可还原的内容地址版本

这样后面做：

- branch
- diff
- merge
- rollback
- promotion

都会自然很多。

---

## 7. 第三层应该由代码主控，Agent 做语义工作

第三层顶层必须以代码为主控。

原因很简单：

- 分支管理必须稳定
- 实验调度必须可重复
- 评分与晋升必须可审计
- 合并不能靠临场发挥
- 并发和资源使用必须可控

所以第三层最合理的结构是：

**代码负责实验治理，Agent 负责语义工作。**

### 代码负责

- 创建快照
- 创建分支
- 调度 campaign
- 控制并发
- 跑统一评估
- 汇总结果
- 执行 merge 流程
- 执行 promotion 决策

### Agent 负责

- 对抗样本生成
- branch 差异解释
- merge 语义建议
- 风险分析
- 规则压缩与凝练建议
- 传播实验结果总结

所以不是“要不要 Agent”，而是：

**不能让 Agent 做第三层总控，但第三层内部会用很多 Agent。**

---

## 8. 第三层的并发原则

第三层后续一定会用到并发，但不应该无节制地开很高并发。

当前更合理的原则是：

- 可以并发
- 并发规模要小
- 必须受控
- 每类任务要有上限

也就是说，第三层应采用：

- 小规模并发
- 有队列
- 有上限
- 以实验效率为目标，而不是盲目同时开很多 session

---

## 9. 第三层当前实现到什么程度

当前第三层已经有了第一版底座，但还不是完整治理系统。

已经有的：

- propagation 仓库目录
- 类似 Git 的基础对象层
- 单分支实验的初步能力
- 第三层直接调用第二层方法作为传播方法的能力

还没做完的：

- merge
- promotion
- 多分支比较
- 完整 campaign 治理
- 分支淘汰和归档

所以现在第三层的状态更准确地说是：

**基础底座已经有了，但仍然属于初步实现阶段。**

---

## 10. 第三层和当前工作的关系

当前主工作仍然是第一层和第二层。

也就是说：

- 先把单任务执行层做稳
- 先把 Judge 和经修 Agent 的闭环做稳
- 先让真正的专家经验稳定产出

第三层当前先做到：

- 不破坏前两层
- 先留出正确接口
- 先实现最小可用的传播实验底座

等前两层真正稳定之后，再把第三层继续往：

- 多分支
- merge
- promotion
- 更复杂传播方法

这些方向推进。

---

## 11. 一句话总结

第三层是：

**建立在现有专家经验之上的传播实验层，它负责版本、分支、候选、评估、合并和晋升；它包含第二层的方法，但不会被第二层的方法所限制。**
