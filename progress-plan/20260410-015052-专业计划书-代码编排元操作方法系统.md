# 专业计划书：代码编排的元操作方法系统

日期：2026-04-10

## 1. 背景与问题定义

当前 `auto-evolve` 已经具备：

- OpenCode 调用能力
- 知识库读写能力
- 评分器
- 监控能力
- 基线方法 `sequential-refine`

但当前的关键问题是：

1. 复杂学习流程仍然主要耦合在 `case-runner.ts`
2. 之前尝试的 `FLOW.md` 方案只能自然表达线性阶段，不适合完整承载：
   - 条件分支
   - 循环
   - 回滚
   - 多候选
   - 双分支实验
3. “回传”作为反馈构造方式，理应属于具体方法，而不应继续被系统固定死

因此，本计划书提出的正式方向是：

**采用“元操作 + 方法代码编排”的架构。**

---

## 2. 核心设计原则

### 2.1 元操作稳定

所有方法共享一套稳定的原子动作。

### 2.2 方法用代码实现

每种反向传播方法使用独立代码模块定义自己的控制流，不依赖 Markdown DSL 承担复杂执行职责。

### 2.3 Markdown 继续保留

Markdown 仍然是以下内容的主载体：

- 方法说明
- 人类可读流程
- Prompt 模板
- 知识内容

但不再作为复杂运行时控制的唯一真源。

### 2.4 系统主干不被方法污染

新增方法不应导致主系统出现越来越多的条件分支。

---

## 3. 目标架构

### 3.1 Kernel 层

职责：

- 运行 OpenCode
- 读写 knowledge-pack
- 评估结果
- 写 artifacts
- 监控 session

现有相关模块：

- `auto-evolve/orchestrator/opencode.ts`
- `auto-evolve/orchestrator/knowledge-pack.ts`
- `auto-evolve/orchestrator/evaluator.ts`
- `auto-evolve/monitor-server.ts`

### 3.2 Primitive Ops 层

职责：

- 提供方法可复用的稳定动作接口

建议的标准元操作集合：

- `solveCase`
- `evaluateResult`
- `buildFeedbackPacket`
- `refineKnowledge`
- `verifyCurrentCase`
- `runRegressionSuite`
- `snapshotKnowledge`
- `restoreKnowledge`
- `classifyFailure`
- `routeRefineTargets`
- `acceptOrRejectChange`
- `recordScorecard`
- 后续扩展：
  - `adversarialProbe`
  - `branchKnowledge`
  - `selectBestBranch`

### 3.3 Method Strategy 层

职责：

- 定义某一种方法如何组织元操作

典型方法模块：

- `SequentialRefineMethod`
- `SequentialLiteMethod`
- `AdversarialTestMethod`

每个方法负责：

- 主循环
- 分支判断
- 反馈包构造方式
- 接受/拒绝策略
- 是否使用回归
- 是否使用对抗探测

### 3.4 Documentation / Prompt 层

职责：

- `METHOD.md`：方法说明
- `FLOW.md`：人类可读流程图
- `prompts/*.md`：模型提示词

这些文件继续保留，但不再承担复杂控制流解释器的职责。

---

## 4. 为什么不再采用“Markdown 作为执行流程真源”

### 4.1 表达能力不足

复杂方法需要表达：

- 条件分支
- 循环
- rollback
- accept / reject
- next attempt
- branch compare

这些结构用 Markdown 线性列表表达，天然不充分。

### 4.2 会演化成 DSL

如果继续强化 `FLOW.md`，最终必然要支持：

- condition
- loop
- labels
- jumps
- retry semantics

这本质上是在创造一门专用流程语言，维护成本很高。

### 4.3 调试难度上升

一旦执行语言变成“配置式 DSL”，排查复杂方法行为通常会比排查代码更困难。

因此，Markdown 适合作为说明和模板，不适合作为复杂方法执行真源。

---

## 5. 推荐的运行模型

### 5.1 执行入口

外层仍然通过：

- `bootstrap`
- `run-case`
- `run-round`
- `run-baseline`

进入系统。

### 5.2 方法选择

由入口选择某个方法模块，例如：

- `sequential-refine`
- `sequential-lite`
- `adversarial-test`

### 5.3 方法内部控制

方法模块内部按代码逻辑调用元操作。

示意：

```text
method.run(context):
  solveCase()
  if passed: return
  if evalMode: return
  feedback = buildFeedbackPacket(...)
  refineKnowledge(feedback)
  verifyCurrentCase()
  runRegressionSuite()
  acceptOrRejectChange()
```

这种方式比 Markdown flow 更容易表达真实复杂路径。

## 6. 推荐的数据与代码组织

### 6.1 代码目录建议

```text
auto-evolve/
  orchestrator/
    kernel/
    primitives/
      solve-case.ts
      build-feedback-packet.ts
      refine-knowledge.ts
      verify-current-case.ts
      run-regression-suite.ts
      accept-or-reject-change.ts
    methods-runtime/
      sequential-refine.ts
      sequential-lite.ts
      adversarial-test.ts
```

### 6.2 文档目录继续保留

```text
auto-evolve/
  methods/
    sequential-refine/
      METHOD.md
      FLOW.md
      prompts/
        bootstrap.md
        solve.md
        refine.md
    adversarial-test/
      METHOD.md
      FLOW.md
      prompts/
        solve.md
        adversarial_probe.md
        refine.md
```

这里的 `FLOW.md` 定位调整为：

- 面向人类理解
- 面向方法说明
- 不承担复杂执行真源

## 7. 当前系统如何迁移

### 7.1 保留已有成果

当前已经有价值的部分继续保留：

- `primitives.ts`
- `method-runtime.ts`
- `method_runtime.json`
- `methods/` 目录结构

### 7.2 调整职责

当前需要调整的是：

- 不再继续强化 `FLOW.md` 的执行语义
- 把 `case-runner.ts` 中剩余逻辑逐步拆到 `primitives/`
- 新增 `methods-runtime/*.ts` 作为真正的策略代码

### 7.3 保持行为稳定

迁移第一阶段应保证：

- `sequential-refine` 对外行为不变
- artifacts 结构尽量兼容
- 评分逻辑不变

---

## 8. 第一阶段实施计划

### 阶段 A：冻结 `FLOW.md` 职责

目标：

- 明确 `FLOW.md` 为文档，不再作为复杂控制流真源

产出：

- 方法文档职责说明
- 运行时职责调整说明

### 阶段 B：提取元操作模块

目标：

- 将 `case-runner.ts` 中的核心动作拆成独立 primitive 模块

优先提取：

- `solveCase`
- `prepareRefineFeedback`
- `refineKnowledge`
- `verifyCurrentCase`
- `runRegressionBeforeRefine`
- `runRegressionAfterRefine`
- `acceptOrRejectChange`

### 阶段 C：新增方法策略代码

目标：

- 用代码定义 `SequentialRefineMethod`

要求：

- 行为与当前基线一致
- 只调整架构，不改策略

### 阶段 D：新增第二方法

目标：

- 增加 `SequentialLiteMethod`

作用：

- 作为当前保守基线方法的轻量对照组

### 阶段 E：再接入 `AdversarialTestMethod`

目标：

- 让对抗测试成为真正独立的方法，而不是在主流程上打补丁

---

## 9. 推荐优先级

建议顺序如下：

1. 停止把 `FLOW.md` 继续发展成执行语言
2. 拆元操作模块
3. 把当前基线方法改写成 `SequentialRefineMethod`
4. 新增 `SequentialLiteMethod`
5. 跑基线对照
6. 再实现 `AdversarialTestMethod`
7. 最后再接 Git-tree 双分支实验

---

## 10. 风险与控制

### 风险 1：迁移过程中行为漂移

控制方式：

- 先保证 `SequentialRefineMethod` 与当前行为一致
- 每一步做 smoke test

### 风险 2：元操作拆分不彻底

控制方式：

- 优先把重逻辑从 `case-runner.ts` 迁出
- 避免“名义上方法化，实际上主逻辑还全在旧文件里”

### 风险 3：文档与代码脱节

控制方式：

- 保留 `METHOD.md` 和 `FLOW.md`
- 把它们明确定位为说明文档
- 不让它们承担复杂执行真源

---

## 11. 最终判断

综合考虑复杂条件、循环、双分支实验、未来多种反向传播方法的扩展性之后，
正式建议如下：

**采用“元操作 + 方法代码编排”的方案。**

同时保留 Markdown 作为：

- 方法说明
- 人类可读流程
- Prompt 模板
- 知识内容

不再把 Markdown 当成复杂控制流的唯一执行来源。

这条路线更稳、更容易测试、更适合未来扩展。
