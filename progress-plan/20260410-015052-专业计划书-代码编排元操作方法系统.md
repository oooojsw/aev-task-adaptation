# 专业计划书：元操作 + 方法代码 + 经修 Agent + 可演化经验工作区

日期：2026-04-10

## 1. 目标定义

本系统的长期目标不是单纯维护一套固定知识包，而是构建一个可持续演化的“专家经验系统”。

该系统需要同时满足：

1. 元操作可扩展
2. 反向传播方法可扩展
3. 经验体系结构可扩展
4. 不同方法之间可比较
5. 未来可支持双分支实验、版本保留、候选淘汰、甚至经验权重

基于此，正式建议采用以下架构：

**元操作层 + 方法代码层 + 经修 Agent 层 + 可演化经验工作区。**

---

## 2. 核心判断

### 2.1 不再把复杂控制流交给 Markdown

复杂控制流包含：

- 条件分支
- 循环
- rollback
- accept / reject
- next attempt
- branch compare

这些能力不适合继续让 `FLOW.md` 作为执行真源。

因此：

- `FLOW.md` 保留
- 但其职责调整为方法说明文档
- 真正的运行时控制交给代码方法模块

### 2.2 不再把经验体系写死成固定结构

当前 `knowledge-pack` 只是经验体系的当前默认实现，不应被视为永久规范。

后续系统必须允许：

- 增加文件
- 删除文件
- 拆分文件
- 合并文件
- 调整目录布局
- 保留多个版本
- 维持候选集合

因此应将当前固定知识包概念升级为：

**经验工作区（Experience Workspace）**

### 2.2.1 模板库与经验工作区必须分离

系统中应同时存在：

1. 模板库（Template Library）
2. 经验工作区（Experience Workspace）

模板库的职责：

- 提供结构模板
- 提供索引模板
- 提供工具使用说明模板
- 提供专题组织方式参考

经验工作区的职责：

- 承载当前真正有效的专家经验
- 作为 solve agent 的长期记忆来源

关键约束：

- 经修 Agent 可以读取模板库
- 但模板库内容不直接视为经验工作区的一部分
- 最终经验工作区只保留当前有效经验，不保留整套模板本体

### 2.3 经验体系维护必须 agent 化

经验体系的维护并非简单文件编辑，而是结构演化问题。

因此：

- 经验体系不应完全由纯代码直接维护
- 应引入专门的知识维护 agent

该 agent 在本计划中命名为：

**经修 Agent**

### 2.3.1 当前阶段的权限策略

当前阶段的正式策略应明确为：

- 经修 Agent 暂不采用严格硬权限切分
- 当前优先目标是打通整条系统链路
- 对经修 Agent 的约束主要来自：
  - 提示词契约
  - 方法层给出的修改要求
  - 验证 / 回滚机制

换句话说，当前阶段采用的是：

**软约束优先，硬权限后置。**

这样做的理由是：

- 可以先观察经修 Agent 的真实修改模式
- 可以先验证 Experience Workspace 设计是否合理
- 可以避免过早权限限制掩盖系统主问题

## 3. 总体架构

建议架构分为五层。

### 3.1 Kernel 层

职责：

- OpenCode 调用
- 评估器
- artifacts 管理
- 监控
- 运行上下文

现有对应模块：

- `auto-evolve/orchestrator/opencode.ts`
- `auto-evolve/orchestrator/evaluator.ts`
- `auto-evolve/monitor-server.ts`

### 3.2 Primitive Ops 层

职责：

- 提供稳定、原子、可复用的系统动作接口

当前和未来建议元操作包括：

- `solveCase`
- `evaluateResult`
- `buildFeedbackPacket`
- `invokeKnowledgeMaintainer`
- `verifyCurrentCase`
- `runRegressionSuite`
- `snapshotExperienceWorkspace`
- `restoreExperienceWorkspace`
- `classifyFailure`
- `routeKnowledgeChangeIntent`
- `acceptOrRejectChange`
- `recordScorecard`
- 后续扩展：
  - `adversarialProbe`
  - `branchExperienceWorkspace`
  - `selectBestVariant`
  - `mergeAcceptedKnowledge`

### 3.3 Method Strategy 层

职责：

- 每种反向传播方法用独立代码模块定义自己的控制流

方法示例：

- `SequentialRefineMethod`
- `SequentialLiteMethod`
- `AdversarialTestMethod`
- `VariantRetainMethod`
- `WeightedKnowledgeMethod`

每个方法负责：

- 主循环
- 分支逻辑
- 反馈包构造
- 经修 Agent 调用方式
- 验证策略
- 接受/拒绝策略

### 3.4 经修 Agent 层

职责：

- 读取当前经验工作区
- 根据方法要求维护经验体系
- 在允许范围内增删改经验文件和目录
- 保持经验体系可读、可追踪、可供新 agent 使用

经修 Agent 不是策略制定者，而是知识维护执行者。

补充说明：

- 当前阶段，经修 Agent 主要通过提示词被约束
- 未来阶段，再逐步引入运行时硬权限边界

### 3.5 Experience Workspace 层

职责：

- 承载整个长期专家经验体系

注意：

- 当前 `knowledge-pack/` 只是该层的第一版实现
- 未来它可以演化成更复杂的结构
- 未来它必须支持“单入口 + 分区 + 选择性读取”

## 4. 关键角色划分

### 4.1 解题 Agent

职责：

- 使用当前经验工作区求解具体案例

不负责：

- 设计经验结构
- 长期维护知识体系
- 决定实验策略

### 4.2 经修 Agent

职责：

- 接受方法层给出的“知识修改意图”
- 在当前经验工作区内重组和维护经验体系
- 必要时参考模板库设计经验结构

经修 Agent 允许做的事：

- 新增经验文件
- 删除过时文件
- 拆分主题
- 合并碎片经验
- 重写索引
- 调整目录结构
- 维护版本说明
- 根据任务规模调整经验分区布局
- 为 solve agent 维护统一入口文件
- 为任务场景维护工具使用说明文档

经修 Agent 不允许做的事：

- 修改数据集
- 擅自改核心系统代码
- 擅自越过方法层定义的约束

说明：

上述“不允许”在当前阶段主要依赖：

- 提示词契约
- 方法层约束
- 验证与回滚

而不是立即通过重型硬权限系统强制执行。

### 4.3 方法代码

职责：

- 定义什么时候调用经修 Agent
- 给经修 Agent 什么修改目标
- 决定修改后如何验证
- 决定是否接受经验工作区变更

---

## 5. 为什么经修 Agent 必须存在

原因有三类。

### 5.1 经验体系维护本质上是“结构性工作”

它不是单纯“补一条规则”。

它可能涉及：

- 信息归类
- 规则抽象
- 反例提炼
- 文件重组
- 主题拆分
- 版本保留

这些动作更接近“知识编辑器”，而不是固定模板替换器。

### 5.2 不同方法对经验体系有不同要求

例如：

- 顺序法可能要求最小修改
- 对抗法可能要求单独沉淀脆弱点专题
- 多版本法可能要求同时保留多个知识版本
- 权重法可能要求把经验区分成高优先级与低优先级

如果全靠固定代码写死，将很快失控。

### 5.3 经验体系未来一定会扩张

当前固定文件布局在小规模数据下可用，但一旦系统扩大：

- 知识量会迅速上升
- 失败模式会增多
- 不同方法可能产生不同形态的知识

因此经验体系必须可演化。

## 6. Experience Workspace 的正式定义

Experience Workspace 是“长期专家记忆”的工作区。

它具备以下特征：

1. 当前默认实现可以是 `knowledge-pack/`
2. 但它不被限定为固定文件集合
3. 它允许在约束内改变自身结构
4. 它应始终可供新的 solve agent 理解和使用

并且建议增加以下硬约束：

5. 必须存在一个统一入口文件
6. solve agent 默认不进行全量读取
7. 经验内容应支持按分区或主题进行选择性加载
8. 模板库不直接并入 Experience Workspace

建议未来至少包含以下概念性组件：

- 总索引
- 统一入口文件
- 核心规则
- 输出约束
- 执行策略
- 失败教训
- 特例集合
- 工具使用说明文档
- 分区索引
- 方法特定经验
- 候选版本或变体集合
- 变更记录

这里强调“概念性组件”，而不是写死具体文件名。

### 6.1 建议的读取协议

未来 solve agent 的推荐读取方式应为：

1. 先读取统一入口文件
2. 根据当前任务判断所属任务类型 / 领域 / 工具类型
3. 再按入口文件导航，选择性读取相关分区
4. 只在必要时继续向下钻取更细文档

不建议：

- 每次 solve 都全量读取整个经验工作区

理由：

- 经验规模增长后成本过高
- 容易把无关经验引入当前任务
- 不利于大型系统稳定运行

## 7. 经修 Agent 的输入与输出

### 7.1 输入

经修 Agent 至少需要接收：

- 当前经验工作区路径
- 模板库路径或模板引用集
- 当前方法要求
- 当前失败案例材料
- 实际输出
- 标准答案
- 结构化评估结果
- 行为轨迹
- 允许的修改边界

### 7.2 输出

经修 Agent 输出的不是一句解释，而是：

- 修改后的经验工作区
- 修改说明
- 改动摘要
- 受影响区域说明

在某些方法下，输出还可能包括：

- 新增版本
- 候选分支
- 优先级调整建议

在大型体系下，还可能包括：

- 新分区设计
- 新入口导航调整
- 新工具说明文档
- 不再加载的旧区域说明

### 7.3 当前阶段的执行原则

当前阶段建议采用以下原则：

1. 先允许经修 Agent 在提示词约束下维护 Experience Workspace
2. 先不引入很重的文件级或目录级硬权限
3. 先通过：
   - 当前 case 验证
   - 回归验证
   - 接受 / 拒绝
   来控制风险
4. 在观察到真实修改模式后，再设计细粒度权限系统

## 8. 方法层如何与经修 Agent 协作

这是本系统最关键的接口。

方法层不直接改经验文件，而是通过以下过程与经修 Agent 协作：

1. 先运行 solve
2. 生成评估结果
3. 根据方法定义构造反馈包
4. 将反馈包和修改要求交给经修 Agent
5. 经修 Agent 修改经验工作区
6. 方法层执行验证
7. 方法层决定接受或拒绝

这意味着：

**回传 = 方法层构造给经修 Agent 的反馈包**

这一点以后必须成为正式系统定义，而不再是隐式逻辑。

同时补充：

- 方法层还应告诉经修 Agent 本次允许的结构性动作
- 例如：
  - 是否允许新增分区
  - 是否允许保留多个版本
  - 是否允许只保留一个最优版本
  - 是否允许加入工具说明文档

当前阶段建议进一步明确：

- 方法层先通过提示词告诉经修 Agent 允许做什么
- 方法层先不依赖复杂硬权限去限制每个细动作
- 当前优先级是“整条链先跑通”，不是“第一天就收得非常死”

---

## 8.1 需要现在就固定的稳定接口

为了最大化泛化性和稳定性，建议现在就固定以下四类接口。

### A. 经修 Agent 契约

经修 Agent 的长期稳定职责应固定为：

- 维护 Experience Workspace
- 不直接承担实验调度
- 不直接替代 solve agent
- 不直接决定哪种方法获胜

建议固定输入：

- `workspace_root`
- `entry_document`
- `template_refs`
- `method_intent`
- `case_context`
- `evaluation`
- `action_trace`
- `change_budget`

建议固定输出：

- `workspace_delta`
- `change_summary`
- `structure_changes`
- `read_guidance_updates`

### B. Experience Workspace 不变量

建议现在就固定以下不变量：

1. 必须有单入口文件
2. solve agent 默认按入口导航做选择性读取
3. 所有有效经验必须可导航
4. 模板库不直接并入 Experience Workspace
5. 工具说明文档是合法的一等内容

这些不变量比具体目录结构更重要。

### C. Method Interface

每种方法应统一返回三类东西：

1. 给经修 Agent 的修改意图
2. 本轮允许的结构动作
3. 本轮验证与接受标准

这样新增方法时，不需要重新发明系统接口。

### D. 权限演化路线

当前阶段：

- 软约束优先

后续阶段：

- 工作区边界
- 方法授权边界
- 结构性规则边界

应将此视为正式路线，而不是未来再临时决定。

## 11. 当前系统如何迁移到新架构

### 第一阶段：保留当前成果

已存在并仍有价值的内容：

- 元操作命名
- 运行时轨迹
- `method_runtime.json`
- 方法目录结构

### 第二阶段：重新定义职责

应明确：

- `FLOW.md` 是说明文档，不是复杂执行真源
- 当前固定 `knowledge-pack` 只是 Experience Workspace v1
- 当前 `refine` 不应再被视为“直接改文件逻辑”，而应演化成“调用经修 Agent”

### 第三阶段：引入经修 Agent 契约

正式定义：

- 经修 Agent 输入格式
- 允许修改的边界
- 需要维护的可读性要求
- 变更记录要求

### 第四阶段：将方法代码改为调用经修 Agent

把当前 `SequentialRefineMethod` 作为第一种使用经修 Agent 的方法。

### 第五阶段：扩展第二种方法

先做：

- `SequentialLiteMethod`

后做：

- `AdversarialTestMethod`

## 12. 推荐优先级

建议顺序如下：

1. 正式定义 Experience Workspace 概念
2. 正式定义模板库与经验工作区的边界
3. 正式定义经修 Agent 契约
4. 正式定义 Experience Workspace 的不变量：
   - 单入口
   - 可导航
   - 选择性读取
   - 模板库分离
5. 把当前 `knowledge-pack` 降级为 Experience Workspace 的默认实现
6. 把当前顺序法改造成“调用经修 Agent”的方法
7. 设计轻量顺序法
8. 再设计对抗测试法
9. 最后接入 Git-tree 双分支实验

## 13. 风险与控制

### 风险 1：经修 Agent 过度自由

控制方式：

- 限定工作区范围
- 限定方法授权
- 强制变更说明
- 保持可回滚

当前阶段的实际控制手段应补充为：

- 先通过提示词契约控制
- 先通过验证与回滚控制
- 先不通过严格硬权限阻断

未来阶段再补：

- 工作区级硬边界
- 方法级结构权限
- 文件 / 目录级限制
- 单入口与索引的强约束校验

### 风险 2：经验体系结构失控

控制方式：

- 经修 Agent 必须维护索引与结构说明
- 验证环节要检查可读性与可用性

### 风险 3：方法与知识维护耦合过强

控制方式：

- 方法只提出要求
- 经修 Agent 负责执行
- 接受/拒绝仍由方法和验证层决定

---

## 14. 最终结论

正式建议如下：

**未来系统应采用“元操作 + 方法代码 + 经修 Agent + 可演化经验工作区”的架构。**

其核心思想是：

- 元操作负责稳定动作
- 方法代码负责反向传播策略
- 经修 Agent 负责经验体系维护
- 经验工作区负责承载长期专家记忆

这条路线比“固定知识包 + 固定回传 + Markdown 流程控制”更适合未来复杂系统扩展。

当前落地顺序必须明确为：

1. 先跑通“方法代码 + 经修 Agent + Experience Workspace”
2. 当前经修 Agent 主要通过提示词契约约束
3. 后续再补强为正式的权限控制体系
