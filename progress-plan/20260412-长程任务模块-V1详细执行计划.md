# 长程任务模块 V1 详细执行计划

## 1. 目标

长程任务模块 V1 的目标不是继续扩短程流程，而是建立一个与短程任务模块平级的第一层执行模块。

这个模块要解决的是：

- 给定 `Task Goal（任务目标）`
- 给定 `Materials（材料）`
- 给定 `Initial Expert Context（初始专家经验）`
- 给定 `Validator Contracts（验证器契约）`

系统可以：

1. 自举 `Work Graph（工作图）`
2. 逐个执行 `Work Unit（工作单元）`
3. 围绕验证器进行局部验证和局部重试
4. 把失败沉淀成 `Failure Packets（失败包）`
5. 把运行中经验沉淀到 `Run-local Scratch Memory（运行内临时记忆）`
6. 在结束时写入：
   - `Evidence Archive（证据归档）`
   - `Shadow Operational Memory（影子运行记忆）`

---

## 2. V1 范围

### 2.1 本轮必须实现

- 新的长程任务契约模型
- 长程任务 spec 加载与校验
- validator-driven 工作图自举
- work-unit 执行循环
- validator 执行器
  - `script`
  - `prompt_json`
- 局部重试与 graph replan
- 明确的终止策略
- archive / shadow-memory 收口
- CLI 命令：
  - `run-long-task`
  - `resume-long-task`
- 示例 spec 与示例 validator

### 2.2 本轮不继续外扩

- 不实现第四层优化器
- 不实现自动 shadow-memory 检索回灌
- 不实现复杂多 run 合并
- 不实现独立的人工 gate 流程

这些不是删掉，而是先不作为 V1 的阻塞项。

## 3. 设计原则

### 3.1 验证器优先

长程任务不是先规划一大堆阶段，再最后想怎么验；而是：

**先接住验证器，再围绕验证器去执行和学习。**

### 3.2 不要求人类提供工作图

用户不需要先手工拆 `Work Graph` 或给几个 `Work Unit`。

系统必须根据：

- goal
- materials
- targets
- expert context
- validators

自己自举出第一版工作图。

### 3.3 不允许经验丢失

失败经验不丢。

所有运行结果都至少进入：

- `Evidence Archive`

之后再决定 shadow 和记忆级别。

### 3.4 优先局部恢复

长程任务不能默认整题重跑。  
优先顺序是：

- `tool retry`
- `work unit retry`
- `subgraph retry / graph replan`
- 终止

### 3.5 只认验证器结果

agent 可以声称成功，但系统完成标准永远由验证器裁决。

## 4. 核心对象

### 4.1 `LongTaskSpec`

字段核心包括：

- `title`
- `goal`
- `taskFamily`
- `domainTags`
- `materials`
- `targetPaths`
- `editablePaths`
- `initialExpertContextPaths`
- `validators`
- `budgets`
- `shadowMemoryScope`
- `reversePropagation`

### 4.2 `ValidatorContract`

V1 支持两种：

#### `script`
- 本地脚本验证器
- 支持 `python / bun / node / powershell / direct`
- 默认可接收统一 JSON 输入包

#### `prompt_json`
- 纯 prompt 验证器
- 通过单独 session 运行
- 必须返回结构化 JSON：
  - `passed`
  - `summary`
  - `details`
  - `blocking`

### 4.3 `WorkGraph`

包含：

- `revision`
- `plannerSummary`
- `completionValidatorIDs`
- `units[]`

### 4.4 `WorkUnit`

每个单元包含：

- `id`
- `title`
- `goal`
- `inputs`
- `dependsOn`
- `expectedArtifacts`
- `claim`
- `checkPlan`
- `validatorIDs`
- `retryBudget`
- `status`
- `attemptCount`

### 4.5 `ProgressState`

记录：

- 当前 run 状态
- graph revision
- active unit
- 当前 attempt
- 已完成 / 失败 / 阻塞单元
- validator 调用计数
- graph replan 计数
- no-progress 计数
- final summary

### 4.6 `VerificationClaim`

每次工作单元执行后写入：

- 当前 claim
- claimedSuccess
- blockers
- nextPriorityFix
- evidenceRefs

### 4.7 `FailurePacket`

每次关键失败写入：

- unit
- attempt
- failureType
- retryLevel
- claimedSuccess
- verificationPassed
- mismatchSummary
- suspectedCauses
- nextPriorityFix
- evidenceRefs
- promotionHint

### 4.8 `ScratchUnit`

运行中的 agent 主要追加写这个。

类型包括：

- `claim`
- `obs`
- `map`
- `hyp`
- `fail`
- `fix`
- `rule_candidate`
- `verified`

### 4.9 `LearningUnit`

比 scratch 更稳定的候选学习对象。

类型包括：

- `obs`
- `map`
- `rule`
- `exception`
- `failure_pattern`
- `repair_pattern`
- `tooling_hint`
- `validator_hint`

### 4.10 `RetryInputBundle`

下一次重试时系统给当前 agent 的最小输入包。

包含：

- current unit
- recent claims
- recent failure packets
- relevant scratch units
- relevant learning units
- progress state

## 6. 执行流程

### 6.1 `run-long-task`

1. 读取 spec
2. 初始化 run
3. 写 placeholder graph
4. 启动 `Graph Bootstrap`
5. 得到初始工作图
6. 切换状态为 `running`
7. 进入 work-unit loop

### 6.2 `Graph Bootstrap`

输入：

- spec
- materials
- targets
- expert context
- validators

输出：

- `planner_summary`
- `completion_validator_ids`
- `units`

如果输出无效：

- 自动回退到 `fallback graph`
- 至少生成一个完整任务单元，挂所有 required validators

### 6.3 `Work Unit Execution`

每轮：

1. 选择下一个 ready unit
2. 激活 unit
3. bump attempt count
4. 构建 `RetryInputBundle`
5. 启动执行 session
6. 解析执行 JSON 输出
7. 写 claim
8. 写 scratch units
9. 写 learning units
10. 运行本 unit validators

### 6.4 `Validator Pass / Fail`

如果本单元 validators 全通过：

- 标记 unit 为 `verified`
- reset `noProgressCycles`
- 继续下一个 unit

如果失败：

- 生成 `FailurePacket`
- 写 `RetryJournal`
- 根据预算决定：
  - 继续当前 unit retry
  - 触发 replan
  - 终止

### 6.5 `Completion Validation`

当所有 unit 都 verified 后：

1. 运行 `completionValidatorIDs`
2. 如果全部通过：
   - `verified_success`
3. 如果失败：
   - 生成 completion failure packet
   - 优先尝试 replan
   - 否则结束为 failure

---

## 7. 重试策略

### 7.1 `tool retry`

由执行 session 内部工具自行重试，小范围。

### 7.2 `work unit retry`

默认主策略。  
单元失败但未超出 `retryBudget` 时，继续围绕当前单元重试。

### 7.3 `subgraph retry / graph replan`

当前单元多次失败后，不直接整题重来，而是：

- 读取最近 failure packets
- 运行 replan session
- 生成新一版剩余工作图

### 7.4 `run retry`

V1 不把整次 run retry 当主策略；主要依靠 graph replan 来避免整题重跑。

---

## 8. 终止策略

长程任务不会无限循环。

只会落到 4 种终态：

- `verified_success`
- `exhausted_failure`
- `stagnation_failure`
- `blocked_failure`

判定逻辑：

### `verified_success`
- 所有 completion validators 通过

### `exhausted_failure`
- `maxTotalUnitAttempts`
- `maxValidatorCalls`
- `maxGraphReplans`
  任意核心预算耗尽

### `stagnation_failure`
- `noProgressCycles >= maxNoProgressCycles`

### `blocked_failure`
- 没有 ready unit
- graph 无法继续 replan

---

## 9. 记忆去向

### 9.1 `Evidence Archive`

全部 run 都写 archive 记录。  
这是无条件保留层。

### 9.2 `Shadow Operational Memory`

每次 run 结束都会写一条 shadow-memory 记录，但默认：

- 有 namespace
- 有 tags
- 有 retrievalMode
- 不会自动全局污染其他任务

默认推荐：

- `retrievalMode = isolated`

### 9.3 `Canonical Candidate`

V1 先只预留目录，不自动推进到 canonical。

---

## 10. 与现有系统的关系

### 10.1 与短程模块

- 平级
- 不替代
- 共享 `Reverse Propagation Control Plane`

### 10.2 与第二层

- 长程运行直接产出 `FailurePacket` 和 `LearningUnit`
- 这些后面可作为第二层维护输入
- 但 V1 不直接把长程失败自动写入 canonical expert memory

### 10.3 与第三层

- 当前不强耦合
- 后续可把 long-task 结果作为 version-governance 的候选输入

### 10.4 与第四层

- 当前只做兼容位
- 不在 V1 实现全局优化器联动

## 12. V1 完成标准

满足以下条件即视为本轮完成：

1. 用户不需要手工给工作图即可启动长程任务
2. 长程任务可以从 spec 直接启动
3. 系统会自举工作图
4. 系统会执行至少一轮工作单元
5. 系统会自动运行 validator
6. validator 失败会产生 failure packet
7. 长程任务有局部 retry / replan
8. 长程任务有明确终止条件
9. run 结束后会写 summary + archive + shadow-memory
10. CLI 下次可直接复用，不需要再补骨架
