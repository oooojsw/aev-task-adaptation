# 长程任务模块 V1 易读版

## 这次真正改了什么

这次长程任务模块不再要求人类先手工拆 `Work Graph（工作图）` 或先给几个 `Work Unit（工作单元）`。

现在的核心改成：

- 给系统 `Task Goal（任务目标）`
- 给系统 `Materials（材料）`
- 给系统 `Initial Expert Context（初始专家经验）`
- 给系统 `Validator Contracts（验证器契约）`

然后系统自己先做：

- `Graph Bootstrap（工作图自举）`
- `Work Unit Execution（工作单元执行）`
- `Validator-driven Retry（围绕验证器重试）`
- `Failure Packet Learning（失败包学习）`

也就是说，长程任务现在是：

**先把验证器接住，再围绕验证器去执行、修正、学习。**

---

## 长程任务和短程任务的关系

长程任务模块和短程任务模块是平级的，不是谁包谁。

- `Short-Task Module（短程任务模块）`
  - 适合单 case、短会话、失败后整轮重试
- `Long-Task Module（长程任务模块）`
  - 适合复杂目标、长链路执行、局部失败恢复、失败经验积累

它们共享：

- `Reverse Propagation Control Plane（反向传播控制平面）`

所以以后短程能挂的很多反向传播能力，长程也能挂，只是挂法不同。

---

## 长程任务现在的核心对象

### `Long Task Spec（长程任务说明）`
人类提供的唯一正式入口。

里面描述：

- 任务标题
- 任务目标
- 材料路径
- 目标文件路径
- 可编辑路径
- 初始专家经验路径
- 验证器列表
- 预算
- 影子记忆范围

---

### `Validator Contract（验证器契约）`
这是长程模块的中心。

当前支持两类：

- `script`
  - 本地脚本验证器
- `prompt_json`
  - 纯 prompt 验证器，但必须返回结构化 JSON

重要边界：

- 验证器来自人类或初始专家经验
- 不是运行中的 agent 临时自己发明

---

### `Work Graph（工作图）`
系统会自己根据：

- 任务目标
- 材料
- 目标路径
- 初始专家经验
- 验证器契约

去自举一版初始工作图。

如果规划结果不稳定，系统会自动退回一个最小 fallback 图，不会因为第一步规划失败就完全卡死。

---

### `Work Unit（工作单元）`
长程任务里最小的“可验证、可局部重试”的语义工作块。

每个单元都必须有：

- `goal`
- `claim`
- `check_plan`
- `validator_ids`
- `retry_budget`

所以不是简单的一次命令，也不是文件切块，而是一个能被验证器检查的局部义务。

---

### `Verification Claim（验证声明）`
每次单元执行后，agent 要输出：

- 我现在声称完成了什么
- 我是否认为自己成功了
- 当前 blocker 是什么
- 下一步优先修什么

这能把：

- `claimed success（自认为成功）`
- `verified failure（验证失败）`

这种非常关键的长程失败，正式记录下来。

---

### `Failure Packet（失败包）`
每次关键失败都会被系统写成正式对象。

里面至少会有：

- 失败单元
- 当前 attempt
- 失败类型
- 自认为成功还是失败
- 验证器结果
- mismatch 摘要
- 疑似原因
- 下一步优先修复点

所以长程任务不是“失败一次就没了”，而是每次失败都变成结构化学习资产。

---

### `Run-local Scratch Memory（运行内临时记忆）`
长程运行过程中，agent 不会乱写很多文件。

现在的设计是：

- agent 主要追加写 `scratch_units.jsonl`
- 系统自动维护：
  - `scratch_index.json`
  - `scratch_summary.md`
  - `claims.jsonl`
  - `failure_packets.jsonl`
  - `learning_units.jsonl`
  - `retry_journal.jsonl`

这样既能持续追加，又不会让运行中的记忆结构失控。

---

## 重试现在怎么做

长程任务现在不是“整题失败就整轮重来”，而是 4 层重试：

- `tool retry`
  - 工具级小修复
- `work unit retry`
  - 当前工作单元局部重试
- `subgraph retry`
  - 当前单元连续失败后，局部修图和重排
- `run retry`
  - 现在还不作为默认主路线，V1 主要靠局部恢复和 replan

系统的真实目标是：

**让任务尽可能局部修正后继续推进，而不是频繁从头来。**

---

## 怎么避免无限循环

现在长程模块有明确的 `Termination Policy（终止策略）`。

会以 4 种方式结束：

- `verified_success`
  - 所有必要验证器通过
- `exhausted_failure`
  - 尝试预算、验证器调用预算、replan 预算耗尽
- `stagnation_failure`
  - 连续很多轮没有真实进展
- `blocked_failure`
  - 没有可推进单元，也无法继续修图

也就是说：

**系统只认验证器结果，不认 agent 自己“感觉已经完成了”。**

---

## 经验最后写到哪里

这里的原则已经定死了：

### 1. 不丢
所有长程运行的失败经验都会保留。

### 2. 先归档
全部先进入：

- `Evidence Archive（证据归档）`

### 3. 再进影子记忆
系统会额外写：

- `Shadow Operational Memory（影子运行记忆）`

而且默认是按：

- `taskFamily`
- `domainTags`
- `shadowMemoryScope`

隔离的，不会默认全局污染下一轮。

---

## 现在能直接怎么跑

新的命令入口是：

```bash
bun run auto-evolve/cli.ts run-long-task --spec auto-evolve/templates/long-task.example.json
```

如果中断后要继续：

```bash
bun run auto-evolve/cli.ts resume-long-task --run <run-id>
```

---

## 一句话总结

这版长程任务模块已经从“纯骨架”推进成了：

**一个可以围绕人类提供的验证器，自举工作图、执行工作单元、写失败包、做局部重试，并在结束后留下归档和影子记忆的第一版可运行系统。**
