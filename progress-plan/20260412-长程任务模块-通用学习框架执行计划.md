# 长程任务模块-通用学习框架执行计划

## 1. 背景判断

当前长程模块已经具备：

- `LongTaskSpec` / `WorkGraph` / `WorkUnit`
- `Validator Contract`
- `Failure Packet`
- `Scratch / Learning / Retry Bundle`
- `Archive / Shadow Memory`

但当前真实 try4 成功链中仍然混入了明显的任务专用脚手架：

- 任务专用 builder / generator 脚本
- 固定 `initialGraph`
- 固定成功路线
- prompt 中存在“优先走最短任务脚本路径”这类带任务落地暗示的规则

这会导致系统验证的是“辅助跑通能力”，不是“通用学习能力”。

本轮目标不是继续补某个任务的答案，而是把长程模块收回到：

`Goal + Validators + Capabilities + Failure Learning + Shadow Feedback`

这一条通用学习框架。

---

## 2. 本轮目标

本轮只做通用框架，不做任务专用答案。

### 2.1 必做

1. 为长程模块增加 `Capability Contract（能力契约）`
2. 让 `LongTaskSpec` 可以声明“有哪些能力可以被调用”，但不声明具体任务步骤
3. 去掉长程 planning / execution / replan prompt 中所有领域化、任务化步骤暗示
4. 把 `Shadow Memory` 真正接入 `Retry Input Bundle`
5. 让长程模块第一次具备：
   - `failure -> scratch`
   - `scratch -> shadow`
   - `shadow -> next retry`
   这一条最小闭环

### 2.2 明确不做

1. 不继续给 try4 写任何任务专用 builder / generator / defaults
2. 不实现新的领域脚本
3. 不实现完整第四层优化器
4. 不实现复杂多 run 的 shadow 检索排序器
5. 不在框架里写“某类材料应该先做什么后做什么”

---

## 3. 设计原则

### 3.1 系统只教方法，不教步骤

框架只回答：

- 当前目标是什么
- 当前验证器要求什么
- 当前缺的是哪类能力
- 当前失败值不值得升格成 shadow

框架不回答：

- 先读 Excel 再读 Word
- 先建字段映射再生成文档
- 某个任务必须先运行哪个脚本

### 3.2 skill 是能力实现，不是框架步骤

`minimax-docx` / `minimax-xlsx` 这类 skill 在框架里只以：

- `inspect`
- `transform`
- `validate`
- `compare`
- `synthesize`

这类能力契约出现。

### 3.3 验证器优先，但验证器允许演化

框架承认：

- 初始 validator 可能只有软目标约束
- 运行中可以长出局部 checker 候选
- 但最终 authoritative validator 仍然来自人类/初始专家经验/已注册能力

### 3.4 影子经验必须可回灌

如果 shadow memory 只在 run 结束时归档、不参与下一轮输入，那它不是学习闭环，只是归档。

---

## 4. 本轮代码改动范围

仅修改：

- `auto-evolve/orchestrator/long-task/*`
- 与长程模块直接相关的 `cli/validate/fs/schema` 若必须联动
- `progress-plan/*` 本轮计划文档

不修改：

- `auto-evolve/monitor-server.ts`
- 监控临时文件
- 非长程模块的业务逻辑

---

## 5. 具体施工项

### 5.1 `Capability Contract`

在长程契约中新增：

- `LongTaskCapabilityKind`
- `LongTaskCapabilityContract`
- `LongTaskCapabilityScope`

能力契约只表达：

- 能做什么
- 输入输出形态
- 是否偏读取/验证/变换/比较
- 允许引用哪些路径

不表达：

- 某个具体任务如何落地

### 5.2 `Spec` 扩展

在 `LongTaskSpec` 中增加：

- `capabilities`

并允许 validator / planning / execution prompt 使用这些能力说明作为“可调用资源”，而不是通过任务专用脚本硬编码。

### 5.3 Prompt 去领域化

重写长程模块 prompt 原则：

- Planning prompt：只强调“围绕目标与验证器构建最小可验证工作图”
- Execution prompt：只强调“围绕 claim 和 validator 推进”
- Replan prompt：只强调“围绕失败包修图”

移除：

- “优先用 task-local script 直接产出答案”
- “最短任务脚本路径”
- 任何带材料领域暗示的固定步骤

### 5.4 `Shadow Feedback V1`

在 `buildRetryInputBundle` 中增加：

- `relevantShadowMemory`

检索规则第一版：

- 默认只在 `shadowMemoryScope.namespace` 相同的范围内读
- `related_only` 再额外按 tags 取交集
- `manual` 暂时不自动注入
- 先限制数量，避免上下文膨胀

### 5.5 Shadow 升格规则收紧

不是任何 run 一结束都机械地写同质 `candidate`。

第一版收紧成：

- 成功 run：写 summary 型 shadow record
- 失败 run：如果存在 failure packets / learning units / scratch summary，则写更明确的 failure-oriented shadow record

### 5.6 校验

补充长程模块校验：

- capability ids 唯一
- validator ids 唯一
- spec 中 capability / validator / reverse propagation 引用合法
- shadow retrieval mode 合法

---

## 6. 预期成果

本轮完成后，长程模块应达到：

1. 框架层不再携带领域步骤
2. skill / script / checker 只以能力契约进入系统
3. shadow memory 第一次真正进入重试输入
4. 后续再做“自主长程学习”时，重点就只剩：
   - validator 演化
   - graph bootstrap 演化
   - task package 去专用脚手架

---

## 7. 本轮不解决但为后续铺路的事项

1. 自动从失败包里生成更强 validator
2. 自动从 scratch 提升 shadow 条目
3. 多 run 的 shadow ranking / retrieval
4. 完全摆脱 `initialGraph`
5. 真正任务无关的能力市场/能力编排器

这些后面会自然接在本轮之后。
