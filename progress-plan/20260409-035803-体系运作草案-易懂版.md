# 体系运作草案（易懂版）

时间：2026-04-09 03:58:03

这份文档是给“不看代码的人”看的。

目标只有一个：

- 让你直接理解我们现在这套系统是什么
- 它为什么能工作
- 后面为什么要加“第二种方法”和“Git-tree 分支”

## 1. 我们现在这个系统，本质上是什么

它本质上是一个“会自己积累专家经验的系统”。

你可以把它想象成下面这三层：

1. `OpenCode`
- 真正干活的执行引擎
- 负责读材料、调工具、输出结果

2. `auto-evolve`
- 外层训练循环
- 决定什么时候让 OpenCode 解题
- 决定什么时候评估
- 决定什么时候把失败经验写回去

3. `knowledge-pack`
- 专家经验本体
- 里面是一套 Markdown 文档
- 新 agent 以后主要靠它来完成任务

一句话说：

**OpenCode 负责执行，auto-evolve 负责训练，knowledge-pack 负责记住经验。**

## 2. 我们现在的主方法是什么

当前系统已经有一种完整的方法，可以把它叫做：

**顺序修改法**

它的逻辑很简单：

1. 先生成一版专家经验
2. 用这版专家经验去解一道题
3. 如果做错，就分析这次错误
4. 把这次错误总结进专家经验
5. 再重新解这道题

也就是：

`解题 -> 评估 -> 修改经验 -> 再解题`

这就是我们现在已经跑通的主链。

## 3. 现在的三阶段 Prompt 系统是什么

我们现在自己的 Prompt 系统，其实不是一个 Prompt，而是三阶段。

### 第一阶段：Bootstrap

作用：

- 根据一批“材料 -> 标准答案”样本
- 先总结出第一版专家经验

你可以把它理解成：

- 写教材
- 写老师讲义

### 第二阶段：Solve

作用：

- 让一个新的 agent 只读当前知识包
- 去解决当前 case

你可以把它理解成：

- 拿着教材参加考试

### 第三阶段：Refine

作用：

- 如果 solve 失败
- 就读取失败信息
- 把失败教训补回知识包

你可以把它理解成：

- 考试错了以后，老师修教材

所以这三阶段其实就是：

- `bootstrap`：写教材
- `solve`：拿教材做题
- `refine`：做错后修教材

## 4. 评估器在中间做什么

评估器不是模型，它是我们自己写的裁判。

它负责判断：

- 这次通过没通过
- 错在哪里
- 有没有工具失败
- 输出是不是空的
- 输出格式对不对

所以它不只是说一句“对”或“错”，而是给出一份结构化的失败说明。

这份说明后面会被送给 refine。

## 5. action trace 是什么

`action_trace.md` 是 solve 过程的简化行动记录。

它的作用是告诉 refine：

- 这次 agent 做了什么
- 调了哪些工具
- 大概在哪一步走偏了

所以 refine 看的不只是：

- 最后答案错了

还会看：

- 它中间是怎么做的

这会让后续修经验更有依据。

## 6. 为什么现在要继续升级

因为现在虽然主链已经跑通了，但它仍然只有一种方法：

- 顺序修改法

这意味着：

- 所有学习都走同一条路
- 所有实验都写同一套知识
- 以后想试不同“反向传播办法”会互相污染

而你后面明确要做两件事：

1. 测不同的“反向传播”方法
2. 并行开不同会话做比较

所以我们必须给系统再加两层能力：

- 方法管理
- 分支管理

## 7. 后面的“第二条路”是什么

你现在已经明确了第二条路线：

**对抗测试**

它和现在的顺序修改法不一样。

顺序修改法的核心是：

- 做错了
- 就修知识

而对抗测试更像：

- 主动攻击当前知识
- 故意找出它的漏洞
- 制造更强的失败信号
- 再让系统去修知识

所以它不是简单替换掉现在的方法，而是：

**作为第二种方法，和顺序修改法并列。**

## 8. 后面越来越多的方法，应该怎么管理

后面不能变成：

- 代码里到处 if / else
- Prompt 文件越来越乱
- 所有方法混在一个大系统里

最好的方式是：

把每一种“反向传播办法”都当成一个独立的方法包。

比如：

- 方法 1：顺序修改法
- 方法 2：对抗测试法
- 方法 3：以后别的方法

每个方法都只回答这些问题：

- 这一轮有哪些阶段
- 每个阶段看什么输入
- 每个阶段允许改什么
- 它怎么把失败变成经验

这样后面新方法越来越多，也不会把主系统搞乱。

## 9. 为什么还要做 Git-tree

因为以后不同方法都要改专家经验。

如果还像现在一样，只维护一套主知识包，就会有这些问题：

- 方法 A 改了知识
- 方法 B 也改了知识
- 最后混在一起，根本看不出来哪个方法更好

所以必须让知识可以“分叉”。

最理想的效果是：

- 大部分知识共享
- 小部分差异分支保存
- 随时可以比较
- 随时可以回退
- 以后还能合并

这就是为什么后面要做 Git-tree。

## 10. 但为什么现在不直接做很大的系统

因为现在的客观条件你也已经说得很清楚：

- 还没有真正的大数据集
- 还没有大型并发条件
- 还不适合做超大规模实验

所以现在最合适的不是一步做到很大，而是做一个：

**小规模、可分支、可比较的实验系统**

当前最现实的目标就是：

- 只支持 2 个实验分支
- 一个分支跑“顺序修改法”
- 一个分支跑“对抗测试法”
- 两边各自维护自己的知识分支
- 最后比较效果

这已经足够开始验证思路了。

## 11. 我们后面最合理的体系

后面的完整体系，我建议理解成 4 层。

### 第 1 层：核心执行层

它负责：

- 调 OpenCode
- 读取 case
- 保存运行记录
- 评估结果

这一层尽量保持稳定，不经常改。

### 第 2 层：方法层

它负责：

- 定义“顺序修改法”
- 定义“对抗测试法”
- 定义以后更多方法

也就是说：

- 方法层决定“怎么学”

### 第 3 层：实验层

它负责：

- 这次实验用哪个方法
- 用哪个知识分支
- 用哪些样本
- 用什么模型

也就是说：

- 实验层决定“这次怎么比”

### 第 4 层：Git-tree 层

它负责：

- 知识从哪里分叉
- 哪些修改形成了新版本
- 哪些实验共享同一个父知识
- 哪个分支表现更好

也就是说：

- Git-tree 层决定“知识怎么长成树”

## 12. 现在最关键的一句话

后面我们不是要推翻现在系统，
而是要把现在系统正式变成：

**方法 1：顺序修改法**

然后在它旁边增加：

**方法 2：对抗测试法**

再用 Git-tree 管理这两条路线的知识分支。

所以未来系统的核心不是“一个大 Prompt”，而是：

- 多种方法
- 多个实验
- 一棵知识树

## 13. 最后的极简总结

如果只记最简单的一版，你就记这三句话：

1. 我们现在的系统已经能“学经验、做题、做错再修经验”。
2. 后面不会推翻它，而是把它作为第一种方法保留下来。
3. 新的“对抗测试法”会作为第二种方法接进来，再用 Git-tree 管理两条知识分支。

这就是我们后面整个体系的发展方向。
