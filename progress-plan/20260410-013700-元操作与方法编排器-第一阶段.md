# 元操作与方法编排器：第一阶段落地记录

日期：2026-04-10

## 这一步做了什么

这一阶段的目标不是改变系统行为，而是把当前唯一可运行的方法 `sequential-refine` 从 `case-runner.ts` 的硬编码流程里抽出来，变成：

- 可见的 Markdown flow
- 可复用的运行时执行器
- 明确命名的元操作

## 新增内容

### 1. 方法 flow 文件

现在每个方法除了 `METHOD.md` 和 `prompts/`，还多了一个 `FLOW.md`：

- `auto-evolve/methods/sequential-refine/FLOW.md`
- `auto-evolve/methods/adversarial-test/FLOW.md`

这里面记录的是方法编排顺序，而不是 prompt 正文。

### 2. 元操作注册表

新增：

- `auto-evolve/orchestrator/primitives.ts`

当前第一批元操作包括：

- `solve_case`
- `finish_if_passed`
- `finish_if_eval_mode`
- `finish_if_max_retries_reached`
- `prepare_refine_feedback`
- `run_regression_before_refine`
- `refine_knowledge`
- `reject_if_refine_failed`
- `reject_if_no_knowledge_change`
- `reject_if_out_of_policy_files`
- `verify_current_case`
- `reject_if_current_case_not_fixed`
- `run_regression_after_refine`
- `accept_or_reject_change`
- `finish_after_accept`

### 3. 方法运行时

新增：

- `auto-evolve/orchestrator/method-runtime.ts`

作用：

- 读取方法 flow
- 按顺序执行元操作
- 记录每一步的执行结果
- 返回这次 attempt 是继续、结束还是进入下一次 attempt

### 4. 方法解析升级

更新：

- `auto-evolve/orchestrator/methods.ts`

现在方法系统会同时解析：

- `METHOD.md`
- `FLOW.md`
- `prompts/*.md`

### 5. case-runner 改为通过 runtime 跑

更新：

- `auto-evolve/orchestrator/case-runner.ts`

现在它的角色变成：

- 准备 case 上下文
- 准备 attempt 上下文
- 调方法运行时

而不是自己直接硬编码完整学习流程。

## 新的运行产物

每次 attempt 现在会多一个文件：

- `method_runtime.json`

这个文件会记录：

- 当前方法 ID
- 对应的 `FLOW.md`
- 实际执行了哪些元操作
- 每个元操作之后的决策
- 这次 attempt 最终为什么结束

## 这一步没有改变什么

为了降低风险，这一阶段刻意保持了以下内容不变：

- `sequential-refine` 的实际学习行为不变
- `bootstrap / solve / refine` 的 prompt 结构不变
- 接受/拒绝策略不变
- 评估器逻辑不变

也就是说，这一步主要是“结构改造”，不是“策略改造”。

## 验证结果

已经完成的验证：

- `bun run auto-evolve/cli.ts validate`
- `bun run auto-evolve/cli.ts run-case --case case-001 --method sequential-refine --mode eval --split test`

结果：

- `validate` 通过
- 单 case 烟测通过
- `method_runtime.json` 显示这次实际走了：
  - `solve_case`
  - `finish_if_passed`

说明方法运行时已经真正接到了当前系统主链上。

## 这一步的意义

这是后面扩展更多“反向传播方法”的关键底座。

现在开始：

- “回传”不再只应该被理解成系统固定步骤
- 它可以逐步变成某个方法自己定义的反馈构造方式
- 后面新方法不需要继续把逻辑堆进 `case-runner.ts`

## 下一步最合理的方向

第一阶段完成后，接下来最合适的是：

1. 继续把更多逻辑从 `case-runner.ts` 搬到独立元操作模块
2. 做一个更轻的第二基线方法，例如 `sequential-lite`
3. 让“反馈包如何构造”成为方法定义的一部分
4. 再考虑真正接入 `adversarial-test`
