## 1. 背景

当前 `auto-evolve` 已具备可运行主链：

- `bootstrap`
- `run-case`
- `run-round`
- Markdown-first `knowledge-pack`
- `solve -> evaluate -> refine -> retry` 闭环

当前默认学习方式可以正式定义为：

**Method-001: Sequential Refine**

该方法已经是稳定基线，后续所有新方法都应与其并列，而不是替换它。

## 3. 设计目标

本阶段目标不是构建大型训练平台，而是构建：

**一个兼容现有系统的、小规模、可分支、可比较的方法实验框架。**

本阶段只追求：

- 保留现有主链完全可用
- 新增“方法系统”
- 新增“双实验分支”
- 新增知识 Git-tree v1
- 支持 2 条方法路线并行对比

## 4. 总体原则

### 原则 1：不推翻现有系统

现有系统应被重新命名为：

- `sequential-refine`

它必须继续作为默认方法存在。

### 原则 2：方法外置

未来不同学习/对抗/选择方法，不应继续写死在 TS 代码里。

应采用：

- Markdown-first 方法定义
- TS 只做装配和执行

### 原则 3：知识树独立于方法

方法决定：

- 怎么跑
- 怎么改

知识树决定：

- 从哪里分叉
- 改成了什么版本
- 如何比较与回退

### 原则 4：先支持 2 个实验分支

当前资源条件下，2 个并行实验已经足够验证思路：

- 分支 A：Sequential Refine
- 分支 B：Adversarial Test

## 5. 核心架构建议

建议把未来系统稳定拆成 4 层。

### 5.1 Core Engine

职责：

- 调用 OpenCode
- 运行 case
- 评估结果
- 记录 artifact
- 管理知识快照

这层尽量稳定。

### 5.2 Method Layer

职责：

- 定义方法
- 定义 phase 顺序
- 定义每个 phase 的输入输出
- 定义每个 phase 是否允许写知识

本层要正式引入：

- `sequential-refine`
- `adversarial-test`

### 5.3 Experiment Layer

职责：

- 指定本次实验使用的方法
- 指定知识分支
- 指定 case 集
- 指定模型
- 记录实验结果

### 5.4 Git-tree Layer

职责：

- 维护知识分支和版本节点
- 保存 parent / branch / changed files / score
- 为实验提供隔离知识根

## 6. 方法系统设计

### 6.1 方法的概念

一个方法不等于“一段 refine prompt”，而是：

- 一组 phase
- 一组提示词
- 一套输入组织方式
- 一种失败转经验的策略

### 6.2 建议目录

```text
auto-evolve/
  methods/
    sequential-refine/
      METHOD.md
      prompts/
        bootstrap.md
        solve.md
        refine.md
    adversarial-test/
      METHOD.md
      prompts/
        solve.md
        adversarial_probe.md
        refine.md
        select.md
```

### 6.3 METHOD.md 至少应描述

- 方法 ID
- 方法类型
- phase 列表
- 每个 phase 的职责
- 每个 phase 的输入文件
- 每个 phase 的输出文件
- 哪些 phase 允许修改知识包
- 是否建议分支运行
- 是否适合并发

## 7. 两个初始方法定义

### 7.1 Method-001: Sequential Refine

定位：

- 基线方法
- 现有系统直接升级命名

主链：

- bootstrap
- solve
- evaluate
- refine
- retry

特点：

- 路径最短
- 已运行验证
- 适合作为对照组

### 7.2 Method-002: Adversarial Test

定位：

- 第二条实验路线
- 用于主动挖掘知识薄弱点

建议最小版主链：

- solve
- evaluate
- adversarial_probe
- refine
- retry

其中：

- `adversarial_probe` 不直接替代 refine
- 它负责输出挑战性失败分析
- refine 再读取 probe 结果更新知识

这样可最大程度复用现有 `case-runner` 思路。

## 8. Git-tree v1 设计

### 8.1 目标

只版本化 `knowledge-pack`，不版本化整个主项目。

### 8.2 为什么只版本化 knowledge-pack

- 当前主仓库工作区较脏
- 现阶段实验目标是比较知识演化，不是比较全仓代码演化
- 这样更容易隔离和回退
- 风险更低

### 8.3 目录建议

```text
auto-evolve/
  knowledge-pack/                 # 默认知识根，同时作为 knowledge git repo
  experiments/
    exp-sequential/
      experiment.md
      knowledge-pack/
    exp-adversarial/
      experiment.md
      knowledge-pack/
  experiment-runs/
    exp-sequential/
    exp-adversarial/
```

### 8.4 v1 行为

- `knowledge-pack/` 初始化为独立 git repo
- bootstrap 后形成基线 commit
- 从基线 commit 分出 2 个实验 branch
- 每个实验 branch 使用独立 worktree
- 每次 refine 若知识有变化，则自动提交

### 8.5 v1 不做的事情

- 自动 merge
- 自动 cherry-pick
- 多候选自动淘汰
- 大规模分支搜索

## 9. 实验系统设计

### 9.1 experiment 的概念

一次 experiment 不是单条 run，而是一套配置：

- 使用哪种方法
- 使用哪一套知识分支
- 使用哪组 case
- 用什么模型
- 最大重试次数

### 9.2 建议目录

```text
auto-evolve/
  experiments/
    exp-sequential/
      experiment.md
    exp-adversarial/
      experiment.md
```

### 9.3 experiment.md 建议内容

- experiment id
- method id
- branch name
- knowledge root
- model
- enabled cases / case group
- max retries
- notes

## 10. 与现有代码的契合方式

### 10.1 不改主链语义，只增加“上下文参数”

当前很多函数默认只读固定知识根。

未来应扩成：

- 支持传入 `experiment context`
- 由 context 决定当前 `knowledge root`
- 其余主链逻辑尽量不变

### 10.2 最关键的代码接点

#### A. `knowledge-pack.ts`

当前职责：

- 只解析一个固定 `knowledgeDir`

未来应支持：

- 从 experiment context 指定 knowledge root
- 支持 knowledge root 快照和恢复

#### B. `case-runner.ts`

当前职责：

- 运行 solve / refine 主链

未来应支持：

- 读取当前方法定义
- 读取当前 experiment 上下文
- 在 refine 后触发 knowledge commit

#### C. `bootstrap.ts`

未来应支持：

- 针对指定 experiment 初始化知识
- 在成功后写入基线 commit

#### D. `opencode.ts`

未来应支持：

- 按 experiment/run 隔离 override config
- 避免并发时共享配置目录冲突

#### E. `cli.ts`

未来应增加：

- `--experiment`
- experiment 初始化命令
- branch 准备命令
- compare 命令

## 11. 分阶段实施建议

### 阶段 1：方法系统显式化

目标：

- 把当前系统正式定义为 `sequential-refine`
- 方法定义外置为 Markdown

不做：

- Git-tree
- 并发

### 阶段 2：双实验与知识分支

目标：

- 初始化 knowledge git repo
- 创建两个实验分支
- 每个实验独立 knowledge root

不做：

- 自动 merge

### 阶段 3：对抗测试方法接入

目标：

- 引入 `adversarial-test`
- 新增 probe phase
- 与 baseline 比较

### 阶段 4：轻量并发

目标：

- 2 个 experiment 并发跑
- 独立 run 目录
- 最终汇总比较

## 12. 风险与注意点

### 风险 1：路径边界

OpenCode 的路径权限和项目边界强关联。

因此：

- knowledge worktree 优先放在当前仓库内部
- 避免第一版把实验根放到仓库外

### 风险 2：共享 override config

当前 `runOpencodeTask()` 写固定 override config 目录。

若并发运行，可能互相覆盖。

### 风险 3：runID 冲突

当前 run 目录命名只有秒级时间戳。

双实验并发时可能冲突。

### 风险 4：评估逻辑仍需增强

当前评估器结构够用，但仍需继续完善：

- 工具失败是否强制算失败
- 结果信号是否足够适配新方法

## 13. 本设计的最终结论

最合理的方向不是推翻当前系统，而是：

1. 把当前系统正式定义为第一种方法
2. 引入第二种方法“对抗测试法”
3. 用知识 Git-tree 管理两个方法的知识分支
4. 先只支持 2 个实验并行

这条路最贴合当前代码状态，也最符合当前资源条件。
