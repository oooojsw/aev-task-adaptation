# 系统整体运作与 Prompt 说明

时间：2026-04-09 03:23:30

这份文档只解释我们自己的系统是怎么运作的，不解释 OpenCode 自身内部的底层实现。
目标是让你不看代码，也能明白现在这套系统到底在做什么、怎么跑、Prompt 是怎么配合工作的。

## 1. 我们现在到底在做什么

我们现在做的，不是一个“让 AI 回答一次问题”的小工具。

我们在做的是一套“会自己积累专家经验的执行系统”。

它的目标是：

- 先给系统一批“材料 -> 标准答案”的样本
- 让系统先总结出一套专家经验
- 再让一个新的 agent 只依靠这套专家经验去解决新案例
- 如果解决错了，就把这次失败总结回专家经验里
- 持续循环，让专家经验越来越完整、越来越稳定、越来越有泛化能力

你可以把它理解成：

- `OpenCode`：真正执行任务的引擎
- `auto-evolve`：外层训练和迭代系统
- `knowledge-pack`：专家经验本体

## 2. 系统里最重要的几个部分

### 2.1 数据集

位置：

- `auto-evolve/dataset/cases/`

每个 case 一般包含：

- `case.json`
- `material/`
- `expected/`

含义：

- `material/`：输入材料
- `expected/`：标准结果
- `case.json`：这道题应该怎么判对错

简单说，数据集就是“训练样本”。

### 2.2 专家经验系统

位置：

- `auto-evolve/knowledge-pack/`

现在它不再是一份大杂烩文档，而是一套 Markdown 文件体系。

当前主要包括：

- `manifest.md`
- `core/expert_rules.md`
- `core/output_contract.md`
- `core/execution_checklist.md`
- `patterns/general_rules.md`
- `patterns/exceptions.md`
- `lessons/failure_lessons.md`
- `change_log.md`

它们的职责可以简单理解成：

- `expert_rules.md`：高层规则和任务理解
- `output_contract.md`：输出纪律，防止多说废话、格式错
- `execution_checklist.md`：执行时的检查清单
- `general_rules.md`：通用规律
- `exceptions.md`：特例和例外
- `failure_lessons.md`：过去失败得到的教训
- `change_log.md`：知识包的修改记录
- `manifest.md`：这套知识包的总说明

简单说：

- `knowledge-pack` 存的是“知识”
- 它要保证一个新 agent 只读这些文档，也能尽量完成任务

### 2.3 scripts

位置：

- `auto-evolve/scripts/`

这个目录现在保留着，但当前主流程还没有重点使用它。

它的定位不是保存规则，而是将来保存：

- 可复用脚本
- 执行工具
- 帮助 agent 落地操作的能力模块

所以我们现在的原则是：

- 规则本身必须保存在 Markdown 里
- `scripts/` 负责“能力”，不负责“真规则”

### 2.4 运行结果目录

位置：

- `auto-evolve/runs/`

每次运行都会留下记录，方便复盘。

里面通常会保存：

- 本次使用的 prompt
- OpenCode 的输出
- 事件流
- action trace
- 评估结果
- 知识包修改前后快照

所以 `runs/` 可以理解成“实验留痕目录”。

## 3. 整个系统是怎么跑起来的

现在这套系统主要有三种运行方式。

### 3.1 bootstrap

作用：

- 生成第一版专家经验
- 或者基于现有样本强制重做一版专家经验

它做的事情是：

1. 读取全部已标注的 case
2. 把这些 case 一起交给 OpenCode
3. 让 OpenCode 从这些样本里总结规律
4. 把规律写进 `knowledge-pack`

所以：

- `bootstrap` 不是解题
- 它是“先写老师讲义”

### 3.2 run-case

作用：

- 跑一个 case
- 用当前知识包去解决这一个问题

它的流程是：

1. 读取当前 `knowledge-pack`
2. 读取当前 case 的材料
3. 调 OpenCode 去解这个 case
4. 评估结果是否和标准答案一致
5. 如果失败，就触发一次经验修正
6. 再用更新后的知识包重跑

所以：

- `run-case` 是单题循环
- 一道题可能会尝试多轮

### 3.3 run-round

作用：

- 按顺序跑一批 case
- 让知识包一路演化下去

它可以理解成：

- 先跑 case-001
- 再跑 case-002
- 再跑 case-003
- 每一题都可能推动知识包继续变化

所以：

- `run-round` 是整轮训练

## 4. 我们自己的 Prompt 系统是怎么工作的

这是最重要的部分。

我们现在自己的 Prompt 系统，不是一个 Prompt，而是三阶段闭环。

### 4.1 第一阶段：Bootstrap Prompt

作用：

- 让系统根据一批样本，写出第一版专家经验

输入给它的东西主要是：

- 一批 case 的材料
- 一批 case 的标准结果
- 当前知识包里的文件

它要做的事情是：

- 从样本中提炼规律
- 把规律分别写入知识包的不同文件

它的角色不是“做题的人”，而是“写教材的人”。

### 4.2 第二阶段：Solve Prompt

作用：

- 让一个执行 agent 使用当前知识包去解题

输入给它的东西主要是：

- 当前 `knowledge-pack`
- 当前 case 的材料
- 当前 case 的要求

它的任务非常明确：

- 只使用当前知识包解题
- 不允许偷偷修改知识包
- 最后只输出答案本身

这个阶段的角色不是学习者，而是“考试的人”。

### 4.3 第三阶段：Refine Prompt

作用：

- 当 solve 失败时，把这次失败转化成新的专家经验

输入给它的东西主要是：

- 当前 `knowledge-pack`
- 当前 case 的材料
- 当前 case 的期望输出
- 这一次 solve 的实际错误输出
- 这一次 solve 的结构化评估结果
- 这一次 solve 的简化事件流 `action_trace.md`

它要做的事情是：

- 分析这次错在哪里
- 判断更适合修改哪一类知识
- 把失败教训补回知识包

这个阶段的角色不是做题者，而是“复盘和修教材的人”。

## 5. 三阶段是怎么连成闭环的

一个 case 的完整流程，简单说就是：

1. 先用 Solve Prompt 解题
2. 用评估器判断对不对
3. 如果对了，这题结束，知识包不变
4. 如果错了，就触发 Refine Prompt
5. Refine 改完知识包后，再回到 Solve Prompt 重新跑

所以系统的真实循环是：

`solve -> evaluate -> refine -> solve`

如果一开始还没有知识，就先跑一次：

`bootstrap`

所以整体全流程是：

`bootstrap -> solve -> evaluate -> refine -> solve -> ...`

## 6. 评估器在整个系统里的作用

评估器不是 Prompt，它是 Prompt 之间的裁判。

它负责做的事情是：

- 对比“实际输出”和“标准输出”
- 判断这次是否通过
- 给出结构化失败信息

当前它主要会看：

- 输出内容是否一致
- 输出格式是否一致
- 是否有工具失败
- 是否有非零退出

所以评估器的作用是：

- 决定这题算不算过
- 决定要不要触发 refine

## 7. action trace 是干什么的

`action_trace.md` 是一次 solve 过程的简化行动记录。

它不是完整底层日志，而是给 refine 用的“行动摘要”。

它会帮助系统看到：

- 这次 agent 做了哪些步骤
- 用了哪些工具
- 哪一步可能出了问题

所以 refine 不再只是看“你错了”，而是看：

- 你是怎么错的
- 你在行动路径上做了什么

这会比只看最终错误答案更有用。

## 8. 为什么现在要把专家经验从单文件升级成知识包

因为如果所有东西都堆在一份 `expert_rules.md` 里，会很快出问题：

- 文件会越来越乱
- 通用规律和特例会混在一起
- 失败教训会堆成一团
- 后面做不同实验时会互相污染
- 多实验并发时很难分叉管理

升级成知识包之后，好处是：

- 规则更清楚
- 经验更容易维护
- 更适合做实验
- 更适合未来接 Git 树式管理
- 更适合支持“共享大部分知识，只分叉少部分知识”的实验方式

## 9. 现在这套系统最关键的约束

当前有几个关键原则：

- Solve 阶段不能修改知识包
- Refine 阶段才允许修改知识包
- 规则内容必须以 Markdown 为主，不藏在脚本里
- `scripts/` 只负责能力，不负责保存真正规则
- 每次运行都要留下结果目录，方便复盘

这些约束的目的，是让系统尽量可解释、可复盘、可持续演化。

## 10. 你现在最需要记住的一句话

我们现在做的系统，本质上是：

**先让 OpenCode 帮我们写专家经验，再让新的 agent 用这套专家经验做题；如果做错，就把这次失败继续补回专家经验里。**

它不是一次性回答问题，而是一套“会不断积累经验”的循环系统。

## 11. 目前这套系统还没有做到的事

现在已经能跑通主链，但还没有完全做到的包括：

- 更强的泛化能力验证
- 多种 refine / “反向传播”策略并行对比
- 知识包的 Git 树式分支管理
- 并发实验调度
- 更细的可视化监控

所以当前状态可以理解成：

- 主流程已经跑起来了
- 专家经验体系已经从单文件升级成知识包
- 下一阶段要做的是更稳定的知识管理和更强的实验能力

## 12. 现在最常用的三个命令

在项目根目录下：

```powershell
bun run auto-evolve/cli.ts bootstrap --force
bun run auto-evolve/cli.ts run-case --case case-001
bun run auto-evolve/cli.ts run-round
```

含义分别是：

- `bootstrap --force`：重新生成一版知识包
- `run-case`：跑一题
- `run-round`：按顺序跑一整轮

## 13. 最后的直白总结

如果完全不看代码，只记一句最简单的话：

**我们在做一个“先学经验，再拿经验做题，做错再修经验”的系统。**

而 Prompt 系统就是这个循环里的三种角色：

- `bootstrap prompt`：写教材
- `solve prompt`：拿教材去考试
- `refine prompt`：考试错了以后修教材

这就是现在整套系统的核心运作方式。
