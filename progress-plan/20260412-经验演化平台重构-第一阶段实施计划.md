# 20260412 经验演化平台重构-第一阶段实施计划

## 一、这次重构要解决什么

这次不是推翻现有 short / long 流程，而是先把平台级边界做对。

当前真实问题：

1. 第一层 Runtime（运行层）与第二层 Maintainer（维护核心）边界不清。
2. short task 已经直接侵入了 maintainer 与 acceptance。
3. long task 还停在 candidate / shadow memory，没有进入统一维护入口。
4. short / long 没有共享同一种维护请求对象，后续第三层、第四层很难顺利接入。
5. 短程虽然已经有 `session_execution_report` / `session_learning_log`，但还没有沉淀成统一证据对象平面。

这次第一阶段的目标是：

- 建立 `Experience Evolution Platform（经验演化平台）` 的最小结构骨架。
- 在第一层与第二层之间补上 `Maintenance Gateway（维护网关层）`。
- 让 short / long 都能产出统一的 `Maintenance Request（维护请求）`。
- 让短程开始沉淀统一证据对象，但不强行把所有对象一次做得过重。
- 保持现有功能不变：short 仍然能直接维护，long 仍然先产 candidate，不强行改成自动直写正式经验区。

## 二、第一阶段采用的结构

本阶段只落最关键的四层：

1. `Runtime Kernels（运行内核层）`
   - short kernel
   - long kernel

2. `Evidence & Memory Plane（证据与记忆平面）`
   - execution report
   - failure packet
   - retry lesson
   - learning unit
   - scratch memory
   - shadow memory

3. `Maintenance Gateway（维护网关层）`
   - 把 short / long 运行产物统一包装成维护请求
   - 不负责真正改专家经验
   - 不负责 acceptance / rollback

4. `Maintainer Core（第二层维护核心）`
   - 仍然沿用当前 knowledge maintainer
   - 但开始改成通过 gateway 提供的 request 进入

注意：

- `Experience Transaction Gate（经验事务门）` 这次只做语义收口，不彻底拆成独立执行总线。
- `Layer 3 Governance（第三层治理）` 与 `Layer 4 Optimization（第四层优化）` 这次不直接实现，只确保后续能挂载。

## 三、这次代码实施范围

### 1. 新增 Maintenance Gateway 契约层

新增统一对象：

- `MaintenanceRequest`
- `MaintenanceEvidenceRef`
- `MaintenanceGatewayPaths`

统一表达这些来源：

- short task 失败后准备维护
- short task 完成后沉淀 run 级经验
- long task 结束后产出的 candidate

### 2. 短程补统一证据对象

短程本次至少补齐：

- `failure_packet.json`
- `learning_units.jsonl`
- `retry_lessons.jsonl`
- `scratch_memory.jsonl`
- `shadow_memory_candidate.json`

说明：

- `execution report` 继续复用现有 `session_execution_report.md`
- `learning log` 继续保留现有 `session_learning_log.md`
- 本次优先做“可统一接入”的最小结构，不追求一开始就做成长程那样重

### 3. 短程通过网关进入 maintainer

改造点：

- `invokeKnowledgeMaintainerPrimitive(...)` 不再直接从散乱 context 拼 maintainer 输入
- 先构造 `MaintenanceRequest`
- 再把 `MaintenanceRequest` 转译成当前 `KnowledgeMaintainerRequest`

这样可以先不重写 maintainer 内核，但边界已经正确

### 4. 长程把 candidate package 同步写成统一维护请求

长程现在已有：

- shadow memory
- candidate package

本次在 finalize 阶段新增：

- 统一 `MaintenanceRequest`

保持当前行为：

- verified_success 仍然只是 `ready_for_maintainer`
- 不自动直写 canonical experience

### 5. 任务语义补一层 transaction 边界

本次只做语义层修正：

- 将 verify / regression / post-judge 归类为 `experience_transaction`
- Maintainer 保持只代表“改经验”

这一步先从 task descriptor 入手，不重写整条 acceptance 执行链

## 四、明确这次不做什么

1. 不把 long task 直接接成“自动写正式专家经验区”。
2. 不让 maintainer 同时承担 acceptance / rollback / promotion。
3. 不一次性实现第三层与第四层。
4. 不改监控线 `monitor-server.ts`。
5. 不推翻现有 short strategy / long runner，只做兼容式嵌入。

## 五、落地顺序

### Phase A：契约与目录

- 新增 maintenance gateway 契约与 repository
- 在 config / schema 中注册 `maintenanceGatewayDir`

### Phase B：短程证据对象

- 在 case runtime 中增加 evidence 路径
- 在 feedback / maintenance / acceptance 节点上补证据对象写入

### Phase C：短程维护网关接入

- 由 gateway 生成 `MaintenanceRequest`
- maintainer 通过 request 转译进入旧内核

### Phase D：长程维护网关接入

- long candidate package 同步写统一 request

### Phase E：语义校正与验证

- task-model 增加 `experience_transaction`
- 运行 validate
- 进行最小链路验证，确认 short / long 都未退化

## 六、预期结果

完成本阶段后，系统会变成：

- short / long 仍然各跑各的 kernel
- 但二者都会向同一个 `Maintenance Gateway` 输出统一维护请求
- 第二层 maintainer 开始只关注“如何改经验”
- acceptance 语义开始从 maintainer 边上剥离
- 后续第三层、第四层可以直接以 `candidate / request` 形式接入，而不是侵入 short / long 内核

## 七、成功标准

1. short task 运行后能看到统一证据对象落盘。
2. short maintainer 仍正常执行，功能不退化。
3. long task finalize 后除了原 candidate package，还能看到统一 maintenance request。
4. `validate` 通过。
5. 现有正式专家经验维护行为不被破坏。
