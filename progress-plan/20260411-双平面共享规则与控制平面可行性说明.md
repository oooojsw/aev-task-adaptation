# 双平面共享规则与控制平面可行性说明

## 一、双平面共享规则为什么要下沉到所有 agent

现在经验工作区实际上有两个平面：

- `Tracked Experience Plane（受跟踪经验平面）`
- `Runtime Sidecar Plane（运行时侧车平面）`

其中：

- `Tracked Experience Plane` 才是真正的专家经验
- 根目录下 `.opencode/**` 属于 `Runtime Sidecar Plane`

如果只有系统代码知道这件事，而 agent 不知道，就会出现三个问题：

1. `Solve Agent（求解代理）` 误把 `.opencode/**` 当知识读
2. `Maintainer（经修代理）` 把 sidecar 变化误当成经验维护成果
3. `Judge（判断代理）` 把 sidecar 垃圾或日志误判成经验污染

所以这条规则必须成为共享基础规则，而不能只存在于实现逻辑里。

## 二、共享规则应该表达什么

不需要写得很重，只要让所有会碰经验库的 agent 知道这几件事：

- 工作区有两个平面
- `.opencode/**` 默认属于 `Runtime Sidecar Plane`
- `Runtime Sidecar Plane` 允许存在
- 它不算正式专家经验
- 它不参与经验更新成果判断
- 除非任务明确要求分析运行日志，否则不要把它当主证据

## 三、哪些 agent 需要这条共享规则

至少包括：

- `Bootstrap Agent（初始化代理）`
- `Solve Agent（求解代理）`
- `Soft Judge Agent（软判断代理）`
- `Knowledge Maintainer Agent（经修代理）`
- `Batch Knowledge Maintainer Agent（批量经修代理）`

## 四、控制平面是否可行

结论：

- `Strong Uniform Platform（强统一平台）` 不可取
- `Control Plane（控制平面）` 可行而且值得做

### 不可取的做法

把所有反向传播算法都变成一种“统一模块”，要求它们：

- 同一接口
- 同一调用方式
- 同一插件模型

这会在后期失败，因为：

- `Momentum` 这种需要跨轮状态
- `Dual-Axis BP` 这种需要 judge / routing 信号
- `branch-preserving` 这种属于第三层治理
- `adversarial-suite-builder` 这种属于第四层优化

它们不是同一类叶子能力。

### 可行的做法

建立一个控制平面，统一管理：

- `Registration（注册）`
- `Classification（分类）`
- `Composition（配方装配）`
- `State Channels（状态通道）`

然后承认不同算法属于不同层和不同类别。

## 五、V1 采取的策略

### 已经开始落地的

- 对维护模块做统一注册
- 对局部 learning recipe 做统一注册
- 对约束策略、路由策略、治理策略、优化策略建立注册位
- 对跨层状态通道建立正式对象

### 还没有强行推进的

- 不强迫所有旧系统立刻都改成控制平面驱动
- 不实现复杂第四层算法
- 不实现真正的跨层策略执行器

## 六、为什么这个 V1 是稳的

因为它做的是“统一语言和统一入口”，而不是“统一一切执行细节”。

它的价值主要在于：

- 以后再想新算法时，马上知道该挂哪类
- 后续可以逐步把现有 recipe、judge、治理、优化接到同一注册表
- 不需要一次性推翻现有工作链

## 七、当前最重要的落地点

1. 让所有会碰经验工作区的 agent 都共享双平面规则
2. 让控制平面先接入真实的两个对象：
   - `Maintenance Module`
   - `Local Learning Recipe`

这样控制平面就不是空壳，而是已经开始管理真实系统。
